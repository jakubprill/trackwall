# Features

What Trackwall does today, view by view. The interface texts are in English (ADR-32), so the names of views and buttons in quotation marks are as in the app. Installation: [release.md](release.md), running from source: [development.md](development.md).

Navigation: views are switched by the bar at the left edge of the window, as in VS Code: Home (Ctrl+1), Repos (Ctrl+2), Sessions (Ctrl+3) and Overview (Ctrl+4) at the top, Daemon (Ctrl+9) and Settings (Ctrl+,) at the bottom; on macOS ⌘ instead of Ctrl. A tooltip on hovering over the icon shows the view's name and shortcut.

Dashboard: the "Home" view (Ctrl+1) opens after startup and shows the environment in one 3D frame (ADR-33): the daemon in the middle, Copilot CLI sessions on the inner track next to their repo, repos on the outer ring in the arcs of the layers (entries, gateways, backends, libraries, like the columns in "Overview") and the connections from the graph. Only what needs attention has a label: a repo with changes, with commits to pull or unavailable, and a session that is waiting for you or has an error; colour and shape say the rest, and hovering with the cursor shows the name and state in the corner. A session whose ended turn you have already seen is idle: calm grey, without a label and outside "Needs you" (ADR-47). The "Needs you" queue on the left lists the same sessions and repos (and, between them, task proposals waiting for a decision; a click opens the proposal in "Sessions"), and the panel on the right the details of the selected object (state, branch, running mise task, the repo's sessions). A session in the queue has the window title next to the repo, so that two sessions of one repo can be told apart. A click selects an object and points the camera at it, a double click or "Open repo" / "Open session" / "Open Daemon" (after selecting the core in the middle) goes to its view; without a selection the panel on the right summarises the environment. Without WebGL (an old driver, a blocked graphics card) or after the graphics context is lost, in place of the scene there is a message with a "Try again" button, and the queue and the details keep working. When the projects folder has disappeared or `workspace.yaml` has an error, the view shows the error and "Open Settings" instead of the old list. With reduced motion turned on in the system the models stand still.

Browsing repos: in the "Settings" view you set the projects folder (by full path), and the "Repos" view shows every git repo that lies directly in it: branch, number of changes and ahead/behind, the README, files and commits from the latest commit, and opens the repo in VS Code. A Markdown README is formatted as on GitHub: headings, tables, task lists, code blocks and Mermaid diagrams (with zoom and full screen); a link to a website opens in the browser, links to files in the repo are text, and images show only their description; a `.txt`, `.rst` or `.adoc` README stays plain text (ADR-35). A repo cloned into the folder appears on the list by itself. The "+" button on the repo list opens a search for repos from GitLab and GitHub (hosts are added in "Settings") and clones the chosen one with one click; it needs a logged-in `glab` (`glab auth login --hostname <host>`) or `gh` (`gh auth login`) in `PATH`, and Trackwall does not store the token. The "Sync all" button fetches the changes of every repo (`git fetch`) and moves the default branch to the remote one when it is a clean fast-forward; a repo with changes in the default branch or with a diverged branch stays untouched. The sync panel in place of the repo details has a sentence about every repo, including an up-to-date one: what happened to the default branch, whether the files changed (no, when you work on another branch) and how many uncommitted files are left, changed and new separately; the same sentence is in the tooltip of the result on the repo list. The list and the repo header write changes as "3 changed, 1 new" (a new directory is one entry), and the "Changes" tab (or a click on the "Working tree" tile) shows the files and diff of the working directory against the latest commit, with new files; you commit and discard them in the editor. The folder path is the `projectsDir` key, and the hosts the `repoHosts` key in `~/.trackwall/workspace.yaml`; both can also be set by hand. Needs `git` in `PATH`.

mise tasks: the "mise tasks" tab in the repo details shows the tasks from `mise tasks ls`, runs them (`mise run <task>` in the repo root) and stops them as a whole process group, together with their descendants (a Job Object on Windows, a POSIX session on macOS, ADR-20); after an error it shows the exit code and the last output lines. The "Log" button next to a task shows its output live (stdout and stderr, without ANSI colours, errors and warnings highlighted), and a run opens the log by itself; the values of environment variables with secret names (`*_TOKEN`, `*_PASSWORD`, `*_SECRET`…) are replaced with `***` in the log. The full log of every task lies in `~/.trackwall/logs/mise-task/<repo>/<task>.jsonl` (at most 10 MB plus one previous file `.1.jsonl`); in the file name characters other than lowercase letters, digits, `_` and `-` are encoded as `%XX`, for example the task `build:ui` is `build%3Aui.jsonl`. A mise configuration that mise does not trust can be trusted with a button (`mise trust`); only then can an agent also run the repo's tasks through MCP (below). Tasks run by an agent show in the same tab, with their log, and can be stopped from here. Quitting the daemon stops all tasks, and its next start cleans up the groups after a daemon crash. Needs `mise` in `PATH` (on macOS the `PATH` from the login shell is enough).

Repo card and tags: the "Card" tab in the repo details shows the facts read from the build and configuration files in the latest commit (ADR-25): the Maven, Gradle and npm packages the repo provides and uses, required tools (mise, `.tool-versions`, `.nvmrc`, wrappers), mechanisms (Spring Boot, Feign, Kafka, Helm, React…), Spring Boot apps with their port, HTTP endpoints from controllers with request and response types, the DTOs these endpoints take and return (records, `data class`, classes with fields and enums from Java and Kotlin, with fields and their types; ADR-38), HTTP clients (Feign, `@HttpExchange`, WebClient, RestClient, RestTemplate, addresses from `application*.yml` in every profile, `.env` and the frontend proxy; ADR-30) and build files, every fact with a file and line. It builds and runs nothing; a card is computed once per commit and lies in `~/.trackwall/cards`. The card gives repo tags (`java`, `typescript`, `frontend`, `backend`, `bff`, `library`, `monorepo` and `no-mise` for a repo without mise tasks in `mise.toml` or in `mise-tasks/`), shown on the repo list with the reason in a tooltip (`no-mise` as the warning "no mise tasks": in such a repo the `setup` and `build` steps of the Batch command and the "mise tasks" tab have nothing to run); the filter above the list narrows it to repos with every selected tag. Your own tags are given by the `repoTags` key in `~/.trackwall/workspace.yaml` (only by hand for now): a tag and identifier or remote address patterns, for example `repoTags: { core-api: ["*-core"] }`.

Connection graph: the "Overview" view (Ctrl+4) draws the repos from the folder as a graph (ADR-29): a line leads from a repo that uses a package to the repo that builds it (Maven coordinates, also from Gradle, and npm names from the cards), and from a repo whose HTTP client calls another repo's app or endpoints (by app name, host, port on `localhost` or paths; ADR-30), from frontends on the left to libraries on the right. Every connection has a confidence: certain, almost certain, likely or possible. Clicking a repo shows in the panel on the right what it uses and who uses it, with evidence (file and line). Connections the cards do not see are added by hand under the `graph` key in `~/.trackwall/workspace.yaml`: `packages` assigns a package to a repo (`com.example:orders-client: orders-api`), `apps` an app name or an address host to a repo (`orders.internal.example.com: orders-api`), and `edges` adds a connection with a description (`- { from: shop-web, to: orders-bff, note: HTTP /api/orders }`); a repo is given by its identifier or its `host/path` address.

MCP server for Copilot CLI: the daemon exposes an MCP server (ADR-24) with the tools `list_repos` (repos from the projects folder: path, remote address, branch, status, the result of the last sync and tags; with the `tags` argument only repos with those tags), `get_repo` (the README, latest commits, mise tasks and tags of one repo), `get_repo_card` (the repo card with tags and evidence), `tail` (a mise task log from a cursor, with secrets replaced with `***`), `get_errors` (errors from the mise task logs of all repos or one repo, most recent first: an `ERROR` line, a compiler error or an exception together with its Java or Node stack trace and the cause from `Caused by:`, the Spring "APPLICATION FAILED TO START" report and the Gradle `FAILURE:` report; a repeated error is one entry with a count, with `minLevel: warn` also warnings; ADR-42), `who_calls` (who uses a given repo, through packages and HTTP, with evidence), `subgraph_for` (a part of the connection graph around a repo), `find_endpoint` (an HTTP endpoint by path or name, with request and response types and the repos that call it), `search_code` (text or a regular expression in the latest commit of all repos at once, narrowed to repos, tags and paths, with the line, column and context of every match; ADR-40), `list_sessions` (Copilot CLI sessions from the "Sessions" view with state, repo and task, and tasks) and `get_session` (one session with its task and the task's changed files, without the diff; ADR-36). Sessions with the Trackwall MCP server thus see each other, but no tool starts, answers or stops a session. mise tasks (ADR-41): `run_mise_task` runs a task from the repo's list (the same as the button in the "mise tasks" tab; it will not run a configuration without trust, and only you can trust it, in Trackwall), `wait_for_mise_task` waits up to 55 s for it to end and returns the exit code, `stop_mise_task` stops the whole process group (also a task you started), and `list_running_mise_tasks` lists the running tasks of all repos; `tail` gives the output. A session from the "Sessions" view runs and stops only tasks of the repo it works in, and every run goes to the daemon log with the repo, task and session. For delegating work (ADR-39) there are `propose_task` (a task proposal: repo, title and prompt for another agent), `report_result` (a summary from a task session to its task) and `wait_for_session` (waiting up to 55 s until a session or task needs someone); described below in "Main session and task proposals". Copilot CLI connects once, with the command from the "Daemon" view (described below in "Connecting Copilot CLI").

Batch command: the "Batch command" button under the repo list opens a panel in which you choose repos (by default all visible after the tag filter) and steps: sync, tools (`mise install`), dependencies (the mise task `setup`) and build (the mise task `build`). The steps run in a repo in order, and repos three at once; the panel shows the result of every step in every repo, and on an error the exit code and the last lines. A repo without the task has the step skipped, an error ends only that repo, and "Cancel" stops the running tasks (also one started earlier from the repo details, which the command joined) and starts no further ones. A repeat is fast when the tasks have `sources` and `outputs` in `mise.toml` (ADR-27).

Copilot CLI sessions: the "Sessions" view runs Copilot CLI in a chosen repo from the projects folder, with the Trackwall MCP server connected, several sessions at once, each in a terminal owned by the daemon (ADR-26), so a session keeps running after the window is closed. The list shows the state of every session from Copilot CLI hooks (working, waiting for you, asking for approval; ADR-17) and what the agent is working on; Trackwall takes the answer to an approval request (Enter or an option number) and the interruption of a turn (Esc, Ctrl+C) from the key in the session terminal and from the message "Operation cancelled by user", because Copilot CLI sends no hook then; the "Next waiting" button switches to a session that is waiting for an answer, and the view bar shows how many sessions are waiting. When the agent ends its turn, the session waits for you only until you have seen it: opening its terminal with the window in focus (or typing into it) turns "waiting for you" into "idle", while a request for approval or for plan approval keeps waiting until you answer (ADR-47). The list, the counter and the Home dashboard get session state changes (and running mise tasks) from the daemon live through the `/ws` WebSocket (ADR-36), and poll it only when that connection is broken. When a session finishes work and waits, the window flashes on the taskbar (on macOS the icon bounces in the Dock), and the tray menu has a "Waiting: <repo>" item that opens that session. "Stop" ends the session's whole process group, "Close" removes an ended session from the list. Copilot CLI takes over the mouse in the terminal, so text is selected by dragging with Option (macOS) or Shift (Windows) held down and copied with Cmd+C or Ctrl+C (Ctrl+C without a selection interrupts the agent's work). Needs Copilot CLI in `PATH` (`copilot`; on Windows, with `npm install -g`, Trackwall runs `copilot.exe` from the package instead of `copilot.cmd`) and the daemon under Bun (the release or `pnpm dev`); under Node there are no sessions. Sessions do not survive the daemon quitting and are not recorded; recordings are made by the script described in [docs/development.md](development.md#recording-copilot-cli-sessions).

Session layout and shortcuts (ADR-48): the switch above the right side of "Sessions" shows the selected session alone (layout 1, with its full panel) or a grid of terminals: 2 and 4 show pages of that many entries, Auto shows the whole list, up to nine at a time, in as many columns and rows as fit the window (six sessions on a 34-inch ultrawide are three columns and two rows). The selected tile has the accent ring and takes the keyboard, a session that is waiting for you has the warning frame (only the selected tile counts as looked at, so a finished turn in another tile keeps waiting until you select it), and a click on a tile or into its terminal selects it; the button in the tile header opens the entry alone. Alt + digit (⌥ on macOS) selects the entry at that position in the list (the shortcut is under its number) and turns the grid to its page, and Alt+J jumps to the next session that is waiting for you, also from other views. These keys, and Ctrl/⌘ + digit for views, work while a terminal has the focus and are not sent to the session, so in Sessions Alt + digit does not type into a terminal or the task prompt; on macOS an Option + key that types an ASCII character on your layout (⌥5 for `[` on a German keyboard) stays a key and is not a shortcut. A task without a session has no terminal in the grid; open it alone to resume it or see its changes. The layout is kept until the app closes.

Agent tasks: the "+" button in the "Sessions" view opens the new task form: a repo and a prompt for the agent. Trackwall creates a new branch `trackwall/<prompt slug>` from the repo's default branch in a separate worktree in `~/.trackwall/worktrees/<repo>/` and runs Copilot CLI in it with the prompt as the first message (ADR-31), so several tasks in one repo run at once without collisions, and your working directory stays untouched. The "Changes" tab shows live the files and diff of the worktree against the default branch, with the task's commits and what the agent has not committed yet. Buttons: "VS Code" opens the worktree, "Resume" runs Copilot CLI with the task's conversation (`--resume`), and "End task" removes the worktree and keeps the branch or removes both; changes that would be lost doing so are deleted by Trackwall only after confirmation. Tasks survive a daemon restart. Copilot CLI asks for trust in every new folder; so that it does not ask for every task, add the `worktrees` directory (the form gives the full path) to `trustedFolders` in `~/.copilot/config.json`.

Main session and task proposals: a Copilot CLI session with the Trackwall MCP server (in the "Sessions" view or in your terminal, for example in the projects folder) can commission work to another agent like a coordinator that opens threads (ADR-39). The `propose_task` tool submits a task proposal with a title and a prompt; the "Sessions" view shows it as "waiting for your decision", and the view bar counts it together with the sessions that are waiting. A proposal from a listed session, and the task made from it, sit indented under that session (or under the task whose session delegated it), and the main session has a "main" badge with the number of items under it; a proposal from an agent outside Trackwall or from a closed session is at the top level. Proposals also show in the "Needs you" queue on the Home dashboard (a click opens it in "Sessions") and in the tray menu ("Proposal: <repo> · <title>"); a new proposal flashes the window in the taskbar or bounces the Dock icon like a session that started waiting, and the tray tooltip counts proposals together with sessions. When selected, it shows who proposed it and the whole prompt, which can be edited; "Start task" turns it into an ordinary task (worktree, branch from the title, a session with the prompt), "Reject" rejects it, and until then nothing starts. A task session finishes its work with the `report_result` tool, and its summary is shown above the task's tabs ("Summary"). The main session waits for the result with the `wait_for_session` tool (it returns when the session ends its turn, asks for approval, reports an error, stops responding or ends, or when the proposal is rejected) and reads the changes through `get_session`. Proposals live only until Trackwall quits (at most 20 at once), summaries stay with the task. Every Trackwall session has its own session token, by which the MCP server knows who is calling; an agent outside Trackwall proposes as "agent outside Trackwall", but does not report summaries. The prompt and title of a proposal and the summary cannot contain invisible characters, so that what you read before "Start task" is the whole prompt.

## Connecting Copilot CLI

Copilot CLI runs the daemon's stdio bridge (`trackwall-daemon mcp-stdio`) as a local MCP server; the bridge finds the running daemon through `daemon.json`, so the configuration does not change after a daemon restart and contains no token. The ready command for this installation is shown in the "Daemon" view (Ctrl+9, copy button). It looks like this:

```sh
copilot mcp add trackwall -- /Applications/Trackwall.app/Contents/MacOS/trackwall-daemon mcp-stdio                     # macOS
copilot mcp add trackwall '--' '<Trackwall directory>\trackwall-daemon.exe' mcp-stdio    # Windows (PowerShell; `--` in single quotes)
copilot mcp add trackwall -- bun --no-env-file --config=<trackwall>/packages/daemon/bunfig.toml <trackwall>/packages/daemon/src/main.ts mcp-stdio --home <state directory>   # from source
```

The command adds a `trackwall` entry to `~/.copilot/mcp-config.json` (on Windows `%USERPROFILE%\.copilot\mcp-config.json`; the same entry in JSON is in the "Daemon" view, in case it needs to be pasted by hand). Trackwall must be running before Copilot CLI starts, because Copilot starts MCP servers at session start; `/mcp` in Copilot CLI shows whether the `trackwall` server is connected. Then it is enough to ask the agent, for example, "Which repos are in my projects folder?".

Manual check (needs a logged-in Copilot CLI): start Trackwall with the projects folder set, run the command from the "Daemon" view, run `copilot` in the projects folder, check in `/mcp` that `trackwall` is connected with the tools `list_repos`, `get_repo`, `get_repo_card`, `tail`, `get_errors`, `who_calls`, `subgraph_for`, `find_endpoint`, `search_code`, `list_sessions`, `get_session`, `propose_task`, `report_result`, `wait_for_session`, `run_mise_task`, `stop_mise_task`, `wait_for_mise_task` and `list_running_mise_tasks`, ask for the repo list, then for the details of one of them (README, mise tasks), for its card (for example "Which packages does orders-bff use?") and for who uses it ("Which repos does a change in core-lib affect?", "Who calls GET /api/orders/{id}?"), for code across many repos ("Where do the Java repos use RestTemplate?"), and with a session from the "Sessions" view running, for Trackwall sessions ("Which Trackwall sessions are waiting for me?"), then for commissioning a task ("Propose a task in orders-bff that adds a health endpoint, then wait for it"): the proposal should appear in the "Sessions" view, and after "Start task" the task session should start working at once, not wait for you. The daemon log (the `pnpm dev` terminal or `trackwall-daemon`) shows every call as `[mcp] list_repos: ok in … ms`.

Other MCP clients can also talk to the daemon directly through Streamable HTTP at `http://127.0.0.1:<port>/mcp` with the header `Authorization: Bearer <token>`; the port and token are in `daemon.json` and change on every daemon start.
