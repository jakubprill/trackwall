# Funkcje

Co Trackwall robi dziś, widok po widoku. Teksty interfejsu są po angielsku (ADR-32), więc nazwy widoków i przycisków w cudzysłowach są takie, jak w aplikacji. Instalacja: [release.md](release.md), uruchomienie ze źródeł: [development.md](development.md).

Nawigacja: widoki przełącza pasek przy lewej krawędzi okna, jak w VS Code: Home (Ctrl+1), Repos (Ctrl+2), Sessions (Ctrl+3) i Overview (Ctrl+4) u góry, Daemon (Ctrl+9) i Settings (Ctrl+,) na dole; na macOS ⌘ zamiast Ctrl. Nazwę i skrót widoku pokazuje podpowiedź po najechaniu na ikonę.

Several windows (ADR-49): a view can open in a new window, for example the session grid on one monitor and Home or Repos on another. Right-click a view icon and choose “Open in new window”, press Ctrl+Shift + the view's digit (Ctrl+Shift+3 opens Sessions; on macOS ⌥⌘3, because ⌘⇧3 takes a screenshot), press Ctrl+Shift+N (⌘⇧N) for the current view (Settings opens in a new window only this way or from the menu), or choose “New window” in the tray. Every window has the activity bar, switches views on its own (Ctrl + digit and Alt + digit work in the window you are in) and shows the same sessions and repos live. A window opens on the monitor, at the size and position where the window in its place was last time; if that monitor is unplugged, it opens at the default position. When you start Trackwall again, the extra windows that were open when you quit come back on their monitors with the same view and session layout; a window you closed yourself does not. Closing an extra window closes it, while the main window still hides to the tray. “Waiting: <repo>” in the tray opens the session in the window that shows Sessions, so the window on the other monitor keeps its view. With the same session open in two windows, the window you work in sets the terminal size.

Pulpit: widok „Home” (Ctrl+1) otwiera się po starcie i w jednym kadrze 3D pokazuje środowisko (ADR-33): daemon w środku, sesje Copilot CLI na wewnętrznym torze obok swojego repo, repo na zewnętrznym pierścieniu w łukach warstw (wejścia, bramy, backendy, biblioteki, jak kolumny w „Overview”) i połączenia z grafu. Podpis ma tylko to, co wymaga uwagi: repo ze zmianami, do pobrania albo niedostępne i sesja, która czeka na Ciebie albo ma błąd; resztę mówią kolor i kształt, a najechanie kursorem pokazuje nazwę i stan w rogu. A session whose ended turn you have already seen is idle: calm grey, without a label and outside "Needs you" (ADR-47). Kolejka „Needs you” po lewej wymienia te same sesje i repo, (and, between them, task proposals waiting for a decision; a click opens the proposal in “Sessions”), a panel po prawej szczegóły wybranego obiektu (stan, gałąź, działający task mise, sesje repo). Sesja w kolejce ma obok repo tytuł okna, żeby dwie sesje jednego repo dało się odróżnić. Klik wybiera obiekt i kieruje na niego kamerę, dwuklik albo „Open repo” / „Open session” / „Open Daemon” (po wybraniu rdzenia w środku) przechodzi do jego widoku; bez wyboru panel po prawej podsumowuje środowisko. Bez WebGL (stary sterownik, zablokowana karta) albo po utracie kontekstu grafiki w miejscu sceny jest komunikat z przyciskiem „Try again”, a kolejka i szczegóły działają dalej. Gdy folder z projektami zniknął albo `workspace.yaml` ma błąd, widok pokazuje błąd i „Open Settings” zamiast starej listy. Przy włączonym ograniczeniu ruchu w systemie modele stoją.

Przeglądanie repo: w widoku „Settings” wskazujesz folder z projektami (pełną ścieżką), a widok „Repos” pokazuje każde repo gita, które leży bezpośrednio w nim: gałąź, liczbę zmian i ahead/behind, README, pliki i commity z ostatniego commita, oraz otwiera repo w VS Code. README w Markdownie jest sformatowany jak na GitHubie: nagłówki, tabele, listy zadań, bloki kodu i diagramy Mermaid (z przybliżaniem i pełnym ekranem); link na stronę otwiera się w przeglądarce, linki do plików w repo są tekstem, a obrazki pokazuje tylko ich opis; README `.txt`, `.rst` i `.adoc` zostaje zwykłym tekstem (ADR-35). Repo sklonowane do folderu pojawia się na liście samo. Przycisk „+” na liście repo otwiera wyszukiwarkę repo z GitLab i GitHub (hostingi dodaje się w „Settings”) i klonuje wybrane jednym kliknięciem; wymaga zalogowanego `glab` (`glab auth login --hostname <host>`) albo `gh` (`gh auth login`) w `PATH`, a Trackwall nie przechowuje tokenu. Przycisk „Sync all” pobiera zmiany każdego repo (`git fetch`) i przesuwa gałąź domyślną do zdalnej, gdy to czysty fast-forward; repo ze zmianami w gałęzi domyślnej albo z rozjechaną gałęzią zostaje nietknięte. Panel synchronizacji w miejscu szczegółów repo ma zdanie o każdym repo, także aktualnym: co stało się z gałęzią domyślną, czy zmieniły się pliki (nie, gdy pracujesz na innej gałęzi) i ile niezacommitowanych plików zostało, zmienionych i nowych osobno; to samo zdanie jest w podpowiedzi wyniku na liście repo. Lista i nagłówek repo piszą zmiany jako „3 changed, 1 new” (nowy katalog to jeden wpis), a zakładka „Changes” (albo klik w kafelek „Working tree”) pokazuje pliki i diff katalogu roboczego względem ostatniego commitu, z nowymi plikami; zatwierdzasz je i odrzucasz w edytorze. Ścieżka folderu jest kluczem `projectsDir`, a hostingi kluczem `repoHosts` w `~/.trackwall/workspace.yaml`; oba można ustawić też ręcznie. Wymaga `git` w `PATH`.

Taski mise: zakładka „mise tasks” w szczegółach repo pokazuje taski z `mise tasks ls`, uruchamia je (`mise run <task>` w korzeniu repo) i zatrzymuje jako całą grupę procesów, razem z ich potomkami (Job Object na Windowsie, sesja POSIX na macOS, ADR-20); po błędzie pokazuje kod wyjścia i ostatnie linie wyjścia. Przycisk „Log” przy tasku pokazuje jego wyjście na żywo (stdout i stderr, bez kolorów ANSI, błędy i ostrzeżenia wyróżnione), a uruchomienie otwiera log samo; wartości zmiennych środowiskowych o nazwach sekretów (`*_TOKEN`, `*_PASSWORD`, `*_SECRET`…) są w logu zamienione na `***`. Pełny log każdego taska leży w `~/.trackwall/logs/mise-task/<repo>/<task>.jsonl` (najwyżej 10 MB plus jeden poprzedni plik `.1.jsonl`); w nazwie pliku znaki spoza małych liter, cyfr, `_` i `-` są zakodowane jako `%XX`, np. task `build:ui` to `build%3Aui.jsonl`. Konfiguracji mise, której mise nie ufa, można zaufać przyciskiem (`mise trust`); dopiero wtedy taski repo może uruchamiać też agent przez MCP (niżej). Taski uruchomione przez agenta widać w tej samej zakładce, z logiem, i można je stąd zatrzymać. Wyjście daemona zatrzymuje wszystkie taski, a grupy po awarii daemona sprząta jego następny start. Wymaga `mise` w `PATH` (na macOS wystarczy `PATH` z powłoki logowania).

Karta repo i tagi: zakładka „Card” w szczegółach repo pokazuje fakty wyczytane z plików buildu i konfiguracji w ostatnim commicie (ADR-25): paczki Maven, Gradle i npm, które repo udostępnia i których używa, wymagane narzędzia (mise, `.tool-versions`, `.nvmrc`, wrappery), mechanizmy (Spring Boot, Feign, Kafka, Helm, React…), aplikacje Spring Boot z portem, endpointy HTTP z kontrolerów z typem żądania i odpowiedzi, DTO, które te endpointy przyjmują i zwracają (rekordy, `data class`, klasy z polami i enumy z Javy i Kotlina, z polami i ich typami; ADR-38), klienci HTTP (Feign, `@HttpExchange`, WebClient, RestClient, RestTemplate, adresy z `application*.yml` w każdym profilu, `.env` i proxy frontendu; ADR-30) i pliki buildu, każdy fakt z plikiem i linią. Niczego nie buduje ani nie uruchamia; karta liczy się raz na commit i leży w `~/.trackwall/cards`. Z karty powstają tagi repo (`java`, `typescript`, `frontend`, `backend`, `bff`, `library`, `monorepo` i `no-mise` dla repo bez tasków mise w `mise.toml` ani w `mise-tasks/`), widoczne na liście repo z powodem w podpowiedzi (`no-mise` jako ostrzeżenie „no mise tasks”: w takim repo kroki `setup` i `build` komendy zbiorczej i zakładka „mise tasks” nie mają czego uruchomić); filtr nad listą zawęża ją do repo z każdym wybranym tagiem. Własne tagi nadaje klucz `repoTags` w `~/.trackwall/workspace.yaml` (na razie tylko ręcznie): tag i wzorce identyfikatora albo adresu repo zdalnego, np. `repoTags: { core-api: ["*-core"] }`.

Graf połączeń: widok „Overview” (Ctrl+4) rysuje repo z folderu jako graf (ADR-29): linia prowadzi od repo, które używa paczki, do repo, które ją buduje (współrzędne Maven, także z Gradle, i nazwy npm z kart), i od repo, którego klient HTTP woła aplikację albo endpointy innego repo (po nazwie aplikacji, hoście, porcie na `localhost` albo ścieżkach; ADR-30), od frontendów po lewej do bibliotek po prawej. Każde połączenie ma pewność: certain, almost certain, likely albo possible. Kliknięcie repo pokazuje w panelu po prawej, kogo używa i kto używa jego, z dowodami (plik i linia). Połączenia, których karty nie widzą, dopisuje się ręcznie pod kluczem `graph` w `~/.trackwall/workspace.yaml`: `packages` przypisuje paczkę do repo (`com.example:orders-client: orders-api`), `apps` nazwę aplikacji albo host adresu do repo (`orders.internal.example.com: orders-api`), a `edges` dodaje krawędź z opisem (`- { from: shop-web, to: orders-bff, note: HTTP /api/orders }`); repo wskazuje identyfikator albo adres `host/ścieżka`.

Serwer MCP dla Copilot CLI: daemon wystawia serwer MCP (ADR-24) z narzędziami `list_repos` (repo z folderu z projektami: ścieżka, adres repo zdalnego, gałąź, stan, wynik ostatniej synchronizacji i tagi; z argumentem `tags` tylko repo z tymi tagami), `get_repo` (README, ostatnie commity, taski mise i tagi jednego repo), `get_repo_card` (karta repo z tagami i dowodami), `tail` (log taska mise od kursora, z sekretami zamienionymi na `***`), `get_errors` (errors from the mise task logs of all repos or one repo, most recent first: an `ERROR` line, a compiler error or an exception together with its Java or Node stack trace and the cause from `Caused by:`, the Spring "APPLICATION FAILED TO START" report and the Gradle `FAILURE:` report; a repeated error is one entry with a count, with `minLevel: warn` also warnings; ADR-42), `who_calls` (kto używa danego repo, przez paczki i HTTP, z dowodami), `subgraph_for` (fragment grafu połączeń wokół repo), `find_endpoint` (endpoint HTTP po ścieżce albo nazwie, z typem żądania i odpowiedzi i z repo, które go wołają), `search_code` (tekst albo wyrażenie regularne w ostatnim commicie wszystkich repo naraz, z zawężeniem do repo, tagów i ścieżek, z linią, kolumną i kontekstem każdego trafienia; ADR-40), `list_sessions` (sesje Copilot CLI z widoku „Sessions” ze stanem, repo i zadaniem oraz zadania) i `get_session` (jedna sesja z zadaniem i zmienionymi plikami zadania, bez diffu; ADR-36). Sesje z serwerem MCP Trackwall widzą więc siebie nawzajem, ale żadne narzędzie nie uruchamia, nie odpowiada ani nie zatrzymuje sesji. Taski mise (ADR-41): `run_mise_task` uruchamia task z listy repo (to samo co przycisk w zakładce „mise tasks”; konfiguracji bez zaufania nie uruchomi, a zaufać możesz tylko Ty w Trackwall), `wait_for_mise_task` czeka do 55 s na jego koniec i zwraca kod wyjścia, `stop_mise_task` zatrzymuje całą grupę procesów (także task uruchomiony przez Ciebie), a `list_running_mise_tasks` wypisuje działające taski wszystkich repo; wyjście daje `tail`. Sesja z widoku „Sessions” uruchamia i zatrzymuje tylko taski repo, w którym działa, a każde uruchomienie trafia do logu daemona z repo, taskiem i sesją. Do zlecania pracy (ADR-39) są `propose_task` (propozycja zadania: repo, tytuł i polecenie dla innego agenta), `report_result` (podsumowanie od sesji zadania do jej zadania) i `wait_for_session` (czekanie do 55 s, aż sesja albo zadanie będzie wymagać kogoś); opis niżej w „Sesja główna i propozycje zadań”. Copilot CLI podłącza się raz, komendą z widoku „Daemon” (opis niżej w „Podłączenie Copilot CLI”).

Komenda zbiorcza: przycisk „Batch command” pod listą repo otwiera panel, w którym wybiera się repo (domyślnie wszystkie widoczne po filtrze tagów) i kroki: synchronizacja, narzędzia (`mise install`), zależności (task mise `setup`) i build (task mise `build`). Kroki idą w repo po kolei, a repo po trzy naraz; panel pokazuje wynik każdego kroku w każdym repo, a przy błędzie kod wyjścia i ostatnie linie. Repo bez taska ma krok pominięty, błąd kończy tylko to repo, a „Cancel” zatrzymuje trwające taski (także uruchomiony wcześniej ze szczegółów repo, do którego komenda dołączyła) i nie zaczyna kolejnych. Powtórka jest szybka, gdy taski mają w `mise.toml` `sources` i `outputs` (ADR-27).

Sesje Copilot CLI: widok „Sessions” uruchamia Copilot CLI w wybranym repo z folderu z projektami, z podłączonym serwerem MCP Trackwall, kilka sesji naraz, każdą w terminalu należącym do daemona (ADR-26), więc sesja działa dalej po zamknięciu okna. Lista pokazuje stan każdej sesji z hooków Copilot CLI (working, waiting for you, asking for approval; ADR-17) i nad czym agent pracuje; odpowiedź na prośbę o zgodę (Enter albo numer opcji) i przerwanie tury (Esc, Ctrl+C) Trackwall bierze z klawisza w terminalu sesji i z komunikatu „Operation cancelled by user”, bo Copilot CLI nie wysyła wtedy hooka, przycisk „Next waiting” przełącza na sesję, która czeka na odpowiedź, a pasek widoków pokazuje, ile sesji czeka. When the agent ends its turn, the session waits for you only until you have seen it: opening its terminal with the window in focus (or typing into it) turns "waiting for you" into "idle", while a request for approval or for plan approval keeps waiting until you answer (ADR-47). Lista, licznik i pulpit Home dostają zmiany stanu sesji (i działające taski mise) od daemona na żywo przez WebSocket `/ws` (ADR-36), a odpytują go tylko wtedy, gdy to połączenie jest zerwane. Gdy sesja kończy pracę i czeka, okno miga na pasku zadań (na macOS ikona podskakuje w Docku), a menu traya ma pozycję „Waiting: <repo>”, która otwiera tę sesję. „Stop” kończy całą grupę procesów sesji, „Close” usuwa zakończoną sesję z listy. Copilot CLI przejmuje mysz w terminalu, więc tekst zaznacza się przeciągnięciem z wciśniętym Option (macOS) albo Shift (Windows) i kopiuje Cmd+C albo Ctrl+C (Ctrl+C bez zaznaczenia przerywa pracę agenta). Wymaga Copilot CLI w `PATH` (`copilot`; na Windowsie z `npm install -g` Trackwall uruchamia `copilot.exe` z paczki zamiast `copilot.cmd`) i daemona pod Bun (wydanie albo `pnpm dev`); pod Node sesji nie ma. Every session gets an instruction from Trackwall on how to work with it (when to reach for which MCP tool) and what its role is: a session in a repo hands larger work over as a task proposal, and a task session stays in its worktree, does not push and ends with a summary (ADR-46); the instruction lives in Trackwall's session directory, so the repo and the Copilot CLI configuration stay unchanged. Sesje nie przeżywają wyjścia daemona i nie są nagrywane; nagrania robi skrypt opisany w [docs/development.md](development.md#recording-copilot-cli-sessions).

Session layout and shortcuts (ADR-48): the switch above the right side of "Sessions" shows the selected session alone (layout 1, with its full panel) or a grid of terminals: 2 and 4 show pages of that many entries, Auto shows the whole list, up to nine at a time, in as many columns and rows as fit the window (six sessions on a 34-inch ultrawide are three columns and two rows). The selected tile has the accent ring and takes the keyboard, a session that is waiting for you has the warning frame (only the selected tile counts as looked at, so a finished turn in another tile keeps waiting until you select it), and a click on a tile or into its terminal selects it; the button in the tile header opens the entry alone. Alt + digit (⌥ on macOS) selects the entry at that position in the list (the shortcut is under its number) and turns the grid to its page, and Alt+J jumps to the next session that is waiting for you, also from other views. These keys, and Ctrl/⌘ + digit for views, work while a terminal has the focus and are not sent to the session, so in Sessions Alt + digit does not type into a terminal or the task prompt; on macOS an Option + key that types an ASCII character on your layout (⌥5 for `[` on a German keyboard) stays a key and is not a shortcut. A task without a session has no terminal in the grid; open it alone to resume it or see its changes. The layout is kept until the app closes; an extra window keeps it across restarts (ADR-49).

Zadania agenta: przycisk „+” w widoku „Sessions” otwiera formularz nowego zadania: repo i polecenie dla agenta. Trackwall tworzy nową gałąź `trackwall/<skrót polecenia>` od gałęzi domyślnej repo w osobnym worktree w `~/.trackwall/worktrees/<repo>/` i uruchamia w nim Copilot CLI z poleceniem jako pierwszą wiadomością (ADR-31), więc kilka zadań w jednym repo działa naraz bez kolizji, a Twój katalog roboczy zostaje nietknięty. Zakładka „Changes” pokazuje na żywo pliki i diff worktree względem gałęzi domyślnej, z commitami zadania i tym, czego agent jeszcze nie zacommitował. Przyciski: „VS Code” otwiera worktree, „Resume” uruchamia Copilot CLI z rozmową zadania (`--resume`), a „End task” usuwa worktree i zostawia gałąź albo usuwa obie; zmiany, które by przy tym przepadły, Trackwall usuwa dopiero po potwierdzeniu. Zadania przeżywają restart daemona. Copilot CLI pyta o zaufanie w każdym nowym folderze; żeby nie pytał przy każdym zadaniu, dopisz katalog `worktrees` (pełną ścieżkę podaje formularz) do `trustedFolders` w `~/.copilot/config.json`.

When another task of the same repo changes the same files, a warning above the task's tabs names the other task and lists the shared files (refreshed every 5 s), with an “Open that task” button; Trackwall only warns and stops nothing (ADR-44).

Sesja główna i propozycje zadań: sesja Copilot CLI z serwerem MCP Trackwall (w widoku „Sessions” albo w Twoim terminalu, np. w folderze z projektami) może zlecić pracę innemu agentowi jak koordynator, który zakłada wątki (ADR-39). Narzędzie `propose_task` zgłasza propozycję zadania z tytułem i poleceniem; widok „Sessions” pokazuje ją jako „waiting for your decision”, a pasek widoków liczy ją razem z sesjami, które czekają. A proposal from a listed session, and the task made from it, sit indented under that session (or under the task whose session delegated it), and the main session has a “main” badge with the number of items under it; a proposal from an agent outside Trackwall or from a closed session is at the top level. Proposals also show in the “Needs you” queue on the Home dashboard (a click opens it in “Sessions”) and in the tray menu (“Proposal: <repo> · <title>”); a new proposal flashes the window in the taskbar or bounces the Dock icon like a session that started waiting, and the tray tooltip counts proposals together with sessions. Po wybraniu widać, kto ją zaproponował, i całe polecenie, które można poprawić; „Start task” tworzy z niej zwykłe zadanie (worktree, gałąź z tytułu, sesja z poleceniem), „Reject” ją odrzuca, a do tej chwili nic się nie uruchamia. Sesja zadania kończy pracę narzędziem `report_result`, a jej podsumowanie widać nad zakładkami zadania („Summary”). Sesja główna czeka na wynik narzędziem `wait_for_session` (zwraca, gdy sesja skończy turę, prosi o zgodę, zgłosi błąd, nie odpowiada albo się zakończy, a propozycja zostanie odrzucona) i czyta zmiany przez `get_session`. Propozycje żyją tylko do wyjścia Trackwall (najwyżej 20 naraz), podsumowania zostają z zadaniem. Każda sesja Trackwall ma własny token sesji, po którym serwer MCP wie, kto woła; agent spoza Trackwall proponuje jako „agent outside Trackwall”, ale nie zgłasza podsumowań. Polecenie i tytuł z propozycji oraz podsumowanie nie mogą zawierać niewidocznych znaków, żeby to, co czytasz przed „Start task”, było całym poleceniem.

## Podłączenie Copilot CLI

Copilot CLI uruchamia most stdio daemona (`trackwall-daemon mcp-stdio`) jako lokalny serwer MCP; most znajduje działający daemon przez `daemon.json`, więc konfiguracja nie zmienia się po restarcie daemona i nie zawiera tokenu. Gotową komendę dla tej instalacji pokazuje widok „Daemon” (Ctrl+9, przycisk kopiowania). Wygląda tak:

```sh
copilot mcp add trackwall -- /Applications/Trackwall.app/Contents/MacOS/trackwall-daemon mcp-stdio                     # macOS
copilot mcp add trackwall '--' '<katalog z Trackwall>\trackwall-daemon.exe' mcp-stdio    # Windows (PowerShell; `--` w apostrofach)
copilot mcp add trackwall -- bun --no-env-file --config=<trackwall>/packages/daemon/bunfig.toml <trackwall>/packages/daemon/src/main.ts mcp-stdio --home <katalog stanu>   # ze źródeł
```

Komenda dopisuje wpis `trackwall` do `~/.copilot/mcp-config.json` (na Windowsie `%USERPROFILE%\.copilot\mcp-config.json`; ten sam wpis w JSON jest w widoku „Daemon”, gdyby trzeba go wkleić ręcznie). Trackwall musi działać, zanim wystartuje Copilot CLI, bo Copilot uruchamia serwery MCP przy starcie sesji; `/mcp` w Copilot CLI pokazuje, czy serwer `trackwall` jest połączony. Potem wystarczy poprosić agenta np. „Which repos are in my projects folder?”. The MCP server also gives an instruction on when to reach for which tool, but Copilot CLI 1.0.103 takes such instructions only from servers on its own allowlist; in a session started outside Trackwall you can turn it on with `copilot --allow-all-mcp-server-instructions` (which turns on the instructions of every connected MCP server). Sessions from the "Sessions" view get it without that (ADR-46).

Sprawdzenie ręczne (wymaga zalogowanego Copilot CLI): uruchom Trackwall z ustawionym folderem z projektami, wykonaj komendę z widoku „Daemon”, uruchom `copilot` w folderze z projektami, sprawdź w `/mcp`, że `trackwall` jest połączony z narzędziami `list_repos`, `get_repo`, `get_repo_card`, `tail`, `get_errors`, `who_calls`, `subgraph_for`, `find_endpoint`, `search_code`, `list_sessions`, `get_session`, `propose_task`, `report_result` i `wait_for_session`, poproś o listę repo, a potem o szczegóły jednego z nich (README, taski mise), o jego kartę (np. „Which packages does orders-bff use?”) i o to, kto go używa („Which repos does a change in core-lib affect?”, „Who calls GET /api/orders/{id}?”), o kod w wielu repo („Where do the Java repos use RestTemplate?”), a przy działającej sesji z widoku „Sessions” o sesje Trackwall („Which Trackwall sessions are waiting for me?”), a potem o zlecenie zadania („Propose a task in orders-bff that adds a health endpoint, then wait for it”): propozycja ma się pojawić w widoku „Sessions”, a po „Start task” sesja zadania ma od razu pracować, nie czekać na Ciebie. Log daemona (terminal `pnpm dev` albo `trackwall-daemon`) pokazuje każde wywołanie jako `[mcp] list_repos: ok in … ms`.

Inne klienty MCP mogą też rozmawiać z daemonem wprost przez Streamable HTTP pod `http://127.0.0.1:<port>/mcp` z nagłówkiem `Authorization: Bearer <token>`; port i token są w `daemon.json` i zmieniają się przy każdym starcie daemona.
