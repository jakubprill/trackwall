# Trackwall architecture

Status: a proposal for discussion, 2026-10-23. The earlier working name "Pitwall" was changed to "Trackwall" (ADR-12).

This document describes how the app is split into components, where the boundaries between modules run, which protocols the components speak, what the data model is, what the key flows look like and which risks come with Windows as the main platform. The product vision (goal, modules, order of work) is an assumption of this document, not its content. Decisions worth being able to reverse later are collected at the end as ADRs.

## 1. Principles that order the rest

1. **The daemon is the single source of truth.** The UI, the MCP server and the `ws` CLI are three clients of the same service facade in the daemon. The dashboard and the agent never disagree about state, because they ask the same object.
2. **The daemon knows identifiers, not commands.** Every action from outside (MCP, CLI, UI) points to a repo, service, task or mise task by identifier. The daemon builds the command from configuration. The only exception is the interactive terminal in the UI.
3. **Process state is observed, not declared.** "Stopped" means the whole process group is dead and the daemon has checked it. "Running" means the health probe answered.
4. **Facts deterministically, the LLM only adds.** The repo card and the graph come from build and configuration files. A language model adds a description and suggestions, it is never the source of a technical field.
5. **Secrets do not pass through the agent.** The daemon injects them into the process environment and masks them in logs. MCP tools answer "set / missing", never with the value.
6. **Nothing company-specific in the code.** Addresses, repo names, paths and company-specific detection rules live in the local workspace, outside the project repository.
7. **Windows first.** Every mechanism (processes, PTY, paths, signals) is designed from the Windows side, and macOS gets the counterpart. The reverse order ends in a "slightly different on Windows" layer.

Four kinds of processes on the user's machine:

| Process | Role | Alive when the window is closed? |
|---|---|---|
| `trackwall.exe` (Tauri) | window, tray, daemon supervision, update | yes, in the tray |

## 4. Daemon: modules and boundaries

The daemon is a single process, but inside it is split into modules with an explicitly declared interface. Every module exposes a service class, and the facade (`Facade`) is the set of these services (plus the `openLink` function, which opens a link from a README in the system, without state and without a module, ADR-35) handed to the three transports (HTTP, MCP, events). A module does not import another module directly, only through the facade, so the dependency graph between modules is visible in one file.

In code: a module is the directory `packages/daemon/src/modules/<module>/`, the facade is `packages/daemon/src/facade.ts`. A module that needs another one declares an interface with what it uses on its own side (for example `WorkspaceVcs`), and `createFacade` gives it the instance of that module. Biome guards both sides: a module file does not import from a neighbouring module directory (from outside only the infrastructure files `src/infra/errors.ts`, `src/infra/atomic-write.ts`, `src/infra/map-limit.ts`, `src/infra/loopback.ts` (HTTP requests on loopback, for `services`, ADR-45) and the `src/platform/` directory, listed in `biome.json`, so a module is a flat directory), and code outside the modules (transports, startup) reaches the modules only through `facade.ts`.

| Module | Responsible for | Depends on | Persistent state |
|---|---|---|---|
| `workspace` | repos from the projects folder, cloning into it, sync, state per repo, browsing contents, code search across many repos, `ws sync` | `vcs` (`batch` composes sync with mise steps on top of them, §4.8) | `workspace.yaml` (ADR-13, ADR-18), `repos` table |
| `vcs` | adapters for git (local), GitHub and GitLab (through `gh` and `glab`: repo list, clone); task worktrees (a new branch with a worktree, changes against the base commit, removal, ADR-31); `git show` without a checkout; status, log, tree, files and `git grep` from HEAD | – | – |
| `mise` | the list of a repo's tasks, running tasks by name and `mise install` (§4.7); later generating `mise.local.toml` and detecting the stack | `procs`, `workspace` (repo root by identifier) | files in the repo |
| `batch` | the Batch command: sync, `mise install`, the `setup` and `build` tasks on selected repos (§4.8) | `workspace` (repo root, repo sync), `mise` (runs awaited until they end) | – (in memory) |
| `cards` | the repo card from build, configuration and code files in the HEAD commit (provided and consumed packages, Spring Boot apps, HTTP endpoints and clients, required tools, mechanisms) and repo tags (§4.6); later completed by an LLM | `workspace` (repos from the folder, tag rules), `vcs` (reading the commit) | `cards/<commit>.json` in the state directory (ADR-25) |
| `graph` | the connection graph between repos: joining the packages and HTTP clients from the cards with the packages, apps and endpoints of other repos, package and app aliases and manual edges from `workspace.yaml`; the queries `who_calls`, `subgraph_for`, `find_endpoint` (§4.6) | `cards` (cards and tags of all repos), `workspace` (`graph` entries) | – (the last graph in memory, keyed by the set of commits and the configuration, ADR-29, ADR-30) |
| `procs` | process groups, start/stop with escalation, orphans, port -> owner | `logs` (group output, §4.2) | `runtime.json` (live groups, §4.1) |
| `logs` | the bus: ring buffer, JSONL, sequences, cursors, masking, `trace` | `secrets` (masks; today masks from the process environment) | `logs/<source kind>/<repo>/<mise task>.jsonl` |
| `services` | service = repo + mise task `dev` + port + readiness; start with dependencies from the graph, endpoint call (§4.3, ADR-45); later leases | `mise` (the task `dev` and its run), `logs` (port from the log, errors, masking), `graph` (dependencies), `cards` (`server.port`); later `leases` | – (in memory; planned: table `services`) |
| `leases` | who holds a service on which port; takeover by a task | – | `leases` table |
| `secrets` | the secrets repo (k8s `Secret` manifests), reading `git show origin/<app>:<file>`, injection into env, `check_secrets` | `vcs` | a clone outside the workspace |
| `agents` | Copilot CLI sessions in a PTY (§4.4, ADR-26), tasks in separate worktrees (ADR-31), state detection; later budget, recording | `procs` (group with a PTY), `workspace` (repo root by identifier), `vcs` (task worktrees and branches); later `logs`, `leases` | today session files in `sessions/<session>/` (session plugin, `hooks.jsonl`), removed when a session closes and when the daemon starts, and tasks in `tasks.json` with worktrees in `worktrees/<repo>/<branch without prefix>`, removed at the user's request; eventually a `tasks` table and recordings |
| `mcp` | the MCP server: mapping tools to the facade, audit; today a transport in `src/mcp/` next to `api/` (§5.3, ADR-24), without audit | everything through the facade | `audit` table |
| `api` | HTTP + WebSocket for the UI and CLI (events `/ws`, session terminals `/ws/pty/<session>`), token, CORS, static UI files | everything through the facade | – (the last snapshot of each event topic in memory, ADR-36) |

Two modules are the "foundation": `procs` and `logs`. `logs` depends on no module, `procs` only on `logs` (it hands it the group output), and everything else stands on them, so they come first and get the most tests, including on Windows.

### 4.1 `procs`: process groups

- A start always creates a **group** (ADR-20): on Windows a Job Object with `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` through `bun:ffi`, on macOS and Linux a new session (`setsid`, `detached` in Node) and signals to `-pgid`. A mise child that runs mvn, which runs java, is one unit. On Windows the leader goes into the job right after `spawn` (Node cannot start a suspended process); a descendant created in that moment, before the leader is in the job, would fall out of the group, but `mise` takes a few milliseconds to start before it runs anything. The system code is in `platform/` (`GroupPlatform`), the `procs` module (`ProcessGroups`) knows only the interface.
- The group owner (`owner`) is the caller's key (today a mise task in a repo or `mise install` in a repo, built in the `mise` module and never parsed back); there is one group per owner, and a second start returns the state of the first until that one is confirmed empty. After the end the last state stays until the next start, in daemon memory. A stop during a start waits for the group, and once the daemon has started exiting no new groups are created. Whoever waits for the result rather than just showing the state (the Batch command, §4.8) gets it from `ended(owner)`: the `exited` state of the current group after confirming that it is empty; a group that cannot be killed never ends.
- A stop escalates: a gentle signal (macOS and Linux: SIGTERM to the group; Windows: closing the leader's stdin, because `GenerateConsoleCtrlEvent` needs a shared console, which a process with a hidden window does not have), after a grace period (5 s; 2 s on Windows, because most servers do not listen for stdin closing) killing the whole group (`SIGKILL` to `-pgid`, `TerminateJobObject`) and up to 3 s of waiting for an empty group, all within the 10 s the shell waits for the daemon to stop (§5.4). The same path stops orphans at startup. **A stop returns success only after confirming** that no process of the group is alive (`kill(-pgid, 0)` gives `ESRCH`, the job has zero active processes); otherwise the error `stop_unconfirmed`, and the run stays `stopping`. The port is not checked yet: that comes with services, which know their port.
- A leader that ended on its own takes the rest of the group with it: the daemon kills what is left, and only after confirming an empty group is the run `exited` (exit code, signal, whether the user stopped it, and the last lines of output). Until then it is `stopping`, and a group that could not be killed stays in `runtime.json` and blocks a new start of that owner. A stop that arrives in that time waits for this cleanup and returns the leader's result (its exit code, without `stoppedByUser`). A stop during a start waits for the start; when the start failed there is no group and the stop ends with `not_found`.
- The group registry in `runtime.json` (in the state directory): owner, command, directory, the leader's PID and its start time according to the system (`ps -o lstart` with fixed `TZ=UTC` and `LC_ALL=C`, to the second). A group goes there after the start and disappears after a confirmed end; an orphan that could not be killed stays until the next start. A file that cannot be read is set aside (`runtime.json.broken-<time>`), and a failed write goes to the log and does not change the in-memory state. At daemon startup, under the startup lock and before the API opens, orphans are cleaned up only when the leader is the same process: it is alive with the same start time (PIDs are recycled), or it is dead but the group with its id is alive (the system does not hand out a PID while a group with that number lives). A live PID with a different start time (or without a recorded time) is not killed: it goes to the log and disappears from `runtime.json`, because later starts would not settle whether it is our process either. On Windows under Bun there are no orphans, because closing the job handle when the daemon dies kills the group; under Node the daemon only reports the live PID.
- Daemon exit (Ctrl-C, a signal, `POST /api/daemon/shutdown`) stops all groups with the same stop, in parallel, before the API closes.
- **A leader in a PTY** (`startTerminal`, ADR-26): the same group, but the leader starts in a pseudo-terminal from `platform/terminal.ts` (`Bun.spawn({ terminal })`: ConPTY on Windows, a PTY with a new POSIX session on macOS and Linux, so the leader's PID is the group id as with `setsid`). The caller gets a terminal to write to and resize, and the PTY output goes to it and to the last lines of the `exited` state (masked by `logs.lastLinesOnly`, without a log, because a screen is not log lines, ADR-28). A gentle stop on Windows closes the terminal (ConPTY then sends `CTRL_CLOSE_EVENT` to the processes, as when a console window closes), on POSIX it is the same SIGTERM to the group. The owner of a group with a PTY must be new: there is no "second start" that would return the existing one. Under Node there is no PTY (`terminal_unavailable`), because it would need a native addon.
- stdout and stderr are always read (an unread pipe blocks the child at about 64–192 KB) and go to the `logs` module (`attachOutput` in `process-groups.ts`): the caller gives the log source (`logSource`) in `PipedGroupSpec`, and `logs.open` gives the run output (`RunOutput`), which turns bytes into records and returns the last 20 non-empty lines (masked, without ANSI sequences and overwritten `\r` progress) for the `exited` state.
- The working directory must be the full path of an existing directory; the caller gives the root of the repo or worktree. The environment is the daemon's environment without `TRACKWALL_HOME`, and on macOS with the `PATH` from the user's login shell (`user-env.ts`): an app opened from Finder gets only the system `PATH` from launchd, without Homebrew and `~/.local/bin`.
- `portOwner(port)` returns the owner with a confidence level: `exact` (a PID from our group), `high` (a descendant of our group), `medium` (the command matches a service), `low`. At `low` the daemon takes no automatic action. (Not done yet.)

### 4.2 `logs`: the bus

The first slice (ADR-28): the log of every mise task (from the repo details and from the Batch command) and of `mise install`, live in the repo details and in a JSONL file. The ECS parser, `trace`, search and the logs of services, tasks and the daemon are the next steps; the MCP tool `tail` reads the same log as the UI, and `get_errors` pulls errors out of the buffers of all sources (§5.3, ADR-42).

- Record: `{ seq, ts, runId, stream, level, msg }` (`LogRecord` in `packages/protocol`), in the file also `source`. The source (`LogSource`) is today `{ kind: 'mise-task', repo, miseTask }` and `{ kind: 'mise-install', repo }` for `mise install` from the Batch command (§4.8); services, tasks and the daemon will come as further kinds, and the target fields (`trace_id`, `span_id`, `fields`, `raw`) will come with the ECS parser.
- One **global** `seq` for all sources. Each daemon lifetime starts it at its start time in milliseconds times 1000, so the numbers of consecutive lifetimes do not repeat, and a cursor from a previous lifetime is smaller than the cursor of the current empty log (start time times 1000). The `sinceSeq` cursor (`logs/tail` in the API and the MCP tool `tail`) works for one source, and for the whole workspace in `get_errors` (ADR-42; later also in `search`). A cursor older than the source's buffer returns `dropped: true` with records from the oldest in the buffer; a cursor from another daemon lifetime (smaller than the empty-log cursor, or larger than the last `seq` when the clock went back) returns `dropped: true` with the latest records, as without a cursor. A clock that went back by less than the previous daemon lifetime lasted can put an old cursor inside the current range; then the client gets the records after it without `dropped`, and the UI starts the log over after a connection change anyway.
- A ring buffer per source (2000 records, `LOG_BUFFER_RECORDS`, and at most 2 million characters of text, so that long JSON lines do not take tens of MB per task) for the UI and MCP, with the records of consecutive runs (`runId`), in memory only. JSONL on disk: `logs/<kind>/<repo>/<mise task>.jsonl` (`logs/mise-install/<repo>.jsonl` for `mise install`) in the state directory, with names encoded to be safe on Windows and macOS (`%XX` for characters outside `[a-z0-9_-]`, including `:` and upper-case letters, a prefix for device names like `con`, a hash for names longer than 60 characters, so that the path fits in 260 characters with a state directory of up to about 100 characters). Writes in batches every 250 ms and at daemon exit; at 10 MB the file becomes `.1.jsonl` (the previous one is gone). A rotation that failed (on Windows a file opened without `FILE_SHARE_DELETE`, for example by `Get-Content -Wait`) does not stop writing: the file grows past the limit until the next successful rotation, and the error goes to the daemon log once. A failed write stays in the buffer until the next attempt (up to 4 MB, after that records do not reach the file), and the error and the loss of records go to the daemon log once; a write cut off halfway (no space left) may repeat some records in the file after a retry. An optional index `trace_id -> (file, offset)` in SQLite for `trace(trace_id)` comes with `trace`.
- Line: a UTF-8 decoder and an unfinished line separately for stdout and stderr, ANSI sequences removed, masking, then of a line with `\r` only what follows the last `\r` remains (progress in a terminal). An unterminated line longer than 64 KB becomes a record (the split never cuts a secret: it falls before it or before the last characters in which a secret could only be starting), a record has at most 16 KB of text, empty lines stay in the log (not in the last lines of the state).
- Level from the line text, until there is an ECS parser: `ERROR`/`FATAL`/`SEVERE`/`npm ERR!`/`npm error`, or `error`/`fatal` at the start of a line, is `error`, and so is a compiler diagnostic with a file location (javac `Foo.java:12: error:`, tsc `a.ts(3,5): error TS2322:`, kotlinc `e: ` with a file) and Vite's `Internal server error:`; `WARN`/`WARNING`, `warning` at the start, `npm warn`, `Foo.java:7: warning:` and kotlinc `w: ` with a file are `warn`; upper-case `DEBUG` and `TRACE`; everything else is `info`. The task prefix `[name] ` mise puts before the lines of dependencies does not change the level (a level is not a prefix: an upper-case level word alone or with a thread, like Maven `[ERROR]` or `[ERROR:main]`, or a lower-case one alone, like sbt `[info]`; so a task named exactly `debug` keeps its prefix). The stream does not decide, because many tools write ordinary progress to stderr.
- **Errors from logs** (`get_errors`, ADR-42): `errorBlocks` (`error-blocks.ts`) splits the records of one source into blocks, separately for each run and stream. A block starts at an unindented record at the threshold (`error`, with `minLevel: warn` also `warn`; an indented line at `error` level, like `b.old(Level.SEVERE);` under a javac warning, is context, not an error), a failed Gradle test (`OrdersTest > rejects FAILED`), an exception header (`java.lang.IllegalStateException: …`, `TypeError: …`, `Exception in thread "main" …`), a `Caused by:` without its beginning, or the opening of a region. It is extended by Java and Node stack frames (`at …`, `... 12 more`), `Caused by:`/`Suppressed:`, an exception header under a logger line (until the block has frames), indented and blank lines, a line of asterisks, Node's `Require stack:` with its `- path` lines, and further lines with the same level tag and no timestamp (Maven `[ERROR]`, `npm error`). Whatever starts an error (an `error` record, an exception header, `Caused by:`, a report) under a warning starts an error of its own, so an error does not depend on `minLevel`. Regions without indentation last until their end: the Spring "APPLICATION FAILED TO START" report until the blank line after the `Action:` paragraph, the Gradle `FAILURE:` report until `BUILD FAILED`, and both until a line starting with a date or time (the logger's next event), a Maven level tag or a Gradle `> Task` line (the build tool that ran the app), or another region's start, which matters for a Spring report without `Action:`; a block has at most 500 records. Outside a region any other line closes the block, and trailing blank lines are not part of it. `collectErrors` (`log-errors.ts`) merges the same errors of one source (the exception and its first frame, or without an exception the first 20 lines, after replacing numbers, UUIDs, hex ids and bracketed parts such as thread names and trace ids, but keeping file locations like `Orders.java:12` so different compiler errors stay apart) into one entry with `count` and `firstTs`, with the lines and `seq` of the latest occurrence, and trims the lines: the first 10 frames of each run of frames (recognised without the mise task prefix), the rest as one line `… N frames omitted`, at most 60 lines of 4000 characters (`omittedLines` counts what was left out). The entry's `exception` is the last `Caused by:` of the main chain (not one at or under the indentation of a `Suppressed:` exception) or the first header. The `sinceSeq` cursor skips errors whose first record is not after it, so a block still being written when asked comes once, with the lines it had at that moment. Errors are computed on every request from the in-memory buffer, without an index and without reading the JSONL files, so errors older than a source's buffer are gone with it.
- ECS parser (later): Spring Boot with `LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs` gives JSON with `log.level`, `trace.id`, `error.stack_trace`. A line that is not JSON gets its `level` from the heuristic and goes to `raw`.
- Masking: the set of secret values of a given process is known to the `logs` module and replaced with `***` **before** being written to the buffer, the file and the last lines of the state. The agent and the file see the masked version only. Today a secret is the value of a variable from the process environment whose name has a segment `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `PASSPHRASE`, `API_KEY`/`APIKEY`, `PRIVATE_KEY`, `CREDENTIAL(S)` or `PAT` (for example `GH_TOKEN`, `DB_PASSWORD`), at least 8 characters long; a multi-line value (a PEM key) contributes each of its lines separately, and overlapping occurrences of secrets are merged before the replacement. Secrets injected by the `secrets` module will join this set (gap: §8).
- ANSI is removed on write; colour in the UI comes from `level`. The view is a light list of lines under the task row in the "mise tasks" tab (the "Log" button; a run opens it by itself), which follows new lines until the user scrolls it up, and stderr has a marker on the side. The UI polls `logs/tail` from the cursor every second while the log is open, and immediately when a response is full; the WebSocket `log.append` (§5.2) will replace polling without changing the record. xterm.js stays for the PTYs of task sessions (ADR-28).

### 4.3 `services` and `leases`

A service is a pair (repo, mise task `dev`) plus a port and a probe. States: `stopped`, `starting`, `healthy`, `unhealthy`, `stopping`, `crashed(exitCode, lastStderr)`.

First slice (ADR-45, `modules/services/`, contract in `packages/protocol/src/services.ts`): a service is a repo with the mise task `dev` (`SERVICE_MISE_TASK`), one per repo (`ServiceId` = repo id), run from the repo root through `mise.start`, so it is the same process group and the same log source (`mise-task`, `dev`) as the button in the "mise tasks" tab, and a `dev` started there (or with `run_mise_task`) is adopted as a service by `list`, `start`, `stop` and `call`; its watch reads the log from the oldest buffered record (`logs.runStartCursor`), so a port logged long ago is still found.
- **Readiness** (`service-watch.ts`, `readiness.ts`, `port-probe.ts`): a watch per run checks every 500 ms (one check at a time; nothing changes the state after the end) the run state from `procs`, the new lines of its log and a TCP connection to the port on `127.0.0.1` and `::1` at once (Node dev servers on `localhost` often listen only on IPv6, and a refused connection on Windows takes about 2 s). The port is the first one the run logs (`Tomcat|Netty|Jetty|Undertow started on port N`, `Local: http://localhost:N`, `listening on port N`, `listening on http://localhost:N`; patterns of a server that listens, not of a client that connects), otherwise `server.port` of the apps on the card, which reads only the default profile. `healthy` once a port accepts a connection, or for a Spring Boot app without a port after its `Started … in N seconds` line; `unhealthy` when the port stops answering, or 5 minutes after the start of the run while still `starting` (Gradle and Maven compile first); `crashed` when the group ended by itself, `stopped` after a stop. The `mise run health` probe from the plan is not used: it needs a task in every repo, and an open port says the same for a web service.
- **Slice** (`slice-plan.ts`): a start with dependencies takes the repo and the repos it calls at runtime, transitively: graph edges `http` and `manual` without `low` confidence (paths that match endpoints of several repos); `package` edges matter only for the build. At most 12 repos (`MAX_SLICE_REPOS`), otherwise `bad_request`. Repos start in waves: one starts once every repo it calls within the slice has settled (healthy, unhealthy, crashed or skipped), so a config server or registry comes up before its clients; repos in a cycle start together. A member without `dev`, with mise unavailable or an untrusted config, or whose `server.port` already answers before its start (another service of the slice or a program Trackwall did not start; the reason names which) is `skipped`, the repo asked for too; the repo asked for without `dev` is `not_found` before anything starts. Two starts at once share one slice. A running service is not started again (`running`), so a second start waits further; a crashed one starts again. The start goes on in the background after the answer (`waitMs`, up to 55 s, MCP calls must end within the bridge limit).
- **Stop**: the service of the repo, and with `dependencies` the members its starts `started` (also an earlier start with dependencies before a start without them), except those another slice uses that is still starting or whose root still runs; the stops run in parallel, and the answer lists the services that were running. A stop during a start cancels it: no further wave, and no member starts after the stop unless another slice still starting needs it; a member whose start was already under way is stopped once it runs; the next start makes a new slice. A start with the other `dependencies` value while a start is in progress is `bad_request`. A repo never started (no slice and no running `dev`) is `not_found`; a stop after the root crashed still stops its dependencies.
- **Endpoint call** (`endpoint-call.ts`): an HTTP request with the caller's method, path, headers (without `host`, `content-length`, `transfer-encoding`, `connection`) and body (64 KB) to the loopback address and port that answered the probe of a `healthy` service, through `loopbackRequest` (not `fetch`, which sends loopback through `HTTP_PROXY` in Bun) with a deadline for the whole request, so an event stream with keepalives does not hold the call; the URL is built by the daemon, so the call does not leave the computer and reaches only a port of a service Trackwall runs. The response body is read up to 128 KB and returned up to 32 KB of text, and it and the headers are masked with the secret values of the service environment, as the log lines are (`logs.mask`). After the response the daemon waits 500 ms and returns the errors (`logs.errors`, ADR-42) of the task `dev` in every repo whose first record came after the cursor taken right before the request, so an exception in a downstream service is in the result too.
- UI: the "mise tasks" tab of a repo with `dev` has a "Service" panel with the state and port, "Start with dependencies" and "Stop with dependencies" and the state of each dependency of the last start. The API actions are `services/list`, `services/start` and `services/stop`.
- Not yet: a service from a task worktree (mise trusts a config by path, so a worktree config is untrusted; trusting it for the agent would let it run any command through `mise.toml`), several services per repo, leases, secrets from the `secrets` module, the services in the graph view.

A lease says **which branch/worktree** holds a service on its port. By default the leaseholder is the main repo. An agent task that changes a service's code asks for the lease; the daemon stops the instance from the main repo, starts the instance from the task worktree on the same port, and gives it back when the task ends (or by hand). Thanks to that the rest of the graph does not need to know anything. Routing by header through a proxy is out of scope until two instances at once are needed; the `leases` interface is designed so that a proxy can be added without changing the other modules.

### 4.4 `agents`: tasks

- **CLI adapter** = a command template (`copilot --prompt {prompt_file} ...`), the way MCP configuration is passed, the session resume command, a set of state detectors. **The only adapter is Copilot CLI** (decision of 2026-10-23). The adapter interface stays, because it keeps the code in order, but we do not design for Claude Code or Codex and do not test their detectors.
- A session runs in a **PTY owned by the daemon** (ConPTY on Windows). The UI attaches xterm.js over a WebSocket, `ws attach` does the same in a terminal. Eventually the PTY output is recorded (asciicast format) to `sessions/<task>.cast`; today only the `copilot-record.ts` script records, and sessions in the daemon (below) do not.
- **State detection**, from the most reliable source: (1) CLI hooks, if the adapter has them, (2) the OSC 9 / 777 / 99 terminal sequences and the `ws notify <state>` command available in agent scripts, (3) screen patterns (on the daemon side, not in the UI; the first works on the output text alone, a VT parser will come with patterns that need it), and next to them the keys with which a human answers in the session terminal, for what the CLI does not report. Every state change carries `source` and `confidence`, so the UI can show "probably asking for approval".
- States: `Working`, `Input`, `Approval`, `Plan`, `Done`, `Error`, plus `Stale` (no signal for longer than a threshold). A budget of time and number of commits with forced termination.
- **Sessions in the daemon** (ADR-26, the "Sessions" view): `agents.start {repo}` starts Copilot CLI (`copilot` from the user's `PATH`; on Windows, instead of `copilot.cmd` from npm, the native `copilot.exe` from the platform package, because `cmd.exe` mangles arguments, `findCopilot`) in the root of a repo from the projects folder, through `procs.startTerminal`, with `--plugin-dir` of the session plugin, in a 120×30 PTY that takes the size of the last terminal window. The environment is `userEnv` with `TERM=xterm-256color` and `COLORTERM=truecolor`. Several sessions can run at once; each has an identifier (UUID) and a directory `sessions/<session>/` in the state directory with the session plugin and `hooks.jsonl`. The plugin's hook is the daemon itself with the subcommand `copilot-hook <event> <hooks.jsonl>` (`selfCommand`: the release binary, or the runtime and script from source, Bun with `--no-env-file`), which appends a hook record to the file, and the session reads new lines every 200 ms (`HookTail`), together with the `Stale` threshold and the end of the group in `procs`. The screen of each session is kept by a windowless terminal emulator (`TerminalScreen`, `@xterm/headless`, 2000 lines of scrollback), from which the window in the UI gets the screen image on attach (§5.2). `stop` stops the group like any other (§4.1), and a stop by the user ends the state as `Done`, not `Error`, even though the process ends with a signal. An ended session stays on the list with its last screen until the user closes it (`dismiss`, which also removes its directory). The X on a grid tile and on a list row (ADR-48) closes a running session too: the UI calls `stop`, then `dismiss` (`lib/use-session-close.ts`, also behind the session panel's Close), and asks first while the agent is in the middle of a turn (`closeCutsOffTurn`); a task's session closes alone, and the task stays listed. Sessions live in memory: daemon exit stops them together with the other groups, and daemon startup removes the `sessions/` directory left by the previous daemon lifetime. A session "waits for you" (`Session.needsAttention`, computed in the daemon by `SessionAttention`, ADR-47) when it runs and its state is `Approval` or `Plan`, or `Input` the user has not seen yet. A session terminal in front of the user (focused and visible for at least 1 s, `FocusReporter` in the UI; the window sends `focus` over `/ws/pty`, §5.2) or a key typed into the session (not an answer xterm.js sends to a terminal query, which starts with ESC) marks the `Input` seen, the `Input` an Esc causes included, and a window in front of the user when the state changes sees the new state at once; only a change to another state makes it unseen again. `Approval` and `Plan` wait until the user answers, because the agent is blocked in the middle of the turn. The UI shows seen `Input` as "idle" (the dashboard state `idle`); the UI (the counter on the view bar, "Next waiting") and the tray (§5.4) only read the field. The first Copilot CLI window in a new directory (folder trust) and sign-in give no hook, so the session then has no state ("state unknown"), even though it is waiting for you. The daemon does not record sessions; recordings are made by the `copilot-record.ts` script. Every session gets the Trackwall MCP server (§5.3, ADR-24): the daemon writes `mcp-config.json` with the stdio bridge into the session directory (`sessionMcpStdioCommand`: the entry from the "Daemon" view with `--session-token-file` of this session, ADR-39; `copilotMcpServers` in `protocol`) and passes it as `--additional-mcp-config @<file>`, so the session has the Trackwall tools without `copilot mcp add` and without changing the user's configuration. In the same way it gets **session instructions** (`session-instructions.ts`, ADR-46): the file `instructions/trackwall.instructions.md` in the session directory with `applyTo: "**"`, whose directory the daemon appends, after a comma, to `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` in the session environment (the user's own value stays first, under the user's spelling of the name on Windows). Copilot CLI loads it as a repository instruction next to the repo's `AGENTS.md` and `.github/copilot-instructions.md`, so the user's repo and `~/.copilot` stay untouched. The file opens with the session's environment: the Trackwall version that started it (`version` in the facade options, `VERSION` in the daemon) and that the user sees it in the "Sessions" view and is told when it ends its turn or asks for approval. Then it holds the session's role, built only from the repo and task ids, never from agent text: a main session in the repo root works in the user's working copy and hands larger or parallel work, especially in another repo, over with `propose_task`; a task session works only in its worktree, commits on the task branch without switching branches, pushing, merging or opening pull requests unless the prompt asks for it, and ends (also when stuck) with `report_result`; it is told that `run_mise_task` runs in the repo root, not in its worktree. The MCP instruction (§5.3) follows. A state directory with a comma in its path does not fit that variable, so the session then starts without the file and the daemon logs it. A task (below) adds a worktree, a starting prompt, resume and live changes to a session; a time budget is the next step.
- **Copilot CLI** (ADR-17, detectors in `modules/agents/`, recording in `scripts/copilot-record.ts`). The daemon gives the session a **session plugin** through `--plugin-dir`: a directory with `plugin.json` and `hooks.json`, outside the worktree and outside `~/.copilot`, so it changes neither the user's configuration nor the repo files. Hooks are programs run without a shell (`exec` + `args`) from the plugin directory, not the repo, and with `--no-env-file` (otherwise Bun would load `bunfig.toml` and `.env` from the user's repo; both are needed), which write a **hook record** to the session's `hooks.jsonl`: the event, the time and only the fields on the list (`CopilotHookPayload`: session id and time, start source, end reason, notification kind and trimmed text, tool name), and of the rest only the field names, so that recordings reveal the undocumented payload without storing the prompt, tool arguments and results; eventually they will report it to the daemon with the session token (ADR-39). Events and states: `sessionStart` → `Input`, `userPromptSubmitted` and `postToolUse` → `Working`, `notification` by kind: `permission_prompt` → `Approval` with `high` confidence (the kind from `@github/copilot-sdk`, confirmed in a session on macOS, ADR-17), `elicitation_dialog` → `Input` with `medium` confidence (a kind known only from the texts of Copilot CLI 1.0.103, not from documentation or a recording); other kinds, among them `agent_idle`, `agent_completed` and `shell_completed` about background agents and commands, do not change the state; without a kind `Approval` / `Plan` / `Input` by whole words of the text with `low` confidence, `agentStop` → `Input` (end of turn), `errorOccurred` → `Error`, `sessionEnd` → `Done` or `Error` by `reason`. No `preToolUse` and `permissionRequest`: a hook of theirs that crashes denies the agent the tool, and `permissionRequest` fires also for an automatically granted approval, so it does not mean "waiting for a human". From the terminal: OSC 9;4 (progress bar, the default `terminalProgress`) gives `Working` at state 1 or 3, `Input` with low confidence when the bar is removed and `Error` with low confidence at error state 2; Copilot CLI 1.0.103 sends it only when it recognises Windows Terminal (`WT_SESSION`), so on macOS and in a session of a daemon started outside Windows Terminal there is no bar, and during an approval request it keeps sending state 3 (ADR-17); the window title (OSC 0 / 2) is a description of the current work, not a state. From the keyboard (`copilot-keys.ts`, source `keyboard`): Copilot CLI sends no hook after an answer to an approval request (after an approval the first hook is `postToolUse` after the command ends) nor after a turn is interrupted with Esc, so the session in the daemon and the recording script look at single keys from the terminal window: Enter or a digit 1–9 (choosing an option without Enter) in `Approval` or `Plan` gives `Working`, Esc or Ctrl+C in `Working`, `Stale`, `Approval` or `Plan` gives `Input`, both with `medium` confidence. A key counts from the state after the hooks already in `hooks.jsonl`, not after the last read cycle (every 200 ms), so an approval request appended just before Enter does not stay in `Approval` after it. Only a whole chunk of input equal to one key counts, so text, a paste and arrows do not change the state, and neither do Enter or a digit while typing a prompt (the hook reports the turn, and a command like `/model` has no hook). Enter on the option "No, and tell Copilot what to do differently" gives `Working`, although Copilot is still waiting for text; the "No" digit also gives `Working` first, because the option number depends on the window, and the screen pattern (below) recognises the interruption right after. From the screen, one pattern (`copilot-screen.ts`, without a VT parser, on the output text alone): the message "Operation cancelled by user" with which Copilot CLI ends an interrupted turn (in recordings from macOS and from Windows a continuous text in one chunk of output) gives `Input` with `medium` confidence, but only up to 10 s after the session key that changed the state (an answer or an interruption), because an interruption always follows such a key, and the same text comes back when the screen history is redrawn. As the `screen` source it can only end `Working`; it catches an interruption the key did not recognise, for example when Enter on "No, and tell Copilot…" or the "No" option digit ends the turn at once. Other screen patterns will come from real recordings if hooks, OSC and keys turn out not to be enough.
- **Combining signals** (`TaskStateTracker`): the best source that has spoken wins, so after the first hook OSC and the screen do not change the state, and a session without working hooks gets its state from OSC. Exception: a weaker source may end `Working` (for example the progress bar being removed), because a lost end-of-turn hook would leave the session in `Working` and then in `Stale`, although it is waiting for a human; it can no longer start `Working` after a hook. A human key (`keyboard`) always passes and does not change the rank of the sources, because it speaks about what the hooks do not report; the key detector decides in which state a key means something. `Stale` only from `Working` after a threshold without output and signals (waiting for a human is not hanging), with the threshold time rather than the moment of checking, so live and from a recording the result is the same; output restores the state from before `Stale`. A process exit is final: `Done` at code 0, `Error` otherwise, unless the `sessionEnd` hook has already reported the end.
- **A recording** `.cast` has, besides the output, markers (`m`) with hook records, the kind of key (`enter`, `choice`, `escape`, `interrupt`) and the exit code, so the state can be computed again from the recording alone (`replayCopilotRecording`) by the same code that runs live. Live, the state is computed from the event time stored in the recording (full ms), not from the moment of computing, so a replay gives the same changes to the millisecond. Keyboard input text is not recorded, only each session key (a single Enter, a digit 1–9, Esc or Ctrl+C), including one that did not change the state. The script writes the recording synchronously at every chunk of output and reads `hooks.jsonl` every 200 ms, with the same code as the daemon (`HookTail`, `runCopilotHook`); when the daemon starts recording sessions, the write must become asynchronous. The script reaches into the module files directly, because it runs without the daemon.
- **Tasks** (ADR-31, `tasks.ts`, the "Sessions" view): `agents.create-task {repo, prompt}` creates the branch `trackwall/<slug>-<6 characters of the task UUID>` (a slug of up to 32 characters from the first words of the prompt without diacritics, only `[a-z0-9-]`, `taskSlug`) from the default branch, and its worktree (`git worktree add -b`) in `worktrees/<repo>/<slug>-<6 characters>` in the state directory, outside the projects folder: the repo list does not see it, and the repo's working directory does not get an untracked `.worktrees`. The default branch without asking the server: from `refs/remotes/<remote>/HEAD`, the local one when it exists (sync moves that one and unpushed commits sit on it), otherwise the remote one; a repo without this pointer gives the checked-out branch, and a detached HEAD the commit alone (`baseBranch: null`). The commit the branch started from is the task's **base commit**. Worktree changes in one repo (`worktree add`, `worktree remove`, `branch -D`) run one after another, because they fight over locks in `.git`; two tasks created at once in one repo get separate branches and directories. On Windows every git command gets `-c core.longpaths=true`, because a worktree in the state directory lengthens the paths of the repo's files. The task goes into `tasks.json` before the session starts, so the worktree does not disappear from the list if the daemon crashes; a failed session start (no Copilot CLI) removes the worktree and the branch, once git stops reading the worktree. A failed `worktree add` (for example a timeout with LFS) may leave a branch and a directory the list does not show; the daemon does not clean them up, because it does not know whether it created them (a branch with that name might have existed already), so they are removed by hand (`git worktree remove`, `git branch -D`). A task session is an ordinary session (above) in the worktree, with `--session-id=<task UUID>` and `--interactive=<prompt>`: Copilot CLI starts the TUI and sends the prompt as the first message (an option from `copilot --help` 1.0.103), and the `=` form makes sure a prompt starting with `-` is not an option. The prompt has at most 8000 characters, because it goes as one argument, and the Windows command line holds 32,767.
- **Resume** (`resume-task`): a new session in the worktree with `--resume=<task UUID>`, so Copilot CLI goes back to the task's conversation; ended sessions of the task disappear from the list. A task with a running session gives `bad_request`, as does a second action on a task during the first. Tasks survive a daemon restart (`tasks.json`, atomic write), and their sessions do not, so after a restart a task is "no session", to resume or end. The worktree directory is not stored, only computed from the repo identifier and the branch (`taskWorktree`), so a hand edit of the file cannot point to a directory outside `worktrees/`; the schema accepts only a `trackwall/[a-z0-9-]` branch, a full base commit hash and a full repo path. A file that fails it is set aside as `tasks.json.broken-<time>`, and the worktrees stay on disk.
- **Task changes** (`task-changes`, `TaskChanges`): the worktree's working directory with new files, without ignored ones, against the base commit, that is the task's commits and what the agent has not committed yet, together. New files (`git ls-files --others --exclude-standard`) go into a temporary index (a copy of the worktree index in a temporary directory, `GIT_INDEX_FILE`, removed after every request) as an entry with the hash of the empty blob (`git update-index --index-info`), as with `git add --intent-to-add`, but without writing that blob to `.git/objects`; a directory with its own repo is, as in `git add`, a submodule entry with that repo's HEAD, and a repo without commits or in another object format is skipped. Computing changes therefore writes nothing to the repo: the index the agent uses stays untouched, and several "Changes" windows at once do not write the same object (on Windows the second write ended with "Permission denied"). Then `git diff <base commit>` (working directory) without rename detection, external diff programs and `textconv`: files with the kind of change and number of lines, the diff cut to 1 MB (the same truncated-result marker when the list of new files exceeds 8 MB), the number of commits since the base and of `git status` entries. The UI polls every 2 s while the "Changes" tab is open and shows at most 4000 lines of diff. Polling instead of a file watcher: git has to compute the diff anyway, and a recursive `fs.watch` on a worktree with `node_modules` or `target` gives event storms and behaves differently on Windows, macOS and Linux. The copy of the index keeps the original's mtime, because git trusts a file whose size and mtime match its index entry unless the index was written no later than that mtime; with a fresh mtime a same-size edit made in the second the index was written (right after the worktree was checked out) would be missed.
- **Shared files** (`task-shared-files {task}`, result `{shared: TaskSharedFiles[]}`, ADR-44): the files on a task's list of changes (as in `task-changes`, without the diff) that are also on the list of changes of another task of the same repo, per such task. Changes of the other task that cannot be read (being ended, worktree deleted by hand, broken index) are left out, because this is only a warning; a failure to read the task's own changes is returned as in `task-changes`. It is computed on request, one git read per task of the repo, at most 3 at a time; the task panel in the UI (`SharedFiles`) asks every 5 s and shows a warning above the tabs with a button to the other task.
- **Ending** (`remove-task {task, keepBranch, discardChanges}`, result `null`): only without a running session, because its processes write in the worktree and on Windows lock its files; it waits for all ongoing change computations (several windows), and while ending, `task-changes` refuses. Without `discardChanges` the daemon computes what would be lost: the worktree's `git status --untracked-files=all` entries, commits from the worktree's detached HEAD that are on no branch or tag (they leave the worktree regardless of `keepBranch`), a worktree directory git no longer knows (an interrupted removal, `worktree prune`, a repo cloned anew in the same place; what is in it cannot be computed), and without `keepBranch` also the commits `<base commit>..<branch>`, and on any of these it refuses with the `unsaved_changes` error listing what would be lost; the UI shows it and only then asks "Remove anyway". Files ignored by git (dependencies, build output) are always lost, and the UI says so before ending. Then `git worktree remove --force`; git removes the registration before deleting the files, so a removal interrupted by a file held by another process leaves a plain directory, which the daemon deletes itself after confirmation, and `git worktree prune` clears the registration of a directory removed by hand. Without `keepBranch` also `git branch -D`; the task's sessions disappear from the list. A task from a repo that no longer exists (moved, disconnected drive) cannot be checked with git: like a directory git does not know, without `discardChanges` it is refused with `unsaved_changes` when the worktree is on disk, and after confirmation the daemon deletes the worktree directory (it lies in `worktrees/`, because it is computed from the repo and the branch), the branch stays in the moved repo, and `git worktree prune` clears its registration there. `open-task-editor` opens the worktree in VS Code (`vscode://`).
- **Folder trust**: Copilot CLI asks for trust in every new directory, so in every worktree. An entry in `trustedFolders` (`~/.copilot/config.json`) covers subdirectories (checked on 1.0.103), so the UI suggests the `worktrees/` directory (`SessionList.worktreesDir`); the daemon does not change the Copilot CLI configuration. The `sessions` list also returns the tasks (`tasks`, newest first, without sessions), and the UI joins a task with its newest session (`Session.task`) and shows them as one item next to the sessions in repo roots.
- **Main session and task proposals** (ADR-39, `task-proposals.ts`, `session-wait.ts`, the "Sessions" view): a session (or a supervising agent outside Trackwall) delegates work to another agent with the MCP tool `propose_task {repo, title, prompt}`. The daemon stores a **task proposal** (`TaskProposal`: identifier, repo, a title of up to 80 characters on one line, a prompt of up to 8000 characters, `proposedBy` with the session identified by the session token, or `null` for an agent outside Trackwall) in memory only, at most 20 waiting at once; nothing starts. The `sessions` list returns them in `proposals`, and the view shows them with "waiting for your decision" and counts them on the view bar together with the sessions that are waiting. The view's list is a tree (`sessionRows` in `lib/session-entries.ts`): a proposal or task with `proposedBy.session` sits under the entry that holds that session (a session in the repo root, or a task, also when it is an older session of the task), in the same order on every level (proposals first, then most recently started), and an entry with children has a "main" badge with their count; proposals from an agent outside Trackwall or from a session no longer listed are at the top level. The proposals of one session are one entry (ADR-55: `kind: "proposals"`, oldest first inside it), and selecting a proposal selects that entry; its panel (`ProposalInbox`) lists them all with their prompts, each opens to be read and edited, and the user starts one, or ticks several and starts them with "Start N selected", one after another (`startProposals` in `lib/proposal-decisions.ts`; a failed start does not stop the rest and leaves that proposal waiting with its error). A proposal for a repo that already has tasks says so, since which files it will change is not known before the start (the shared-files warning of ADR-44 needs changes). A proposal can be ticked only after it has been opened, so a prompt is never started unread. A decision first selects the group by its proposer (`{kind: "proposals", proposer}`), so the panel stays while its proposals turn into tasks one by one; afterwards, if the user is still there (`showsGroup`), the view opens the next proposal of the same session that still waits, then the first task just started, and after the last rejection the session that proposed them (`selectionAfterDecision`). A proposal selected from the tray, a notification or a `trackwall://task/` link selects its group and opens there. The "main" badge counts each proposal of a group. A grid tile with proposals (ADR-48) shows every prompt in full with "Start task" and "Reject…"; editing and starting several are in the full panel. "Next waiting" and Alt+J go through proposals as well as waiting sessions, in list order; a group is one stop, while the count on the button and the view bar counts each proposal. Proposals also show in the dashboard's "Needs you" queue (§5.5) and in the tray menu (§5.4). "Start task" (`approve-proposal {proposal, prompt}`, with the prompt the user may have edited) creates a task like `create-task`, but with the proposal's identifier, its title (`Task.title`; the branch slug comes from it, not from the prompt) and origin (`Task.proposedBy`). While it is being approved the proposal stays on the list, so that the panel in the UI does not disappear together with an error and the edited prompt, but a second approval or a rejection gives `not_found`, and waiting sees `starting`; the `sessions` list stops returning it as soon as a task with its identifier is on the list, and a proposal selected in the UI switches to that task (during a decision the group stays selected instead, and when it is gone its newest task stands in, ADR-55). When the task was not created, the proposal waits for a decision again (a failed `worktree add` cleans up the branch git creates before the checkout, so a retry with the same branch succeeds; when the cleanup itself fails, for example because of a file held on Windows, the error names the directory and branch to remove by hand), and the user ends a task left behind by a failed cleanup themselves. "Reject…" asks for an optional reason of up to 1000 characters (`reject-proposal {proposal, reason?}`, ADR-55), removes the proposal from the list, and the daemon remembers the last 100 rejections with their reasons, so that a waiting session gets `proposal_rejected` with `rejectionReason` (`null` without a reason) and can propose differently. A task session reports its result with the tool `report_result {summary}` (up to 4000 characters): the daemon stores it in `Task.summary` with the time (in `tasks.json`, so it survives a restart), and the UI shows it above the task tabs; only a session that has a task can call it, and only for its own. `wait_for_session {session | task, timeoutSeconds ≤ 55}` reads the state from daemon memory every 200 ms and stops waiting when the proposal was rejected, the session does not respond (`Stale`), is waiting for a human (`needsAttention`) or reported an error (`Error`, because it is unknown whether an end of turn follows), has ended, or the task has no session; after the time limit it returns `proposal_pending`, `starting` (a proposal being approved, or a task with an ongoing action, for example a session start) or `working`. Waiting on a task follows its newest session, and waiting on one's own session is refused. A task session with a starting prompt (`--interactive`) gets the state `Working` instead of `Input` from the first `sessionStart` hook (the next one, after `/clear` or `/resume` in the session, no longer carries the prompt), because it works on the prompt right away; otherwise waiting would end before the agent starts, and the tray would flash "waiting for you". **Session token** (`session-tokens.ts`): every session gets a random token (32 bytes) in the file `sessions/<session>/session-token`, and its stdio bridge the option `--session-token-file`; the bridge sends the token with every message in the `x-trackwall-session-token` header, and the daemon keeps only its SHA-256 hash in memory and recognises the calling session by it. The same session sees its own identifier through `list_sessions` (`caller`).

### 4.5 `workspace` and `vcs`: repo list, browsing, cloning from a host and sync

The first slice of the `workspace` module (stage 3 in §11, done earlier at the user's request): repos from the projects folder, browsing them, cloning from GitLab or GitHub into the folder, and syncing all repos (fetch and fast-forward, without the mise step and extractors; the Batch command gives mise steps on selected repos, §4.8).

- **The projects folder** (`projectsDir`, ADR-18) is the only source of the repo list. Its full path is the `projectsDir` key in `workspace.yaml` (ADR-13); it is set in the "Settings" view (`set-projects-dir`, the directory must exist) or by hand in the file. The file is read on every request, so a hand edit works without a restart; a write from the UI changes only this key and keeps comments and the other keys. There is no default: until the folder is set, the list is empty, and the UI leads to the settings.
- **The repo list** is built on every request from the direct subdirectories of the folder that have `.git` (a directory or a file, as in a worktree); directories starting with a dot are skipped, a link to a directory counts as a directory. Trackwall does not look deeper. The repo identifier comes from the directory name (`orders-bff`; on a collision, for example `Zażółć` and `zazolc`, a `-2` suffix in name order, so a new directory that sorts earlier takes over the identifier without a suffix). The folder is read, and checked on write, asynchronously (it may sit on a network drive or a sleeping external drive), and the repo status on the list is fetched for at most 8 repos at once. A repo cloned or deleted outside Trackwall appears or disappears at the next list request; in Trackwall a repo is added only by cloning from a host (below), and there is no removal. A folder that disappeared after being set (for example a disconnected drive) gives the error `projects_dir_unavailable` with its path. A folder dropped on the window (ADR-51) does not add a single repo either: `dropped-folder` says what it is (a listed repo or a folder inside one, the projects folder itself, a git repo elsewhere, a repo in the projects folder whose name starts with a dot, a folder with repos directly inside it, a folder without any, a file), and the UI opens the listed repo or offers the folder, or the folder that holds the dropped repo, as the projects folder through `set-projects-dir`.
- **Show in Explorer/Finder** (`open-folder`, ADR-51) opens the folder of a listed repo in the system's file manager, like `open-editor` opens VS Code: the action takes a repo id, `Workspace.openFolder` looks the path up in the list and hands it to the `openFolder` the facade injects (`explorer.exe` with the path in quotes on Windows, because Explorer splits its command line at commas, `open` on macOS, `xdg-open` on Linux, `infra/system-open.ts`), and the daemon does not wait for it. It works in the page opened from the daemon too.
- **Repo hosts** (`repoHosts`, ADR-19) are a list in `workspace.yaml` (`- kind: gitlab` + `host: gitlab.example.com`, likewise `github`), set in the "Settings" view (`set-repo-hosts`) or by hand, without duplicates (the `RepoHosts` schema); every `workspace.yaml` key is checked separately, so a bad entry in `repoHosts` breaks only the hosts, not the repo list; only the user's file knows the address of the GitLab instance (ADR-7). The daemon asks the host through the program the user is signed in to it with: `glab api --hostname <host> projects?membership=true…` for GitLab and `gh api --hostname <host> user/repos?affiliation=owner,collaborator,organization_member…` for GitHub. The token stays in those programs (`glab auth login`, `gh auth login`); Trackwall neither reads nor stores it. **Search** (`remote-repos {query}`) in GitLab runs on the GitLab side (`search` with `search_namespaces`, so the group path matches too), one page of 100 projects, most recently changed first, because a company instance has thousands of them; a full page is `truncated` and a request to narrow it down. GitLab matches fragments only from 3 characters, so the daemon matches a shorter query itself on the first page without searching. The GitHub API for the user's repos has no search, so the daemon fetches up to 10 pages (1000 repos) and filters them itself by name and description. Fetched pages serve later queries for 60 s (a failed fetch does not), so typing in the search box does not ask the host at every character. The list is the repos the user is a member of (`membership=true` in GitLab; in GitHub own, collaborator and organisation repos), not all visible public projects. Archived repos are skipped, and a name outside `RemoteRepoName` (segments `[A-Za-z0-9_][A-Za-z0-9._-]*`) does not reach the list. A host that does not respond (no program, no sign-in or no network) is on the list as `unavailable` with the program's message and does not take away the results of the others; the UI suggests the sign-in command. An API page has a 30 s limit.
- **Clone** (`clone {host, fullName}`) is `glab repo clone <full name> <folder>/<last segment>` or the same with `gh`, with `GITLAB_HOST` / `GH_HOST`, so the protocol (SSH or HTTPS) and credentials are as the user set them in those programs. The daemon rejects a host outside the settings, an unset folder and a directory name that is already in the folder (a case-insensitive comparison, because that is how Windows and macOS drives work); a remote repo with that name is on the list as "Already in the folder". Cloning runs in the background: the action returns it at once in the `running` state, and `clones` returns the clones into the current projects folder since the daemon started (`running`, `done`, `failed` with a message), kept in memory only. A second click on the same repo in the meantime returns the same clone, and another repo with the same directory name waits for it to end. The repo reaches the list by itself, because it lies in the folder (ADR-18), so nothing is stored; during the clone its directory may already be on the list. A clone has a 30-minute limit, because a large repo takes minutes to clone, and ssh waiting for a host key confirmation in a hidden console would wait forever; after the limit the clone has failed, and a retry goes through only once git finishes by itself and removes its directory. A clone cannot be cancelled from the UI, and killing `glab` or `gh` (the limit, daemon exit) does not stop the git it started, because the clone is not in a process group: a gap to close together with the `procs` module (§8). Without a terminal and with `GIT_TERMINAL_PROMPT=0` git does not wait for a password; ssh started from the daemon's terminal (development mode) may still ask about the host key in that terminal.
- **Sync** (`sync`, ADR-21) is the "Sync all" button on the repo list: for every repo from the projects folder, at most 4 at once, `git fetch` of the main remote, then a fast-forward of the local default branch to the remote one. The Batch command (§4.8) composes mise steps (`mise install`, `setup`, `build`) with sync through `syncRepo {id}`: the same sync of one repo, with an error when a clone into the repo is in progress. The extractors from §7 do not exist yet, and the `ws sync` CLI will come together with the `ws` CLI.
  - **Remote and branch.** The main remote is `origin`, and without it the only remote. The default branch is `refs/remotes/<remote>/HEAD` (set by `git clone`); when it is missing or points to a branch that no longer exists (the host changed the default branch, and a fetch with `prune` removed the old one), the daemon asks the server once through `git remote set-head --auto`. It does not detect a change of the default branch whose old version still exists on the remote.
  - **Moving.** A checked-out default branch moves through `git merge --ff-only`, so the working directory gets the new files, and an untracked file in the way ends in a git error instead of being overwritten. A branch that is not checked out moves through `git fetch . <remote>:<local>` (without `+`): git accepts only a fast-forward and refuses when the branch is in use in some worktree, also during a rebase or bisect, when HEAD is detached; then the repo ends with an error carrying git's message, and the branch stays. The checked-out branch and the working directory stay unchanged.
  - **Skips.** Sync never merges, rebases or switches branches. A repo without a remote, without a default branch (remote or local), with uncommitted changes in tracked files of the checked-out default branch, with a diverged branch or unpushed commits, or with the default branch checked out in another worktree is skipped with a reason (`SyncSkipReason`) and a sentence for the user. Untracked files do not block, and changes on a feature branch do not get in the way of moving a default branch that is not checked out. A git error (network, sign-in, host key, time limit) is a `failed` result for that repo with git's message and does not stop the others.
  - **Result and working directory** (ADR-34). Every result without an error (`updated`, `up-to-date`, `skipped`) also has the state of the working directory after sync (`SyncWorkingTree`): the checked-out branch and the number of changed tracked files and, separately, of new untracked entries, from one `git status` at the end (when it fails, `workingTree: null`, and the result stays); `updated` and `up-to-date` also have the remote branch (`origin/main`). The UI builds a sentence from this for every repo, including an up-to-date one: what happened to the default branch, whether the files in the working directory changed (no, when another branch is checked out), and that uncommitted files were left untouched, split into changed and new.
  - **No prompts.** Commands that connect to the server (`fetch`, `remote set-head` and `merge`, because the LFS filter downloads objects) get, besides `GIT_TERMINAL_PROMPT=0`, an empty `GIT_ASKPASS`, `GCM_INTERACTIVE=never` (Git Credential Manager without windows) and `GIT_SSH_COMMAND="ssh -o BatchMode=yes"` (`networkEnv` in `vcs/git.ts`), unless the user has set an ssh program themselves (`GIT_SSH_COMMAND`, `GIT_SSH` or `core.sshCommand`): then theirs stays, and only the 5-minute limit protects against hanging. A clone through `gh` and `glab` does not get this environment yet (only `GIT_TERMINAL_PROMPT=0`).
  - **In the background.** Like cloning: `sync` returns the sync at once with the repos in the `waiting` state, and `sync-run` returns the last sync of the current projects folder (in daemon memory, until a restart). One runs at a time: a second click returns the running one, and a start in another folder meanwhile is `bad_request`. A repo being cloned into is skipped without an entry. List entries with the same `.git` directory (a repo and its worktree, or a link in the folder) sync one after another, because two simultaneous fetches in one `.git` fight over refs. The UI polls progress every 1.5 s during a sync and every 10 s outside it, and shows the result of every repo, including "up to date", under the repo status on the list (a sentence in the tooltip) and in full in the sync panel (in place of the repo details), with the number of up-to-date repos next to the moved, skipped and failed ones. The `sync.progress` event (§5.2) will replace polling together with the WebSocket.
- **The remote address** (`Repo.remote`, ADR-21) is the address of the main remote in the form `host/path`, without the scheme, user (also with a token written into the URL), port and `.git`, with the host in lower case: `git@gitlab.example.com:shop/api.git` and `https://gitlab.example.com/shop/api` give `gitlab.example.com/shop/api`. It identifies a repo next to the directory name: it does not change when the directory is renamed, and it links SSH and HTTPS clones. A local path, `file://`, no remote, or several remotes without `origin` give `null`. The address is computed after `url.<base>.insteadOf` shorthands, as in git, and `transport::` (for example `ext::`) also gives `null`, because it is a command, not an address. The daemon reads it on every list request from `git config -z --list` (the third git process per repo) and stores nothing; the UI shows it in the repo header under the path.
- **The repo status** (`RepoStatus`) is observed on every request with one `git status --porcelain=v2 --branch` plus `git log -1`: the branch, the last commit, the number of changes in the working directory (with new untracked entries separately, `untracked`, ADR-34; a new directory is one entry, as in `git status`; the UI writes "3 changed, 1 new"), ahead/behind against the tracking branch. None of this is stored. A repo git cannot read (a broken `.git`, no permissions) stays on the list as `unavailable` with git's message.
- **Working directory changes** (`changes {repo}`, the "Changes" tab in the repo details, ADR-34) are the files and diff of the working directory against HEAD, with new files and without ignored ones, by the same read as task changes (`workingTreeChanges` in `vcs/worktree-changes.ts`, ADR-31): a copy of the index in a temporary directory with the new files as `--intent-to-add`, so the user's index stays untouched, and at most the empty blob reaches `.git/objects` (not a new version of every file), a diff without external diff programs and `textconv`, cut to 1 MB (`PATCH_MAX_BYTES`). A repo without commits is compared with the empty tree (`git hash-object -t tree --stdin`, so it works for SHA-1 and SHA-256). Read only: committing and discarding changes stay in the editor. The UI polls the tab every 10 s after the previous response while it is open, and at once after a HEAD change; the file list is cut to 500 in the UI, and `--name-status`/`--numstat` output cut in the daemon gives `truncated`; the "Working tree" tile with changes opens this tab.
- **Browsing** reads from the HEAD commit, not from the working directory (ADR-14): one `cat-file --batch-check` says whether HEAD and `HEAD:<path>` exist, what type and size they are, then `ls-tree` or `cat-file blob`. The path from the request is a path in the commit's tree, so it cannot lead outside the repo or hit a file ignored by git. The file and README preview is cut to 512 KB; a file with a NUL byte in its first 8000 bytes is binary (the same heuristic as in git).
- **Code search** (`searchCode`, MCP tool `search_code`, ADR-40) reads from the HEAD commit, like browsing: for each chosen repo, at most 4 at once, `git grep -n -z -I --column --no-textconv --no-recurse-submodules -C<context>` with `-F` (fixed string) or `-E` (POSIX extended regular expression, without `\d` and `\s`), optionally `-i`, the pattern after `-e` and git pathspecs after `--` (`code-search.ts` in `workspace`, `grep.ts` in `vcs`, where `commitGrep` owns these flags together with reading source files for cards). It searches the commit's objects, so uncommitted changes are invisible, a path cannot leave the tree, ignored files are never in the result, and the repo makes git run no program (no `textconv` or filters) and pull in no submodule. A repo without commits is skipped. The pattern is one line: git would split a pattern with a newline into several, and an empty line matches everywhere. A match is told from context by the column field of the output line (`-z` with `--column`: a match has a column, context does not). **Limits**: git output 2 MB per repo, `git grep` 30 s, lines cut to 500 characters, at most `limit` matches from one repo; repos start in list order, so once finished repos have given `limit` matches no further repo is searched; repos not started because of that, or 60 s after the start, go to `skipped`; line text in the whole result at most 100,000 characters (the result goes to the agent twice, like the README in `get_repo`). Each of these cuts sets `truncated`, and in `searched` also on the repo it affects (so `truncated` can be true when the skipped repos had no matches). A repo git could not search (invalid pattern, time limit, broken `.git`) goes to `failed` with git's message and does not take away the results of the others. The MCP tool builds the tag filter from the card tags (`cards`), and `workspace` gets a ready list of ids; an unknown id is `not_found`, also when tags are given. There is no index: every query reads the repos again.
- **Git, `gh` and `glab`** are run through `runProgram` (`modules/vcs/run.ts`): `spawn` with an argument array, without a shell, with a time limit, bounded output and the end of stderr as the error message. **Git** gets `-C <repo>`, `GIT_CEILING_DIRECTORIES` on the parent of the repo root after resolving links (with an empty or broken `.git` git does not look for a repo higher up and does not show the repo the projects folder lies in; an explicit `--git-dir` would disable the repo ownership check, `safe.directory`, so we do not use it), `-c core.fsmonitor=false -c log.showSignature=false` (§8), a 15 s time limit (`git grep`: 30 s; sync commands: 5 minutes and the no-prompt environment, above), `GIT_OPTIONAL_LOCKS=0` (reading the status does not take `index.lock` when the user happens to be committing) and `GIT_TERMINAL_PROMPT=0`, without inherited variables that choose a repo (`GIT_DIR`, `GIT_WORK_TREE`…), which would override `-C`. The result is settled without waiting for the pipes to close, because on Windows `git` from `PATH` can be a launcher whose grandchild holds them after the time limit. Output is parsed from machine formats (`-z`, `--porcelain=v2`), so it does not depend on git's language.
- **"Open in VS Code"** opens the address `vscode://file/<repo root>` with the system's URL-opening mechanism (the same as `--ui`), without running `code` through a shell. With the same mechanism the facade opens an `http` or `https` link clicked in a README (`workspace/open-link`, ADR-35); `overview` gives the README format (`markdown` or `text`).
- `workspace.yaml` is written through a temporary file and `rename` (`atomic-write.ts`, shared with `daemon.json`), with a retry on Windows when an antivirus or an editor holds the file for a moment. The projects folder path in the file must be full (on Windows with a drive letter or UNC; `\projects` would depend on the daemon's current drive). The `repos` key from version 0.2.0 is no longer read, but a write does not remove it.
- The UI polls the list 10 s after the previous response (a slow git does not pile up requests) and only while the window is visible; a new HEAD in the list fetches the overview and the tree again. The repo list is not a `/ws` topic (ADR-36), because its snapshot is a `git status` of every repo; an event will come when the daemon starts watching repos.

### 4.6 `cards` and `graph`

A card is built in two steps. The deterministic step reads the repo's files: `pom.xml` / `build.gradle(.kts)` (artifacts, dependencies on Feign/WebClient clients, OpenAPI configuration), `application*.yml` (URLs, ports, topic names, environment variable names = secret candidates), `package.json` (packages, scripts), OpenAPI files, Kafka definitions. Extractors are separate files per build system, each returns only facts with a position in a file. The LLM step gets the card and selected fragments and returns a description and connection proposals, marked `origin: 'llm'`.

The first slice (ADR-25): the deterministic step for build files, tools and the mechanism inventory, repo tags with a filter in the repo list, and the card in MCP. The second (ADR-30): Spring Boot apps, HTTP endpoints and clients from Java and Kotlin code, Spring configuration with profiles, and backend addresses in the frontend. Topics, environment variable names (secret candidates) and the LLM step are the next steps.

- **Reading the commit** (`read-snapshot.ts`): `git ls-tree -r -z --long <commit>` gives the list of files with sizes, and `git cat-file --batch` in one process the contents of the files some extractor selects (each has its own `reads…File` function, combined in `readsCardFile`): `pom.xml`, `build.gradle(.kts)`, `settings.gradle(.kts)`, `gradle/libs.versions.toml`, `package.json`, `pnpm-workspace.yaml`, mise configuration and `.tool-versions` in the repo root, `.nvmrc`, `.node-version`, `.java-version`, `.sdkmanrc`, Maven and Gradle wrapper properties, Spring configuration (`src/main/resources/application*` and `bootstrap*`), `.env*` files and frontend proxy configuration. Besides these, Java and Kotlin source files (ADR-30): `git grep -l -z -I -E` in the commit (without textconv) selects those with a controller, mapping or client annotation, `WebClient`, `RestClient`, `RestTemplate` or a constant with a path (`JVM_SOURCE_PATTERN` in `spring.ts`), from `src/main/` at any depth, and without it only outside `src` directories (no tests; `isJvmSource`); they go through the same `cat-file --batch`. Then the read pulls in the type files those files name (ADR-38): capitalised names from the tokens (`referencedTypeNames`) point to source files with that name (`OrderDto.java`, `OrderDto.kt`, with the same `isJvmSource`), in at most three rounds (controller, DTO, field type, nested field type) and at most 3000 files, each round with one `cat-file --batch` within the shared byte limit. These files go into `RepoSnapshot.typeFiles`: only the contracts read them, not the Spring extractor, so the HTTP facts depend only on the files from the search; type files that did not fit within the limits give one card problem with their count. Files in `node_modules` and `bower_components` do not exist for the card (neither for reading nor for mechanisms). Limits: 1 MB per file, 2000 build and configuration files, 3000 source files (4 MB of `git grep` list) and 64 MB in total; a file git did not return within the limit is a card problem, so an incomplete card says what it is missing. The commit is HEAD read once before both commands (`rev-parse` through `cat-file --batch-check`), so a commit made meanwhile does not mix two trees. The working directory does not matter (ADR-14). Files with a BOM and `\r\n` are normalised before the extractors see them.
- **Extractors** are pure functions on a commit snapshot (`RepoSnapshot`: the list of files, the contents of the ones read, type files and read problems), in `modules/cards/`: `maven.ts` (with the `xml.ts` parser), `gradle.ts` (with the version catalogue in `gradle-catalog.ts` and the comment scanner in `gradle-code-lines.ts`), `npm.ts`, `tools.ts`, `mise-tasks.ts` (ADR-34), `mechanisms.ts`, `spring.ts` and `frontend-http.ts` (ADR-30, below), combined in `extract-card.ts`; `repo-path.ts` handles paths in the repo (with `/`). Endpoint contracts and DTOs (`endpoint-contracts.ts`, ADR-38) read syntax trees from `syntax-tree.ts` (ADR-37): `loadSyntaxParsers()` once per process, `withParseBudget` with a total time for each card (`cards.ts`), then a synchronous `read(language, text, reader)` with a tree-sitter syntax tree, freed after the read, so only values leave the read; a file whose parsing exceeds `PARSE_TIME_LIMIT_MS` gives the result `timeout` instead of a tree, and a read after the card's budget is spent gives `over-budget`. When the grammars cannot be loaded, the card is built without contracts, with a problem (`unavailableParsers`). The files are untrusted (§8), so no regular expression backtracks quadratically on a long line, and workspace globs are matched by dynamic programming, not a regular expression (`glob.ts`). A build file that cannot be read (bad XML, JSON, TOML, YAML) is a card problem (`problems`), and the rest of the card is built without it.
  - **Build roots.** A build file without a file of the same kind in any parent directory is a root; a deeper one belongs to the build only when the root names it (a Maven module, also from a profile; a Gradle `include`; a workspace package from `workspaces` in `package.json` or from `pnpm-workspace.yaml`, patterns with `*`, `**` and `!`). Thanks to that a `pom.xml` from test fixtures does not reach the card, and a repo with `backend/pom.xml` and `frontend/package.json` without a root has both builds. Every build file on the card has `memberOf`: the file that names it, or `null`.
  - **Maven** reads the pom with its own XML parser with line numbers (`xml.ts`; without attributes, namespaces and DTDs). `groupId` and `version` without a value of their own inherit from `<parent>`; `${…}` in versions substitutes the properties of the pom, of its parents from the repo (`relativePath`, by default `../pom.xml`) and `project.*`, and leaves an unknown property (or one whose value would exceed 4096 characters) in the text. It provides the coordinates of every module; it consumes a parent from outside the repo (`parent`), dependencies (with `scope`, by default `compile`), BOMs from `dependencyManagement` in the `import` scope, and plugins from `build/plugins` (`plugin`, default group `org.apache.maven.plugins`). It skips ordinary `dependencyManagement` entries and dependencies from profiles. The Java version from `maven.compiler.release`, `java.version` or `maven.compiler.source` is a tool hint.
  - **Gradle** does not run scripts (they are Groovy or Kotlin code), it only reads lines in the typical form, without comments (strings are skipped when looking for them, so `exclude("META-INF/*.SF")` does not start a comment; lines over 2000 characters are skipped): `rootProject.name` and `include` from settings (also spread over several lines), `group` and `version` (of the project or the root project), dependencies `configuration("g:a:v")` (also inside `platform(...)`) and from the version catalogue (`libs.…`), plugins `id("…")` with a dot in the name and `alias(libs.plugins.…)`, the Java version from `JavaLanguageVersion.of(N)` or `sourceCompatibility`. A project has `group:name` coordinates only with a known group and name. A dependency composed in code (a variable, a loop, `project(...)`) does not reach the card.
  - **npm** reads the fields of `package.json` separately (a wrong type of one does not take away the rest): a package with a name and without `"private": true` is provided, dependencies from `dependencies`, `devDependencies`, `peerDependencies` and `optionalDependencies` (the scope is the field name). The package manager from `packageManager`, and without it from the lock file in the root directory (`pnpm-lock.yaml`, `yarn.lock`, `bun.lock(b)`, `package-lock.json`, by default npm); workspace packages inherit it from the root. `engines.node` and the version from `packageManager` are tool hints.
  - **Packages from the repo** are not on the list of consumed ones (a module that depends on another module of this repo, a private workspace package), and every consumed package is on the card once, with its first occurrence.
  - **Tools** (`ToolRequirement`): `[tools]` from the mise configuration in the repo root (`mise.toml`, `.mise.toml`, `mise/config.toml`, `.mise/config.toml`, `.config/mise.toml`, `.config/mise/config.toml`; without `mise.local.toml`, `mise.<environment>.toml`, `conf.d/` and configuration in subdirectories) and `.tool-versions` (source `mise`), and hints (source `hint`) from the root and the build directories: `.nvmrc`, `.node-version`, `.java-version`, `.sdkmanrc`, versions from the distribution URLs of the Maven and Gradle wrappers, and from the build extractors the Java version, `engines.node` and the package manager. Not from `mise ls --json` (ADR-25).
  - **Mechanisms** (`Mechanism`) are an inventory from the rules in `mechanisms.ts`: a package by `<ecosystem>:<name>` (Spring Boot, Feign, WebClient, OpenAPI, Kafka, RabbitMQ, Eureka, Config Server and client, Spring Cloud Kubernetes, Jib, React, Angular, Vue, Svelte, Express, NestJS) or a file by path (OpenAPI and Swagger files, `Chart.yaml`, `Dockerfile`, `compose.yaml`, `kustomization.yaml`, YAML in a `k8s/` or `kubernetes/` directory; manifests in other directories, for example `deploy/`, are not recognised), with at most three pieces of evidence. The rules are general; company rules will come from the workspace (ADR-7).
  - **Spring configuration** (`spring-config.ts`, ADR-30): a module is the directory above `src/main` (a repo with several apps has several modules); everything under `src/test`, including a sample project in test resources, is test code and is skipped (code and configuration, `isTestPath`). `application` and `bootstrap` files (`.yml`, `.yaml`, `.properties`) from `src/main/resources`, the profile from the file name (`application-prod.yml`) or from a document activated by `spring.config.activate.on-profile` (formerly `spring.profiles`; YAML `---` documents, `#---` in `.properties`). A profile's view is the configuration without a profile overridden by the profile's documents, and a profile file (`application-prod.yml`) overrides an `on-profile` document from the file without a profile, as in Spring Boot (every `bootstrap*` is below every `application*`); the `default` profile is the configuration without a profile, and a profile with the same address value as `default` is not listed separately (at most 32 profiles per module). Keys are compared as in Spring Boot (ignoring case, `-` and `_`, so `baseUrl` is `base-url`). `placeholders.ts` expands `${key}` and `${key:default}`: nested, with a default value, an unknown key stays as text, and a cycle, a depth over 10 and a result over 4096 characters stop the expansion. Environment variables are not known, so `${PORT:8081}` gives `8081`.
  - **App** (`ProvidedApp`, `kind: "app"`): the module's `spring.application.name` with the port from `server.port` (a number 1–65535 after expansion, otherwise `null`) and evidence from the name line.
  - **HTTP endpoints** (`ProvidedEndpoint`, `kind: "endpoint"`, `spring-endpoints.ts`): a class with `@RestController` or `@Controller`, the path from `server.servlet.context-path` (or `spring.webflux.base-path`), the class's `@RequestMapping` and the method's annotation (`@GetMapping`, `@PostMapping`, `@PutMapping`, `@PatchMapping`, `@DeleteMapping`, `@RequestMapping` with `method` or without it, which means every method: `method: null`), every combination of paths and methods separately (at most 20 per method). Mappings from an interface the controller implements (API-first style, an interface from the OpenAPI generator) count as its own, with evidence in the interface file. Paths are in `value`, `path` or the first argument, in an array `{…}` (Kotlin `[…]`, `arrayOf(…)`), also from constants (`ApiPaths.ORDERS + "/{id}"`, `static final` and `const val` constants from the files read); a constant not in the files read stays as `<Class.NAME>`. The code is read by a tokenizer (`java-tokens.ts`: comments, strings, text blocks) and a simple declaration parser (`java-source.ts`, `java-expr.ts`), without compiling, so an annotation in a comment or a string is not a mapping, and a mapping composed in code (for example `RouterFunction`) does not reach the card.
  - **Endpoint contracts and DTOs** (`endpoint-contracts.ts` with `contract-java.ts` and `contract-kotlin.ts`, ADR-38): an endpoint gets, from the syntax tree of the method in which its mapping line lies (in the controller or the API interface), the type of the `@RequestBody` parameter (`request`) and the return type without wrappers that do not change the content (`ResponseEntity`, `HttpEntity`, `Mono`, `Optional`, `CompletableFuture`, `CompletionStage`, `Callable`, `DeferredResult`, `WebAsyncTask`; `response`; also with Kotlin's `?`; `Flux<T>` stays, `void`, `Unit`, `Void`, `?`, `*` and a wrapper without an argument are `null`, as is a Kotlin function without an explicit type). Types are in type notation: the text from the tree without annotations, with a space only before a word following a word or after `?` (`List<? extends Line>`), longer than 256 characters cut with "…" (DTOs are discovered from the full notation). The method is identified by the name from the handler and the mapping line inside the method (a file may have several classes and overloads), and without the line or without such a method by the first method of the file with that name. `RepoCard.dtos` are the repo's types reachable from these types through field types, in discovery order, at most 500 types, each with at most 200 fields or constants: a record (fields from the header), a `data class` (constructor parameters and properties from the body), a class with fields (instance fields without `static`; in Kotlin properties from the constructor and the body; a type without fields, like a service or an empty record, is not a DTO), an enum (constants). A type is identified by its simple name, and in a qualified name (`Api.Summary`, `java.math.BigDecimal`) by its last part: first the file with that name, then the first file read in which the text `class|record|enum|object <Name>` occurs, so two types with the same name in the repo give the first one, and a type from outside the files read (a library, the JDK) is not a DTO. Parsing the whole card has a total budget of 10 s (§8), checked before every file, so exceeded at most by the time of the last file (parsing up to 1 s and a linear tree read); after it the rest of the endpoints stay without types, and the card has a problem.
  - **HTTP clients** (`ConsumedHttp`, `kind: "http"`) have a kind (`via`), a name (interface, class or key), the name of the target app (`app`) or an address (`url`) in profiles (`profiles`, with the configuration entry the address comes from: `urlSource`) and calls (`calls`: method and path with a line). An address with `${…}` gives a separate client for every profile in which it has a different value (`default` first). `lb://name` is an app name (the Spring Cloud load balancer). Kinds: `feign` (`@FeignClient`: the app name from `name`, `value` or `serviceId`, the address from `url` or from `spring.cloud.openfeign.client.config.<name>.url` / `feign.client.config.<name>.url`, the prefix from `path` and the interface's `@RequestMapping`, calls from the methods' mapping annotations), `http-interface` (an interface with `@HttpExchange` and `@GetExchange`…), `webclient`, `rest-client` and `rest-template` (`imperative-clients.ts`: the base address from `baseUrl`, `rootUri`, `create(…)` or a `@Value("${…}")` field, calls from `.uri(…)` with the method from the chain (`.get()`, `.method(HttpMethod.POST)`) and from `RestTemplate` methods (`getForObject`, `exchange` with `HttpMethod`…); a part concatenated after a string, for example `"/orders/" + id`, is a path variable `{}`), `config` (`config-clients.ts`: a configuration key with an HTTP or `lb://` address in some profile that the code did not use as a client address, for example `spring.cloud.gateway.routes[0].uri`; without calls).
  - **Backend addresses in the frontend** (`frontend-http.ts`): variables with an HTTP address in `.env*` files next to `package.json` (`via: "env"`, the variable name), the `proxy` field in `package.json` and quoted addresses in the development server's proxy configuration (`vite.config.*`, `webpack.config.*`, `vue.config.*`, `next.config.*`, `proxy.conf.*`, `setupProxy.*`; `via: "proxy"`, the file name). It does not run JS configuration.
  - **Secrets in addresses**: every address on the card loses its user and password (`http://***@host`), query and path segments that look like a token (`withoutCredentials` in `protocol`), and call paths lose their query, before they reach the card (§8).
- **Card cache** (`card-cache.ts`): a card depends only on the commit's tree and the extractor version (`EXTRACTOR_VERSION`), so it is computed once per commit. It lives in daemon memory (the last 1000) and in `<state directory>/cards/<commit>.json` (written through `writeFileAtomic`; a failed write goes to the log). A file with another extractor version or not matching the schema counts as missing (version 4 since ADR-38, so cards from before it are computed again). A card for which the parsers did not give some tree because of time or missing grammars (`CardParsers.complete`) depends on the moment of computing, so it stays only in memory, and the next daemon start computes it again. Daemon startup removes files beyond the 2000 newest. Two simultaneous requests for the same commit read git once.
- **Repo tags** (`RepoTag`, `tags.ts`) are computed on every request from the card, the repo identifier, the remote address and the rules, each with a reason: `java` (a Maven or Gradle build file), `typescript` (a `typescript` dependency), `frontend` (React, Angular, Vue, Svelte), `backend` (Spring Boot, Express, NestJS), `bff` (the word `bff` in the identifier, the remote address or the name of a provided package), `library` (provides a package, and has no app framework or deployment files), `monorepo` (a build file names at least two modules or packages, or at least two build roots in different directories), `no-mise` (the commit stores no mise task, below, ADR-34). Tags are orthogonal: "a BFF in Java" is `java` + `bff`. On top of that, **tag rules** (`repoTags` in `workspace.yaml`, by hand only): a tag and patterns of the identifier or the remote address (`*` without `/`, `**` with `/`, ignoring case), for example `core-api: ["*-core", "gitlab.example.com/core/**"]`; the names of a company's teams and groups stay in the user's file (ADR-7).
- **API and UI**: `cards/card {repo}` returns the repo's card and tags, `cards/tags` the tags of every repo from the folder (at most 4 repos at once; a repo git cannot read is `unavailable` with a message). The repo list shows tags under the repo status (reasons in the tooltip) and a filter: every tag with its number of repos, and the selected tags narrow the list to repos that have all of them. Tags are fetched again when the set of repos or the HEAD of one of them changes, and every minute (a hand change of the rules). The `no-mise` tag (ADR-34) goes to a repo whose commit stores no mise task (`RepoCard.mise`: mise configuration files in the root and the tasks from their `[tasks]` and from files in the task directories `mise-tasks/`, `.mise-tasks/`, `mise/tasks/`, `.mise/tasks/`, `.config/mise/tasks/`), with the reason "no mise config in the repo root" or "mise.toml declares no tasks"; the repo list shows it as the warning "no mise tasks", and a filter on it picks the repos to normalise. The tag only speaks about the absence of any task; a repo with tasks but without `setup` or `build` learns that from a skipped step of the Batch command (§4.8). The configuration is the files from the root (`mise.toml`, `.mise.toml`, `mise/config.toml`, `.mise/config.toml`, `.config/mise.toml`, `.config/mise/config.toml`, `.config/mise/mise.toml`) and `*.toml` from `conf.d` directories; a file the card did not read (limits) disables the tag, because it is unknown whether it has tasks. Tasks from the user's global configuration and from `task_config.includes` are not counted, and the name of a file task is the path in the task directory with `:` (without the extension shortening mise does; `_default` gives the directory name); the "mise tasks" tab gives the full list, §4.7. The "Card" tab in the repo details shows tags with reasons, problems, mechanisms, tools, apps (name, port), HTTP endpoints (method, path, request and response types, handler), DTOs (kind, name, fields with types or enum constants), HTTP clients (kind, name, app or address with profiles, calls), provided and consumed packages, and build files, every fact with evidence.
- **MCP**: `list_repos` gives the tag names of every repo and accepts `tags` (repos with each of the given ones), `get_repo` the repo's tag names, and `get_repo_card` the whole card with tags and reasons (§5.3). Tags do not take away the rest: `get_repo` for a repo whose card cannot be computed has empty tags, and `list_repos` without a filter with a bad `repoTags` gives repos without tags (with a filter, a configuration error). `list_repos` always computes tags, so the first call after startup with hundreds of new commits reads git for every repo; after that the cards are in memory.

The graph = joining `consumes` with `provides` by keys: URL/base-path, artifact name, topic name, environment variable name with a host. Every edge has `confidence` and `evidence` (file, line). MCP queries work on this graph and return identifiers with evidence, not prose.

The first slice of the graph (ADR-29): edges from packages, package aliases and manual edges from `workspace.yaml`, the "Overview" view and the MCP tools `who_calls` and `subgraph_for`. The second (ADR-30): HTTP edges from the clients and endpoints on the cards, app aliases and `find_endpoint`. Topics and service states in the subgraph will come together with the extractors and services.

- **A node** (`GraphNode`) is a repo from the list (today a repo, not a service): the identifier, the remote address, tag names, the number of distinct packages it builds, the names of Spring Boot apps and the number of HTTP endpoints from the card, and the reason when the card cannot be computed (`problem`; the repo stays in the graph without edges from cards).
- **An edge from a package** (`kind: "package"`): repo A consumes a package (`consumes`) that repo B builds (`provides`), in the same namespace (`PackageEcosystem`: Maven `group:artifact` also from Gradle, npm, Gradle plugins). The direction is from the repo that consumes to the one consumed. Evidence from both sides: the build file and dependency line in A (with version and scope), and the file and line in which B builds it. Confidence `exact`, and when several repos from the list build the same package (two clones of one repo, a fork), an edge to each with `medium` confidence; a repo that builds a package with two build files (for example while moving from Maven to Gradle) counts once. The dependency scope (for example `test`) is in the evidence, it does not change the edge.
- **An HTTP edge** (`kind: "http"`, ADR-30, `http-index.ts` and `http-edges.ts`): an HTTP client from repo A's card calls repo B. The target is the first of: an app with the name from the client (`app`: Feign `name`, `lb://name`) in B's card; an app alias from `workspace.yaml` for that name or the address's host; an app or repo with a name equal to the first part of the host (`http://payments-service:8080`, `orders-api.shop.svc.cluster.local`; a repo's name is its identifier or the last part of its remote address); an app with the port from an address on `localhost` (also `127.0.0.1`, `host.docker.internal`), like an address from a frontend's `.env` in development mode. Without any of these the graph looks for a repo whose endpoints match the call paths (by method and path: a variable `{id}`, `{}` or `*` matches one segment, `**` the rest; a path without a fixed segment, like `/{id}`, does not point to a repo). An endpoint without a fixed segment (`/**`, `/{path}`: forwarding everything to a SPA) is neither a target nor evidence of a call. An app name, alias or port that points only to the client's own repo ends the search without an edge (an app calls another app from the same repo). The edge key is the app name, alias, host, `localhost:<port>` or, for a match by path, the client name. Confidence: `exact` when the app name points to one repo and every call of the client has a matching endpoint in it; `high` for the app name or an alias alone; `medium` for a host equal to a repo name, a port on `localhost`, paths matching the endpoints of one repo, or an app name in several repos (a clone, a fork); `low` for paths matching the endpoints of several repos. Evidence: the client (kind, name, address with profiles), the configuration entry with the address, the target app, and call–endpoint pairs (at most 5 per client). A client in several profiles is one edge with evidence from each (at most 20 pieces of evidence), with the higher confidence. A repo does not connect to itself, and a client without a target (for example a Zipkin address) gives no edge.
- **User entries** (the `graph` key in `workspace.yaml`, schema `GraphConfig`, by hand only, like `repoTags`): `packages` are package aliases (package name → the repo that delivers it), working only for a package no repo from the list builds, with `high` confidence; `apps` are app aliases (an app name or an address host, ignoring case → repo), for when the name from a client is not the `spring.application.name` of any card (an address behind a gateway, DNS from another name), with `high` confidence (ADR-30); `edges` are manual edges (`from`, `to`, `note`, kind `manual`, confidence `exact`), for example an HTTP call through a gateway the cards do not see. A repo is given by its identifier or its remote address (`host/path`, ignoring case; the address survives a directory rename, ADR-18). The evidence of an entry is `workspace.yaml` (`repo: null`, full path) and a sentence with the entry's name. An empty subkey (`packages:` without entries) means no entries. An entry pointing to a repo outside the list, or a manual edge from a repo to itself, goes to the graph's `configProblems`. A bad `graph` key (for example `edges` is not a list) or `repoTags` is not a graph error: the graph is built without user entries (or without tags from rules), and the message goes to `configProblems`, so the edges from cards stay.

```yaml
graph:
  packages:
    com.example:orders-client: orders-api            # package -> repo (identifier or host/path)
  apps:
    orders.internal.example.com: orders-api          # app name or host -> repo
  edges:
    - from: gitlab.example.com/shop/shop-web
      to: orders-bff
      note: HTTP /api/orders
```

- **Computing** (`modules/graph/`): `Cards.all()` gives the cards, addresses and tags of all repos (at most 4 repos at once, cards from memory by commit), and the pure function `buildGraph` joins them with the `graph` entries; the graph has no persistent state: the module keeps only the last computed graph with the input key (commits, addresses and tags of all repos, reasons for missing cards, and the `graph` configuration), because HTTP edges compare calls with the endpoints of all repos (ADR-30), so a new commit, a new repo in the folder and a hand change of `workspace.yaml` work at once. The cost of a request is the cost of the tag list: reading HEAD and the remote of every repo. Edges are sorted, and the same pair of repos, kind and key is one edge. Package names from repos do not reach the object prototype (aliases are in a `Map`).
- **Queries**: `who_calls(repo)` are the edges to the repo (who consumes it), `subgraph(repo, depth)` the repos within `depth` edges in both directions (1–3, `MAX_SUBGRAPH_DEPTH`) and the edges between them. A repo outside the list is `not_found`. `findEndpoint(query, method?)` (ADR-30, `find-endpoint.ts`) are the endpoints from the cards of all repos matching the query: starting with `/` a path, also a concrete one (`/api/orders/42` finds `/api/orders/{id}`), or a fragment of a path, a handler (`Class.method`) or an app name, ignoring case; with a method only endpoints of that method and without a method. Each with the repos that call it (`callers`: repo, client kind and name, full call path, confidence as for an edge, evidence), at most 50 (`truncated`).
- **API and UI**: `graph/graph` returns the whole graph (`RepoGraph`). The "Overview" view (`GraphView`, Ctrl+4) draws it at full width in columns: a column is the longest path from a repo nobody consumes (frontends on the left, libraries on the right, like the scene layers in §5.5; edges going back in a cycle are skipped when computing columns), and the order within a column comes from the average position of the neighbours (barycentre), so that lines cross less often. The UI computes the layout without a graph library (`lib/graph-layout.ts`): repos are HUD cards, the edges of one pair of repos are one curve in SVG, manual ones dashed. Repos without edges are below the drawing ("No connections"). Selecting a repo highlights its neighbourhood, and the panel on the right shows the repo's apps, the number of packages and endpoints, whom the repo consumes and who consumes it, with the kind (package, HTTP, manual), keys, confidence and evidence; without a selection the panel has the counts, errors in the `graph` entries and the path of `workspace.yaml`. The UI polls the graph every 30 s and on a button.

### 4.7 `mise`: repo tasks and running them

The first slice of the `mise` and `procs` modules (ADR-20): the "mise tasks" tab in the repo details shows the mise tasks of a repo from the projects folder, runs them and stops them. Task logs are in the `logs` module (§4.2, ADR-28); services (port, probe, leases) are the next step.

- **Log**: the task's output goes to the `logs` module as a `mise-task` source (§4.2), live in the tab under the task row.
- **The task list** is `mise tasks ls --json` in the repo root on every request (the UI polls while the tab is open: every 2 s when something runs, otherwise every 10 s, because in a trusted repo mise evaluates `[env]` while doing it), without hidden ones (`hide`) and without names mise would take for an option. No `mise` on `PATH`, configuration without trust (`untrusted`) and another mise error (for example `mise.toml` syntax) are list states, not API errors (likewise an exceeded time limit); mise warnings (`mise WARN`) that are not the cause are removed from the message. A running task stays until it is stopped even when it disappeared from the configuration or mise stopped giving the list (for example an error in `mise.toml` while it works): a state without a list carries `running`.
- **A run** is `mise run <task>` in the repo root through `procs`, only for a task from the current list (§1.2); a running task returns its state instead of a second group. No mise at start is `mise_unavailable`, a task outside the list `not_found`.
- **Trust**: mise does not read configuration with `[env]`, templates or hooks until the user trusts it, and `mise run` itself trusts its configuration automatically. The `trust` action (`mise trust` in the repo root, without parent directories) is only in the UI, with a warning that mise configuration can run programs (§8).
- **For the Batch command** (§4.8) the module has two runs awaited until the group ends: `runToEnd` (a task from the current list, `null` when the repo does not have it; a task already running, for example from the repo details, does not start a second time, and the result is its end) and `installTools` (`mise install` in the repo root, its own group owner `mise-install:<repo>`, because a task may be called `install`). Both take an `AbortSignal`: an abort before the start runs no process, and after the start it stops the group with the same stop as the repo details; when the stop cannot be confirmed, the result is the error `stop_unconfirmed` instead of waiting further.
- **The agent through MCP** (ADR-41, §5.3): `run_mise_task`, `stop_mise_task`, `wait_for_mise_task` and `list_running_mise_tasks` are the same `start`, `stop` and `running` as in the UI, plus `waitForEnd`: the current run after the end of the group confirmed in the system (`procs.ended`) or after the time limit, and an abort by the client ends only the waiting, not the task. Tasks run by the agent and from the UI are the same groups, so the agent sees and stops also a task started with the button, and the UI the agent's task.
- **Running tasks of all repos** (`mise/running`, `RunningMiseTask`): a read from the module's memory (tasks started by the daemon whose group has not ended yet), without asking mise and without reading the folder; from it the dashboard (§5.5) knows in which repo something is running, without `mise tasks ls` on every repo every few seconds.
- Short `mise` calls (`tasks ls`, `trust`) go through `mise-cli.ts`: an argument array, without a shell, a 15 s limit and 4 MB of output; they do not need a process group.

### 4.8 `batch`: the Batch command

The Batch command (ADR-27) is selected steps on selected repos with one button in the "Repos" view: sync, tools, dependencies and build, with the result of every step in every repo. The module runs nothing itself, it only composes `workspace` and `mise` on top of them.

- **Steps** (`BatchStep`) always run in a repo in this order, regardless of the order in the request: `sync` (sync of one repo, §4.5, ADR-21; `vcs` syncs one `.git` directory at a time anyway, so a parallel "Sync all" does not get in the way; a repo being cloned is a step error), `tools` (`mise install` in the repo root: the JDK, Node and the rest from the repo's mise configuration), `setup` (the mise task `setup`, that is dependencies) and `build` (the mise task `build`). The task names are the convention from `CONTEXT.md`; a repo without a given task has the step `skipped` with a reason and goes on. The daemon builds the commands from the step name (§1.2); the client gives only repo identifiers and steps from the list.
- **Step result** (`BatchStepState`): `waiting`, `running`, `done` (sync with the branch and number of new commits), `skipped` (with a reason; a skipped sync does not stop the repo, because the next steps work on what is there locally), `failed` (message and the last lines of the process output; the repo's remaining steps are `skipped`, and the other repos go on) or `cancelled`. A mise step ends `done` at code 0, and `cancelled` when the user stopped the group: by cancelling the command, by stopping the task in the repo details, or by daemon exit.
- **Parallelism**: at most 3 repos at once (a Java or frontend build takes several cores and GBs of memory, and `mise install` downloads JDKs), step by step within a repo. Tasks go through `procs` under the same owner as from the repo details, so the repo details show them as running and can stop them, and a second start of the same task joins the running one instead of starting a second group.
- **Cache**: a rerun is cheap thanks to mise, not to Trackwall. mise skips a task with `sources` and `outputs` when the outputs are newer than the sources, and `depends` runs a task's dependencies once per `mise run`. `build` with `depends = ["setup"]` will run `setup` a second time in the same command, unless `setup` has `sources` and `outputs`; a deliberate choice (ADR-27). With the `setup` and `build` steps mise also installs missing tools itself, so the `tools` step exists to make the installation visible as a separate result.
- **Cancellation** (`cancel`): waiting repos and steps that have not started end as `cancelled`, and an ongoing mise step gets a group stop (`AbortSignal`, §4.7). An ongoing sync cannot be cancelled, because git is not in a process group (§8); it ends by itself. A group whose killing cannot be confirmed ends the step with the error `stop_unconfirmed` (the group stays `stopping` in the repo details, from where the stop can be retried), so a cancellation always ends the command. Without cancellation the command waits for a group whose end cannot be confirmed (for example a task from the repo details after a failed stop) and shows that step as ongoing. A cancellation also stops a task the command joined, although the user started it from the repo details. Daemon exit cancels the command before stopping the groups and rejects the start of a new one, including one that is just checking repos.
- **State** lives only in daemon memory, like sync: `run` returns the last command, one runs at a time (a second start is `bad_request`), and an unknown repo rejects the whole request (`not_found`) before anything moves. The UI polls every 1.5 s during a command and every 10 s outside it; the Batch command may become another `/ws` topic (ADR-36).
- **Choosing repos** is done by the client: the Batch command panel (in place of the repo details, like the sync panel) has a list of repos with checkboxes, all selected by default. The list is the repos after the tag filter of the repo list (ADR-25), so "build all `java` + `bff`" is two clicks in the filter; a filter change starts the selection over (all from the new group).
- **The same directory, another entry**: a link in the projects folder to another repo on the list is a separate repo (ADR-18), so the command groups repos by directory on disk (`realpath`, ignoring case), and the repos of one group run one after another: two `pnpm install` runs or builds at once in one directory would break each other's files. Before every step the command also checks that the repo identifier points to the same directory as at the start, because an identifier from a directory name can move to a new directory (ADR-18); otherwise the step ends with an error.
- **mise monorepo mode** (`monorepo_root`, `mise run '//...:build'`) was checked as an engine and rejected (ADR-27): it requires a configuration file in the projects folder and one process for all repos, and it stops the others after the first error.
## 5. Protocols

### 5.1 Discovering the daemon

At startup the daemon writes `~/.trackwall/daemon.json`: `{ pid, port, token, startedAt, version }` with permissions for the user only. The port is random from the loopback range, listening only on `127.0.0.1`. A second daemon exits when `/api/health` of the existing one answers with the same version; with another version it asks for a restart from the UI. Clients (Tauri, `ws`, the MCP stdio bridge) read this file; nothing is configured by hand.

### 5.2 Daemon ↔ UI and CLI: HTTP + WebSocket

- **HTTP JSON** for commands and queries: `POST /api/<module>/<action>` with a body validated by zod from `packages/protocol`. The response is `{ ok, data }` or `{ ok: false, error: {code, message} }`. One convention for the UI and `ws`. A body has at most 64 KB; an empty one means `{}`. An action is described in `packages/protocol` by one `Endpoint` object (path, body schema, `data` schema): the daemon validates input with it (`api/routes.ts`), and the UI types the body and checks the response, so the two sides cannot pair them differently. Today these `workspaceApi` actions work: `list` (`{ projectsDir, repos }`), `settings` (`{ projectsDir, configFile }`), `repo-hosts` (the list of hosts), `set-projects-dir {path}`, `overview {repo}` (README and 30 commits), `tree {repo, path}`, `file {repo, path}`, `changes {repo}` (`WorkingTreeChanges`: files and diff of the working directory against HEAD, ADR-34), `open-editor {repo}`, `open-folder {repo}` (the repo folder in Explorer or Finder, `null`, ADR-51), `dropped-folder {path}` (`DroppedFolder`, ADR-51), `open-link {url}` (an `http` or `https` address from a README opened in the system browser, ADR-35), `set-repo-hosts {repoHosts}` (the stored list), `remote-repos {query}` (`{ projectsDir, hosts }`), `clone {host, fullName}` (a clone in the `running` state), `clones`; `open-editor` returns `data: null`. Then `agentsApi` (§4.4, ADR-26): `sessions` (`SessionList`: sessions, newest first, with the process group `RunState`, the last state change, the window title and whether it is waiting for you), `start {repo}` (`Session`), `stop {session}` (returns after a confirmed end of the group) and `dismiss {session}` (only an ended session, otherwise `bad_request`); for tasks (ADR-31) `create-task {repo, prompt}` and `resume-task {task}` (`Task`), `task-changes {task}` (`TaskChanges`), `open-task-editor {task}` (`null`) and `remove-task {task, keepBranch, discardChanges}` (`null`); `sessions` also returns the tasks and the directory of their worktrees. And `miseApi` (§4.7): `tasks {repo}` (`MiseTasks`: a list with `RunState`, or `not_installed` / `untrusted` / `error`), `start {repo, miseTask}` and `stop {repo, miseTask}` (`RunState`; `stop` returns after a confirmed end of the group), `trust {repo}`, `running` (`RunningMiseTask[]`: running tasks of all repos, from daemon memory). Then `batchApi` (§4.8): `start {repos, steps}` (`BatchRun`: a command started in the background), `run` (the last command or `null`) and `cancel`. Then `logsApi` (§4.2): `tail {source, sinceSeq?, limit}` (`LogTail`: `records`, `nextSeq`, `dropped`; `limit` up to 1000). Then `cardsApi` (§4.6): `card {repo}` (`RepoCardResult`: the card, or `null` in a repo without commits, and tags) and `tags` (the tags of every repo from the folder, or `unavailable`). And `graphApi` (§4.6, ADR-29): `graph` (`RepoGraph`: nodes, edges with evidence, errors in the `graph` entries and the path of `workspace.yaml`). Validation messages are in English (the default zod locale, ADR-32). An error a module raises deliberately (`DomainError`) comes back with its code and text: `bad_request` 400, `not_found` 404, `repo_unavailable` 409, `projects_dir_unavailable` 409 (the projects folder disappeared), `invalid_config` 500 (a bad `workspace.yaml`), `mise_unavailable` 409 (no mise, configuration without trust, or a mise error when starting a task), `stop_unconfirmed` 500 (the group is alive after killing), `agent_unavailable` 409 (no Copilot CLI on `PATH`, or no PTY in this runtime), `unsaved_changes` 409 (ending a task would delete changes the caller did not confirm); any other exception is `internal` without details.
- **WebSocket `/ws`** for events (ADR-36, `api/event-socket.ts`, `api/event-hub.ts`): JSON text frames `DaemonEvent` `{ type, payload }` (`packages/protocol/src/events.ts`), in which `payload` is the whole **topic snapshot**, the same as the response of the HTTP action: `sessions.changed` (`SessionList`, like `agents/sessions`) and `mise.running.changed` (`RunningMiseTask[]`, like `mise/running`). After connecting the daemon first sends the snapshot of every topic, then an event only when a topic's snapshot changed, so a client reconnects after a broken connection and needs no event buffer, event number or `resync`; one connection gives the order. The daemon detects a change by comparing the snapshot's JSON every 200 ms (as often as the session cycle) while someone is listening, and serialises an event once for all clients; the compiler checks the set of topics (`TOPICS` in `event-hub.ts`). A topic whose read failed goes to the daemon log once per identical error, and when clients already had its snapshot, the daemon closes their connections with code 1011: after reconnecting they get snapshots without that topic, so the UI goes back to HTTP polling for it and shows the error instead of an old snapshot as live state. The client sends nothing (a frame over 1 KB ends the connection), and a client that does not receive (over 4 MB in the buffer) gets a close with code 4429 (`EVENTS_CLOSE_SLOW`) and reconnects from the snapshots. The connection goes through the same checks as a session terminal (below, `api/sockets.ts`), with the `trackwall.events` subprotocol next to the token; in `vite dev` the Vite proxy adds the token, as for the terminal. The UI (`lib/daemon-events.ts`) keeps one connection per daemon connection, reconnects after 1 s and then less and less often, up to 10 s, and gives the topics as a `LiveFeed` to `useRemote` (the `live` option): a snapshot replaces the data like a response, HTTP polling waits while the topic has a snapshot from the current connection, and the first fetch, `reload` after an action and time without a connection stay on HTTP. One counter numbers requests and snapshots (`LoadOrder`: a request when sent, a snapshot when it arrives), and the response to a request sent before a snapshot does not replace a newer snapshot; a snapshot read in the daemon just before an action but received after it counts as newer than the action until the next one (at most 200 ms later) corrects it. Further topics (logs `log.append`, services, sync and cloning, the repo list once the daemon starts watching repos) are further variants of `DaemonEvent` and entries in `TOPICS`; the Tauri shell still polls `sessions` over HTTP (§5.4).
- **PTY** as a separate WebSocket `/ws/pty/<session>` (ADR-26, `api/pty-socket.ts`, the `upgrade` handling and checks shared with events in `api/sockets.ts`, the `ws` library, because Node has no WebSocket server): after connecting the daemon sends the session's screen image (a text frame from `@xterm/addon-serialize`, with terminal modes and the alternate screen), then the PTY output in binary frames, exactly from where the image ends. The client sends JSON text frames `PtyClientMessage`: `input` (keys and pasted text, up to 65,536 characters) and `resize` (columns and rows). A window that comes to the front sends `resize` again for each of its terminals, so with the same session in two windows (ADR-49) the window the user works in sets the PTY size. The client also sends `focus {focused}` after the window has been focused and visible for 1 s and when it stops being so; a focused window marks the session seen (ADR-47), and a closed connection counts as unfocused. In the session grid (ADR-48) only the selected tile reports `focused: true`; the other tiles report that they are not in front. The connection goes through the same `Host` and `Origin` checks as the rest of the API; the token is a second subprotocol (`bearer.<token>`, `SOCKET_TOKEN_PREFIX`, constant-time comparison), and the server confirms only `trackwall.pty`, because a browser cannot set a header on a WebSocket, and an address ends up in logs and history. The socket's address and subprotocol go together (`DaemonSocket`, `ptySocket`, `EVENTS_SOCKET`, `daemonSocketAt` in `packages/protocol/src/sockets.ts`), so the daemon, the Vite proxy and the UI cannot combine them differently. The token is checked before the address (without a token 401 also at an unknown address), then the address (404) and the socket's subprotocol (400). An unknown, closed (`dismiss`) or non-UUID session closes the connection with code 4404 (`PTY_CLOSE_NOT_FOUND`, the window does not reconnect), a window that does not receive output (over 8 MB in the buffer) with code 4429 (`PTY_CLOSE_SLOW`). A request whose address cannot be parsed is refused, and an error in handling a connection ends only that connection, not the daemon. In `vite dev` the Vite proxy adds the token, as for `/api` (§8). The session state reaches the UI with the `sessions.changed` event from `/ws` (above); without an event connection the UI polls `sessions` every 1 s with the view open and every 3 s outside it (the counter on the view bar).
- **Authentication**: the token from `daemon.json` in the `Authorization: Bearer` header, constant-time comparison. Requests whose `Host` or `Origin` is not loopback are rejected (DNS rebinding, CSRF from a page in the browser). Tauri gives the token to the WebView through a Tauri command, not through a query string.

### 5.3 Daemon ↔ agent: MCP

The daemon exposes an MCP server over the **Streamable HTTP** transport at `/mcp` with the same token. For CLIs that only support stdio there is the stdio bridge `trackwall-daemon mcp-stdio`, which forwards JSON-RPC messages to `/mcp`. Eventually the "connect an agent" feature in the UI adds an entry to the given CLI's MCP configuration without touching the rest of the file; today the UI shows the command that does this on the Copilot CLI side (below).

The first slice (ADR-24) gives a **supervising agent** (Copilot CLI started by the user, for example in the projects folder) a map of the repos, read only; ADR-39 adds delegating tasks to other sessions through proposals the user approves, and ADR-41 running and stopping mise tasks from the repo's trusted configuration:

- **The server** (`src/mcp/endpoint.ts`) is `createMcpHandler` from `@modelcontextprotocol/server`, without MCP sessions: every request gets a fresh `McpServer` with the same tools, because the facade holds the state. `handle()` in `api/server.ts` recognises a request with the `x-trackwall-session-token` header (the stdio bridge of a Trackwall session, ADR-39) through `agents.callerSession`, and the calling session goes to the server factory as `authInfo.clientId` and to every tool call; an unknown token (a closed session) is `401 unauthorized` before the SDK, so that the session does not look like an agent from outside Trackwall. It supports revision 2026-07-28 and older clients with `initialize` (statelessly; GET and DELETE of a session give 405). `handle()` in `api/server.ts` checks `Host`, `Origin` and the daemon token (one token check for the API and MCP; only `GET /api/health` and the UI files are public) before the request reaches the SDK; a body has at most 256 KB, and a disconnected client aborts the request in the SDK too. `main.ts` builds the MCP server from the facade and passes it to `startApi`. The server announces `instructions` with the MCP instruction (`MCP_INSTRUCTIONS` in `protocol`, ADR-46): what Trackwall is and when to reach for which tool (the repo card before reading build files, `search_code` to find code across repos, `find_endpoint` and `who_calls` before changing an API, `get_errors` (then `tail`) to diagnose a failure, `run_mise_task` and `wait_for_mise_task` to build and test, `propose_task` and `wait_for_session` to hand work over, `report_result` at the end of a task, the documentation site and its `llms.txt` (`TRACKWALL_DOCS_URL` in `protocol`) when the agent or the user is unsure what Trackwall can do). Tool names come from `mcpTools`, and a test requires the instruction to mention every tool, so a new tool cannot land without a sentence on when to use it. Copilot CLI 1.0.103 adds `instructions` to the prompt only for servers on its own allowlist (unless started with `--allow-all-mcp-server-instructions`), so Trackwall sessions get the same instruction in their session instructions too (§4.4).
- **Tools** (`src/mcp/tools.ts`): `list_repos`, `get_repo`, `get_repo_card`, `tail` (mise task log, §4.2), `get_errors` (errors from logs, ADR-42), `who_calls`, `subgraph_for` and `find_endpoint` (connection graph, §4.6), `search_code` (code search, §4.5, ADR-40) and `list_sessions` and `get_session` (sessions and tasks, §4.4, ADR-36), and for delegating work `propose_task`, `report_result` and `wait_for_session` (§4.4, ADR-39), and for mise tasks `run_mise_task`, `stop_mise_task`, `wait_for_mise_task` and `list_running_mise_tasks` (§4.7, ADR-41), and for services `start_service`, `stop_service`, `list_services` and `call_endpoint` (§4.3, ADR-45). A tool's contract (name, description for the agent, input and result schema) is an `McpTool` object in `mcpTools` (`packages/protocol/src/mcp.ts`), like `Endpoint` for the API; the daemon only supplies its execution on the facade (`defineTool`), and the UI takes the names from it. The annotations come from the contract: `readOnlyHint` from the `readOnly` field, and a tool with `readOnly: false` must give `destructive` (`destructiveHint`). `propose_task` and `report_result` store only text for a human (`destructive: false`); `run_mise_task` runs repo code, and `stop_mise_task` can kill a process the user needs (a server, a migration), so both have `destructive: true`, and an MCP client that asks for approval of destructive tools will ask about them. Each returns `structuredContent` checked against the schema and the same JSON as text for clients that do not read it. An error raised by a module (`DomainError`) comes back as a result with `isError` and the text `<code>: <message>`, anything else as `internal` without details. Every call goes to the daemon log (tool, calling session, time, result, without arguments); a destructive tool (`run_mise_task`, `stop_mise_task`) adds a line with its arguments, that is the repo and the mise task, before acting (ADR-41). The `audit` table will come with SQLite. A further tool is a further `mcpTools` entry with its execution in `runs` in `tools.ts` (its absence is a compile error) and a registration whose completeness the `tools/list` test checks.
- **The stdio bridge** (`trackwall-daemon mcp-stdio [--home <dir>] [--session-token-file <file>]`, `src/mcp/stdio-bridge.ts`) reads JSON-RPC lines from stdin and sends each separately to `/mcp` with the port and token from `daemon.json`, read at every message: a daemon restart (new port and token) needs no change to the agent's configuration, and the token never goes into it. In a Trackwall session the bridge also reads the session token from the `--session-token-file` file at every message and sends it in the `x-trackwall-session-token` header (ADR-39); without the file (a closed session) it answers with error `-32000` instead of sending the request as an agent from outside Trackwall. The time limit of one request is 120 s, with room for `wait_for_session` (up to 55 s). Messages go in parallel; a JSON or SSE response comes back as lines on stdout, and the bridge's own messages only on stderr. The bridge adds the version from `initialize` to later requests as `MCP-Protocol-Version`. A transport error the daemon returns with `id: null` (for example a header the SDK rejected) the bridge sends back with the request's `id`, because a stdio client pairs responses by `id`. The bridge rejects the revision 2026-07-28 probe (`server/discover`) like a server without that method (`-32601`), because in that revision an HTTP request repeats content fields in headers, which stdio does not have; the client then falls back to `initialize` (as Copilot CLI 1.0.103 does). Without a running daemon, with a rejected request, or with a response that has no message for that `id` (a stream broken midway), the bridge answers with error `-32000` and an instruction to start Trackwall; it does not start the daemon itself. A line that is not JSON gets `-32700`, and JSON that is not a JSON-RPC object (including a batch, which MCP has not had since revision 2025-06-18) `-32600`. After stdin ends the bridge waits for the responses in flight and exits by itself once stdout drains.
- **Connecting Copilot CLI**: `/api/daemon/info` gives `mcpStdioCommand`, this daemon's bridge command (the release binary, recognised by the Bun virtual file system in the script path, `isCompiledBinary`; when running from source the runtime and the script, under Bun with `--no-env-file` and `--config` pointing to the empty `packages/daemon/bunfig.toml`; a non-default state directory as `--home`). The "Daemon" view shows the command `copilot mcp add trackwall -- <bridge command>` built from it (quoted for PowerShell on Windows, where arguments with `,` and `@` and those starting with `-` are in single quotes too, because PowerShell eats a bare `--` before the `copilot.ps1` script; sh on macOS) and the same entry for `mcp-config.json` in the user's `.copilot` directory to copy. Copilot CLI starts the bridge at startup and keeps it until the session ends, so Trackwall must be running before.

### 5.4 Tauri ↔ daemon

Tauri starts the daemon as a sidecar with the argument `--parent <pid>`, waits for `/api/health`, shows a splash screen, and after a failure a dialog with the startup log. The window shows only after the UI has loaded, with the background effect already set (ADR-11). Closing the main window hides it to the tray. The shell can have several windows (ADR-49, `src-tauri/src/windows.rs`): the main window from `tauri.conf.json` (label `main`) and extra windows the user opens with "Open in new window" in the context menu of a view icon on the view bar, Ctrl+Shift + the view's digit (⌥⌘ on macOS, where ⌘⇧3 and ⌘⇧4 take screenshots; `viewKeyAction`, not for a held key), Ctrl+Shift+N (⌘⇧N; the current view) or "New window" in the tray (the UI's first view, Home). The context menu is the native menu (`@tauri-apps/api/menu` under `core:default`), one per window, reused for every right click. An extra window is built from the main window's configuration (`WebviewWindowBuilder::from_config`) in an async command or the async runtime, never on the main thread, where building a window deadlocks on Windows, and one at a time (`Windows::opening`), so two quick opens do not pick the same label; its label is `window-<n>` with the lowest free number from 2, its page is `index.html?view=<view>&sessionLayout=<layout>` (only a lowercase word or number reaches the address, `window_url`), and it gets the background effect on the main thread and the same reveal after page load as the main window (`WindowEffects`, per label, with the entry created before the window, so a reveal from its page or the tray always lands on it). Every window is the same UI with its own view and its own connection to the daemon (`daemon_connection`, `/ws`, `/ws/pty`), so sessions and changes are live in all of them; the capability `default` covers `main` and `window-*`. Closing an extra window closes it; only the main window hides to the tray. On macOS the shell sets its own menu bar (`app_menu.rs`) instead of Tauri's default: the app menu with About, Settings… (⌘,), Services, Hide and Quit; Edit with the system's items, which copy and paste in the web view need; View with the view bar's views and their shortcuts (⌘1…⌘4, ⌘9; `apps/desktop/test/shell-events.test.ts` keeps the list equal to `VIEWS` in `App.tsx`) and full screen; Window (`WINDOW_SUBMENU_ID`, so macOS lists the open windows by title and adds "Bring All to Front") with New Window (⌘⇧N, as on the view bar), Minimize, Zoom and Close Window; and Help, where macOS puts its search. A Trackwall item sends the event `app-menu` with `{kind: "view", view}` or `{kind: "new-window"}` to the last focused window (`Windows::last_focused`, shown first, because the app can be active with every window hidden), whose UI shows the view or opens its current view in a new window (`use-app-menu.ts`). The web view gets a key press first and the menu only one the page did not handle (wry), so a shortcut the UI takes (⌘1, ⌘⇧N) acts once, and the menu's item acts when focus is elsewhere. A click when the window's page is still loading is lost: the page shows itself (ADR-11) and has no listener yet. The title of a window is the name of its view from the same table (`app_menu::view_name`). Windows has no menu bar, because there it would be a bar inside every window. `tauri-plugin-window-state` keeps the position, size, maximized and full-screen state of each label in `.window-state.json` in the shell's configuration directory (not the visibility, which stays with the reveal) and restores it when a window with that label is created; a saved position is used only if a monitor still contains it, so a window from an unplugged monitor opens at the default position. The file is written when an extra window closes (`windows::closed`) and when the shell exits; a killed shell loses the moves since then. The open extra windows are saved in `windows.json` in the same directory (`saved_windows.rs`: label, view and session layout of each, written through a temporary file and a rename whenever a window reports what it shows or the user closes one), and the shell's `setup` opens them again under the same labels (the list enters the registry first and `Windows::opening` is held for the whole restore, so a window reporting or closing meanwhile does not drop the others and "New window" cannot take a saved label; a window that cannot be built stays in the list, since the failure may be the app quitting mid-restore; the file is written with the registry locked, so writes from the restore and from the main thread do not overtake each other), so each comes back on its monitor with its view and layout. Quitting the app closes windows without `CloseRequested`, so they stay in the list; closing an extra window removes it. The file is read like any external input: entries whose label is not `window-<n>` (n ≥ 2), whose view or layout is not a lowercase word or number, repeated labels and anything past 16 windows are dropped, and a file that is not the expected JSON opens no windows. Every exit from the shell stops the daemon: the shell aborts an ongoing start, sends `POST /api/daemon/shutdown` (when the start failed, to the daemon from `daemon.json`), the daemon stops services and sessions with the same gentle stop as Ctrl-C, and Tauri waits until it stops answering and does not start a new one after that. A daemon that already answers gets the gentle stop also when the exit came during the start; only a sidecar that has not come up yet is killed. "Quit" from the tray hides the windows and the icon, and stops the daemon in the background before the event loop ends, so the single instance is held until the end. Cmd+Q and "Quit" from the Dock on macOS (and, according to tao's code, also the end of a Windows session, where the system may end the process before the waiting ends) end the loop skipping `ExitRequested`, so the `RunEvent::Exit` handler does it, after hiding the windows and removing the tray icon. The shell asks the daemon for sessions every 2 s (`POST /api/agents/sessions`, with the same hand-written HTTP client), because the WebView of a hidden window may have its timers suspended, and it does not listen to events from `/ws`, because they would need a WebSocket client in Rust, and 2 s is enough for flashing the window (ADR-36): a session that goes from `Working` or `Stale` to waiting for a human triggers `request_user_attention` (flashing on the Windows taskbar, a bounce in the macOS Dock), and every waiting session has a tray menu item "Waiting: <repo>" that shows the window and asks the UI for a jump to `{kind: "session", id}`. The window is the one for sessions (`Windows::session_window`, ADR-49): the last focused window that shows the Sessions view (each window reports its view and session layout with `window_shows` when either changes; the view's name becomes the window's title, `<view> – Trackwall`, so windows differ in the taskbar and the macOS Window menu), otherwise the last focused window, otherwise the main window; the event goes only to that window (the UI listens on its own window, `getCurrentWebviewWindow().listen`, because a global `listen` also gets events sent to other windows), and `request_user_attention` flashes it too. Task proposals work the same way (ADR-39, from `proposals` in the same reply): the item "Proposal: <repo> · <title>" above the sessions asks for a jump to `{kind: "proposal", id}`, and a proposal that was neither a proposal nor a task at the previous poll (a proposal being approved is already a task, and comes back after a failed start) calls `request_user_attention`; at the first poll after the shell starts none is new. `&` in a menu item's text is doubled, because it marks a mnemonic. The icon tooltip says how many sessions and proposals are waiting. The daemon does not exit when its parent dies (the "runs with the window closed" mode), it checks `--parent` only to tell a start from Tauri from a manual one. After the shell crashes or is killed the daemon keeps running, and the next start of the app connects to it through `daemon.json`.

A jump (`Jump` in `jump.rs`: `repo`, `session`, `task` or `proposal` with an id) goes to the window for sessions (ADR-49) or, for a repo, to the main window. The shell keeps it with that window's label and sends that window the event `jump-requested` without a payload; the window's UI takes the jump with the command `take_jump`, which answers only the window it is meant for, on the event and once when it starts, so a jump that comes before the page listens is not lost. A newer jump replaces one not taken yet. `trackwall://` links (ADR-52, `link.rs`, `tauri-plugin-deep-link`) become jumps the same way: `trackwall://repo/<repo id>`, `trackwall://session/<session id>` and `trackwall://task/<task id>` (a task link also finds a task proposal with that id). The shell checks the shape (scheme and kind without regard to case, exactly one id of letters, digits, `.`, `_` and `-` up to 64 characters, no query, fragment, port or user); the UI checks the id against `RepoId`, `SessionId` and `TaskId`, the only definition of an id. Anything else only shows the main window. A jump to a window whose page is still loading does not show it early (`windows::show_once_loaded`, ADR-11); that page shows itself and takes the jump when it starts. A jump waiting for a window that closes is dropped, because a new window may get the same label. macOS delivers a link to the running app, or starts it, through `Info.plist`, which the bundle gets from `plugins.deep-link` in `tauri.conf.json`. On Windows a link starts a second `trackwall.exe` with the link as its only argument; `tauri-plugin-single-instance` with its `deep-link` feature hands it to the running instance, and a link that starts the app is read from the arguments. A second start that carries a link does not bring the main window forward (`link::in_args`): the link shows its own window. The portable build has no installer, so the release shell registers the scheme for the current user (`HKCU\Software\Classes\trackwall`, pointing at the running `trackwall.exe`) at every start, which follows the folder when the user moves it; with two copies, the one started last gets the links. `tauri dev` does not register, so it does not take links away from the installed app. A `trackwall://` link printed in a session terminal opens on Ctrl+click (Cmd+click on macOS) through the command `open_link`, which applies the same check without the round trip through the system; the click also reaches Copilot CLI, which takes the mouse. Known limits: a link cut off by a wrapped row is not underlined, a wide character earlier in the row shifts the underline, and a link that Copilot CLI shows as an OSC 8 hyperlink with other visible text is not found (xterm.js opens only `http` and `https` OSC 8 links).

The shell also gives the window two things that need the system (ADR-51). The app command `pick_projects_folder` opens the system folder picker (`tauri-plugin-dialog`, called from Rust) and returns the chosen full path, which the UI saves with `set-projects-dir`; the plugin's own JavaScript commands stay unreachable, because the windows' capability is still only `core:default` and the app's own commands. Files dropped on the window come as Tauri's webview drag-and-drop events (`onDragDropEvent`: full paths and a point); the point is in physical pixels only on Windows (WebView2), while on macOS and Linux wry hands over CSS pixels under the same type, so the UI divides by the device pixel ratio on Windows only. The drop target that holds the point (`[data-file-drop]`, today the session terminal) is highlighted while dragging and gets a `FileDropEvent` with the paths, which it pastes; a drop outside every target goes to `dropped-folder` (§4.5), a drag without paths (text, a link, an image) is ignored, and so is a drop while the UI has no daemon connection. Tauri's drag-and-drop handling turns off HTML5 drag and drop inside the page on Windows, so the UI does not use it.

System notifications, the global shortcut and the tray panel (ADR-50; `notification.rs`, `global_shortcut.rs`, `tray_panel.rs`, jumps through `jump.rs`): at the same moments that flash the window (a session that starts waiting, a new task proposal), the shell also shows a system notification, but only while no Trackwall window has the focus: "Session in <repo>" with what the session waits for, in the words of the UI's state labels, or "Task proposal for <repo>" with the proposal's title; new proposals are held until three polls in a row (about six seconds) bring no new one, so a plan the main session writes over several `propose_task` calls makes one notification, "N task proposals" with their repos and titles, which opens the first; proposals decided meanwhile are left out (`HeldProposals` in `attention.rs`, ADR-55). The taskbar flash waits with it. Clicking it does what the tray menu item does. On Windows the toast goes out under the app's AppUserModelID (the app identifier, with `.dev` in a debug build), which the shell registers at every start under `HKCU\Software\Classes\AppUserModelId` with the display name "Trackwall" and the app icon, written to `notification-icon.png` in the state directory, because the portable build has no installer and no Start menu shortcut. The click handler is attached to the toast in the running shell, so a click on the toast on screen opens the entry; whether a click on it later in the notification centre does too is to be checked on a real machine, and after Trackwall has quit such a click does nothing, because the shell registers no COM activator. On macOS the notification is an `NSUserNotification` under the app's bundle identifier (a debug build runs outside a bundle and shows it under another app's name), and a thread waits until it is clicked, closed or cleared; up to eight notifications wait like that at once, and the ones past that are shown without a click action. On Linux nothing is shown. Win+Alt+J on Windows and ⌃⌥J on macOS, registered system-wide from Rust (`tauri-plugin-global-shortcut`, with no permission for the UI), jump to `{kind: "next-waiting"}` in the window for sessions (ADR-49), for which the UI opens the next waiting session or task proposals after the selected entry, like Alt+J (ADR-48, ADR-55); the window comes up even when nothing waits. When another app holds the shortcut, the shell starts without it and logs why. A left click on the tray icon opens the tray panel next to it (a double click on Windows opens the main window, as a single click did before): the frameless window `tray-panel` from `tauri.conf.json`, created hidden at start, which loads the UI with `#tray-panel`, takes the daemon's address and token with `daemon_connection` like the main window (and again, with a fresh list, each time the shell shows and focuses it, since the daemon may have been restarted with a new port and token), and lists the task proposals and the waiting sessions, live from `/ws`. A click on an entry or on "Open Trackwall" calls the command `open_from_tray_panel`, which hides the panel and then jumps like the tray menu (or shows the main window). The panel is not a window for sessions: its focus does not count in the window registry, and the window effect leaves it alone. The panel hides when it loses the focus; a press on the icon that finds the panel open, and a double click, only close it. It sits above the icon when the icon is in the lower half of the screen and below it otherwise, always inside the work area of the icon's monitor; Windows places it in physical pixels, macOS in points, because macOS reports each display in pixels of its own scale; the display is the one that holds the icon read in its scale and whose menu bar is as tall as the icon (`screen_for_icon`). With the menu bar hidden automatically that check has nothing to compare, and next to a Retina display the panel may open on the wrong one.

### 5.5 Daemon ↔ 3D scene

`@trackwall/scene` has no transport of its own and does not know the daemon API (ADR-33). From the same responses as the repo list, the "Sessions" view and "Overview", the UI computes the dashboard snapshot `HomeModel`: repos with a status (`clean`, `behind`, `changed`, `unavailable`), the number of changes or commits to pull and the running mise task (from `mise/running`, §4.7), sessions with a state (`working`, `attention`, `idle`, `error`, `done`; `idle` is `Input` the user has seen, ADR-47), connections from the graph, the number of layers and whether the daemon is running. A repo's layer is the column from the graph layout in "Overview" (the longest path from a repo nobody consumes), so the dashboard and the graph do not disagree about layers; a repo without connections has the layer `null`. `HomeScene.apply(model)` takes successive snapshots and keeps one Pawn entity per object (`KeyedEntities`): a new object gets an entity, a vanished one loses it together with its sessions and connections, each stands in its place in the new layout, and a three.js model is rebuilt only when something visible changed. Sessions and running mise tasks reach it from `/ws` events (ADR-36), the rest from polling; the scene does not know where a snapshot comes from.

The "Orbit" layout (`orbitLayout`, a pure function): the daemon in the middle, sessions on the inner track opposite their repo, repos on the outer ring in the arcs of the layers, and repos without connections in the last arc. The kind of a repo's solid follows from its layer: an entry (a terminal), a gateway (a cylinder with an antenna), a backend (a cabinet), a library (a crate). The scene decides which objects have a label (repos that are not clean, and sessions that are waiting or have an error), and the UI writes the label's text; colour and shape say the rest. A click selects an object and highlights its repo's connections, a double click reports going to the session or repo, and pointing reports the object under the cursor for the preview card. Colours come from UI tokens converted to `#rrggbb`, because three.js does not read `oklch`. With `prefers-reduced-motion` the models stand in their pose at time 0.

The "Home" view (`views/home/`, Ctrl+1, the first screen after startup) builds the snapshot in `lib/home-model.ts` (`homeModel`) from the repo list (every 10 s, like the "Repos" view), sessions (the same list as the view bar, from `sessions.changed` events), the graph (every 30 s) and running mise tasks (from `mise.running.changed` events; without an event connection sessions every 1 s and `mise/running` every 3 s, §5.2). The daemon "runs" while it answers: a repo list error with a code (for example `invalid_config`) came from it, and when the projects folder needs fixing (`projects_dir_unavailable`, `invalid_config`), the view shows the error and a way to "Settings" instead of the old list, like "Repos". On the left the "Needs you" queue (sessions that are waiting or have an error, with the state from the "Sessions" view, task proposals from the session list, ADR-39, and repos that are not clean; proposals are neither in the snapshot nor on the scene, and a click opens one in "Sessions" right away, because the decision, with an edited prompt, is made there), in the middle the canvas, on the right the details of the selected object with an "Open repo", "Open session" or "Open Daemon" button (without a selection a summary of the environment), and in the corner of the canvas a preview card of the object under the cursor. The tone and text of a dashboard object's status have one place (`homeRepoStatus`, `HOME_SESSION_STATUS`, `homeDaemonStatus`), from which the queue, the details, the preview and the scene labels take them; a repo with commits to pull is not clean on the dashboard, although the repo list counts only changes in the working directory. Selecting from the queue and from the scene is the same state, and the selection of an object that vanished from the snapshot is dropped: the scene highlights the object, and `CameraRig` points the camera at it; without a selection the camera goes back to the starting angle and looks at the middle from a distance chosen for the canvas's proportions (`lib/home-camera.ts`), also after the window is resized, so that the whole ring is in frame. A double click or the button goes to the "Sessions" view with that session, to "Repos" with that repo (only on that transition) or to "Daemon". The canvas (`HomeCanvas`) is loaded lazily (`React.lazy`), because three.js and Pawn are most of the view's weight: the rest of the UI takes only `@trackwall/scene/model` from the scene (the entry `src/model.ts`: keys, snapshot types and the palette, without three.js), which Biome guards, and the build removes the unused Draco decoder files three.js reports despite there being no glTF (`drop-unreferenced-draco.ts`). `lib/scene-palette.ts` reads the scene's colours: it paints every token on one pixel of a 2D canvas over the `--background` and reads back sRGB, so translucent tokens come out as they look in the app. When WebGL 2 does not work (checked on a separate canvas before the engine, because a failed `Engine` constructor leaves a koota world behind, and koota has at most 16 of them) or the context is lost (`webglcontextlost`), in place of the canvas there is a message with a "Try again" button, and the "Needs you" queue and the details keep working. A hidden window (`visibilitychange`) stops the engine loop, because Pawn does not pause it itself; rendering only on change is a request filed with Pawn.

## 6. Data model

The types live in `packages/protocol`. Below is the core; auxiliary fields are left out.

```ts
type RepoId = string;      // slug from the directory name in the projects folder, e.g. "orders-bff"
type ServiceId = string;   // usually = RepoId; a repo can have several services
type TaskId = string;      // ulid

// Today in protocol: { id, path, remote, status: RepoStatus } (§4.5; remote as host/path, ADR-21); the other fields come with cards.
interface Repo {
  id: RepoId; path: string; remote: string; vcs: 'github' | 'gitlab' | 'git';
  defaultBranch: string; head: string;
  analysis?: { commit: string; at: string; cardId: string };
  lastSetup?: RunResult; lastTest?: RunResult;
}

// Today in protocol (cards.ts, http.ts, ADR-25, ADR-30): RepoCard without `repo` (a card depends only on the commit) and without
// `description`; provides are kind 'package' (ecosystem 'maven' | 'npm' | 'gradle-plugin', name, version), 'app'
// (spring.application.name, port, module) and 'endpoint' (method, path, app, handler, request and response types, ADR-38), consumes are 'package'
// (with scope) and 'http' (client kind, name, app or address with profiles, calls); instead of `stack`
// and `runtime` there are build files, tools, mechanisms and problems.
interface RepoCard {
  commit: string;
  buildFiles: BuildFile[];   // { path, tool: 'maven'|'gradle'|'npm'|'pnpm'|'yarn'|'bun', name, memberOf }
  provides: Provided[];   // { kind: 'http'|'topic'|'package', key, evidence }
  consumes: Consumed[];   // { kind: 'http'|'topic'|'package'|'env-url', key, evidence }
  dtos: Dto[];            // { name, kind: 'record'|'data-class'|'class'|'enum', fields: { name, type }[], values, evidence } (ADR-38)
  tools: ToolRequirement[];   // { tool, version, source: 'mise'|'hint', evidence }
  mise: MiseSetup;            // { configFiles, tasks: { name, evidence }[] }: mise configuration and tasks from the commit (ADR-34)
  mechanisms: Mechanism[];    // { id: MechanismId, evidence: (Evidence & { detail })[] }
  problems: CardProblem[];    // { path, message }: a file the extractor did not read
  runtime: { ports: number[]; databases: string[]; secretNames: string[] };   // plan: from application*.yml
  description?: { text: string; origin: 'llm'; model: string; at: string };
}

interface RepoTag { name: string; reason: string }   // from the card and from the `repoTags` rules in workspace.yaml

// Today in protocol (graph.ts, ADR-29, ADR-30): GraphEdge between repos (RepoId), kind 'package' | 'http' | 'manual',
// EdgeEvidence with a repo (or null for workspace.yaml) and a `detail` sentence.
interface Edge { from: ServiceId; to: ServiceId; kind: Consumed['kind']; key: string;
                 confidence: 'exact' | 'high' | 'medium' | 'low'; evidence: Evidence[] }

// Today in protocol (services.ts, ADR-45): Service { repo, state, port, portSource ('card' | 'log'), run (RunState
// of the task dev), since, reason }, one per repo, in memory; no groupId, lease or lastStderr (errors come from logs).
interface Service {
  id: ServiceId; repo: RepoId; port?: number;
  state: 'stopped'|'starting'|'healthy'|'unhealthy'|'stopping'|'crashed';
  groupId?: string; exitCode?: number; lastStderr?: string;
  lease: Lease;
}

interface Lease { service: ServiceId; holder: { kind: 'main' } | { kind: 'task'; taskId: TaskId };
                  worktree: string; since: string }

// Today in code: `RuntimeGroup` in runtime.json (owner as a text key) and `RunState` in protocol (§4.1).
interface ProcessGroup { id: string; leaderPid: number; command: string[]; cwd: string;
                         startedAt: string; owner: { kind: 'service'|'task'|'run'; id: string } }

// Today in protocol: LogRecord without source and ECS fields, LogSource = { kind: 'mise-task'; repo; miseTask } (§4.2, ADR-28).
interface LogRecord { seq: number; ts: string; source: LogSource; stream: 'stdout'|'stderr'|'pty';
                      level: 'trace'|'debug'|'info'|'warn'|'error'; msg: string;
                      traceId?: string; spanId?: string; fields?: Record<string, unknown>; raw: string }

// Today in protocol (agents.ts, ADR-31, ADR-39): Task with prompt, branch, baseBranch, base (base commit), worktree,
// createdAt, title and proposedBy (from a task proposal) and summary ({ text, reportedAt } from report_result); a session points
// to its task (Session.task); without adapter, budget, leases, changedPaths and recording, and the task state is its session's state.
interface Task {
  id: TaskId; title: string; repo: RepoId; branch: string; worktree: string;
  adapter: 'copilot' | 'claude' | 'codex'; prompt: string;
  state: 'Working'|'Input'|'Approval'|'Plan'|'Done'|'Error'|'Stale';
  stateSource: 'hook'|'osc'|'screen'|'keyboard'|'timeout'|'exit'; stateConfidence: 'exact'|'high'|'medium'|'low';
  stateSince: string;   // TaskState, TaskStateChange: packages/protocol/src/task-state.ts
  budget: { maxMinutes?: number; maxCommits?: number };
  leases: ServiceId[]; changedPaths: string[]; recording: string;
  summary?: string;   // the summary block from the completion protocol
}

interface AuditEntry { id: number; at: string; client: string; tool: string;
                       args: unknown; durationMs: number; ok: boolean; resultDigest: string }
```

Persistence: SQLite (`~/.trackwall/trackwall.db`) for repos, cards (today files `cards/<commit>.json`, ADR-25), edges (a cache; today the daemon keeps only the last graph with its input key in memory, ADR-29, ADR-30), services, leases, tasks, audit; JSONL for logs; session recordings as files; `runtime.json` only for live process groups. The workspace configuration is `workspace.yaml` (projects folder, repo hosts, repo tag rules, package aliases and manual graph edges, port overrides, the pointer to the secrets repo), which the user can keep in a private repo; until a workspace directory is chosen it lives in the daemon's state directory (ADR-12). State never mixes with configuration.

## 7. Flows

**App start.** Tauri → sidecar → `daemon.json` → `/api/health` → the UI fetches the views' data with HTTP actions and opens `/ws`, from which it gets the event topic snapshots (ADR-36). At startup the daemon: cleans up orphans according to `runtime.json`, restores the task list and offers to resume agent sessions (the resume command from the adapter).

**`ws sync`.** For every repo in parallel (with a concurrency limit): fetch, fast-forward of the default branch, if `head` ≠ `analysis.commit` then dependencies (`mise run setup`) and the card extractors; after all of them, recomputing the graph and a `graph.updated` event (once the graph gets a cache; today it is computed on every request, ADR-29). A repo in which a fast-forward would touch local changes (uncommitted changes in the checked-out default branch, a diverged branch or unpushed commits) is skipped with a warning; changes on another branch do not get in the way (ADR-21). Done (ADR-21, §4.5): fetch and fast-forward from a button in the UI, with a skip reason per repo. The Batch command gives dependencies with the `mise install`, `setup` and `build` steps on selected repos (ADR-27, §4.8), for now always, not only on a new `head`; extractors, the graph and the CLI command will come together with those modules.

**Starting a service.** Today (ADR-45, §4.3): UI or `start_service` → `services.start {repo, dependencies}` → plan from the graph's `http` and `manual` edges → waves from the dependencies: `mise.tasks` (is there `dev`?) → `server.port` from the card free → `mise.start(repo, 'dev')` through `procs` → observed: log (port, `Started`) and a TCP connection → `healthy`, `unhealthy` or `crashed` with errors from its log → next wave → `call_endpoint` to the port that answered, with errors from every `dev` log. Eventually: UI → `services.start(id)` → `leases.check` → `secrets.resolve(repo)` (git show of the `Secret` manifest from the `origin/<repo>` branch, keys from `data` decoded from base64, from `stringData` taken as they are, into env) → `mise.run('dev')` through `procs.spawn` in a group → `logs` registers the source and masks → the `mise run health` probe periodically → `service.state`. Failure: `crashed` with the code and the last stderr line on the service row, without restarting in a loop (at most three attempts, then giving up).

**Agent task.** Today (ADR-31, §4.4): UI → `create-task {repo, prompt}` → `vcs.addWorktree` from the default branch → `tasks.json` → a Copilot CLI session in the worktree with `--interactive=<prompt>` → the "Changes" tab polls `task-changes` → after the session ends, resume (`--resume`) or `remove-task` (worktree, optionally the branch). While the task runs, its panel also asks `task-shared-files` for the shared-files warning (ADR-44). From a main session (ADR-39): session → `propose_task` → a proposal in the "Sessions" view → the user reads the prompt, edits it and clicks "Start task" (`approve-proposal`) → the same as `create-task`, with the proposal's identifier → the task session works and calls `report_result` → the main session gets the result from `wait_for_session` and reads the changes through `get_session`. Eventually: the UI creates a task (repo, prompt, adapter, budget) → `vcs.worktree.add` → the prompt written to a file → the adapter builds the command and the MCP configuration (the `/mcp` address, a session token) → `procs.spawnPty` → state detectors → a `sessions.changed` event with the session snapshot (ADR-36) → tray and "jump to the waiting one". When the agent changes a service, it asks for the lease (`Approval` in the UI, or automatically depending on a setting). Ending: the summary block → `summary`, a PR proposal, leases given back, recording closed.

**A cross-repo error.** The user sees an error in the FE → clicks a record with a `trace_id` → `trace(trace_id)` returns the records from the BFF and the services in `seq` order → a timeline view per service → "create a task with this context" pastes the service identifiers and the `seq` range into the prompt, and the agent pulls in the details itself through MCP.

## 8. Security

- Loopback only, a token, the `Host`/`Origin` check, constant-time comparison.
- The session token (ADR-39) next to the daemon token: the daemon knows which session calls MCP, so `report_result` writes only to its own task, and the call goes to the log with the session, and `run_mise_task` and `stop_mise_task` work only in the session's repo (ADR-41); later it will write the session into the audit. The token lies in the session directory in the state directory (a file with user-only permissions on macOS and Linux), not in the bridge's arguments, because other users of the system can see process arguments; the daemon keeps only its hash. A process running as the same user can read another session's token (like `daemon.json`), so the token says who is calling but does not protect against a user process; it also grants no permission the daemon token does not have.
- A process's working directory is always inside a repo or worktree; paths from input are normalised and checked for escaping the root. Repo browsing reads only objects from the HEAD commit, and the `RepoPath` schema validates the path in the repo (no `.`, `..`, empty segments and control characters; `\` is an ordinary name character).
- The daemon runs `git` in every subdirectory of the projects folder that has `.git` (ADR-18), so the list also gets a repo the user did not knowingly choose (for example an unpacked archive). The repo configuration (`.git/config`) applies as in a terminal, except for keys with which the repo would make git run a program: the daemon disables `core.fsmonitor` (`git status`) and `log.showSignature` (`git log` would call `gpg.program`). Repo browsing and status commands (`status`, `log`, `ls-tree`, `cat-file`) run no hooks and no `textconv` (sync does, below), but `git status` can run a `clean` filter (for example git-lfs) defined in `.git/config` for paths from `.gitattributes`: a gap we leave, because disabling filters would break the status of LFS repos; only an allowlist of filters or asking the user for trust at the first repo will close it. A new git command in the daemon must check this again.
- Cloning from a host (ADR-19) runs `glab` or `gh` with the full repo name from the UI request. The `RemoteRepoName` schema validates the name (segments do not start with `-` or `.`), so it will not be taken for a program option or produce a directory outside the projects folder; the host must be in `workspace.yaml`. The host's token stays in `glab` and `gh`. The API response is external data: parsed with a schema, and an error does not contain its content. A cloned repo is subject to the same rules as every repo in the folder (the `clean` filter gap above). Gap: `glab`/`gh` and the clone's git are not in a process group, so a clone interrupted by the time limit or by daemon exit may keep running in the background until git finishes by itself (§4.5).
- A mise task is a program from the repo configuration: running it from the UI is the user's consent to executing the repo's code, like `mise run` in a terminal. The daemon runs only a task from the current `mise tasks ls` list, in the repo root, without a shell on the daemon side; mise refuses to give the list itself for configuration without trust. `mise trust` (the `trust` action) is only in the UI and applies only to the configuration in the repo root; MCP has no tool that would trust. On macOS the daemon runs the user's interactive login shell once (`$SHELL -ilc`) to learn the `PATH`, so it executes their shell startup files, like every new terminal.
- The Batch command (ADR-27, §4.8) runs `mise install` and the `setup` and `build` tasks with one click in every selected repo, by default in all of them from the projects folder, including one the user did not knowingly choose (ADR-18). Choosing repos and steps in the UI is consent, like running a task from the repo details. Tasks come only from the `mise tasks ls` list, which mise does not give without trust. Gap: `mise install` does not ask for trust when the repo configuration has only `[tools]` (checked on mise 2026.10.18: `mise trust --show` says `untrusted`, and the installation goes ahead), so it downloads and runs the installer of a tool the repo names (for example an asdf plugin with an address from `mise.toml`), like `mise install` in a terminal. Requiring `mise trust` before the `tools` step, or an allowlist of tool backends in the settings, will close it.
- Cleaning up orphans trusts `runtime.json` in the state directory; a user process that writes someone else's PID there could kill that process itself anyway. A group whose leader is dead is killed without checking the start time: the exception would be a new process with the same PID that created its own POSIX session and then ended, leaving descendants in it.
- Under Node on Windows (the compatibility mode, ADR-20) a group is a tree with `taskkill /T`: an empty group means only "the leader is dead", a descendant orphaned by an earlier death of its parent falls out of the tree and survives the stop, and after the daemon is killed hard nothing is cleaned up (a live PID from `runtime.json` only goes to the log). The release is a Bun binary with Job Objects, so the gap concerns running from source under Node.
- Short queries to `mise` (`tasks ls`, `trust`) go outside `procs`, like `git`: after the limit the daemon ends `mise` itself, and a program mise started from the `[env]` of a trusted configuration may survive.
- Sync (ADR-21) runs `git fetch` and `git merge --ff-only` in every repo from the projects folder, including one the user did not knowingly choose (ADR-18). Gap: fetch runs programs named in the repo's local `.git/config` (`core.sshCommand`, `remote.<name>.uploadpack`, `credential.helper`), and `merge` the repo's hooks (`post-merge`, `reference-transaction`) and `smudge` filters (for example git-lfs), like `git pull` in a terminal. It is the same class of gap as the `clean` filter above, but wider, because it also covers keys the daemon does not disable; we leave it, because disabling credential helpers, ssh and LFS would break syncing ordinary repos. Only reading these keys from the user and system configuration alone, or asking for trust at the first repo, will close it. The remote name from `.git/config` goes to git after `--`, so it will not be taken for an option. The remote address on the list contains no user or token from the URL, and `transport::` (with a command) does not reach the list at all. Gap: the sync's git is not in a process group, so when interrupted by the time limit or daemon exit it may keep running in the background (like a clone, §4.5).
- The repo card (ADR-25) reads files from a repo the user may not have chosen (ADR-18), so their content is untrusted: git reads objects (`ls-tree`, `cat-file --batch`) without filters, textconv and hooks, and paths from the tree go to `cat-file` through stdin, not as arguments. Extractors execute nothing (a Gradle script is read as text), the XML parser knows no DTDs or external entities, and the limits (1 MB per file, 2000 build and configuration files, 3000 source files, 3000 type files pulled in for endpoint contracts, 64 MB in total, 64 MB of file list, 4096 characters of a value after substituting Maven properties) bound the memory per repo. Time too: the extractors' expressions have no adjacent `\s*` or classes that give quadratic backtracking on a long line (the wrapper address matched only in the file name, `${` without nesting), Gradle lines over 2000 characters and paths over 1024 characters in the mechanism inventory are skipped, key lines (evidence for npm dependencies and mise tools) are computed in one pass over the file, workspace globs from the repo are matched by dynamic programming (pattern × path), and build roots check only a file's ancestors; `cards-limits.test.ts` keeps each of these cases under 1–2 s. A key from the repo does not reach the object prototype (`version.ref = "constructor"`). Knowingly left: the `k8s/…/*.yaml` pattern in the mechanism inventory is quadratic in the path length, but a path has at most 1024 characters (a fraction of a millisecond per file), and the Gradle scanner does not treat `\` as an escape in triple quotes (right for Kotlin; in Groovy it shows at most a few more lines, it never hides a line). The facts on a card are text from the repo: the UI shows them as text, and the agent gets them through MCP as data that may contain an attempted prompt injection (like the README from `get_repo`). A card file in the state directory is named only by the commit hash checked against a pattern and is parsed with a schema on read.
- Java and Kotlin code, Spring configuration and frontend files (ADR-30) are as untrusted as build files: nothing is compiled or executed (a Vite or webpack configuration is text), `git grep` gets a fixed expression from the daemon and paths from the tree do not reach the arguments, and source files have the same read limits (3000 files, 4 MB of list). The tokenizer and the declaration parser go through a file once, a stack counts nested brackets, and concatenating constants has a depth limit (8) and a length limit (2048 characters); `${…}` in configuration expands with memoisation, a depth limit (10) and a length limit (4096), so neither a cycle nor keys that double each other take memory; YAML has a depth limit (64), and proxy configuration lines over 2000 characters are skipped. Bracket pairs are computed once per file, an unclosed bracket does not drag an expression to the end of the file, and of a call's argument list longer than 256 tokens only the arguments that fit within the limit as a whole are taken (the address and method come first). YAML is read without checking for repeated keys (the library compares each with each), a file has at most 20,000 entries across all documents, a module at most 32 profiles (more is a card problem), and in each profile only keys with an address or `${…}` are expanded. An error or time limit of `git grep` is a card problem, it does not take the card away (the card stays without facts from code). The number of facts is bounded too (20 endpoints per method, 200 calls per client, 2000 `.uri(…)` and `RestTemplate` calls taken apart per file, 500 addresses from configuration per module, and beyond that last limit a card problem). `.env*` files are read from the whole commit (choosing a file knows only its path), but only variables with an HTTP address from files next to `package.json` reach the card, without the user, password and query; the other values stay in daemon memory while the card is computed. Addresses on the card lose the user and password (up to the last `@` before the path, and when there is no host with a port before the first `/`, up to the last `@` before the query, because a password may contain `/`; a part before the path that is still not a host with a port disappears entirely), the query, the fragment and path segments that look like a token (20+ characters with letters and digits, for example a webhook key), and call paths lose their query, because an address from `.env` or `application.yml` may carry a password or an API key, and the card goes to the UI and to the agent. Matching calls to endpoints in the graph compares a call only with endpoints with the same number of segments that have its rarest fixed segment (or a variable) at the same position (and with `**`), so thousands of endpoints in a few dozen repos are computed in a fraction of a second; `cards-limits.test.ts` keeps these cases under 1–2 s.
- The tree-sitter parser (ADR-37) gets the code from the repo unchanged: it runs in WASM memory without access to files and the network, but synchronously in the daemon's thread, and the Kotlin grammar grows in time faster than linearly on malicious input. That is why every parse has a time limit (`PARSE_TIME_LIMIT_MS`, 1 s), after which it is aborted and the file has no tree, and the whole card a total budget of 10 s (ADR-38), after which it parses nothing more. Gap: the first computation of the card of such a repo can stall the daemon API for about 11 s (the budget and the time of the last file: parsing up to 1 s and reading the tree; once per commit, and once more after a daemon restart, because such a card does not go to disk); parsing in a worker thread would close it.
- The connection graph (ADR-29) reads nothing from the repo beyond the card: the edges from cards carry the same untrusted strings (package names, paths; a package name does not reach the object prototype), and the `graph` entries come from the user's `workspace.yaml`. No MCP tool changes them; `who_calls` and `subgraph_for` only read the graph, `subgraph_for` has a bounded depth (3) so that the result does not grow to the whole graph, and `find_endpoint` a bounded number of results (50) and query length (300 characters).
- The secrets repo is cloned outside the workspace, in a directory invisible to worktrees; in a task's profile the secrets repo is excluded from the agent's file tools (adapter configuration).
- Environment variables never reach logs or the audit; values are masked before the buffer (§4.2). Gap: the daemon masks only the values of variables with secret names from the environment it starts the process with itself. A secret the process gets otherwise (from the `[env]` of a mise configuration, from a `.env` file, from a password manager), or one with a name outside the list, reaches the log in the UI, the JSONL file in the state directory and the agent through the MCP tool `tail` in plain text, as it reaches the terminal. The `secrets` module, which knows the values it injects itself, will close this; reading `[env]` from mise (`mise env --json`) is a possible addition. Log files lie in the state directory with user permissions, like the rest of the state. Known edge cases of masking: a secret cut by an ANSI sequence in the process output, a line of a multi-line key shorter than 8 characters (for example the last base64 line of a PEM key), and an unterminated line longer than 64 KB made entirely of overlapping occurrences of secrets (then the split falls at the end).
- The session terminal (ADR-26) accepts any keys from the UI: the only exception to the rule of identifiers instead of commands (§1.2), like the terminal in VS Code. The daemon starts the session with a command it builds itself (a program from the user's `PATH` and the plugin directory), in the root of a repo from the projects folder. The terminal and event WebSockets have the same protections as HTTP, with the token in the subprotocol (`api/sockets.ts`). Copilot CLI gets the user's environment (`userEnv`), as in their terminal; the session screen goes neither to logs nor to MCP, only to the user's window, so only the last lines of the session state are masked (`logs.lastLinesOnly`, §4.2). The plugin's hook is the daemon binary run by Copilot CLI from the plugin directory (not the repo), which only appends a record to the session file, without the daemon token. The `vite dev` proxy adds the token also to a terminal connection without an `Origin` header, so in development mode any local process gets the session terminal and the `/ws` events through Vite, as it gets `/api` today; the release has no such proxy. Gap: Copilot CLI started from a PTY can itself start programs outside the process group if they create their own POSIX session (`setsid`) or leave the job with `BREAKAWAY_OK`; such processes survive a session stop.
- A task's state from hooks and OSC comes from the session's process, so the session can forge it (append a record to `hooks.jsonl`, print OSC 9;4). The state is only information for a human and gives the session no permission; it is to stay that way. A hook record stores only the fields on the list (without the prompt, tool arguments and results), and the hook payload is parsed with a schema like every input from outside. Exceptions to remember with fixtures: the trimmed notification text (it may contain the command or full path the agent asks about) and the window title in `states.jsonl` (a description of the current work), and a `.cast` recording has the whole session screen (from the keyboard only the kind of session key, without content). The state from session keys comes from the terminal window through `/ws/pty/<session>`, but the session's process runs as the same user, can read the token from `daemon.json` and send a key over the same WebSocket, so it can forge this state too, like hooks and OSC.
- A task (ADR-31) passes the user's prompt from the UI to Copilot CLI as one argument `--interactive=<prompt>`, without a shell: the prompt is content, not a command, and the `=` form does not let it become an option. The daemon builds the branch and the worktree directory from the prompt only from `[a-z0-9-]` characters. `git worktree add` fills the working directory like `git checkout` in a terminal: it runs the repo's filters (`smudge`, LFS) and `post-checkout` hook; the same consent to the repo's code as an agent session in it. `tasks.json` lies in the state directory and can be changed by hand, and ending a task deletes the worktree with `--force` and the branch with `branch -D`, so the worktree directory is not in the file (the daemon computes it in `worktrees/`), and the read accepts only a `trackwall/[a-z0-9-]` branch and a full base commit hash, which goes to `git diff`. Task changes are computed by `git diff` without external diff programs and `textconv` from the repo configuration; the working directory diff runs the `clean` filter, like `git status` (the `clean` filter gap above). The same applies to the "Changes" tab of a repo from the projects folder (ADR-34), including a repo the user did not knowingly choose.
- Sessions in MCP (ADR-36): every session with the Trackwall MCP server sees all sessions and tasks through `list_sessions` and `get_session`, with the task prompts and window titles; these are the user's prompts in their own daemon, and the tools only read. The session screen and the last lines of an ended group (`run.lastLines`) do not reach MCP: the last lines are masked only with the values of secrets from the process environment (§4.2), and the agent also prints in the terminal what it read from files (`.env`) or got in the prompt, so a secret printed in one session's terminal does not pass to another. Gap: the window title (`windowTitle`, from OSC 0 / 2) goes to MCP without masking; Copilot CLI writes a description of the current work there, but the session's process can print any text there. The session token (above) will later make it possible to narrow what a session sees; today each sees everything, including task proposals.
- Task proposals and summaries (ADR-39) are text from an agent that may have read untrusted content from repos (READMEs, code, task output), so they carry the same class of prompt injection as tool results: a proposal's prompt will reach another session as its first message, and a summary will reach the session that is waiting. A human is the gate: a proposal starts nothing, the UI shows the whole prompt to read and edit before "Start task", and a task from it has the same boundaries as a task from the form (a worktree in the state directory, a command built by the daemon, the prompt as the content of `--interactive=`). Automatic approval, if it ever exists, will only be a setting in the UI, never an MCP tool. The UI shows the prompt, title and summary as text, and the MCP tools reject characters in them that a human will not see but a model will read (`visibleText`: format characters, with hidden tag characters U+E0000–E007F and direction changes, private-use characters, line separators; not unassigned ones, because their list depends on the engine's Unicode tables); at the cost that emoji joined with U+200D will not pass in proposals. The limits (20 waiting proposals, 80 characters of title, 8000 of prompt, 4000 of summary, 55 s of waiting in one call) bound how much daemon memory and time a session in a loop takes. Gaps: a session can propose endlessly after every decision, and the list does not say how many proposals this session has already made. Approval in the UI is a gate for an agent that uses the MCP tools, not a security boundary: the session's process runs as the same user, can read the token from `daemon.json` and call `approve-proposal` or `create-task` itself through the HTTP API, just as it can start any process without Trackwall. Only a separate UI token the session processes cannot read will close this.
- The README in the UI (ADR-35) is content from the repo: HTML goes through sanitisation with GitHub's schema, a Mermaid diagram is rendered in `strict` mode, images do not load, and a link opens outside the window only as `http` or `https` in canonical form. `workspace/open-link` makes the system open such an address; whoever has the daemon token can do it without a click, like `open-editor`. Gap: the daemon sends no CSP header with the UI files, so in browser mode (`--ui`) an image from the internet in a Mermaid diagram label (`strict` mode lets `<img>` through) will load; in the Tauri window CSP blocks it. The Tauri window also has no navigation guard (`on_navigation`), so the protection against a link from a README is only intercepting the click in the UI; the WebView context menu ("open in new window") remains to be checked manually.
- mise tasks through MCP (ADR-41): `run_mise_task` runs code from the repo's mise configuration, like the button in the UI and like `mise run` in the agent's terminal. Boundaries: a task only from the current `mise tasks ls` list (mise does not give it for configuration without trust, and trust can be given only in the UI), the command built by the daemon from the name (§1.2), in the repo root through `procs`, a Trackwall session only in the repo it works in, a line in the daemon log with the repo, task and session before the start, and `destructiveHint` (also on `stop_mise_task`), so that the MCP client asks for approval as for a shell command (Copilot CLI asks about every MCP tool until the user allows all of them). The task's output comes back to the agent through `tail` with masking and the gap with secrets from `[env]` (above), and `lastLines` in `run` is masked the same way. Gaps: mise trusts the configuration's path, not its content, so an agent that can change a trusted `mise.toml` or a task file in the repo root (a session in the repo root, the supervising agent) can run any command through `run_mise_task`; it is the same consent the MCP client gives anyway for writing a file and for a shell command, but consent to the MCP tool alone does not show the task's content. mise's `paranoid` mode (trust in a content hash) or running only tasks from the commit (the repo card knows them from `RepoCard.mise`) will close it. A task session works in a worktree, and `run_mise_task` in the root of a repo from the projects folder, so it runs code from the branch the repo is on, not from the task's branch. Calls go only to the daemon log, because there is no `audit` table. Limiting a session to its repo works only for calls from its bridge (with the session token): the session's process can read the daemon token from `daemon.json` itself and call `/mcp` without a session token, like an agent outside Trackwall, so it is a gate for an agent, not a security boundary (like approving proposals, ADR-39).
- Services over MCP (ADR-45): `start_service` runs the same task `dev` from the trusted config as `run_mise_task`, also in the repos the service calls; which repos comes from the graph (cards and `workspace.yaml`), not from the agent, and a Trackwall session names only its own repo. A repo can thus get its dependencies started because its code or config names them; they are repos from the user's projects folder, with a config the user trusted. `call_endpoint` sends the agent's method, path, headers and body only to `127.0.0.1` or `::1` and only to the port that answered the probe of a service Trackwall started, so it is not a proxy to other hosts or to other local programs; within that it can change data (a `DELETE` reaches the service's database), hence `destructiveHint`. Unlike start and stop, a Trackwall session may call the service of any repo: checking a change end to end means calling the services behind its own, and these are the user's local dev services, which the session could reach with `curl` anyway. The response is masked with the secret values of the service environment, as its log; a secret the service returns from elsewhere (its own config, a database) reaches the agent, as it would with `curl` in the agent's terminal. The path, headers and body do not go to the daemon log (`auditArgs`). Gap: a port that answers is assumed to be the service's own; a process Trackwall did not start that takes the logged port after the start (`portOwner`, §4.1, is not done) would get the requests.
- Folder picker, Show in Explorer/Finder and drag and drop (ADR-51): `dropped-folder` reads any full path the UI sends (a `stat` and the folder's entries) and answers what it is, which tells a token holder no more than `set-projects-dir` already does; it saves nothing. `open-folder` takes only a repo id, so the system opens a path from the list, never one from the request. A path dropped on a session goes into its terminal as pasted text, the same as the user typing it. The window still gets no plugin commands: the picker is the app's own `pick_projects_folder` command. The dialog plugin also replaces `window.alert` and `window.confirm` in every page with calls to its `message` command, which the capability does not grant: `alert` would fail and `confirm` would return a Promise, which is always truthy, so Biome bans both globals in `packages/ui/src` and the test `apps/desktop/test/ui-dialogs.test.ts` also catches calls through `window` and `globalThis`.
- The shell on Windows writes two registry values at every start (`HKCU\Software\Classes\AppUserModelId\<app identifier>`, `DisplayName` and `IconUri`, ADR-50) and the icon file `notification-icon.png` in the state directory, and never removes the registry key, so a portable build deleted with its folder leaves it behind (the portable `README.txt` says so). A notification for a task proposal shows its title, which is agent text (ADR-39), as plain text. The tray panel window has the same capability as the main window (`core:default` and the app's commands); `open_from_tray_panel` only shows windows and passes the target on to the UI, which parses it with a schema. The global shortcut is registered from Rust, and the UI has no permission of the shortcut plugin.
- `trackwall://` links (ADR-52) can come from anywhere: a web page, a chat, an agent's answer. A link only switches the view in the window: the shell turns only `repo`, `session` or `task` with one id of safe characters into a jump, the UI parses the id with the protocol schemas, and no link starts, stops, approves or changes anything. Gap: a page the user has allowed to open `trackwall://` links without asking can raise the window and switch views as often as it likes; a jump to a repo also resets the "Repos" view. A link to a session or repo that no longer exists shows the first entry of the list instead, without a message. Registering the scheme on Windows writes the current user's `HKCU\Software\Classes\trackwall`; a moved or deleted portable folder leaves a key that points nowhere until the next start.
- Autostart and "connect an agent" only from the UI; the agent has no tool for changing the daemon configuration.
- The MCP server (ADR-24) accepts the daemon token, and Trackwall sessions add a session token (ADR-39): the supervising agent is the user's program, and the tools read, store a proposal and a summary, or run and stop mise tasks (ADR-41). The stdio bridge takes the token from `daemon.json`, so it does not reach the Copilot CLI configuration; a user process can read this file anyway, as the UI can. A task proposal becomes a task only after the user clicks in the UI, and only `run_mise_task` starts processes (above). Content from repos in tool results (READMEs, commit subjects, mise task descriptions, task output in `tail`, code lines from `search_code`) is external data for the agent too: a repo can slip the agent instructions this way (prompt injection); Trackwall does not filter it. `search_code` (ADR-40) returns any committed text from every repo in the projects folder, including secrets someone committed (`.env`, keys, passwords in `application.yml`), and to every session with the Trackwall MCP server, not only the one working in that repo; Trackwall does not mask them (the masks from §4.2 cover only values from process environments). The pattern and pathspecs from the agent reach git only as arguments after `-e` and `--`, without a shell; a pathological regular expression keeps git busy for at most 30 s per repo, and the whole search starts no new repo after 60 s, but a running `git grep` is not stopped when the MCP client gives up. `get_repo` asks mise for the task list just like the tab in the UI, so in a trusted configuration mise evaluates `[env]` while doing it (§4.7); it does not read configuration without trust, and trust can be given only in the UI.
- The daemon binary reads neither `.env` nor `bunfig.toml` from the current directory (`--no-compile-autoload-dotenv`, `--no-compile-autoload-bunfig` in `scripts/build.ts`), because the MCP bridge starts in the agent's directory, that is in the user's repo; from source under Bun, `--no-env-file` and `--config` with the daemon package's empty `bunfig.toml` in `mcpStdioCommand` do the same.
- If database tools ever appear: a role without superuser and a read-only transaction.
- Vulnerabilities are reported privately as described in `SECURITY.md` (GitHub Security Advisories).

## 9. Windows: risks and how we check them early

| Risk | What can go wrong | How we check |
|---|---|---|
| Job Objects with Bun/Node | no native API; needs N-API or `koffi`; a child process already in another job (for example started from the VS Code terminal) cannot be added without `JOB_OBJECT_LIMIT_BREAKAWAY_OK`; under Node (without FFI) a group is a tree with `taskkill /T`, from which a descendant falls out after its parent dies, and orphans after a hard kill of the daemon remain | settled in stage 1 (ADR-1, ADR-20): the `procs` module with a test that stops the whole group together with grandchildren (`procs.test.ts`); in the compiled binary only by hand before a release (gap in ADR-1) |
| ConPTY + `node-pty` in Bun | a native addon may not work under Bun; `bun build --compile` does not embed `.node` | settled in stage 1 (ADR-1, ADR-26: `Bun.spawn({ terminal })`); in the compiled binary only by hand before a release (gap in ADR-1); plan B: Node 22 + SEA, plan C: PTY on the Rust side in Tauri (`portable-pty`) with a bridge to the daemon |
| Gentle stop on Windows | no SIGTERM; `GenerateConsoleCtrlEvent` needs a shared console; `taskkill` reports success with the process still alive | a stop is always confirmed by observation; for Spring Boot additionally `POST /actuator/shutdown`, if enabled |
| Detecting Copilot CLI state | hooks from `--plugin-dir` do not start on Windows (the `exec` path, AppData), ConPTY loses or reorders OSC 9;4; the ConPTY screen differs from Unix; `Bun.spawn({ terminal })` is described in the Bun documentation as POSIX only, although the stage 1 spike passed on Windows (ADR-1) | stage 2 (ADR-17): `copilot-record.ts` on a real Windows and macOS following the list in the PR description; screen patterns only from recordings, if hooks, OSC and session keys are not enough (the first one, "Operation cancelled by user", comes from recordings on macOS and Windows). Sessions in the daemon (ADR-26): the `agents.test.ts` test with a real PTY and a fake Copilot CLI in the CI matrix, on a real Windows the list of manual tests in the PR description |
| Portable exe | WebView2 may not be installed; SmartScreen blocks an unsigned file; auto-update must replace a running file | stage 1: build with `tauri.conf` → bundle `none` + a WebView2 check at startup; a test on a real Windows; signing with Azure Trusted Signing before publication |
| Long paths and file locks | a task's worktree in `worktrees/<repo>/<branch>` of the state directory (branch shortened to 32 characters, ADR-31) lengthens the paths of the repo's files and can exceed 260 characters; `git worktree remove` does not delete files held by a process | `\\?\` and `core.longpaths` (the daemon calls git with `-c core.longpaths=true` on Windows); ending a task only without a running session, that is after a confirmed stop of the group, and the daemon deletes the directory left by an interrupted `worktree remove` itself after confirmation |
| Port → owner | `netstat`/`Get-NetTCPConnection` are slow; a PID without a tree | `GetExtendedTcpTable` through N-API, the tree from `runtime.json` and the Job Object |
| Antivirus / EDR | random slowdowns, the daemon quarantined | portable without UPX packing, an early test on a real Windows |

## 10. Tests and CI

- `procs` and `logs`: integration tests that start real child processes (a script that starts a grandchild and ignores a gentle stop), on both systems in the CI matrix (every PR, ADR-22).
- `cards`: extractors, tags and mechanisms tested on in-memory commit snapshots (small `pom.xml`, Gradle scripts, `package.json`, `mise.toml`) without git and network; the module with commit reading and the card store on a real git repo in a temporary directory.
- `agents`: sessions tested with a real PTY, a process group, the daemon's `copilot-hook` subcommand and an interactive fake Copilot CLI (`test/fixtures/fake-copilot-session.ts`), tasks likewise on real git (a clone from `origin/HEAD`, `tasks.test.ts`), also through the terminal WebSocket (`pty-socket.test.ts`); state detectors tested on `.cast` recordings replayed by `replayCopilotRecording`; recordings of real Copilot CLI sessions go into the repo as fixtures only after anonymisation. Until then the fixture is synthetic (`test/fixtures/copilot/`, marked in the recording title), and the full path (PTY, session plugin, hook processes, recording) is checked by the test with the fake Copilot CLI.
- `api`/`mcp`: the contract from `packages/protocol`, tests through a real MCP SDK client (`@modelcontextprotocol/client`): through Streamable HTTP in both revisions, through the bridge in the same process and through the bridge command from `/api/daemon/info` with the daemon process under Bun and under Node; the binary smoke test (`scripts/smoke.ts`) does `initialize` through `mcp-stdio`.
- CI (ADR-22): every PR and push to `main` goes in parallel through lint, `cargo fmt`, typecheck, tests and the documentation site build (ADR-56) on `ubuntu-latest`, the dependency audit, the `test` job (tests) and the `desktop` job (daemon build as a binary and Tauri → clippy → `cargo test` → sidecar smoke test → portable → artifacts) on `windows-latest` and `macos-latest`. The aggregate `CI ok` job is green only when all the others are green; it is meant to be the only required check in the protection of `main`, which the repo owner sets. A vulnerability without a fixed version goes into `auditConfig` in `pnpm-workspace.yaml` (`pnpm audit --ignore`) with a justification, so that it does not block every PR. CI also runs on documentation-only changes, because the required check must report on every PR. A new push to a PR branch cancels its previous run, and every `main` commit has its own run that nothing cancels. Manual runs remain for branches without a PR. A release from a tag (`release.yml`): the GitHub Release is created only after both builds pass, described in `docs/release.md`.

## 12. Decisions (ADRs in brief)

**ADR-1 Daemon runtime: Bun, keeping compatibility with Node.** Bun gives `bun build --compile` into one binary and built-in SQLite. The code is written so that it also runs under Node 22 (`node:` APIs, no Bun-specific APIs outside the `platform/` layer). If the stage 1 spike shows that ConPTY or Job Objects do not work under Bun, we move to Node 22 + SEA without changes to the modules. Addendum (2026-10-23): compatibility with Node is guarded by a tool, because without one it drifted (a constructor parameter property in `api/guard.ts` blocked the start under Node). The daemon and `protocol` have `erasableSyntaxOnly` and required extensions in imports, Biome rejects Bun APIs outside `platform/`, and the daemon process tests run under Bun and under Node with the flags from the `start:node` script (Node 22.12+ runs the source code without compilation). Result of the stage 1 spikes (Bun 1.4.2, Windows x64, macOS arm64, Linux, also in a binary built with `--compile` moved outside the repo): Job Objects through `bun:ffi` work on Windows, a process group (`setsid` + `kill(-pgid)`) on macOS; PTYs come from `bun-pty` and `Bun.spawn({ terminal })` (ConPTY on Windows), while `node-pty` does not work under Bun and does not load `.node` in `--compile`. ADR-1 is therefore confirmed. The spike code (`spikes/job-objects`, `spikes/conpty`) was removed from the repo and from CI on 2026-10-24, because the answer is here, and their solutions live in the daemon's `platform/` and its tests on Windows and macOS; the code is in git history (last in `9e1c1bd`). Deliberate gap: the spikes also ran the Job Object and the PTY in the compiled binary. The daemon tests do it from source, and the binary smoke test (`scripts/smoke.ts`) checks only the start, `/api/health`, `/api/daemon/info`, MCP and the stop, so a Bun version change that breaks FFI or PTY only in `--compile` is caught only by the manual step before the tag in `docs/release.md`. A smoke test that starts a session with a fake Copilot CLI in the binary will close it. Addendum (2026-10-24, PR #46): Bun 1.4.2 on Windows crashed (segfault) or hung `bun test` about 1–2 s after a test file had run four ConPTY sessions, at a random point that did not depend on how the session was stopped (closing the terminal or killing the leader), on garbage collection or on `--isolate`; macOS and Linux were fine. Bun 1.4.4 passes the same tests, so `mise.toml` and both workflows moved to 1.4.4. What would reverse it: the crash coming back on a later Bun, which would mean running the PTY test files in separate `bun test` processes.

**ADR-2 UI transport: HTTP + WebSocket, not only Tauri IPC.** This way the same UI works in a browser (stage 1) and in Tauri, and the `ws` CLI and tests use the same API. Tauri IPC remains for native matters: tray, autostart, token.

**ADR-3 MCP in the daemon, Streamable HTTP transport, stdio as a bridge.** One process holds the state, so the MCP tools need no separate channel. A stdio bridge for CLIs that do not support HTTP. The first slice (a server from the SDK, stateless, read-only, Copilot CLI through the bridge): ADR-24.

**ADR-4 Persistence: SQLite + JSONL, no external database.** One person, one machine; SQLite is enough, and JSONL is readable by hand and cheap to write.

**ADR-5 Leases instead of a proxy.** One service instance on a port and a takeover by a task solve 90% of cases without a proxy; the `leases` interface leaves room for routing by header.

**ADR-6 Facts from extractors, an LLM only in the `description` field and in proposals with `origin: 'llm'`.** Repeatable analysis and tests without a model.

**ADR-7 Nothing company-specific in the repo.** All company-specific rules (URL patterns, topic names, a GitLab adapter with the instance address) are workspace configuration, and the extractors take them as parameters.

**ADR-8 Copilot CLI only.** (2026-10-23) One agent adapter. The adapter abstraction stays as a boundary in the code, but is not developed for other CLIs.

**ADR-9 No auto-merge and no planner, permanently.** (2026-10-23) A task ends with a summary and a PR proposal; merging and splitting goals is done by a human. The data model has no place for dependencies between tasks or a queue.

**ADR-10 The secrets repo holds k8s `Secret` manifests.** (2026-10-23) The `origin/<repo>` branch contains YAML files with `kind: Secret`; `secrets.resolve` reads `data` (base64) and `stringData` (plain text) and maps the keys to environment variables 1:1. Key names are compared with `runtime.secretNames` from the repo details, hence `check_secrets`. The target sops + age encryption does not change the format, it only adds a decryption step before parsing.

**ADR-11 A translucent window with a system effect, an opaque background as a fallback.** (2026-10-23) The Tauri window is transparent (`transparent`, theme `Dark`), and the shell in `setup` tries effects in turn through `window-vibrancy`: on Windows Mica (Windows 11), then Acrylic (Windows 10 1809+), on macOS the `UnderWindowBackground` vibrancy. After the page loads, the shell sets the `data-window-effect` attribute on `<html>` with the name of the effect it got and shows the window (it starts with `visible: false`) only after this script has run, so an opaque background does not flash at startup; if the page did not report the end of loading, the window shows after 10 s. Reloading the page (F5) paints it opaque until loading ends, which we leave as a rare case. The attribute removes the page background and makes surfaces translucent; without it (no effect, a browser) the UI stays opaque, and `prefers-reduced-transparency` restores opacity also with a working effect. Tauri's `set_effects` is out, because it takes only the first effect from the list and does not say whether it worked. `macOSPrivateApi` is not needed: since Tauri 2.12.1 (the lower bound in `Cargo.toml`) transparency on macOS works without this flag. What would reverse it: noticeable Acrylic stutter when dragging the window on Windows 10 (then Windows 10 gets an opaque background) or poor readability on light wallpapers (then less surface transparency). Clarification (2026-10-24, ADR-49): the effect and the reveal are kept per window label (`WindowEffects`), so an extra window gets the same effect, applied on the main thread right after it is built, and shows only after its page has set the attribute; a page that loads before the effect is applied shows its window opaque at first, and the effect reaches it as soon as it is applied.

**ADR-12 Name: Trackwall.** (2026-10-23) The working name "Pitwall" was taken by existing developer tools (quanticstudios/pitwall, aenzenith/pitwall-vscode), so the project is called Trackwall: packages `@trackwall/*`, binaries `trackwall` and `trackwall-daemon`, data directory `~/.trackwall`, variables `TRACKWALL_*`, app identifier `dev.trackwall.desktop`. The name keeps the motif of the wall by the track and at the time of the decision was free on npm (also as a scope), crates.io and PyPI. The state from version 0.1.0 in `~/.pitwall` is not migrated, because apart from the token and logs there is nothing in it. What would reverse it: a name collision with a tool or a trademark found before publication.

**ADR-13 `workspace.yaml` in the daemon's state directory, until a workspace is chosen.** (2026-10-23) The repo list (since ADR-18: the projects folder) is in `<state directory>/workspace.yaml` (`~/.trackwall/workspace.yaml`). This way the first version needs no workspace selection screen, and the file already has its target format and can be moved. What will reverse it: choosing the workspace directory in the UI (for example a private repo with configuration): then the daemon gets the path to the file, and only a pointer to it stays in the state directory. The manual `repos` list in this file was replaced by ADR-18; the location of the file still applies.

**ADR-14 Repo browsing from the HEAD commit, not from the working directory.** (2026-10-23) The file tree, README and preview read git objects (`ls-tree`, `cat-file`). A path from the UI does not touch the file system, so there is no risk of escaping the repo, symbolic links, files locked by processes or accidentally showing secrets from ignored files (`.env`). The cost is that uncommitted changes are not visible in the browser; the number of changes in the repo status shows them, and eventually a diff (Monaco). What will reverse it: a need to edit files in the UI or to preview the working directory; then a separate route with path validation against the root.

**ADR-15 CI on PRs only on Linux; Windows and macOS on `main`, manually and at release.** (2026-10-23) In a private repo a Windows runner minute counts double against the GitHub Actions limit, and macOS ten times, and the full matrix on every PR and push used up the limit. A system-specific bug in a PR without a manual run comes out on `main` at the latest, and the release (`release.yml`) runs the tests on both systems before publication. What will reverse it: making the repo public (standard runners are then unlimited) or a self-hosted runner: then the Windows + macOS matrix comes back to every PR. Superseded by ADR-22.

**ADR-16 UI look: one dark HUD theme with one accent, tokens only in `index.css`.** (2026-10-23) The UI has one theme, dark, in the spirit of a HUD: a black background (the same as `ACRYLIC_TINT`, so ADR-11 works without changes in the shell), cool glass surfaces with thin lines and a grid under the content, cyan as the only accent for what is active, and green, amber and red only for state (`success`, `warning`, `destructive`). All tokens are in `packages/ui/src/index.css`: colours in `:root`, in `@theme` the typefaces, the `text-2xs` size, the `tracking-hud` letter spacing, the dimensions `--spacing-activity-bar` (`w-activity-bar`) and `--spacing-sidebar`, the `shadow-glow-*` glows, and the utilities `surface`, `hud-label` (section and field labels, mono in capitals; not for sentences), `hud-grid` and `hud-active-edge`. Components use only tokens, and the test `packages/ui/test/design-tokens.test.ts` rejects raw colours and arbitrary appearance values in `.tsx`. Other spacing is the Tailwind scale. Shared building blocks: `Surface` (a surface with a header and a footnote), `StatusLabel` (a state dot with text; the tone from `repoStatusTone`), `Loading` and the shadcn/ui components in `components/ui`. Fonts are system fonts (Segoe UI Variable and Cascadia Mono on Windows, SF on macOS), because the app works offline and we do not want to add font files. The direction comes from the inspiration for the graph and the 3D scene (stage 5), so that the rest of the UI matches them; the main view with the scene or the graph is to have the layout "the scene at full width, details of the selected node in a panel on the right". What would reverse it: poor readability on a real Windows with Mica/Acrylic or a need for a light theme; then a second colour set under a class and a switch.

Clarification (2026-10-23): the app's views are switched by a view bar at the left edge of the window (`ActivityBar`, like the activity bar in VS Code) instead of tabs in the header, because a vertical bar fits more views (sync, graph, Copilot CLI sessions) without squeezing the header and leaves the whole window height to the content. Work views are at the top of the bar, Daemon and Settings at the bottom edge; each has an icon, a tooltip with the name and shortcut, and a Ctrl (⌘ on macOS) + key shortcut (digits by physical key, also from the numeric keypad, comma by character, because in AZERTY and Dvorak it sits elsewhere, and its key may hold a letter with its own shortcut; in Cyrillic layouts the comma needs Shift, so there only the icon opens Settings): Repos 1, Daemon 9, Settings comma, further work views the next digits. A view appears on the bar only together with working content, with no empty placeholders. Tabs (`TabBar`) remain only inside a view, for example in the Repos view. Clarification (2026-10-24, ADR-48): the view shortcuts listen in the capture phase on `window` and stop the event, because xterm.js turned Ctrl + digit into a control character for the session and stopped it, so with the focus in a session terminal the views did not switch. Clarification (2026-10-24, ADR-49): Ctrl+Shift + digit (⌥⌘ + digit on macOS) opens the view in a new window, and Ctrl+Shift+N (⌘⇧N) opens the current view; Settings has no such shortcut, because Shift and Option change the comma on most layouts.

**ADR-17 Copilot CLI state from the session plugin's hooks, OSC 9;4 as a fallback, no screen parser at the start.** (2026-10-23) According to its documentation Copilot CLI has hooks for the end of a turn (`agentStop`), notifications (`notification`, including approval requests), errors and the end of a session, and a plugin given through `--plugin-dir` loads them for one session only, without changes in `~/.copilot` and without files in the repo. Checked on Copilot CLI 1.0.103 (Linux): `copilot plugin list` shows such a plugin, and its `sessionEnd` hook with `exec` + `args` fired already on the folder trust screen, before login; the other events could not be triggered without a logged-in account. A hook is a program with `exec` + `args`, without a shell, so the same definition works on Windows and macOS. Copilot CLI sends the OSC 9;4 progress bar by default, so it gives `Working` also when the hooks do not work (only with `WT_SESSION`, clarification of 2026-10-24 below). We put off the screen parser (VT in the daemon), because it needs dependencies and patterns that cannot be checked without recordings. The considered `copilot --acp` mode (Agent Client Protocol: JSON-RPC on stdio with exact state and approval requests) is out for now, because it replaces the Copilot CLI TUI with our own conversation view in the UI; it comes back if hooks turn out unreliable or the UI gets its own session view anyway. Other sources rejected: `copilot -p --output-format json` gives JSONL events, but only without the TUI and with `--allow-all-tools`, so it has no `Approval` state and no conversation with a human; the `~/.copilot/session-state/<session>/` directory and the logs in `~/.copilot/logs` have an undocumented, internal format that may change with every version. What would reverse it: hooks from `--plugin-dir` not working on Windows (then a plugin in the worktree's `.github/hooks` excluded through `.git/info/exclude`), hooks working only partly, for example without `notification` (after the first hook OSC can only end `Working`, so then a per-event combining rule or screen patterns), or `notification` kinds that do not tell approval from a question (then screen patterns for `Approval`). The PTY in the prototype comes from `Bun.spawn({ terminal })` (ADR-1); if it did not work in ConPTY, `bun-pty` from the spike comes back (code in git history, ADR-1). Result from macOS (2026-10-24, Copilot CLI 1.0.103 with a logged-in account, `copilot-record.ts` with `-p`): hooks from `--plugin-dir` all arrive (`sessionStart`, `userPromptSubmitted`, `postToolUse`, `agentStop`, `sessionEnd` with `reason: complete`), and an approval request is a `notification` with the field `notification_type: permission_prompt`, the title "Permission needed" and the path or command in the text, so `Approval` comes from the kind, not from the text. Copilot CLI asks only about what is not on its list of safe actions (for example writing outside the session directory); it runs `ls` and `date` without asking. Clarification (2026-10-24): sessions with the TUI in the "Sessions" view on macOS gave the same `notification_type: permission_prompt` for an approval request to write and delete a file, so `Approval` from this kind has `high` confidence (UI: "asking for approval"); `elicitation_dialog` stays `medium`, because no recording has shown it yet. Left: Windows, `elicitation_dialog` and the notification kind for a ready plan. Clarification (2026-10-24, five sessions with the TUI on macOS, `copilot-record.ts` in a 120×30 PTY): after an answer to an approval request Copilot CLI sends no hook. After approval the first one is `postToolUse` after the command ends (many seconds for tests), after "No, and tell Copilot…" with a message, the first one is the next tool's `postToolUse`, and after Esc, which interrupts the whole turn ("Operation cancelled by user"), nothing until `sessionEnd`; so the state hung in `Approval` and the session was "asking for approval" while working or after the interruption. Hence the key detector (§4.4): Enter in `Approval` or `Plan` → `Working`, Esc and Ctrl+C → `Input`. Copilot CLI sends OSC 9;4 only with `WT_SESSION` (without it, also with `TERM=xterm-256color` and `COLORTERM=truecolor` as in the daemon, not once): state 3 from the start of the turn, then every 5 s, also throughout an approval request, and state 0 about 20 ms before `agentStop`; so the OSC fallback works only in Windows Terminal and does not tell `Approval` from `Working`. Setting `WT_SESSION` in the session environment to get the bar outside Windows Terminal too is put off: Copilot CLI could change other behaviour under Windows Terminal as well. The window title (OSC 0) does not change on an approval request, a refusal or the end of a turn. Further sessions (2026-10-24): Ctrl+C works like Esc, with one press, during an approval request and while working, without a hook and without asking for a second Ctrl+C; after the interruption the screen shows "Operation aborted by user" at the tool and "Operation cancelled by user" at the end, both as continuous text, so the second one is a screen pattern (§4.4). The same refusal on Windows (the test thread) gave "Operation cancelled by user" without any hook, and the state held `Approval` for over a minute. Sessions with the fix (keys and replay) gave the same changes live and from the recording. Still left: Windows with the fix, `elicitation_dialog`, the notification kind for a ready plan and choosing an option with a digit (whether Copilot CLI accepts it). Clarification (2026-10-24, Windows after PR #38): in the "Allow path access" window the digit of the "No" option works at once, without Enter, and ends the turn with the message "Operation cancelled by user" without a hook, so a digit 1–9 in `Approval` or `Plan` is an answer (`choice`), like Enter.

**ADR-18 The repo list is the git repos in the projects folder, not a manual list.** (2026-10-23) `workspace.yaml` points to one folder (`projectsDir`), and the repo list is its direct subdirectories with `.git`, read on every request. That is how the user keeps repos anyway (one folder with clones), so the configuration is one path instead of a list, and a repo cloned from a terminal or deleted from disk does not drift from Trackwall. The same model will handle adding repos by choosing from the list available on GitHub or GitLab: the clone goes into the folder and is on the list at once, without a separate write (done: ADR-19). Adding by path by hand and removing from the list disappear; the repo identifier now depends on the directory name, so renaming the directory changes the identifier, and a new directory with a colliding name that sorts earlier can take over an existing repo's identifier (today nothing stores it; the `tasks` table from §6 will have to store the path too; cards are keyed by the commit hash, so they are not affected, ADR-25). The scan goes one level only, because nested repos (submodules, examples in a repo) would give false entries, and scanning the whole tree is expensive with `node_modules`. What would reverse it: a need for repos outside the folder (then an extra `extraRepos` list next to `projectsDir`), a folder layout with groups as in GitLab (`<group>/<repo>`, then the scan depth in the configuration) or several folders at once (`projectsDir` as a list).

**ADR-19 Repos into the projects folder from a GitLab and GitHub search through `glab` and `gh`.** (2026-10-23) A repo is added by searching for it on a host from `workspace.yaml` (`repoHosts`) and clicking "Clone"; the clone goes into the projects folder, so the repo list picks it up by itself (ADR-18). The daemon queries the host and clones through `glab` (GitLab) and `gh` (GitHub) logged in on the system, not through its own HTTP client: login (also SSO and company instances), the token in the system keychain, the proxy and the clone protocol choice (SSH or HTTPS) are already set in these programs, and Trackwall does not touch the token, so it does not have to protect or mask it. The cost is two programs to install and log in to, and a dependency on their output, limited to `api` (JSON from the REST API, stable) and `repo clone`. GitLab is primary: a company instance has thousands of projects, so GitLab does the search (one page of results), while for GitHub, where the user's repo list is small and has no search, the daemon filters itself. A clone runs in the background, and its state lives only in daemon memory, because after it ends the directory in the folder is the truth. What would reverse it: no `glab` on the user's machine without a way to install it (then an HTTP client in `vcs` with the token as a secret, §4 `secrets`), a need to clone from another host (Bitbucket, Gitea: another program or an HTTP client) or GitLab groups as subdirectories of the folder (then together with the scan depth change from ADR-18).

**ADR-20 Process group: a Job Object under Bun on Windows, a POSIX session on macOS, no Effect and no native addon.** (2026-10-23) The `procs` module runs every mise task as a group: on Windows a Job Object with `KILL_ON_JOB_CLOSE` through `bun:ffi` (the stage 1 spike, ADR-1), on macOS and Linux `setsid` and signals to `-pgid`; the `exited` state and the success of a stop only after the system confirms the group is empty. The system code sits in `platform/` behind the `GroupPlatform` interface, so the module does not depend on Bun. Under Node on Windows there is no FFI: a group is a tree with `taskkill /T /F`, without orphan cleanup; Node is the compatibility mode (ADR-1), and the release is a Bun binary. A gentle stop on Windows is closing stdin, because Ctrl+C needs a shared console. Orphans on macOS are cleaned up by the next daemon start according to `runtime.json` with the leader's start time from `ps`. Effect (cancellation, resources, time limits as a library) considered and put off: the stop sequence is a few steps with time limits that read plainly, and Effect would change the style of the whole daemon, so it is a separate decision. The `ProcessGroups` interface (promises) can be wrapped later without changes in `platform/`. What would reverse it: a leader escaping the job before assignment (then a start suspended by `CreateProcessW` with `CREATE_SUSPENDED` through FFI), servers on Windows that need Ctrl+C for a clean shutdown (then a separate console and `GenerateConsoleCtrlEvent`), or a release under Node (then a Job Object through a native addon).

**ADR-21 Sync is a fetch and a fast-forward of the default branch, nothing more; the remote address as a repo identifier.** (2026-10-23) "Sync all" fetches the changes of every repo from the projects folder and moves the local default branch to the remote one only when it is a clean fast-forward and does not touch uncommitted changes; every other case leaves the repo untouched with a reason. The user usually works on feature branches, so a default branch that is not checked out moves without touching the working directory (`git fetch . <remote>:<local>`, which itself refuses for a branch in use, also during a rebase and bisect), and a checked-out one through `merge --ff-only`; merging, rebasing and `git pull` with the user's configuration (`pull.rebase`) are out, because nobody resolves a conflict in the background. The default branch comes from `refs/remotes/<remote>/HEAD`, because the name (`main`, `master`, `develop`) differs between repos. Considered multi-repo tools (`meta`, `mu-repo`, `gita`, `myrepos`) are out: they need their own file with the repo list, whose source is already the projects folder (ADR-18), and run arbitrary commands through a shell, while the daemon builds commands itself (§1.2). Fetch gets an environment without password and host key prompts, because the daemon has no terminal; an ssh program set by the user takes precedence over batch mode. Sync runs in the background, 4 repos at once (a company GitLab and a VPN can limit concurrent SSH connections), and the state lives only in memory, like clones (ADR-19). The address of the main remote (`host/path`, without the protocol and user) goes to every repo on the list as an identifier independent of the directory name (ADR-18), to which cards, the graph and MCP will attach; it is computed on every request, because nothing is stored yet. What would reverse it: a need to update feature branches too (then a fast-forward of every branch to its tracking branch, with the same rules), repos with several remotes without `origin` at the user (then a remote choice in `workspace.yaml`) or a list too slow with hundreds of repos on Windows (then the address stored in the `repos` table and refreshed on sync).

**ADR-22 Full CI on every PR: Windows and macOS in parallel with Linux, one required check `CI ok`.** (2026-10-23) The repo is public, so standard GitHub Actions runners have no minute limit, and the reversal condition of ADR-15 has been met. Every PR runs tests and the build on `windows-latest` and `macos-latest`, without a manual `workflow_dispatch`; it is on Windows that most bugs Linux does not see come out. Tests and the build are separate jobs without waiting for Linux, so a run takes as long as the longest job (the build on Windows), not the sum. The protection of `main` (a repo setting, done by a human) requires one check `CI ok`, which collects the results of the other jobs: a change of the matrix or a job name needs no change in the repo settings, and a skipped or cancelled job gives a red result (GitHub counts a skipped required check as passed). For the same reason CI has no `paths-ignore`: a documentation-only PR must also get a verdict, and a test checks `docs/release-notes`. Every `main` commit has its own concurrency group, because a shared group cancels a waiting run when the next one comes, and then nobody knows which commit broke `main`. The dependency audit is part of `CI ok`: a new high-severity vulnerability blocks every PR until someone bumps the dependency or, when there is no fixed version, writes it with a justification into `auditConfig` in `pnpm-workspace.yaml`; we prefer that to a quiet release with a vulnerability. What would reverse it: going back to a private repo, the audit blocking PRs more often than it catches a vulnerability introduced by a PR (then the audit outside `CI ok` and separately before a release), or a macOS runner queue so long that waiting for it slows PRs more than a bug found only on `main` costs.

**ADR-23 The "Node" icon from one SVG; the tray on macOS as a template, outside macOS the colour app icon.** (2026-10-23) The app icon is a cyan ring (Trackwall) connected to four nodes (repos and agents), one of which glows as active, on a dark tile in the UI theme (ADR-16). Chosen from five proposals, because it shows the connection graph with Trackwall at its centre plainly, and the silhouette stays readable at 16 px. The sources are `apps/desktop/assets/icon.svg` and `tray-icon.svg`, and `apps/desktop/scripts/icons.ts` generates from them the files from `bundle.icon`, the UI favicon and the tray template; the generated files are in the repo, so that the build does not depend on SVG rendering. The tray on macOS gets a monochrome template (`icon_as_template`), which the system recolours for the light and dark menu bar; on Windows and Linux the colour app icon stays, because the notification area can be light or dark, and a black or white mark would disappear on one of them. What would reverse it: an unreadable colour icon in the Windows notification area (then separate tray marks for the light and dark theme, switched by the system theme) or task state shown on the tray icon (then icon variants with a state marker from the same SVG).

**ADR-24 MCP for the supervising agent: a server from the SDK in the daemon, stateless, read-only, Copilot CLI through a stdio bridge.** (2026-10-23) The daemon exposes `/mcp` through `createMcpHandler` from `@modelcontextprotocol/server` 2.x (dependencies: only `zod` and `@modelcontextprotocol/core`), with the `list_repos` and `get_repo` tools mapped to the facade. The SDK instead of our own JSON-RPC, because the protocol changes every few months (the 2026-07-28 revision added the `server/discover` probe, headers with content fields and a new envelope), and the SDK supports both it and clients with `initialize`; version 1.x (`@modelcontextprotocol/sdk`) was out, because it pulls Express, Hono and an OAuth client into the daemon binary, and the `@modelcontextprotocol/node` adapter for the same reason (Hono), so `IncomingMessage` is turned into a `Request` in a dozen or so lines in `endpoint.ts`. The server is stateless, because the tools only read the facade; sessions and notifications will come when there is something to announce (for example `graph.updated`). Copilot CLI connects through the stdio bridge (`copilot mcp add trackwall -- <trackwall-daemon> mcp-stdio`), not through an HTTP entry with a header, because the daemon's token and port change on every start, and the bridge reads them from `daemon.json` for every message and leaves no token in `~/.copilot/mcp-config.json`. The bridge speaks only the protocol with `initialize`; it rejects the 2026-07-28 probe, because over stdio there are no headers that this revision requires in HTTP. The Copilot CLI configuration is written by its own `copilot mcp add` command run by the user, and the UI only shows it: the daemon does not touch files in `~/.copilot`, and the format stays Copilot CLI's business. The daemon token is enough as long as the tools only read (§8). Checked with Copilot CLI 1.0.103 on Linux without login: Copilot starts the bridge at startup, the `server/discover` probe gets `-32601`, `initialize` (revision 2025-11-25) and `tools/list` pass; a tool call cannot be triggered without a logged-in account. What would reverse it: the first tool that changes state or starts processes (then a task token and an audit in SQLite before it), a need for server notifications (then Streamable HTTP sessions and a GET stream, and in the bridge a channel from the daemon), Copilot CLI requiring the 2026-07-28 revision without falling back to `initialize` (then the bridge rewrites the content fields into HTTP headers) or SDK 2.x changing its API every release (then our own JSON-RPC server for the revision with `initialize`). Changed by ADR-39 (2026-10-24): the server is no longer read-only, because `propose_task` stores a task proposal and `report_result` a task summary, although no tool starts anything still; Trackwall sessions add a session token to the daemon token, and the call goes to the log with the calling session. The `audit` table in SQLite still does not exist: ADR-39 explains why it is not a precondition for these two tools. Changed by ADR-41 (2026-10-24): the `run_mise_task` and `stop_mise_task` tools run and stop mise tasks.

**ADR-25 The repo card deterministically from the files of the HEAD commit, cached by commit hash; repo tags from the card and from workspace rules.** (2026-10-23) The `cards` module reads build files and tool configuration from the git objects of the HEAD commit (`ls-tree` and `cat-file --batch`, without a checkout and without filters), extracts from them the provided and used packages (Maven, Gradle, npm), the required tools and the mechanism inventory, every fact with a file and line, and caches the card by commit hash in memory and in `cards/<commit>.json`. From the card, the identifier and the remote address it computes repo tags with reasons, and the `repoTags` rules in `workspace.yaml` add tags from names (for example a team's) that are not visible in the files. Reasoning: the commit instead of the working directory, because the card is to describe what is in the repo, not unsaved changes on a feature branch, and because only then is the commit hash the cache key: hundreds of repos are computed once, and a daemon restart does not read them again. Without running the build (Maven, Gradle, `mise ls --json`): that would run code from the repo (Gradle scripts, plugins, mise configuration requiring trust, ADR-20), need installed tools and network, take seconds per repo and read the working directory and global configuration instead of the commit. The price is that Gradle is read from typical line forms, and a dependency assembled in code does not reach the card; the reliable graph edges (shared packages) use typical forms anyway. Our own XML parser (about 140 lines, with line numbers, without DTDs and external entities, so without XXE) instead of a dependency, because evidence needs lines, and a pom needs no namespaces or attributes; TOML through `smol-toml` (no dependencies, pure JS, works in `bun build --compile`), because the Gradle version catalog and mise are full TOML, and YAML through the existing `yaml` dependency. Tags are orthogonal and short (`java`, `bff`, `frontend`, `monorepo`…), instead of compound ones like `#java-bff`, because the filter combines them itself (selected tags are AND), and one tag per combination would multiply rules. Tags without an LLM and without state: computed on every request from the cached card, so a rule change works at once. The card gives provided and used packages in one namespace, but joining them into edges (who uses what) is a separate step: the `graph` module and MCP tools over it, the next task. What would reverse it: a need for facts that cannot be read from files without running the build in many of the user's repos (then an optional step with a build in a worktree, marked with a different source), or a card computed so slowly that it must be kept in SQLite together with the graph (§6).

**ADR-26 Copilot CLI sessions in a daemon PTY, a terminal in the UI through a WebSocket with a screen image, hooks through a session file.** (2026-10-23) The "Sessions" view runs Copilot CLI in a repo from the projects folder in a PTY owned by the daemon (`Bun.spawn({ terminal })`, ConPTY on Windows), as a process group of the `procs` module, several sessions at once; a session runs with the window closed and ends together with the daemon. The terminal window is xterm.js connected through the `/ws/pty/<session>` WebSocket. The daemon keeps every session's screen in a windowless emulator (`@xterm/headless`) and on connection sends its image (`@xterm/addon-serialize`), because the Copilot CLI TUI works on the alternate screen, and replaying the whole output from the start grows with the session's time; both packages are pure JavaScript that works in `bun build --compile` and under Node. The token goes in the WebSocket subprotocol (a browser will not set a header), not in the address. The session plugin's hook (ADR-17) is the daemon itself with the `copilot-hook` subcommand, which appends a record to the session's `hooks.jsonl`, and the daemon reads the file every 200 ms: an HTTP request to the daemon would require giving the hook the token in `hooks.json`, while a file in the state directory requires nothing. "Waiting for you" is `Input`, `Approval` and `Plan` of a running session, computed in the daemon (`needsAttention`); the UI shows the number of such sessions on the view bar and switches to the next one, and the Tauri shell polls the daemon itself (the WebView of a hidden window may have its timers suspended) and, when a session goes from working to waiting, flashes the window on the taskbar (a bounce in the Dock) and adds the session to the tray menu. (Note 2026-10-24: `Input` waits only until the user has seen it; superseded in this part by ADR-47.) System notifications (toasts) are out for the start: on Windows they need a registered AppUserModelID, which a portable app does not have. Considered and rejected: `node-pty` (does not work under Bun, ADR-1), PTY on the Rust side (`portable-pty`, plan C from §9; it adds a bridge between the shell and the daemon, and sessions are to run without a window) and the `--acp` mode (ADR-17). Every session gets the Trackwall MCP server (ADR-24) through `--additional-mcp-config` with a file in the session directory, on the same stdio bridge as the supervising agent. Under Node there are no sessions (`agent_unavailable`), because Node has no PTY without a native addon, and Node is the compatibility mode (ADR-1). The daemon does not record sessions (`copilot-record.ts` does that), and sessions do not survive a daemon restart. What would reverse it: `Bun.spawn({ terminal })` not working in ConPTY on a real Windows (then `bun-pty` from the spike behind the same `TerminalPlatform`; code in git history, ADR-1), the screen image from `@xterm/headless` drifting from the TUI screen (then replaying the output since the last screen switch), a need to resume sessions after a daemon restart (then `copilot --resume` with the session identifier from the `sessionStart` hook) or a release under Node (then a PTY from a native addon).

Clarification (2026-10-24): toasts came back with ADR-50, under an AppUserModelID that the shell registers itself.

**ADR-27 The Batch command as a daemon module over `workspace` and `mise`, one `mise run` per repo, without the mise monorepo mode.** (2026-10-23) The Batch command (§4.8) is a fixed list of steps (sync, `mise install`, the `setup` task, the `build` task) on the selected repos, at most 3 repos at once, in each repo in order, with the result of every step in every repo and cancellation. Every mise step is a separate `mise run <task>` or `mise install` in the repo root, in a `procs` process group under the same owner as from the repo details, so the state, stop and cleanup after a crash are the same as for a task run by hand, and caching and dependencies between tasks stay in mise (`sources`, `outputs`, `depends`). An engine checked and rejected: the mise monorepo mode (mise 2026.10.18, `monorepo_root = true` in the `mise.toml` of the projects folder, `mise run '//...:build'`). The tasks of all repos then run in one process with output prefixed by `[//repo:task]`, so the per-repo result would have to be read out of text, and only the whole can be stopped; the first error interrupts the other repos (without `-c`); the projects folder needs a configuration file with `monorepo_root` and an explicit `[monorepo].config_roots` list (automatic discovery is deprecated), which Trackwall would have to write and maintain, and mise to trust; repos without `mise.toml` and git sync are outside it, and the mode is experimental. Checked on a folder with three repos: `mise run '//...:build'` with one repo's build ending with code 3 interrupted the running build of another, and mise warns that `experimental_monorepo_root` and automatic discovery are deprecated. Separate `setup` and `build` steps instead of `build` alone with `depends` are deliberate: the dependency result is visible separately, at the cost of a second `setup` run without `sources` and `outputs` when `build` depends on it. What would reverse it: a monorepo mode with a stable, machine-readable per-task result (for example JSON) and without requiring a file in the projects folder, or a need for a dependency graph between repos (building a library before its consumers), which does not exist today: then the order comes from the graph of cards, and mise can stay the engine.

**ADR-28 mise task logs: an in-memory buffer and JSONL in the `logs` module, a light list in the UI instead of xterm.js, polling from a cursor until the WebSocket.** (2026-10-23) The output of every process group with output through pipes goes from `procs` to the `logs` module, which turns it into records with a global `seq`, masks secrets and strips ANSI before writing to the buffer (2000 records per source) and to a JSONL file rotated at 10 MB (§4.2). The last lines of the `exited` state are also made in one place, so they are masked too; that is why `procs` depends on `logs` (table in §4). The UI shows the log as a list of lines coloured by the record's level, not as an xterm.js terminal: a record is already text without ANSI (the same for the UI, the file and the MCP tool `tail`, so it can be masked, filtered and searched), the list has ordinary selection and wrapping, and xterm.js would add a few hundred KB to the UI and its own screen buffer with no benefit for output without interaction. ANSI colours the tools print themselves are lost; the level from the line content (`ERROR`, `WARN`) highlights what matters. Live means polling `logs/tail` from the cursor every second while the log is open: reading from memory is cheap, and the `/ws` WebSocket does not exist yet. The `seq` number starts from the moment the daemon starts (ms × 1000), so that a cursor from a previous daemon lifetime can be recognised without a separate lifetime identifier in every cursor. The MCP tool `tail` is a thin mapping to `logs.tail` with `repo` and `miseTask` instead of `source`, so that the agent gives what it knows from `get_repo`. Groups with a leader in a PTY (task sessions, ADR-26) have no log, because a TUI screen is not lines; their last state lines go through the same masking (`logs.lastLinesOnly`). What would reverse it: a need for interactive output (that is the PTY, ADR-17) or ANSI colours in the log (then `raw` with the sequences next to `msg`), and a `log.append` WebSocket will replace polling without changing the record.

Addendum (2026-10-24, ADR-36): the `/ws` WebSocket exists now, but logs are not one of its topics: their snapshot is the whole source buffer, so they will come as `log.append` with records from a cursor, and until then the UI polls `logs/tail` as above.

**ADR-29 The connection graph between repos computed on every request from cards and the `graph` entries in `workspace.yaml`, drawn in the UI without a graph library.** (2026-10-23) The `graph` module joins the used and built packages from the cards of all repos (ADR-25) into edges from the repo that uses to the repo that is used, with evidence from both sides, and adds package aliases and manual edges from the `graph` key in `workspace.yaml`; the MCP tools `who_calls` and `subgraph_for` and the "Overview" view read the same graph. Reasoning: a shared package is the most reliable connection that can be read from files without knowing the company's infrastructure (discovery, Config Server, Feign or WebClient), so the graph starts from it, and connections the files do not show are added by the user in a file they keep locally anyway (ADR-7) and that the agent can read but not change (§8). A node is a repo, because services (several per repo) do not exist yet. Without state and without SQLite: cards are in memory by commit, and joining a few dozen cards takes milliseconds, so a graph computed on every request does not drift from the cards, a new repo or a manual change of `workspace.yaml` and needs no `graph.updated` event. An alias works only for a package no repo on the list builds, because a fact from build files takes precedence over an entry that may have gone stale; a repo in the entries is given by identifier or remote address, because the identifier changes with the directory name (ADR-18). A bad `graph` or `repoTags` key does not take away the edges from cards, it only goes into `configProblems`, just as a bad `repoTags` does not take away the repo list in `list_repos`. The layout in the UI is columns from the longest path (the same layers as in the 3D scene, §5.5) and a barycentre in a few dozen lines (`lib/graph-layout.ts`), instead of a library (React Flow, Cytoscape, ELK), because for a few dozen repos it gives a readable drawing from frontends to libraries, without a dependency in the WebView bundle and with the look from the HUD tokens (ADR-16); the three-dimensional scene is a separate package (Pawn). What would reverse it: a graph with hundreds of repos and thousands of edges (then zoom, a filter by tags and maybe a library with a layered layout), edges whose computation stops being cheap (HTTP from `application*.yml` and code, then caching the graph by the set of commits and a `graph.updated` event), or services as nodes (then a `ServiceId` node and the repo as a group). Clarification (ADR-30): HTTP edges from code stopped being cheap to compute on every request, so the module keeps the last graph with its input key (the set of commits and the configuration); a `graph.updated` event is still not needed, because the key changes together with the commits.

**ADR-30 HTTP edges from Spring code and configuration with profiles, read deterministically from the commit, with a confidence that depends on what links the client to its target.** (2026-10-23) The repo card gets apps (`spring.application.name`, port), endpoints from controllers (`@RestController`, `@*Mapping`, also from API-first interfaces) and HTTP clients (Feign, `@HttpExchange`, `WebClient`, `RestClient`, `RestTemplate`, addresses from `application*.yml` and `.properties` in every profile with `${…}` expanded, addresses from `.env` and the frontend proxy), every fact with a file and line; the graph links a client to a repo by app name, an alias from `workspace.yaml`, host, port on `localhost` or by call paths that match endpoints, and the MCP tool `find_endpoint` gives an endpoint with the repos that call it. Reasoning: the user does not know what their company uses (discovery, Kubernetes, Feign or WebClient), so the extractor recognises all the typical forms and each gives a fact with evidence, and whether a connection is certain is said by the edge's `confidence`, not by guessing: an app name under which every call has an endpoint is `exact`, a bare path matching several repos is `low`. Profiles are separate clients, because a local address (`localhost:8081`) and a production one (`orders-api.svc`) point to the same repo in different ways, and an agent asking "who calls" needs both. Without compilation and without a Java parser from a dependency: a tokenizer and a declaration parser (about 470 lines) are enough for annotations, constants and call chains, work the same on Java and Kotlin, execute no code from the repo (ADR-25) and have a linear cost on a malicious file; the price is that a path assembled in code (`RouterFunction`, an address from a method) does not reach the card or stays as `<Class.NAME>`. Source files are chosen by `git grep` in the commit, because reading the whole code of hundreds of repos would cost gigabytes, and the facts are only in files with annotations and clients. Without an LLM: the LLM step (§4.6) can later describe what the rules do not see, with a different `origin`. The graph keeps the last result with its input key, because matching calls to the endpoints of all repos stopped being free when polled every 30 s (the condition from ADR-29). The word "app" instead of "service", because a service is a process started by Trackwall (§4.3). What would reverse it: a company with another HTTP framework (Micronaut, Quarkus, JAX-RS; then another extractor next to `spring.ts`), many false edges from paths (then path matching only on demand or a threshold), addresses in Config Server or in Kubernetes manifests instead of in the app repo (then an extractor for the configuration repo and an alias from a `ConfigMap`), or a need for paths computed in code (then the LLM step or analysis with a compiler in a worktree).

**ADR-31 An agent task in its own worktree in the state directory, the prompt through `copilot --interactive`, changes by polling git.** (2026-10-23) The "Sessions" view creates a task: a new branch `trackwall/<prompt slug>-<6 characters of a UUID>` from the repo's default branch, its worktree in `worktrees/<repo>/` of the state directory and a Copilot CLI session (ADR-26) in that worktree with the prompt as the first message (`--interactive=<prompt>`) and the task's UUID as the conversation identifier (`--session-id`), so resuming is `--resume=<UUID>`. Tasks are in `tasks.json` and survive a daemon restart; the worktree and the branch disappear only at the user's request, and changes that would be lost doing so, only after confirming the `unsaved_changes` refusal (§4.4). A task's changes are the working directory against the base commit, computed by git with a temporary index, and the UI polls them every 2 s. Checked on Copilot CLI 1.0.103: `--session-id` in the help is "set the UUID for a new session", and a try with it created `~/.copilot/session-state/<that UUID>`, so `--resume=<task UUID>` hits the task's conversation; `--interactive=<prompt>` with `=` is accepted also for a prompt starting with `-`. Reasoning: a worktree gives every task its own working directory and branch, so several tasks in one repo and the user's work in the main repo do not get in each other's way, without a copy of the repo; the state directory instead of `<repo>/.worktrees` from the earlier plan (§4.4), because a worktree in the repo is an untracked directory in the user's `git status` (without an entry in `.git/info/exclude`) and another repo directory that tools (IDE, `mise`, search) browse, and the repo list does not see directories outside the projects folder anyway. A branch from the default branch, not from the checked-out one, because a task is new work, and the user's feature branch could have their unfinished changes; the local default branch, because that is what sync moves. The prompt as an argument instead of a file, because Copilot CLI in interactive mode does not read a prompt from a file, and `-p` (non-interactive mode) turns off the TUI, approvals and conversation (ADR-17). Polling instead of a file watcher, because git computes the diff anyway, and a recursive watcher on a worktree with `node_modules` or `target` is expensive and different on every system; a temporary index with `--intent-to-add`, so that the agent's new files are in the diff without touching the index the agent uses for commits, and without writing objects to `.git` on every request. The cost of one request is a copy of the index and a few git commands (`add -N`, `diff`, `rev-list`, `status`), on the Trackwall repo (350 files, Linux) about 30 ms; only an open "Changes" tab polls, and the next request goes after the answer. The task did not get a time budget, a warning about path conflicts between tasks or a task token for MCP: those are the next steps. What would reverse it: Copilot CLI with its own worktree management that gives the same without the daemon (the 1.0.103 help mentions a `--worktree` directory, but with no option), `--interactive` stopping sending the prompt (then typing the prompt into the PTY after the first `sessionStart` hook), polling too expensive on large repos on Windows (then a watcher only as a signal to recompute) or a need for a worktree next to the repo, for example for tools that look for configuration in parent directories. Clarification (2026-10-24, #36): the first version added new files through `git add --intent-to-add`, which on every request writes (or refreshes) an empty blob in `.git/objects`; several "Changes" windows at once thus wrote the same object file, and on Windows the second write ended with "Permission denied" and a momentary `repo_unavailable`. Entries through `ls-files --others` and `update-index --index-info` give the same diff without any write (request cost: `ls-files` and `update-index` instead of `add -N`), so neither a queue of computations in one repo nor a retry after an error is needed, and a write of the empty blob by the agent itself (`git add` of an empty file) no longer has anyone on the daemon side to race with. Clarification (2026-10-24, ADR-39): instead of a task token every session, also in a repo root, gets a session token; a task can come from a task proposal, with its identifier and title (the branch slug from the title), and has a summary from its session (`Task.summary`).

**ADR-33 A 3D dashboard on Pawn from npm, fed with a `HomeModel` snapshot instead of an event stream, in the "Orbit" layout of models built from simple solids.** (2026-10-24) The first screen of Trackwall is to be a 3D dashboard (the view in the UI came after the scene package, see the clarification below), which says at once whether the environment works, which Copilot sessions are waiting for a human and what state the repos are in. The scene is a separate package `@trackwall/scene` on `@pawnjs/core` at an exact version from npm (the three.js + koota engine); Trackwall uses nothing outside the published Pawn packages, and what they lack it reports to the Pawn project and works around on its side until a decision (rendering on demand and WebGL context loss on the UI side, arcs and wires as our own three.js models). The "Orbit" layout won over layers in rows and a grid, because at this scale it fits everything in one frame, and sessions stand next to their repo. **ADR-34 The sync result says what was left in the working directory; working directory changes in the "Changes" tab; the `no-mise` tag from the card.** (2026-10-24) Every sync result without an error has the state of the working directory after it (the checked-out branch, changed and, separately, new files), and the UI shows a sentence about the result for every repo, including an up-to-date one; the "Changes" tab in the repo details shows the files and diff of the working directory against HEAD; a repo without mise tasks in the commit gets the `no-mise` tag. Reasoning: after "Sync all" the user saw "4 changes" on the list and got no message, because the repo was up to date (the list hid "up to date"), and the number of changes could not be opened; nor did the result itself make clear that a moved default branch does not change the files when another one is checked out. **ADR-36 Sessions in MCP read-only and `/ws` events as topic snapshots, detected by comparison in the daemon.** (2026-10-24) The "Sessions" view is to be the registry of all sessions, and an agent (the supervising agent or another session) is to know about them, so the MCP server gets two read-only tools: `list_sessions` (sessions and tasks, the same `Session` and `Task` as in the UI, optionally for one repo) and `get_session` (a session, its task and the task's changes without the diff: a diff of up to 1 MB does not fit sensibly into an agent's context, the agent can read the worktree itself, and git then does not have to compute it). The tools do not return the session screen, nor the last lines of an ended group (`AgentSession`): the last lines are masked only with the values of secrets from the process environment (§4.2), and the agent also prints in the terminal what it read from files (`.env`) or got in the prompt, so the screen could carry a secret printed in the terminal to another session (§8). The `/ws` events (§5.2) carry the whole topic snapshot (`sessions.changed`, `mise.running.changed`), not a difference or a domain event like `task.state`: after every connection the client gets the snapshots, so the event buffer, `seq` and `resync` from the original §5.2 are not needed (an event has no number, because one connection gives the order, and nobody read it), and the UI gets the same value as from the HTTP action and the same view code works with both sources (polling stays as a fallback for the time without a connection and for a topic the daemon cannot read). The daemon detects a change by comparing the snapshot JSON every 200 ms while someone listens, instead of notifications from modules: session state changes in many places (hooks, OSC, keys, the `Stale` threshold, the end of a group in `procs`), snapshots are a read from memory, and one comparison will not miss a change a module forgot to notify about. Deliberate cost: two `JSON.stringify` calls and a session read five times a second the whole time the UI window is open, also when hidden in the tray (before, the UI did not ask with the window hidden); with a dozen or so sessions that is fractions of a millisecond. The first topics are the ones the UI polled most often and that the Home dashboard reads (§5.5); the Tauri shell still polls HTTP (§5.4). WebSockets have one `upgrade` handler (`api/sockets.ts`) with the same checks for events and terminals, and the address with the socket subprotocol has one place in `protocol` (`DaemonSocket`). The event source (`EventHub`) is in `api/` today, because only `/ws` listens to it; `wait_for_session` in MCP will get the same object from `main.ts`, just as `createMcpEndpoint` gets the facade, and the hub will then move to `infra/`. What would reverse the decision: a topic whose snapshot is expensive (the repo list with `git status`, the graph; then a notification from the module or watching the repo and an event without a snapshot), a topic with a large snapshot or frequent changes (logs: then `log.append` with records from a cursor, like `logs/tail`), the cost of comparison with the window hidden visible in a profile (then rarer comparison or disconnecting the UI with the window hidden) or a need for the agent to wait for an event (then `wait_for_session` in MCP on the same event source). Clarification (2026-10-24, ADR-39): `wait_for_session` does not listen to `EventHub`, it reads the state of one session, task or proposal from daemon memory every 200 ms, because it waits for one object, and comparing the snapshots of all topics would gain nothing here; the hub stays in `api/`, and `list_sessions` marks the calling session (`caller`) by the session token.

**ADR-37 Java and Kotlin syntax trees from tree-sitter in WASM in the daemon process, grammars embedded in the binary.** (2026-10-24) When the tokens from `java-tokens.ts` are not enough for a card extractor (DTOs: `@RequestBody` and response types, fields of records and classes, `data class`), it will take a syntax tree from `modules/cards/syntax-tree.ts`: `web-tree-sitter` with the grammars `tree-sitter-java` and `@tree-sitter-grammars/tree-sitter-kotlin` (all MIT) as `.wasm` files. The runtime and the grammars are loaded once per process by `platform/tree-sitter.ts` (`Parser.init` replaces the WASM module of the whole library): under Bun the files come through an import with the `type: "file"` attribute (`bun-grammar-files.ts`), which `bun build --compile` embeds in the binary, under Node the same files from `node_modules` through `import.meta.resolve`. The extractors stay synchronous: `loadSyntaxParsers()` is asynchronous only because of loading the grammars, and `read` gives the tree to a read function and frees it right after it (GC does not clean up WASM memory), so a read that returns a node or a promise is an error (the result itself is checked; a node in an array or an object field is left to the review). pnpm does not run install scripts outside `onlyBuiltDependencies` anyway, so `ignoredBuiltDependencies` for the grammar packages only records that we knowingly do not build their native addons; the author's tool, which the Kotlin package has in `dependencies`, is removed by `overrides`. This PR is a spike: no extractor parses yet, so the daemon binary does not contain the grammars today, and the first extractor (DTOs) will add a parser check to `scripts/smoke.ts`, so that the evidence is the real binary, not a probe. Reasoning: research of tools for Java code analysis (jQAssistant, Joern, CodeQL, scip-java, Spoon, JavaParser, jdtls, spring-service-graph, GitNexus and others) did not find a tool that would replace the extractors from ADR-30 without a JDK, a repo build or a license that rules out company code; tree-sitter is the only full Java and Kotlin parser that runs in the daemon process under Bun and Node, without compiling the repo and without a native addon (ADR-1), and on syntactically invalid code it gives a tree with `ERROR` nodes instead of an exception. The tokenizer stays where it is enough (annotations, HTTP client calls), because it is about four times faster. Spike on Linux x64 (Bun 1.4.4, Node 22.22; Windows and macOS to be measured by hand): a probe compiled with the grammars is 4.1 MB larger than an empty binary (Kotlin grammar 3.4 MB, Java 0.4 MB, runtime 0.2 MB), and the daemon binary will grow by that much; loading the parsers 30–60 ms; 3000 files of 12.8 KB (38 MB of code) in 8.3 s under Bun and 11.4 s under Node, at 69 and 168 MB RSS of the whole process, that is about 4.6 MB/s, against 2.1 s for the tokenizer on the same input. A card is computed once per commit (`card-cache.ts`), and the source file limit is 3000, so the worst case is a few seconds per repo on the first read. The test `syntax-tree.test.ts` checks on Linux (the `check` job) and in the Windows and macOS matrix (the `test` job) the parser under Bun, under Node and in a binary from `bun build --compile --minify` run from another directory, with the WASM files in the binary's virtual file system; the review also checked cross-compiling `bun-windows-x64` with the flags of `scripts/build.ts` (files in `B:\~BUN\`). What would reverse it: parsing that clearly lengthens the first card read for larger repos at work (then a tree only for files the tokenizer points to as DTOs, or the parser in a worker thread), a grammar that stops keeping up with Java or Kotlin syntax, or a change in `bun build --compile` after which `type: "file"` files are no longer embedded. Addendum (2026-10-24, ADR-38): the first extractor with a tree is endpoint contracts and DTOs, `scripts/smoke.ts` computes a real card in the compiled daemon binary, and the parsers are loaded once per process.

**ADR-38 Endpoint request and response types and DTOs on the repo card from the syntax tree.** (2026-10-24) An HTTP endpoint on the card has `request` (the type of the `@RequestBody` parameter) and `response` (the return type without wrappers that do not change the body), and the card a `dtos` list: types from the repo reachable from these types through field types, with fields and their types or with enum constants (§4.6). They are read by `endpoint-contracts.ts` from tree-sitter syntax trees (ADR-37), only in files that have endpoints and in the type files that follow from them; the commit read pulls in these files by type name (`OrderDto` → `OrderDto.java`/`.kt`) in at most three rounds. An endpoint's contract is the method with the handler's name that contains the line of its mapping, not the first method with that name, because one file can have several classes and overloads. A type without fields is not a DTO, and a qualified name points to its last segment, so that the list does not spill over to services injected into the controller. Reasoning: the tool research (ADR-37) ended with DTOs as the first extractor with a tree, because an agent changing an API asks what shape of data an endpoint takes and returns, and tokens will not separate a parameter type from an annotation or a field from a method. Simple names are enough for what is visible on one repo's card; resolving symbols (LSP, scip-java) is left to the task session. What would reverse it: repos at work where DTOs come from generated code (OpenAPI generator, files outside the commit) or from a package other than the controller's, which would require reading the contract from `openapi.yaml` or from the card of the package's repo; cards whose first computation reaches the budget (then the parser in a worker thread).

An unknown token is a refusal, not an anonymous call, so that a closed session cannot pass itself off as an agent outside Trackwall. Proposals only in memory (at most 20 waiting), because a session that waits for an answer does not survive a daemon restart anyway. Waiting polls daemon memory every 200 ms instead of `EventHub` (clarification of ADR-36), because it concerns one object; the 55 s limit is under a minute, so that the MCP client does not abort the call with its own limit, and the agent calls it again. **ADR-40 Code search through `git grep` in the HEAD commit, without an index and without ripgrep.** (2026-10-24) The `search_code` MCP tool searches for a fixed string or a regular expression in many repos of the projects folder at once, with `git grep` over the objects of each repo's HEAD commit (§4.5, §5.3). Git is required anyway, and `git grep` over a commit gives the same guarantees as browsing (ADR-14): paths only from the commit tree, no ignored files, no programs run from the repo (`--no-textconv`), and machine-readable output (`-z`) that does not depend on git's language. ripgrep is faster on a working tree, but it is a second native binary to ship and sign for every platform, and it would search the working tree, including files the repo does not track (`node_modules` without `.gitignore`, secrets in `.env`). There is no index (e.g. trigrams, as in Zoekt): the pool holds dozens of repos, not thousands, and an index would need refreshing after every sync. What would reverse it: searches over hundreds of large repos taking longer than a few seconds (then an index), a need to search uncommitted changes (then `git grep --untracked` in the working tree), or a need for PCRE (`-P` depends on git being built with PCRE2). Without an index every query costs a full read of each commit, so the search is bounded: per-repo output and time limits, an overall budget after which no new repo starts, and a stop once the limit of matches is reached (§4.5).

Justification: an agent working across microservices needs the loop "change, start the slice, call the endpoint, read the response and the downstream stack trace, fix" without a human starting five terminals; the graph (ADR-29, ADR-30) already knows who calls whom, `run_mise_task` (ADR-41) set the consent rule (a trusted config, a command built by the daemon), and `get_errors` (ADR-42) turns a log into a cause. `dev` is a convention like `setup` and `build` in the batch command (ADR-27), so a service needs no new config; readiness is a TCP connection to the port from the log or from `server.port` on the card instead of the planned `mise run health`, because no repo has that task and an open port says the same for a web service; the port from the log wins because profiles and `--server.port` change it and the card reads the default profile. The service is the same process group and log as the mise task (`mise.start`), so the UI tab, `tail` and `get_errors` see it without a new log source. The daemon builds the URL (loopback, the probed port), so `call_endpoint` is not a general HTTP client; the response is masked like a log line, and only `repo` and `method` go to the audit line. State lives in memory, like the process groups (§4.1). Not in this slice: a service from a task worktree (mise trusts by path, and auto-trusting the worktree config would let the agent run any command through `mise.toml`), several services per repo, leases (ADR-5), secrets. What would reverse it: services that need a health URL rather than a port (then a `health` task or `management.endpoints` from the card), or repos where `dev` is not the service (then a `services` key in `workspace.yaml`).

**ADR-46 The agent learns how to work with Trackwall from the MCP server and from session instructions, without changes to the user's repo.** (2026-10-24) One MCP instruction (`MCP_INSTRUCTIONS` in `protocol`) says what Trackwall is and when to reach for which tool; the MCP server announces it in `instructions` (§5.3), and every Trackwall session gets it in its **session instructions** together with the session's role (§4.4): the file `trackwall.instructions.md` in the session directory, whose directory the daemon appends to `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` in the session environment. Rationale: tool descriptions say what a tool returns, not in which order and why to use them (the repo card instead of reading build files, `find_endpoint` and `who_calls` before changing an API), and a task session did not know it should stay in its worktree and end with `report_result`. Checked in the Copilot CLI 1.0.103 binary without signing in: MCP server `instructions` reach the prompt only for servers on an allowlist (`mcpRegistryServerInstructionAllowlist`; the `--allow-all-mcp-server-instructions` workaround would also turn on the instructions of every other server the user has), so the MCP server alone is not enough; `copilot instruction list` shows a file from a `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` directory as a repository instruction, and the variable separates directories with commas. The variable rather than a file in the repo (`AGENTS.md`, `.github/instructions`), because the repo and worktrees belong to the user and a file in a worktree would show up in the task's changes; rather than `~/.copilot/copilot-instructions.md`, because that is the user's configuration and would apply to sessions outside Trackwall too; rather than a skill in the session plugin, because a skill loads only when the model finds its description relevant, while the role must hold from the first turn; rather than a custom agent (`--agent`), because an agent replaces Copilot CLI's default agent and its tools. The role is built only from the repo and task ids, so agent text never becomes another session's instruction (§1.2). A test requires the MCP instruction to mention every tool in `mcpTools`, so a new tool comes with its instruction. No `llms.txt` in the Trackwall repo: agents that develop Trackwall have `AGENTS.md`, and agents that use it get the instruction from Trackwall. To check by hand with a signed-in Copilot CLI: whether the file with `applyTo: "**"` is in the prompt from the first turn (not only after a file is opened) and whether the agent follows its role. What would reverse it: a Copilot CLI that takes `instructions` from every local MCP server or lets the user allow a single server (then the server is enough and the file keeps only the role); a change or removal of `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` (then an instruction file in the session plugin, if Copilot CLI starts reading one there, or a preamble in the task prompt). Addendum (2026-10-25): a session also learns at start which environment it runs in, so that it does not have to ask or guess. The session instructions open with the Trackwall version that started the session and where the user sees it, and the MCP instruction ends with the address of the documentation site and its `llms.txt`, so every MCP client, not only a Trackwall session, can look up a feature instead of guessing. The version comes in through the facade options rather than from `infra/version.ts`, because a module takes only the listed infrastructure files (§4). The site is published from `main`, so it describes the development version rather than the session's; a versioned site would let the link carry the version. The ADR's "no `llms.txt` in the Trackwall repo" still holds for developers: the `llms.txt` agents get is the documentation site's (ADR-56), for people using Trackwall.

**ADR-47 "Waiting for you" ends when the user has seen the end of the turn; approval and plan wait for an answer.** (2026-10-24) A session in `Input` (the turn ended, the agent asked a question, or the user interrupted it) stops waiting for you once a session terminal window has been in front of the user (focused and visible) or the user typed into the session; `Approval` and `Plan` keep waiting until the answer, which the hooks and the session keys already report. Before this, `Input` waited until the next prompt, so a session the user had already looked at kept the warning, the counter and the tray entry for as long as it stayed idle, and "waiting for you" stopped meaning anything. The rule follows tools that solved the same problem: Agent Deck has `waiting` (yellow, not acknowledged) and `idle` (grey, acknowledged on attach), and a tmux status indicator for Claude Code clears a finished session when its pane is viewed but keeps the permission prompt until work resumes. The window counts as in front only after 1 s, because a click on "Waiting: <repo>" in the tray first brings the window to the front with the previous session's terminal and only then switches to the chosen session. Focus comes from the window over the existing PTY WebSocket instead of a separate HTTP action: the daemon sees when the window disconnects, so a closed window cannot leave the session "watched", and the window that shows the session is the one that knows whether the user can see it. Only a change to another state makes a seen session unseen again, so a hook that confirms `Input` after a session key does not bring the warning back. The state stays `Input` (the detectors do not change); "idle" is how the UI and the dashboard show seen `Input`. Reversed if Copilot CLI reports turns in a way that tells a question apart from an ended turn (then a question could wait like `Approval`), or if the user wants an explicit "mark as read" instead of focus.

**ADR-48 Sessions switch from the keyboard with Alt + digit and Alt+J, and show several terminals in a grid of pages.** (2026-10-24) The Sessions view gets a layout switch: `1` is the selected entry with its full panel as before, `2` and `4` show a page of that many entries as a grid of terminals, and `auto` shows the whole list, up to nine per page (`lib/session-grid.ts`). The page is always the one with the selected entry, so a shortcut to any position also turns the page and the selected tile never leaves the screen. Columns and rows come from the size of the area (`gridShape`: the shape with the largest tile of ratio 1.6 that fits a cell), so two tiles sit side by side on a wide window and stack on a tall one, and six fill three columns and two rows on a 34-inch ultrawide. Alt + digit (⌥ on macOS) selects the entry at that position in the list, and Alt+J opens the next session that is waiting for you from any view, after the selected one like the "Next waiting" button (`lib/session-shortcut.ts`; `App` owns Alt+J, the view the positions). The selected tile has the accent ring and the keyboard (a tile of a task without a session takes the focus itself, so keys stop going to the terminal selected before); a waiting tile keeps its warning frame also when selected. The last page keeps the tile size of a full page, and tiles appear only once the grid area is measured, so that no terminal reports a size to its session from a shape that is about to change. Rationale: switching between sessions that need you was a mouse click each time, and a large screen fits several Copilot CLI sessions at once. Ctrl/⌘ + digit already switches views (ADR-16), and Ctrl+J, proposed first, is a line feed in a terminal, which a TUI can read as Enter; Alt + digit and Alt+J have no meaning in Copilot CLI 1.0.103 that we know of, and on macOS Option + key on a US layout only types a character such as `¡`, so the keys are matched by position (`code`). What Alt and Option exist for stays a key: AltGr (Ctrl + Alt on Windows), the keypad (Alt + keypad digits type a character by its code on Windows) and, on macOS, an Option + key that types an ASCII character (⌥5 is `[` on a German layout, ⌥2 `@` on a Swedish one), which on such layouts leaves those positions without a shortcut. Pages instead of choosing the tiles by hand, because the list order is already the order the user knows and the shortcut numbers match it without a second list to maintain. The shortcuts listen in the capture phase on `window` and stop the event: xterm.js turns Ctrl + digit into a control character and stops its propagation, so the view shortcuts did not work while a terminal had the focus, and a session shortcut must not also reach the terminal. In Sessions the session shortcuts are always taken, also when there is nothing to switch to; outside Sessions Alt+J is taken only when a session is waiting, so ⌥J still types in a text field. The capture listener is one function for view and session shortcuts (`lib/window-shortcuts.ts`). Only the selected tile counts as in front of the user for ADR-47, so a session that waits in another tile keeps its warning frame until the user selects it. A terminal in a grid tile reports its size to the PTY like any other window (§5.2), so a session shown in a small tile is resized; switching back to layout 1 resizes it again. Known gap: a tile smaller than the PTY minimum (10 columns, 4 rows; nine tiles in a window about 400 px tall) sends a size the daemon rejects, so the PTY keeps its last size and the terminal shows a fragment of the screen. The layout lives in `App`; the main window loses it when the app closes, and an extra window gets it back at the next start (ADR-49). Not done yet, from the same proposal: opening a main session with all its tasks as a grid, and pinning a session to a panel on the right that stays visible in other views. Clarification (2026-10-25, ADR-55): Alt+J and "Next waiting" also open task proposals, a group of one session being one stop, and a grid tile with proposals shows their prompts with "Start task" and "Reject…" instead of only leading to the full panel. What would reverse it: Copilot CLI giving Alt + digit or Alt+J a meaning (then another modifier, or shortcuts that work only outside the terminal), more than nine sessions being the usual case (then chosen tiles instead of pages), or terminals that need a minimum size the grid cannot give (then a minimum tile width). Clarification (2026-10-25): a grid tile and a list row with a session have an X that closes that session, because in a grid there was no way to close one session without switching to layout `1`, and the list had none at all. One click stops the process group if it still runs and removes the session from the list; while the agent is working or asking for approval of a step or a plan, the X first asks "Stop it and close the session?" in a strip that lies over the top of the terminal (so the PTY is not resized mid-turn) or sits under the row, so a stray click does not cut off a turn, while an idle, waiting or ended session closes at once. A task's X closes only its session: the task and its worktree stay on the list, because ending a task deletes the worktree and keeps its own confirmation in the task panel; a task proposal and a task without a session have no X. A press on the X does not take the focus, so closing a tile that is not selected does not select it first; closing the selected session selects its neighbour on the list, so the grid stays on the same page (`selectionAfterClose`, decided with the selection as it is when the stop ends; the Close of an ended session in layout `1` follows the same rule). There is no keyboard shortcut yet, because keys in a terminal go to Copilot CLI. The UI calls `stop` and then `dismiss` instead of a new daemon action, so a window closed during the stop leaves the session stopped on the list, where its X closes it.

**ADR-49 Trackwall opens views in several windows, each remembering its monitor.** (2026-10-24) The desktop shell can open extra windows besides the main one: "Open in new window" in the native context menu of a view icon on the view bar, Ctrl+Shift + the view's digit (Ctrl+Shift+2 opens Repos; ⌥⌘ on macOS, because ⌘⇧3 and ⌘⇧4 are the system's screenshot shortcuts), Ctrl+Shift+N (⌘⇧N) for the current view, and "New window" in the tray. A held key opens one window, not one per autorepeat. Every window is the full UI with the view bar, starts with the view from its address (`?view=`) and switches views on its own, so the session grid can fill a 34-inch ultrawide while Home or Repos sits on the second monitor. Extra windows have stable labels (`window-2`, `window-3`…, the lowest free number), and `tauri-plugin-window-state`, the official Tauri plugin, restores the monitor, position and size of the last window with the label, falling back to the default position when the monitor is gone. Decisions taken with the user: an extra window closes for real and only the main window hides to the tray, so the tray does not collect invisible windows; the same session may be open in two windows, and the window that comes to the front resizes the PTY again, because the PTY has one size and the window the user works in should get it; an extra window keeps the view bar; a session from the tray (or a proposal) opens in the last focused window that shows Sessions, otherwise the last focused window, so a click on "Waiting: <repo>" does not turn the Home window on the other monitor into Sessions. Rationale: the daemon already serves any number of clients (`/ws` broadcasts to every connection, `/ws/pty` takes several windows per session, ADR-47 counts several windows), so a second window needs no daemon change, only the shell. A ready plugin instead of our own position file, because it already handles monitors, maximized and minimized windows and the order of restore and show; it runs in Rust only, and the UI needs no permission beyond `core:default`, which already covers events and the native context menu. The tray's event goes only to the chosen window, so the UI listens on its own window; a global listener would turn every window into Sessions. The window registry (what each window shows, the list of extra windows saved for the next start and the focus order) lives in the shell, because only the shell sees focus across windows and the tray needs it while windows may be hidden. Each window keeps its own UI state (view, session layout, selection) in memory. Clarification (2026-10-24): the next start of the app opens the extra windows that were open when it quit, each under its label (so on its monitor) with its view and session layout from the page address (`?view=…&sessionLayout=…`); the list is the shell's file `windows.json`, because the window state plugin keeps geometry only and the UI's `localStorage` is not readable before a window exists. The main window still starts with Home. The UI served by the daemon in a browser (`--ui`) has no shell and so no extra windows. Clarification (2026-10-25): the desktop shell has a native menu bar on macOS with the views, Settings and a Window menu that lists the open windows, and every window's title names its view; Tauri's default macOS menu had no views and showed every window as "Trackwall". Windows gets no menu bar, since there it would sit inside every window and duplicate the view bar. What would reverse that part: users on Windows asking for a menu bar, or Tauri offering an app-wide menu bar there that does not sit inside every window. What would reverse it: Tauri gaining multi-webview layouts inside one window that make docking easier than separate windows, or one session shown in two windows turning out to need one owner (then the second window would show a placeholder instead of the terminal).

**ADR-50 Waiting sessions reach you outside the window: a system notification, a global shortcut and a tray panel.** (2026-10-24) A session that starts waiting for you and a new task proposal show a system notification while no Trackwall window has the focus, and clicking it opens that session or proposal; Win+Alt+J (⌃⌥J on macOS) from any app opens the next waiting session; a left click on the tray icon opens a small panel with the waiting sessions and proposals (§5.4). Rationale: the sessions work while the user is in another app (the IDE, the browser), and a flashing taskbar button or a bouncing Dock icon is easy to miss and does not say which session waits; the notification says it and leads there in one click, the shortcut does it without the mouse, and the panel shows the whole queue without bringing up the big window. The notification is skipped while a Trackwall window has the focus, because the badges are on screen then. The shell talks to the system itself instead of using `tauri-plugin-notification`: on the desktop the plugin does not report a click, and on Windows it shows toasts only under an AppUserModelID that an installer registered, which the portable build does not have (the reason ADR-26 left toasts out). Registering the AppUserModelID in HKCU with a display name and an icon is the documented way for unpackaged apps and needs no Start menu shortcut; reopening Trackwall from a toast after it has quit would also need a COM activator, which is left out. On macOS `mac-notification-sys` reports the click and works from a background thread, at the cost of a waiting thread per notification, hence the limit of eight. `tauri-plugin-positioner` is not used either: the tray click carries the icon's rectangle, placing the panel is one tested function (`panel_position`), and the plugin computes in physical pixels, which on macOS go wrong across displays of different scale. The shortcut is not Ctrl+Alt+J on Windows, because Ctrl + Alt is AltGr there and a system-wide AltGr+J would stop layouts that type a character with it (ADR-48 keeps AltGr a key); Win + Alt types nothing. On macOS ⌃⌥J types nothing either, while ⌥⌘J opens a browser's console. The panel is a second WebView with the same UI and the same capability as the main window, so it reads the daemon the same way and no new transport is needed; it is created with the app, so a click shows it at once, which costs one more WebView kept in memory. Clarification (2026-10-25, ADR-55): new task proposals are held until the main session stops proposing for about six seconds and then make one notification, and the global shortcut also opens task proposals. What would reverse it: the notification plugin reporting clicks on the desktop and working without an installer (then the plugin replaces `notification.rs`), the shortcut colliding with tools users rely on (then it becomes a setting), or a panel nobody opens (then the left click shows the window again).

**ADR-51 The projects folder is chosen in the system picker, a repo opens in Explorer or Finder, and dropped files go to the session or the repo list.** (2026-10-24) Settings gets "Choose…" next to the path field in the Tauri window: the app command `pick_projects_folder` (Rust, `tauri-plugin-dialog`) opens the system folder picker and the chosen folder is saved at once. The repo header gets "Show in Explorer" (Finder on macOS): the daemon opens the folder of the listed repo, like "Open in VS Code" (`open-folder`), so it also works in the browser. A file or folder dropped on a session terminal is pasted into it as its path (quoted when it has a space or a quote, with a space after it), and a folder dropped anywhere else goes to `dropped-folder`: a listed repo opens in Repos, and a folder with repos, or the folder that holds a dropped repo, is offered as the projects folder. Reasoning: Trackwall lists the repos of one folder (ADR-18), so a single repo from elsewhere cannot join the list without changing that rule; offering its folder keeps the rule and still makes the drop useful. The picker is an app command rather than the plugin's JavaScript API, so the window's capability stays `core:default` and the page gets no general dialog or file access; Show in Explorer/Finder goes through the daemon rather than `tauri-plugin-opener` because the daemon already opens things in the system from its own configuration (`open-editor`, `open-link`) and the page opened from the daemon gets it too. `clipboard-manager` is not needed: the terminal already copies with `navigator.clipboard`. What would reverse it: a list of repos from several folders (dropping a repo would then add it), or a need for the plugin dialog in the page (file pickers in several views).

**ADR-52 `trackwall://` links show a repo, session or task in the window, and only navigate.** (2026-10-24) `trackwall://repo/<repo id>`, `trackwall://session/<session id>` and `trackwall://task/<task id>` open Trackwall at that thing, so an agent's answer or a notification can point the user at it. The MCP instruction tells agents the format (`trackwallLink` in `protocol`), and a link printed in a session terminal opens on Ctrl+click or Cmd+click. The shell takes links with `tauri-plugin-deep-link` and, on Windows, `tauri-plugin-single-instance` with its `deep-link` feature, and turns them into the same jump as the tray (`Jump`, §5.4). A notification shown by the shell should call `jump::request` directly; text for the user and other apps use `trackwallLink`. Jumps go through a slot in the shell that the UI takes with `take_jump`, instead of an event payload, because a link that starts the app arrives before the page listens. Why: the alternative, a URL the daemon serves, would open a browser tab instead of the window and need the token. A link is untrusted, so it is a closed set of kinds; the shell checks the shape and the UI the id, with the protocol schemas as the only definition of an id, and a link can never run anything: a link that ran a task or approved a proposal would let any web page act for the user (§8). The Windows portable build has no installer, so the release shell registers the scheme for the current user at every start; macOS takes it from `Info.plist`. Linux is not registered (no release there). Reverse if: Trackwall gets an installer that registers the scheme (then drop the registration at start), or links need actions (each would need a confirmation in the UI, like a task proposal).

**ADR-55 The task proposals of one main session are reviewed together, and a rejection carries a reason.** (2026-10-25) The Sessions view shows the proposals of one session as one entry with one panel: every prompt, readable and editable, with "Start task" for one and "Start N selected" for the ticked ones, started one after another. "Reject…" asks for an optional reason, which the daemon keeps with the rejection and `wait_for_session` returns as `rejectionReason`. After a decision the view opens the next waiting proposal of that session. A grid tile with proposals shows the prompts with "Start task" and "Reject…", "Next waiting" and Alt+J go through proposals too (a group is one stop, while the counts on the button and the view bar count each proposal), and new proposals are announced in one system notification once the main session stops proposing for a few seconds. Rationale: a main session usually proposes a plan of several tasks at once, and the old flow (one list entry and one panel per proposal, Home and the tray only leading to it, a dead grid tile, Alt+J skipping proposals while the view bar counted them, "Reject" with no way to say why) made the user hunt for each proposal and left the main session guessing after a rejection. Considered and left out: approving from Home and the tray panel (the prompt comes from an agent and is to be read before it runs, ADR-39, and there is no room to read it there; they keep leading to the panel), and a drawer next to the main session's terminal instead of list entries (better context, but proposals from an agent outside Trackwall have no session to sit next to, and it reshapes the list and the grid more). Nothing is ticked at first and a proposal can be ticked only once it has been opened, so starting several still takes a look at each; starts go one at a time because each runs `git worktree add` and starts a Copilot CLI session, which on a slow Windows machine is felt, and worktree commands on one repo wait for git's lock anyway. While a decision runs the group stays selected by its proposer, and once its last proposal has become a task, the newest task from that proposer stands in for it until the decision moves on. What would reverse it: users mostly approving single proposals (then the per-proposal entries were simpler), a main session that needs an answer richer than a reason (then a reply that reaches its terminal), or plans larger than one panel can show (then a dedicated view).

**ADR-56 Features are documented on a VitePress site in `apps/docs`, published on GitHub Pages.** (2026-10-25) The single `docs/features.md` grew into one long page with a paragraph per feature, which was hard to browse and to link to. The feature documentation moves to `apps/docs`, a VitePress site with one page per feature (`features/`) and a short guide (`guide/`: what Trackwall is, installation, connecting Copilot CLI), and `docs/features.md` is removed so that a feature is described in one place. The site is Markdown in the repo, so a PR that changes a feature changes its page, and the reviewer sees both. It wears the app's look on the VitePress default theme: the dark theme takes the app's tokens (ADR-16, a test keeps the copies equal), the HUD shows only in small labels and the screenshot frame, and a light theme is offered too. `.github/workflows/pages.yml` publishes it at `https://jakubprill.github.io/trackwall/` after a push to `main` that changes it or its address (`TRACKWALL_DOCS_URL` in `protocol`); the `check` job in CI builds it on every PR, so a broken link between its pages fails CI (links to GitHub are not checked). Turning Pages on (Settings → Pages → Source: GitHub Actions) is a repo setting the owner makes. VitePress 1.6 asks for Vite 5, whose dev server has known vulnerabilities fixed only in 6.4.4+, so `pnpm-workspace.yaml` overrides VitePress's Vite to 6.4.5 (the site builds and `vitepress dev` serves with it); moving to VitePress 2 once it is stable makes the override unnecessary. Considered: WordPress (cannot be served by GitHub Pages and keeps the text outside the repo), Starlight (Astro, another framework next to Vite) and MkDocs Material (needs Python in CI, against "scripts in TypeScript"). Architecture, ADRs, development and release documents stay in `docs/`, for people who work on Trackwall. Would be reversed by: a need for content the default theme cannot carry well (interactive demos, versioned docs), or the site moving out of the repo. Addendum (2026-10-25): the pages moved over from `features.md` read like a specification, with ADR numbers, so they are rewritten for people using Trackwall, to be read on their own or in a technical meeting. Every feature page follows `apps/docs/TEMPLATE.md` (a one-sentence description, then "What you get", "How it works", "Use it", optional reference tables, "Good to know") and cites no ADRs; the why stays here, and `apps/docs/test/pages.test.ts` holds the pages to the template. "All features" lists every feature with its description, grouped like the sidebar (`.vitepress/sidebar.ts`), so it cannot miss a page. For AI tools the site also publishes `llms.txt` (the pages with their descriptions), `llms-full.txt` (every page in one file) and a Markdown copy of each page with a "Copy page" button, from `vitepress-plugin-llms` (MIT); `@types/markdown-it` is pinned to 14.1.2, the types VitePress 1.6 bundles, so the plugin's markdown hook type-checks. The plugin types itself against Vite without declaring it, so `packageExtensions` in `pnpm-workspace.yaml` gives it VitePress's Vite 6.4.5 instead of whichever Vite pnpm hoists. "All features" is drawn by Vue from the sidebar, so its Markdown source holds no list: it is left out of the Markdown copies, and `llms.txt` lists the features anyway. The site links to no document in `docs/`: the installation steps for users move from `docs/release.md` to the site's "Install" page, and `docs/release.md` and `README.md` point there.
