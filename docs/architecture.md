# Architektura Trackwall

Stan: propozycja do dyskusji, 2026-10-23. Wcześniejsza robocza nazwa „Pitwall” została zmieniona na „Trackwall” (ADR-12).

Ten dokument opisuje, jak aplikacja jest podzielona na komponenty, gdzie przebiegają granice między modułami, jakimi protokołami komponenty rozmawiają, jaki jest model danych, jak wyglądają najważniejsze przepływy i jakie ryzyka niesie Windows jako platforma główna. Wizja produktu (cel, moduły, kolejność prac) jest założeniem tego dokumentu, a nie jego treścią. Decyzje, które warto umieć później cofnąć, są zebrane na końcu jako ADR-y.

## 1. Zasady, które porządkują resztę

1. **Daemon jest jedynym źródłem prawdy.** UI, serwer MCP i CLI `ws` to trzy klienty tej samej fasady usług w daemonie. Dashboard i agent nigdy nie różnią się co do stanu, bo pytają ten sam obiekt.
2. **Daemon zna identyfikatory, nie komendy.** Każda akcja z zewnątrz (MCP, CLI, UI) wskazuje repo, serwis, zadanie lub task mise po identyfikatorze. Komendę składa daemon z konfiguracji. Jedyny wyjątek to terminal interaktywny w UI.
3. **Stan procesów jest obserwowany, nie deklarowany.** „Zatrzymany” znaczy, że cała grupa procesów nie żyje i daemon to sprawdził. „Działa” znaczy, że sonda zdrowia odpowiedziała.
4. **Fakty deterministycznie, LLM tylko dopisuje.** Karta repo i graf powstają z plików buildu i konfiguracji. Model językowy dodaje opis i sugestie, nigdy nie jest źródłem pola technicznego.
5. **Sekrety nie przechodzą przez agenta.** Daemon wstrzykuje je do środowiska procesu i maskuje w logach. Narzędzia MCP odpowiadają „ustawiony / brak”, nigdy wartością.
6. **Nic firmowego w kodzie.** Adresy, nazwy repo, ścieżki, reguły wykrywania specyficzne dla firmy żyją w lokalnym workspace, poza repozytorium projektu.
7. **Windows pierwszy.** Każdy mechanizm (procesy, PTY, ścieżki, sygnały) jest projektowany od strony Windowsa, a macOS dostaje odpowiednik. Odwrotna kolejność kończy się warstwą „na Windowsie trochę inaczej”.

## 4. Daemon: moduły i granice

Daemon jest jednym procesem, ale wewnątrz jest podzielony na moduły z jawnie zadeklarowanym interfejsem. Każdy moduł wystawia klasę serwisu, a fasada (`Facade`) jest zbiorem tych serwisów (i funkcji `openLink`, która otwiera w systemie link z README bez stanu i bez modułu, ADR-35) przekazanym do trzech transportów (HTTP, MCP, zdarzenia). Moduł nie importuje innego modułu bezpośrednio, tylko przez fasadę, więc graf zależności między modułami jest widoczny w jednym pliku.

W kodzie: moduł to katalog `packages/daemon/src/modules/<moduł>/`, fasada to `packages/daemon/src/facade.ts`. Moduł, który potrzebuje innego, deklaruje u siebie interfejs z tym, czego używa (np. `WorkspaceVcs`), a `createFacade` podaje mu instancję tamtego modułu. Biome pilnuje obu stron: plik modułu nie importuje z sąsiedniego katalogu modułu (z zewnątrz tylko pliki infrastruktury `src/infra/errors.ts`, `src/infra/atomic-write.ts`, `src/infra/map-limit.ts` i katalog `src/platform/`, wymienione w `biome.json`, więc moduł jest płaskim katalogiem), a kod poza modułami (transporty, start) sięga do modułów tylko przez `facade.ts`.

| `agents` | sesje Copilot CLI w PTY (§4.4, ADR-26), zadania w osobnych worktree (ADR-31), wykrywanie stanu; później budżet, nagrywanie | `procs` (grupa z PTY), `workspace` (korzeń repo po identyfikatorze), `vcs` (worktree i gałęzie zadań); później `logs`, `leases` | dziś pliki sesji w `sessions/<sesja>/` (wtyczka sesji, `hooks.jsonl`), usuwane przy zamknięciu sesji i przy starcie daemona, oraz zadania w `tasks.json` z worktree w `worktrees/<repo>/<gałąź bez prefiksu>`, usuwane na prośbę użytkownika; docelowo tabela `tasks` i nagrania |

Dwa moduły są „fundamentem”: `procs` i `logs`. `logs` nie zależy od żadnego modułu, `procs` tylko od `logs` (oddaje mu wyjście grupy), a wszystko inne na nich stoi, więc powstają najpierw i dostają najwięcej testów, w tym na Windowsie.

### 4.1 `procs`: grupy procesów

- Start zawsze tworzy **grupę** (ADR-20): na Windowsie Job Object z `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE` przez `bun:ffi`, na macOS i Linuksie nowa sesja (`setsid`, w Node `detached`) i sygnały do `-pgid`. Dziecko mise, które odpala mvn, który odpala javę, jest jedną jednostką. Na Windowsie lider trafia do joba zaraz po `spawn` (Node nie umie uruchomić procesu wstrzymanego); potomek utworzony w tej chwili, zanim lider trafi do joba, wypadłby z grupy, ale `mise` startuje kilka milisekund, zanim cokolwiek uruchomi. Kod systemowy jest w `platform/` (`GroupPlatform`), moduł `procs` (`ProcessGroups`) zna tylko interfejs.
- Właściciel grupy (`owner`) to klucz wołającego (dziś task mise w repo albo `mise install` w repo, budowany w module `mise` i nigdy nierozbierany z powrotem); na właściciela przypada jedna grupa, a drugi start zwraca stan pierwszej, dopóki ta nie jest potwierdzona jako pusta. Po końcu zostaje ostatni stan do następnego startu, w pamięci daemona. Stop w trakcie startu czeka na grupę, a po rozpoczęciu wyjścia daemona nowe grupy nie powstają. Kto czeka na wynik, a nie tylko pokazuje stan (komenda zbiorcza, §4.8), dostaje go z `ended(owner)`: stan `exited` bieżącej grupy po potwierdzeniu, że jest pusta; grupa, której nie da się zabić, nie kończy się nigdy.
- Stop eskaluje: łagodny sygnał (macOS i Linux: SIGTERM do grupy; Windows: zamknięcie stdin lidera, bo `GenerateConsoleCtrlEvent` wymaga wspólnej konsoli, której proces z ukrytym oknem nie ma), po czasie łaski (5 s; na Windowsie 2 s, bo zamknięcia stdin większość serwerów nie słucha) zabicie całej grupy (`SIGKILL` do `-pgid`, `TerminateJobObject`) i do 3 s czekania na pustą grupę, razem w 10 s, które powłoka czeka na zatrzymanie daemona (§5.4). Ta sama droga zatrzymuje sieroty przy starcie. **Stop zwraca sukces dopiero po potwierdzeniu**, że żaden proces grupy nie żyje (`kill(-pgid, 0)` daje `ESRCH`, job ma zero aktywnych procesów); inaczej błąd `stop_unconfirmed`, a uruchomienie zostaje `stopping`. Port nie jest jeszcze sprawdzany: przyjdzie z serwisami, które znają swój port.
- Lider, który zakończył się sam, zabiera resztę grupy: daemon zabija to, co zostało, i dopiero po potwierdzeniu pustej grupy uruchomienie jest `exited` (kod wyjścia, sygnał, czy zatrzymał je użytkownik i ostatnie linie wyjścia). Do tego czasu jest `stopping`, a grupa, której nie udało się zabić, zostaje w `runtime.json` i blokuje nowy start tego właściciela. Stop, który przyjdzie w tym czasie, czeka na to dobijanie i zwraca wynik lidera (jego kod wyjścia, bez `stoppedByUser`). Stop w trakcie startu czeka na start; gdy start się nie udał, grupy nie ma i stop kończy się `not_found`.
- Rejestr grup w `runtime.json` (w katalogu stanu): właściciel, komenda, katalog, PID lidera i jego czas startu według systemu (`ps -o lstart` ze stałymi `TZ=UTC` i `LC_ALL=C`, z dokładnością do sekundy). Grupa trafia tam po starcie i znika po potwierdzonym końcu; sierota, której nie udało się zabić, zostaje do następnego startu. Plik, którego nie da się odczytać, jest odkładany obok (`runtime.json.broken-<czas>`), a nieudany zapis trafia do logu i nie zmienia stanu w pamięci. Przy starcie daemona, pod blokadą startu i przed otwarciem API, sieroty są sprzątane tylko, gdy lider to ten sam proces: żyje z tym samym czasem startu (PID-y są recyklingowane) albo już nie żyje, a grupa o jego identyfikatorze tak (system nie nadaje PID-u, dopóki żyje grupa o tym numerze). Żywy PID z innym czasem startu (albo bez zapisanego czasu) nie jest zabijany: trafia do logu i znika z `runtime.json`, bo kolejne starty i tak nie rozstrzygną, czy to nasz proces. Na Windowsie pod Bun sierot nie ma, bo zamknięcie uchwytu joba przy śmierci daemona zabija grupę; pod Node daemon tylko zgłasza żywy PID.
- Wyjście daemona (Ctrl-C, sygnał, `POST /api/daemon/shutdown`) zatrzymuje wszystkie grupy tym samym stopem, równolegle, przed zamknięciem API.
- **Lider w PTY** (`startTerminal`, ADR-26): ta sama grupa, ale lider startuje w pseudoterminalu z `platform/terminal.ts` (`Bun.spawn({ terminal })`: ConPTY na Windowsie, PTY z nową sesją POSIX na macOS i Linuksie, więc PID lidera jest identyfikatorem grupy jak przy `setsid`). Wołający dostaje terminal do pisania i zmiany rozmiaru, a wyjście PTY idzie do niego i do ostatnich linii stanu `exited` (zamaskowanych przez `logs.lastLinesOnly`, bez logu, bo ekran to nie linie logu, ADR-28). Łagodny stop na Windowsie zamyka terminal (ConPTY wysyła wtedy procesom `CTRL_CLOSE_EVENT`, jak przy zamknięciu okna konsoli), na POSIX jest tym samym SIGTERM do grupy. Właściciel grupy z PTY musi być nowy: nie ma „drugiego startu”, który zwróciłby istniejącą. Pod Node PTY nie ma (`terminal_unavailable`), bo wymagałby natywnego addonu.
- stdout i stderr są zawsze czytane (nieczytany pipe blokuje dziecko przy ok. 64–192 KB) i idą do modułu `logs` (`attachOutput` w `process-groups.ts`): wołający podaje w `PipedGroupSpec` źródło logu (`logSource`), a `logs.open` daje wyjście uruchomienia (`RunOutput`), które robi z bajtów rekordy i oddaje 20 ostatnich niepustych linii (zamaskowanych, bez sekwencji ANSI i nadpisanego `\r` postępu) dla stanu `exited`.
- Katalog roboczy musi być pełną ścieżką istniejącego katalogu; wołający podaje korzeń repo lub worktree. Środowisko to środowisko daemona bez `TRACKWALL_HOME`, a na macOS z `PATH` z powłoki logowania użytkownika (`user-env.ts`): aplikacja otwarta z Findera dostaje od launchd tylko systemowy `PATH`, bez Homebrew i `~/.local/bin`.
- `portOwner(port)` zwraca właściciela z poziomem pewności: `exact` (PID z naszej grupy), `high` (potomek naszej grupy), `medium` (komenda pasuje do serwisu), `low`. Przy `low` daemon nie podejmuje akcji automatycznie. (Jeszcze nie zrobione.)

### 4.2 `logs`: magistrala

Pierwszy wycinek (ADR-28): log każdego taska mise (ze szczegółów repo i z komendy zbiorczej) i `mise install`, na żywo w szczegółach repo i w pliku JSONL. Parser ECS, `trace`, wyszukiwanie oraz logi serwisów, zadań i daemona to następne kroki; narzędzie MCP `tail` czyta ten sam log co UI, a `get_errors` wyciąga błędy z buforów wszystkich źródeł (§5.3, ADR-42).

- Rekord: `{ seq, ts, runId, stream, level, msg }` (`LogRecord` w `packages/protocol`), w pliku także `source`. Źródło (`LogSource`) to dziś `{ kind: 'mise-task', repo, miseTask }` oraz `{ kind: 'mise-install', repo }` dla `mise install` z komendy zbiorczej (§4.8); serwisy, zadania i daemon dojdą jako kolejne rodzaje, a pola docelowe (`trace_id`, `span_id`, `fields`, `raw`) przyjdą z parserem ECS.
- Jeden **globalny** `seq` dla wszystkich źródeł. Każde działanie daemona zaczyna go od chwili startu w milisekundach razy 1000, więc numery kolejnych działań się nie powtarzają, a kursor z poprzedniego działania jest mniejszy niż kursor pustego logu obecnego (chwila startu razy 1000). Kursor `sinceSeq` (`logs/tail` w API i narzędzie MCP `tail`) działa dla jednego źródła, a dla całego workspace w `get_errors` (ADR-42; później także w `search`). Kursor starszy niż bufor źródła zwraca `dropped: true` z rekordami od najstarszego w buforze; kursor z innego działania daemona (mniejszy niż kursor pustego logu albo większy niż ostatni `seq`, gdy zegar się cofnął) zwraca `dropped: true` z ostatnimi rekordami, jak bez kursora. Zegar cofnięty o mniej, niż trwało poprzednie działanie, może dać stary kursor w zakresie obecnego; wtedy klient dostaje rekordy po nim bez `dropped`, a UI i tak zaczyna log od nowa po zmianie połączenia.
- Ring buffer per źródło (2000 rekordów, `LOG_BUFFER_RECORDS`, i najwyżej 2 mln znaków treści, żeby długie linie JSON nie zajęły dziesiątek MB na task) dla UI i MCP, z rekordami kolejnych uruchomień (`runId`), tylko w pamięci. JSONL na dysku: `logs/<rodzaj>/<repo>/<task mise>.jsonl` (`logs/mise-install/<repo>.jsonl` dla `mise install`) w katalogu stanu, z nazwami kodowanymi tak, żeby były bezpieczne na Windowsie i macOS (`%XX` dla znaków spoza `[a-z0-9_-]`, w tym `:` i wielkich liter, prefiks dla nazw urządzeń jak `con`, skrót przy nazwie dłuższej niż 60 znaków, żeby ścieżka mieściła się w 260 znakach przy katalogu stanu do ok. 100 znaków). Zapis paczkami co 250 ms i przy wyjściu daemona; po 10 MB plik staje się `.1.jsonl` (poprzedni znika). Rotacja, która się nie udała (na Windowsie plik otwarty bez `FILE_SHARE_DELETE`, np. przez `Get-Content -Wait`), nie wstrzymuje zapisu: plik rośnie ponad limit do następnej udanej rotacji, a błąd trafia do logu daemona raz. Nieudany zapis zostaje w buforze do następnej próby (do 4 MB, potem rekordy nie trafiają do pliku), a błąd i utrata rekordów trafiają do logu daemona raz; zapis przerwany w połowie (brak miejsca) może po ponowieniu powtórzyć część rekordów w pliku. Opcjonalny indeks `trace_id -> (plik, offset)` w SQLite dla `trace(trace_id)` przyjdzie z `trace`.
- Linia: dekoder UTF-8 i niedokończona linia osobno dla stdout i stderr, sekwencje ANSI usuwane, maskowanie, potem z linii z `\r` zostaje to, co po ostatnim `\r` (postęp w terminalu). Linia bez końca dłuższa niż 64 KB staje się rekordem (podział nigdy nie przecina sekretu: zostaje przed nim albo przed ostatnimi znakami, w których sekret mógłby się dopiero zaczynać), rekord ma najwyżej 16 KB treści, puste linie zostają w logu (w ostatnich liniach stanu nie).
- Level from the line text, until there is an ECS parser: `ERROR`/`FATAL`/`SEVERE`/`npm ERR!`/`npm error`, or `error`/`fatal` at the start of a line, is `error`, and so is a compiler diagnostic with a file location (javac `Foo.java:12: error:`, tsc `a.ts(3,5): error TS2322:`, kotlinc `e: ` with a file) and Vite's `Internal server error:`; `WARN`/`WARNING`, `warning` at the start, `npm warn`, `Foo.java:7: warning:` and kotlinc `w: ` with a file are `warn`; upper-case `DEBUG` and `TRACE`; everything else is `info`. The task prefix `[name] ` mise puts before the lines of dependencies does not change the level (a level is not a prefix: an upper-case level word alone or with a thread, like Maven `[ERROR]` or `[ERROR:main]`, or a lower-case one alone, like sbt `[info]`; so a task named exactly `debug` keeps its prefix). The stream does not decide, because many tools write ordinary progress to stderr.
- **Errors from logs** (`get_errors`, ADR-42): `errorBlocks` (`error-blocks.ts`) splits the records of one source into blocks, separately for each run and stream. A block starts at an unindented record at the threshold (`error`, with `minLevel: warn` also `warn`; an indented line at `error` level, like `b.old(Level.SEVERE);` under a javac warning, is context, not an error), a failed Gradle test (`OrdersTest > rejects FAILED`), an exception header (`java.lang.IllegalStateException: …`, `TypeError: …`, `Exception in thread "main" …`), a `Caused by:` without its beginning, or the opening of a region. It is extended by Java and Node stack frames (`at …`, `... 12 more`), `Caused by:`/`Suppressed:`, an exception header under a logger line (until the block has frames), indented and blank lines, a line of asterisks, Node's `Require stack:` with its `- path` lines, and further lines with the same level tag and no timestamp (Maven `[ERROR]`, `npm error`). Whatever starts an error (an `error` record, an exception header, `Caused by:`, a report) under a warning starts an error of its own, so an error does not depend on `minLevel`. Regions without indentation last until their end: the Spring "APPLICATION FAILED TO START" report until the blank line after the `Action:` paragraph, the Gradle `FAILURE:` report until `BUILD FAILED`, and both until a line starting with a date or time (the logger's next event), a Maven level tag or a Gradle `> Task` line (the build tool that ran the app), or another region's start, which matters for a Spring report without `Action:`; a block has at most 500 records. Outside a region any other line closes the block, and trailing blank lines are not part of it. `collectErrors` (`log-errors.ts`) merges the same errors of one source (the exception and its first frame, or without an exception the first 20 lines, after replacing numbers, UUIDs, hex ids and bracketed parts such as thread names and trace ids, but keeping file locations like `Orders.java:12` so different compiler errors stay apart) into one entry with `count` and `firstTs`, with the lines and `seq` of the latest occurrence, and trims the lines: the first 10 frames of each run of frames (recognised without the mise task prefix), the rest as one line `… N frames omitted`, at most 60 lines of 4000 characters (`omittedLines` counts what was left out). The entry's `exception` is the last `Caused by:` of the main chain (not one at or under the indentation of a `Suppressed:` exception) or the first header. The `sinceSeq` cursor skips errors whose first record is not after it, so a block still being written when asked comes once, with the lines it had at that moment. Errors are computed on every request from the in-memory buffer, without an index and without reading the JSONL files, so errors older than a source's buffer are gone with it.
- Parser ECS (później): Spring Boot z `LOGGING_STRUCTURED_FORMAT_CONSOLE=ecs` daje JSON z `log.level`, `trace.id`, `error.stack_trace`. Linia niebędąca JSON-em dostaje `level` z heurystyki i trafia do `raw`.
- Maskowanie: zbiór wartości sekretów danego procesu jest znany modułowi `logs` i zamieniany na `***` **przed** zapisem do bufora, pliku i ostatnich linii stanu. Agent i plik widzą już zamaskowaną wersję. Dziś sekretem jest wartość zmiennej ze środowiska procesu, której nazwa ma segment `TOKEN`, `SECRET`, `PASSWORD`, `PASSWD`, `PASSPHRASE`, `API_KEY`/`APIKEY`, `PRIVATE_KEY`, `CREDENTIAL(S)` albo `PAT` (np. `GH_TOKEN`, `DB_PASSWORD`), o długości co najmniej 8 znaków; wartość wieloliniowa (klucz PEM) daje każdą swoją linię osobno, a wystąpienia sekretów, które na siebie zachodzą, są łączone przed zamianą. Sekrety wstrzykiwane przez moduł `secrets` dojdą do tego zbioru (luka: §8).
- ANSI usuwane przy zapisie; kolor w UI wynika z `level`. Widok to lekka lista linii pod wierszem taska w zakładce „mise tasks” (przycisk „Log”, uruchomienie otwiera go samo), która idzie za nowymi liniami, dopóki użytkownik nie przewinie jej w górę, a stderr ma znacznik z boku. UI odpytuje `logs/tail` od kursora co sekundę, póki log jest otwarty, i od razu, gdy odpowiedź jest pełna; WebSocket `log.append` (§5.2) zastąpi odpytywanie bez zmiany rekordu. xterm.js zostaje dla PTY sesji zadań (ADR-28).

### 4.3 `services` i `leases`

Serwis to para (repo, task mise `dev`) plus port i sonda. Stany: `stopped`, `starting`, `healthy`, `unhealthy`, `stopping`, `crashed(exitCode, lastStderr)`.

Dzierżawa mówi, **która gałąź/worktree** zajmuje serwis na jego porcie. Domyślnie dzierżawcą jest repo główne. Zadanie agenta, które zmienia kod serwisu, prosi o dzierżawę; daemon zatrzymuje instancję z repo głównego, startuje instancję z worktree zadania na tym samym porcie, a po zakończeniu zadania (lub ręcznie) oddaje. Dzięki temu reszta grafu nie musi niczego wiedzieć. Routing po nagłówku przez proxy jest poza zakresem, dopóki nie pojawi się potrzeba dwóch instancji naraz; interfejs `leases` jest tak pomyślany, żeby proxy dało się dołożyć bez zmiany pozostałych modułów.

### 4.4 `agents`: zadania

- **Adapter CLI** = szablon komendy (`copilot --prompt {prompt_file} ...`), sposób podania konfiguracji MCP, komenda wznowienia sesji, zestaw detektorów stanu. **Jedynym adapterem jest Copilot CLI** (decyzja z 2026-10-23). Interfejs adaptera zostaje, bo porządkuje kod, ale nie projektujemy pod Claude Code ani Codex i nie testujemy ich detektorów.
- Sesja działa w **PTY należącym do daemona** (ConPTY na Windowsie). UI podłącza xterm.js przez WebSocket, `ws attach` robi to samo w terminalu. Docelowo wyjście PTY jest nagrywane (format asciicast) do `sessions/<task>.cast`; dziś nagrywa tylko skrypt `copilot-record.ts`, a sesje w daemonie (niżej) nie.
- **Wykrywanie stanu**, od najpewniejszego źródła: (1) hooki CLI, jeśli adapter je ma, (2) sekwencje terminala OSC 9 / 777 / 99 oraz komenda `ws notify <state>` dostępna w skryptach agenta, (3) wzorce ekranu (po stronie daemona, nie w UI; pierwszy działa na samym tekście wyjścia, parser VT przyjdzie z wzorcami, które go wymagają), a obok nich klawisze, którymi człowiek odpowiada w terminalu sesji, dla tego, czego CLI nie zgłasza. Każda zmiana stanu niesie `source` i `confidence`, więc UI może pokazać „probably asking for approval”.
- Stany: `Working`, `Input`, `Approval`, `Plan`, `Done`, `Error`, plus `Stale` (brak sygnału dłużej niż próg). Budżet czasu i liczby commitów z wymuszonym zakończeniem.
- **Sesje w daemonie** (ADR-26, widok „Sessions”): `agents.start {repo}` uruchamia Copilot CLI (`copilot` z `PATH` użytkownika; na Windowsie zamiast `copilot.cmd` z npm natywny `copilot.exe` z paczki platformy, bo `cmd.exe` psuje argumenty, `findCopilot`) w korzeniu repo z folderu z projektami, przez `procs.startTerminal`, z `--plugin-dir` wtyczki sesji, w PTY 120×30, który przyjmuje rozmiar ostatniego okna terminala. Środowisko to `userEnv` z `TERM=xterm-256color` i `COLORTERM=truecolor`. Sesji może działać kilka naraz; każda ma identyfikator (UUID) i katalog `sessions/<sesja>/` w katalogu stanu z wtyczką sesji i `hooks.jsonl`. Hook wtyczki to sam daemon z podkomendą `copilot-hook <zdarzenie> <hooks.jsonl>` (`selfCommand`: binarka z wydania albo runtime i skrypt ze źródeł, Bun z `--no-env-file`), który dopisuje rekord hooka do pliku, a sesja czyta nowe linie co 200 ms (`HookTail`), razem z progiem `Stale` i końcem grupy w `procs`. Ekran każdej sesji trzyma emulator terminala bez okna (`TerminalScreen`, `@xterm/headless`, 2000 linii przewijania), z którego okno w UI dostaje obraz ekranu przy podłączeniu (§5.2). `stop` zatrzymuje grupę jak każdą inną (§4.1), a zatrzymanie przez użytkownika kończy stan jako `Done`, nie `Error`, choć proces kończy się sygnałem. Zakończona sesja zostaje na liście z ostatnim ekranem, dopóki użytkownik jej nie zamknie (`dismiss`, usuwa też jej katalog). Sesje żyją w pamięci: wyjście daemona zatrzymuje je razem z resztą grup, a start daemona usuwa katalog `sessions/` po poprzednim działaniu. A session "waits for you" (`Session.needsAttention`, computed in the daemon by `SessionAttention`, ADR-47) when it runs and its state is `Approval` or `Plan`, or `Input` the user has not seen yet. A session terminal window in front of the user (focused and visible for at least 1 s, `FocusReporter` in the UI; the window sends `focus` over `/ws/pty`, §5.2) or a key typed into the session (not an answer xterm.js sends to a terminal query, which starts with ESC) marks the `Input` seen, the `Input` an Esc causes included, and a window in front of the user when the state changes sees the new state at once; only a change to another state makes it unseen again. `Approval` and `Plan` wait until the user answers, because the agent is blocked in the middle of the turn. The UI shows seen `Input` as "idle" (the dashboard state `idle`); the UI (the counter on the activity bar, "Next waiting") and the tray (§5.4) only read the field. Pierwsze okno Copilot CLI w nowym katalogu (zaufanie folderu) i logowanie nie dają hooka, więc sesja jest wtedy bez stanu („state unknown”), choć czeka na Ciebie. Daemon sesji nie nagrywa; nagrania robi skrypt `copilot-record.ts`. Każda sesja dostaje serwer MCP Trackwall (§5.3, ADR-24): daemon zapisuje w katalogu sesji `mcp-config.json` z mostem stdio (`sessionMcpStdioCommand`: wpis z widoku „Daemon” z `--session-token-file` tej sesji, ADR-39; `copilotMcpServers` w `protocol`) i podaje go jako `--additional-mcp-config @<plik>`, więc sesja ma narzędzia Trackwall bez `copilot mcp add` i bez zmiany konfiguracji użytkownika. In the same way it gets **session instructions** (`session-instructions.ts`, ADR-46): the file `instructions/trackwall.instructions.md` in the session directory with `applyTo: "**"`, whose directory the daemon appends, after a comma, to `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` in the session environment (the user's own value stays first, under the user's spelling of the name on Windows). Copilot CLI loads it as a repository instruction next to the repo's `AGENTS.md` and `.github/copilot-instructions.md`, so the user's repo and `~/.copilot` stay untouched. The file holds the session's role, built only from the repo and task ids, never from agent text: a main session in the repo root works in the user's working copy and hands larger or parallel work, especially in another repo, over with `propose_task`; a task session works only in its worktree, commits on the task branch without switching branches, pushing, merging or opening pull requests unless the prompt asks for it, and ends (also when stuck) with `report_result`; it is told that `run_mise_task` runs in the repo root, not in its worktree. The MCP instruction (§5.3) follows. A state directory with a comma in its path does not fit that variable, so the session then starts without the file and the daemon logs it. Zadanie (niżej) dodaje do sesji worktree, polecenie na start, wznowienie i zmiany na żywo; budżet czasu to kolejny krok.
- **Copilot CLI** (ADR-17, detektory w `modules/agents/`, nagrywanie w `scripts/copilot-record.ts`). Daemon podaje sesji **wtyczkę sesji** przez `--plugin-dir`: katalog z `plugin.json` i `hooks.json`, poza worktree i poza `~/.copilot`, więc nie zmienia konfiguracji użytkownika ani plików repo. Hooki to programy uruchamiane bez powłoki (`exec` + `args`) z katalogu wtyczki, nie repo, i z `--no-env-file` (inaczej Bun wczytałby `bunfig.toml` i `.env` z repo użytkownika; potrzebne są oba), które zapisują **rekord hooka** do `hooks.jsonl` sesji: zdarzenie, czas i tylko pola z listy (`CopilotHookPayload`: identyfikator i czas sesji, źródło startu, powód końca, rodzaj i przycięta treść powiadomienia, nazwa narzędzia), a z reszty same nazwy pól, żeby z nagrań poznać nieudokumentowany payload bez zapisywania promptu, argumentów i wyników narzędzi; docelowo zgłoszą go do daemona z tokenem sesji (ADR-39). Zdarzenia i stany: `sessionStart` → `Input`, `userPromptSubmitted` i `postToolUse` → `Working`, `notification` po rodzaju: `permission_prompt` → `Approval` z pewnością `high` (rodzaj z `@github/copilot-sdk` potwierdzony w sesji na macOS, ADR-17), `elicitation_dialog` → `Input` z pewnością `medium` (rodzaj znany tylko z tekstów Copilot CLI 1.0.103, nie z dokumentacji ani z nagrania); inne rodzaje, m.in. `agent_idle`, `agent_completed` i `shell_completed` o agentach i komendach w tle, nie zmieniają stanu; bez rodzaju `Approval` / `Plan` / `Input` po całych słowach treści z pewnością `low`, `agentStop` → `Input` (koniec tury), `errorOccurred` → `Error`, `sessionEnd` → `Done` albo `Error` po `reason`. Bez `preToolUse` i `permissionRequest`: ich hook, który się wysypie, odmawia agentowi narzędzia, a `permissionRequest` działa także przy zgodzie udzielonej automatycznie, więc nie znaczy „czeka na człowieka”. Z terminala: OSC 9;4 (pasek postępu, domyślne `terminalProgress`) daje `Working` przy stanie 1 lub 3, `Input` z niską pewnością przy zdjęciu paska i `Error` z niską pewnością przy stanie błędu 2; Copilot CLI 1.0.103 wysyła go tylko wtedy, gdy rozpozna Windows Terminal (`WT_SESSION`), więc na macOS i w sesji daemona uruchomionego poza Windows Terminal paska nie ma, a przy prośbie o zgodę wysyła dalej stan 3 (ADR-17); tytuł okna (OSC 0 / 2) to opis bieżącej pracy, nie stan. Z klawiatury (`copilot-keys.ts`, źródło `keyboard`): Copilot CLI nie wysyła hooka po odpowiedzi na prośbę o zgodę (po zgodzie pierwszy hook to `postToolUse` po końcu komendy) ani po przerwaniu tury Esc, więc sesja w daemonie i skrypt nagrywający patrzą na pojedyncze klawisze z okna terminala: Enter albo cyfra 1–9 (wybór opcji bez Entera) w `Approval` albo `Plan` daje `Working`, Esc albo Ctrl+C w `Working`, `Stale`, `Approval` albo `Plan` daje `Input`, oba z pewnością `medium`. Klawisz liczy się ze stanu po hookach, które już są w `hooks.jsonl`, a nie po ostatnim cyklu odczytu (co 200 ms), więc prośba o zgodę dopisana tuż przed Enter nie zostaje po nim w `Approval`. Liczy się tylko cały kawałek wejścia równy jednemu klawiszowi, więc tekst, wklejka i strzałki nie zmieniają stanu, a Enter ani cyfra przy wpisywaniu promptu też nie (turę zgłasza hook, a komenda w rodzaju `/model` hooka nie ma). Enter na opcji „No, and tell Copilot what to do differently” daje `Working`, choć Copilot czeka jeszcze na tekst; cyfra „No” też daje najpierw `Working`, bo numer opcji zależy od okna, a przerwanie rozpoznaje zaraz potem wzorzec ekranu (niżej). Z ekranu jeden wzorzec (`copilot-screen.ts`, bez parsera VT, po samym tekście wyjścia): komunikat „Operation cancelled by user”, którym Copilot CLI kończy przerwaną turę (w nagraniach z macOS i z Windowsa ciągły tekst w jednym kawałku wyjścia), daje `Input` z pewnością `medium`, ale tylko do 10 s po klawiszu sesji, który zmienił stan (odpowiedź albo przerwanie), bo przerwanie zawsze idzie po takim klawiszu, a ten sam tekst wraca przy przerysowaniu historii ekranu. Jako źródło `screen` może tylko zakończyć `Working`; łapie przerwanie, którego klawisz nie rozpoznał, np. gdy Enter na „No, and tell Copilot…” albo cyfra opcji „No” od razu kończy turę. Inne wzorce ekranu powstaną z prawdziwych nagrań, jeśli hooki, OSC i klawisze okażą się za mało.
- **Łączenie sygnałów** (`TaskStateTracker`): najlepsze źródło, które się odezwało, wygrywa, więc po pierwszym hooku OSC i ekran nie zmieniają stanu, a sesja bez działających hooków dostaje stan z OSC. Wyjątek: słabsze źródło może zakończyć `Working` (np. zdjęcie paska postępu), bo zgubiony hook końca tury zostawiłby sesję w `Working`, a potem w `Stale`, choć czeka na człowieka; zacząć `Working` po hooku już nie może. Klawisz człowieka (`keyboard`) przechodzi zawsze i nie zmienia rangi źródeł, bo mówi o tym, czego hooki nie zgłaszają; to, w jakim stanie klawisz coś znaczy, rozstrzyga detektor klawiszy. `Stale` tylko z `Working` po progu bez wyjścia i sygnałów (czekanie na człowieka nie jest zawieszeniem), z czasem progu, a nie chwili sprawdzenia, więc na żywo i z nagrania wychodzi to samo; wyjście przywraca stan sprzed `Stale`. Wyjście procesu jest ostateczne: `Done` przy kodzie 0, `Error` przy innym, chyba że hook `sessionEnd` już zgłosił koniec.
- **Nagranie** `.cast` ma oprócz wyjścia znaczniki (`m`) z rekordami hooków, rodzajem klawisza (`enter`, `choice`, `escape`, `interrupt`) i kodem wyjścia, więc stan da się policzyć jeszcze raz z samego nagrania (`replayCopilotRecording`) tym samym kodem, który działa na żywo. Na żywo stan liczy się z czasu zdarzenia zapisanego w nagraniu (pełne ms), a nie z chwili liczenia, więc odtworzenie daje te same zmiany co do milisekundy. Treść wejścia z klawiatury nie jest nagrywana, tylko każdy klawisz sesji (pojedynczy Enter, cyfra 1–9, Esc albo Ctrl+C), także taki, który stanu nie zmienił. Skrypt zapisuje nagranie synchronicznie przy każdym kawałku wyjścia i czyta `hooks.jsonl` co 200 ms, tym samym kodem co daemon (`HookTail`, `runCopilotHook`); gdy daemon zacznie nagrywać sesje, zapis musi przejść na asynchroniczny. Skrypt sięga do plików modułu wprost, bo działa bez daemona.
- **Zadania** (ADR-31, `tasks.ts`, widok „Sessions”): `agents.create-task {repo, prompt}` tworzy gałąź `trackwall/<skrót>-<6 znaków UUID zadania>` (skrót do 32 znaków z pierwszych słów polecenia bez polskich znaków, tylko `[a-z0-9-]`, `taskSlug`) od gałęzi domyślnej i jej worktree (`git worktree add -b`) w `worktrees/<repo>/<skrót>-<6 znaków>` w katalogu stanu, poza folderem z projektami: lista repo go nie widzi, a katalog roboczy repo nie dostaje nieśledzonego `.worktrees`. Gałąź domyślna bez pytania serwera: z `refs/remotes/<remote>/HEAD`, lokalna, gdy istnieje (to ją przesuwa synchronizacja i na niej leżą niewypchnięte commity), inaczej zdalna; repo bez tego wskazania daje gałąź wybraną, a odłączony HEAD sam commit (`baseBranch: null`). Commit, od którego wyszła gałąź, to **commit bazowy** zadania. Zmiany worktree w jednym repo (`worktree add`, `worktree remove`, `branch -D`) idą po kolei, bo walczą o blokady w `.git`; dwa zadania tworzone naraz w jednym repo dostają osobne gałęzie i katalogi. Na Windowsie każde polecenie gita dostaje `-c core.longpaths=true`, bo worktree w katalogu stanu wydłuża ścieżki plików repo. Zadanie trafia do `tasks.json` przed startem sesji, więc worktree nie zniknie z listy, gdy daemon padnie; nieudany start sesji (brak Copilot CLI) usuwa worktree i gałąź, gdy git przestanie czytać worktree. Nieudany `worktree add` (np. limit czasu przy LFS) może zostawić gałąź i katalog, których lista nie pokazuje; daemon ich nie sprząta, bo nie wie, czy to on je utworzył (gałąź o tej nazwie mogła już istnieć), więc usuwa się je ręcznie (`git worktree remove`, `git branch -D`). Sesja zadania to zwykła sesja (wyżej) w worktree, z `--session-id=<UUID zadania>` i `--interactive=<polecenie>`: Copilot CLI startuje TUI i wysyła polecenie jako pierwszą wiadomość (opcja z `copilot --help` 1.0.103), a forma z `=` sprawia, że polecenie zaczynające się od `-` nie jest opcją. Polecenie ma najwyżej 8000 znaków, bo idzie jednym argumentem, a wiersz poleceń Windowsa mieści 32 767.
- **Wznowienie** (`resume-task`): nowa sesja w worktree z `--resume=<UUID zadania>`, więc Copilot CLI wraca do rozmowy zadania; zakończone sesje zadania znikają z listy. Zadanie z działającą sesją to `bad_request`, tak jak druga akcja na zadaniu w trakcie pierwszej. Zadania przeżywają restart daemona (`tasks.json`, zapis atomowy), a ich sesje nie, więc po restarcie zadanie jest „no session” do wznowienia albo zakończenia. Katalog worktree nie jest zapisywany, tylko liczony z identyfikatora repo i gałęzi (`taskWorktree`), więc ręczna zmiana pliku nie wskaże katalogu spoza `worktrees/`; schemat dopuszcza tylko gałąź `trackwall/[a-z0-9-]`, pełny hash commita bazowego i pełną ścieżkę repo. Plik, który go nie przechodzi, trafia obok jako `tasks.json.broken-<czas>`, a worktree zostają na dysku.
- **Zmiany zadania** (`task-changes`, `TaskChanges`): katalog roboczy worktree z nowymi plikami, bez ignorowanych, względem commita bazowego, czyli commity zadania i to, czego agent jeszcze nie zacommitował, razem. Nowe pliki (`git ls-files --others --exclude-standard`) trafiają do indeksu tymczasowego (kopia indeksu worktree w katalogu tymczasowym, `GIT_INDEX_FILE`, usuwana po każdym pytaniu) wpisem z hashem pustego bloba (`git update-index --index-info`), tak jak przy `git add --intent-to-add`, ale bez zapisu tego bloba do `.git/objects`; katalog z własnym repo to, jak w `git add`, wpis submodułu z HEAD tamtego repo, a repo bez commitów albo w innym formacie obiektów odpada. Liczenie zmian niczego więc nie zapisuje do repo: indeks, którego używa agent, zostaje nietknięty, a kilka okien „Changes” naraz nie pisze tego samego obiektu (na Windowsie drugi zapis kończył się „Permission denied”). Potem `git diff <commit bazowy>` (katalog roboczy) bez wykrywania zmian nazw, zewnętrznych programów diff i `textconv`: pliki z rodzajem zmiany i liczbą linii, diff ucięty do 1 MB (ten sam znacznik uciętego wyniku, gdy lista nowych plików przekroczy 8 MB), liczba commitów od bazy i wpisów `git status`. UI odpytuje co 2 s, póki zakładka „Changes” jest otwarta, i pokazuje najwyżej 4000 linii diffu. Odpytywanie zamiast watchera plików: git i tak musi policzyć diff, a rekursywny `fs.watch` na worktree z `node_modules` albo `target` daje burze zdarzeń i działa różnie na Windowsie, macOS i Linuksie.
- **Shared files** (`task-shared-files {task}`, result `{shared: TaskSharedFiles[]}`, ADR-44): the files on a task's list of changes (as in `task-changes`, without the diff) that are also on the list of changes of another task of the same repo, per such task. Changes of the other task that cannot be read (being ended, worktree deleted by hand, broken index) are left out, because this is only a warning; a failure to read the task's own changes is returned as in `task-changes`. It is computed on request, one git read per task of the repo, at most 3 at a time; the task panel in the UI (`SharedFiles`) asks every 5 s and shows a warning above the tabs with a button to the other task.
- **Zakończenie** (`remove-task {task, keepBranch, discardChanges}`, wynik `null`): tylko bez działającej sesji, bo jej procesy piszą w worktree i na Windowsie blokują jego pliki; czeka na wszystkie trwające liczenia zmian (kilka okien), a w trakcie zakończenia `task-changes` odmawia. Bez `discardChanges` daemon liczy, co przepadnie: wpisy `git status --untracked-files=all` worktree, commity z odłączonego HEAD worktree, których nie ma na żadnej gałęzi ani tagu (znikają z worktree niezależnie od `keepBranch`), katalog worktree, którego git już nie zna (przerwane usuwanie, `worktree prune`, repo sklonowane od nowa w tym samym miejscu; nie da się policzyć, co w nim jest), a bez `keepBranch` także commity `<commit bazowy>..<gałąź>`, i przy czymkolwiek odmawia błędem `unsaved_changes` z tym, co by przepadło; UI pokazuje go i dopiero wtedy pyta „Remove anyway”. Pliki ignorowane przez gita (zależności, wyniki buildu) przepadają zawsze i UI mówi o tym przed zakończeniem. Potem `git worktree remove --force`; git zdejmuje rejestrację przed kasowaniem plików, więc usunięcie przerwane przez plik trzymany przez inny proces zostawia zwykły katalog, który daemon po potwierdzeniu kasuje sam, a rejestrację katalogu usuniętego ręcznie czyści `git worktree prune`. Bez `keepBranch` jeszcze `git branch -D`; sesje zadania znikają z listy. Zadanie z repo, którego już nie ma (przeniesione, odłączony dysk), nie da się sprawdzić gitem: tak jak katalog, którego git nie zna: bez `discardChanges` odmowa `unsaved_changes`, gdy worktree jest na dysku, a po potwierdzeniu daemon kasuje katalog worktree (leży w `worktrees/`, bo jest liczony z repo i gałęzi), gałąź zostaje w przeniesionym repo, a jego rejestrację czyści tam `git worktree prune`. `open-task-editor` otwiera worktree w VS Code (`vscode://`).
- **Zaufanie folderu**: Copilot CLI pyta o zaufanie w każdym nowym katalogu, więc w każdym worktree. Wpis w `trustedFolders` (`~/.copilot/config.json`) obejmuje podkatalogi (sprawdzone na 1.0.103), więc UI podpowiada katalog `worktrees/` (`SessionList.worktreesDir`); daemon nie zmienia konfiguracji Copilot CLI. Lista `sessions` zwraca też zadania (`tasks`, od najnowszego, bez sesji), a UI łączy zadanie z jego najnowszą sesją (`Session.task`) i pokazuje je jako jedną pozycję obok sesji w korzeniu repo.
- **Sesja główna i propozycje zadań** (ADR-39, `task-proposals.ts`, `session-wait.ts`, widok „Sessions”): sesja (albo agent nadrzędny spoza Trackwall) zleca pracę innemu agentowi narzędziem MCP `propose_task {repo, title, prompt}`. Daemon zapisuje **propozycję zadania** (`TaskProposal`: identyfikator, repo, tytuł do 80 znaków w jednej linii, polecenie do 8000 znaków, `proposedBy` z sesją po tokenie sesji albo `null` dla agenta spoza Trackwall) tylko w pamięci, najwyżej 20 czekających naraz; nic się nie uruchamia. Lista `sessions` zwraca je w `proposals`, a widok pokazuje je z „waiting for your decision” i liczy na pasku widoków razem z sesjami, które czekają. The view's list is a tree (`sessionRows` in `lib/session-entries.ts`): a proposal or task with `proposedBy.session` sits under the entry that holds that session (a session in the repo root, or a task, also when it is an older session of the task), in the same order on every level (proposals first, then most recently started), and an entry with children has a “main” badge with their count; a proposal from an agent outside Trackwall or from a session no longer listed is at the top level. Proposals also show in the dashboard's “Needs you” queue (§5.5) and in the tray menu (§5.4). „Start task” (`approve-proposal {proposal, prompt}`, z poleceniem, które użytkownik mógł poprawić) tworzy zadanie jak `create-task`, ale z identyfikatorem propozycji, jej tytułem (`Task.title`; z niego, a nie z polecenia, powstaje skrót gałęzi) i pochodzeniem (`Task.proposedBy`). W trakcie zatwierdzania propozycja zostaje na liście, żeby panel w UI nie zniknął razem z błędem i poprawionym poleceniem, ale drugie zatwierdzenie albo odrzucenie to `not_found`, a czekanie widzi `starting`; lista `sessions` przestaje ją zwracać, gdy tylko zadanie o jej identyfikatorze jest na liście, a wybrana w UI propozycja przechodzi na to zadanie. Gdy zadanie nie powstało, propozycja znów czeka na decyzję (nieudany `worktree add` sprząta gałąź, którą git zakłada przed checkoutem, więc ponowna próba z tą samą gałęzią się udaje; gdy samo sprzątanie się nie uda, np. przez plik trzymany na Windowsie, błąd wymienia katalog i gałąź do usunięcia ręcznie), a zadanie, które zostało po nieudanym sprzątaniu, użytkownik kończy sam. „Reject” (`reject-proposal`) usuwa ją z listy, a daemon pamięta 100 ostatnich odrzuceń, żeby czekająca sesja dostała `proposal_rejected`. Sesja zadania zgłasza wynik narzędziem `report_result {summary}` (do 4000 znaków): daemon zapisuje go w `Task.summary` z czasem (w `tasks.json`, więc przeżywa restart), a UI pokazuje go nad zakładkami zadania; wołać może tylko sesja, która ma zadanie, i tylko do swojego. `wait_for_session {session | task, timeoutSeconds ≤ 55}` co 200 ms czyta stan z pamięci daemona i kończy czekanie, gdy propozycję odrzucono, sesja nie odpowiada (`Stale`), czeka na człowieka (`needsAttention`) albo zgłosiła błąd (`Error`, bo nie wiadomo, czy po nim przyjdzie koniec tury), skończyła się albo zadanie nie ma sesji; po limicie czasu zwraca `proposal_pending`, `starting` (zatwierdzana propozycja albo zadanie z trwającą akcją, np. start sesji) albo `working`. Czekanie na zadanie idzie za jego najnowszą sesją, a na własną sesję jest odmawiane. Sesja zadania z poleceniem na start (`--interactive`) dostaje z pierwszego hooka `sessionStart` stan `Working` zamiast `Input` (kolejny, po `/clear` albo `/resume` w sesji, już nie niesie polecenia), bo od razu pracuje nad poleceniem; inaczej czekanie kończyłoby się, zanim agent zacznie, a tray mignąłby „czeka na Ciebie”. **Token sesji** (`session-tokens.ts`): każda sesja dostaje losowy token (32 bajty) w pliku `sessions/<sesja>/session-token`, a jej most stdio opcję `--session-token-file`; most wysyła token przy każdej wiadomości w nagłówku `x-trackwall-session-token`, a daemon trzyma w pamięci tylko jego skrót SHA-256 i po nim poznaje sesję, która woła. Ta sama sesja przez `list_sessions` widzi swój identyfikator (`caller`).

### 4.5 `workspace` i `vcs`: lista repo, przeglądanie, klon z hostingu i synchronizacja

Pierwszy wycinek modułu `workspace` (etap 3 w §11, zrobiony wcześniej na prośbę użytkownika): repo z folderu z projektami, ich przeglądanie, klon z GitLab albo GitHub do folderu i synchronizacja wszystkich repo (fetch i fast-forward, bez kroku mise i ekstraktorów; kroki mise na wybranych repo daje komenda zbiorcza, §4.8).

- **Folder z projektami** (`projectsDir`, ADR-18) to jedyne źródło listy repo. Jego pełna ścieżka jest kluczem `projectsDir` w `workspace.yaml` (ADR-13); ustawia się go w widoku „Settings” (`set-projects-dir`, katalog musi istnieć) albo ręcznie w pliku. Plik jest czytany przy każdym zapytaniu, więc ręczna edycja działa bez restartu; zapis z UI zmienia tylko ten klucz i zachowuje komentarze oraz pozostałe klucze. Nie ma wartości domyślnej: dopóki folder nie jest ustawiony, lista jest pusta, a UI prowadzi do ustawień.
- **Lista repo** powstaje przy każdym zapytaniu z bezpośrednich podkatalogów folderu, które mają `.git` (katalog albo plik, jak w worktree); katalogi z kropką na początku są pomijane, dowiązanie do katalogu liczy się jak katalog. Głębiej Trackwall nie szuka. Identyfikator repo pochodzi z nazwy katalogu (`orders-bff`; przy kolizji, np. `Zażółć` i `zazolc`, przyrostek `-2` w kolejności po nazwie, więc nowy katalog, który sortuje się wcześniej, przejmuje identyfikator bez przyrostka). Folder jest czytany i sprawdzany przy zapisie asynchronicznie (bywa na dysku sieciowym albo uśpionym dysku zewnętrznym), a stan repo na liście jest pobierany najwyżej dla 8 repo naraz. Repo sklonowane albo usunięte poza Trackwallem pojawia się i znika przy następnym odpytaniu listy; w Trackwallu repo dodaje się tylko klonem z hostingu (niżej), a usuwania nie ma. A folder dropped on the window (ADR-51) does not add a single repo either: `dropped-folder` says what it is (a listed repo, a git repo elsewhere, a folder with repos directly inside it, a folder without any, a file), and the UI opens the listed repo or offers the folder, or the folder that holds the dropped repo, as the projects folder through `set-projects-dir`. Folder, który zniknął po ustawieniu (np. odłączony dysk), daje błąd `projects_dir_unavailable` z jego ścieżką.
- **Show in Explorer/Finder** (`open-folder`, ADR-51) opens the folder of a listed repo in the system's file manager, like `open-editor` opens VS Code: the route takes a repo id, the facade's `openFolder` gets the path from the list (`explorer.exe` on Windows, `open` on macOS, `xdg-open` on Linux, `infra/system-open.ts`), and the daemon does not wait for it. It works in the page opened from the daemon too.
- **Hostingi repo** (`repoHosts`, ADR-19) to lista w `workspace.yaml` (`- kind: gitlab` + `host: gitlab.example.com`, tak samo `github`), ustawiana w widoku „Settings” (`set-repo-hosts`) albo ręcznie, bez powtórzeń (schemat `RepoHosts`); każdy klucz `workspace.yaml` jest sprawdzany osobno, więc zły wpis w `repoHosts` psuje tylko hostingi, a nie listę repo; adres instancji GitLab zna tylko plik użytkownika (ADR-7). Daemon pyta hosting przez program, którym użytkownik jest w nim zalogowany: `glab api --hostname <host> projects?membership=true…` dla GitLab i `gh api --hostname <host> user/repos?affiliation=owner,collaborator,organization_member…` dla GitHub. Token zostaje w tych programach (`glab auth login`, `gh auth login`); Trackwall go nie czyta i nie zapisuje. **Wyszukiwanie** (`remote-repos {query}`) w GitLab idzie po stronie GitLab (`search` z `search_namespaces`, więc pasuje też ścieżka grupy), jedna strona 100 projektów od ostatnio zmienianych, bo firmowa instancja ma ich tysiące; pełna strona to `truncated` i prośba o zawężenie. GitLab dopasowuje fragmenty dopiero od 3 znaków, więc krótsze zapytanie daemon dopasowuje sam na pierwszej stronie bez wyszukiwania. API repo użytkownika w GitHub nie ma wyszukiwania, więc daemon pobiera do 10 stron (1000 repo) i filtruje je sam po nazwie i opisie. Pobrane strony służą kolejnym zapytaniom przez 60 s (nieudane pobranie nie), więc pisanie w wyszukiwarce nie pyta hostingu przy każdym znaku. Lista to repo, których użytkownik jest członkiem (`membership=true` w GitLab; w GitHub własne, współpracownika i organizacji), a nie wszystkie widoczne publiczne projekty. Zarchiwizowane repo są pomijane, a nazwa spoza `RemoteRepoName` (segmenty `[A-Za-z0-9_][A-Za-z0-9._-]*`) nie trafia na listę. Hosting, który nie odpowiada (brak programu, logowania albo sieci), jest na liście jako `unavailable` z komunikatem programu i nie zabiera wyników pozostałych; UI podpowiada komendę logowania. Strona API ma limit 30 s.
- **Klon** (`clone {host, fullName}`) to `glab repo clone <pełna nazwa> <folder>/<ostatni segment>` albo to samo z `gh`, z `GITLAB_HOST` / `GH_HOST`, więc protokół (SSH albo HTTPS) i poświadczenia są takie, jak użytkownik ustawił w tych programach. Daemon odrzuca hosting spoza ustawień, nieustawiony folder i nazwę katalogu, która już jest w folderze (porównanie bez wielkości liter, bo tak działają dyski Windowsa i macOS); repo zdalne z tą nazwą jest na liście jako „Already in the folder”. Klonowanie biegnie w tle: akcja od razu zwraca je w stanie `running`, a `clones` zwraca klonowania do bieżącego folderu z projektami od startu daemona (`running`, `done`, `failed` z komunikatem), trzymane tylko w pamięci. Drugie kliknięcie tego samego repo w trakcie zwraca to samo klonowanie, a inne repo o tej samej nazwie katalogu czeka na jego koniec. Repo trafia na listę samo, bo leży w folderze (ADR-18), więc nic nie jest zapisywane; w trakcie klonu jego katalog może już być na liście. Klon ma limit 30 minut, bo duże repo klonuje się minutami, a ssh czekające na potwierdzenie klucza hosta w ukrytej konsoli czekałoby zawsze; po limicie klonowanie jest nieudane, a ponowna próba przejdzie dopiero, gdy git sam skończy i usunie swój katalog. Klonowania nie da się anulować z UI, a zabicie `glab` albo `gh` (limit, koniec daemona) nie zatrzymuje gita, którego uruchomił, bo klon nie jest w grupie procesów: to luka do zamknięcia razem z modułem `procs` (§8). Bez terminala i z `GIT_TERMINAL_PROMPT=0` git nie czeka na hasło; ssh uruchomionego z terminala daemona (tryb deweloperski) może jednak zapytać o klucz hosta w tym terminalu.
- **Synchronizacja** (`sync`, ADR-21) to przycisk „Sync all” na liście repo: dla każdego repo z folderu z projektami, najwyżej 4 naraz, `git fetch` głównego remote, a potem fast-forward lokalnej gałęzi domyślnej do zdalnej. Kroki mise (`mise install`, `setup`, `build`) z synchronizacją składa komenda zbiorcza (§4.8) przez `syncRepo {id}`: ta sama synchronizacja jednego repo, z błędem, gdy do repo trwa klonowanie. Ekstraktorów z §7 jeszcze nie ma, a CLI `ws sync` powstanie razem z CLI `ws`.
  - **Remote i gałąź.** Główny remote to `origin`, a bez niego jedyny remote. Gałąź domyślna to `refs/remotes/<remote>/HEAD` (ustawia go `git clone`); gdy go nie ma albo wskazuje gałąź, której już nie ma (hosting zmienił gałąź domyślną, a fetch z `prune` usunął starą), daemon raz pyta serwer przez `git remote set-head --auto`. Zmiany gałęzi domyślnej, której stara wersja nadal istnieje na zdalnym, nie wykrywa.
  - **Przesunięcie.** Wybrana gałąź domyślna przesuwa się przez `git merge --ff-only`, więc katalog roboczy dostaje nowe pliki, a nieśledzony plik na drodze kończy się błędem gita zamiast nadpisaniem. Niewybrana przesuwa się przez `git fetch . <zdalna>:<lokalna>` (bez `+`): git przyjmuje tylko fast-forward i odmawia, gdy gałąź jest w użyciu w którymś worktree, także w trakcie rebase albo bisect, kiedy HEAD jest odłączony; wtedy repo kończy się błędem z komunikatem gita, a gałąź zostaje. Wybrana gałąź i katalog roboczy zostają bez zmian.
  - **Pominięcia.** Synchronizacja nigdy nie scala, nie robi rebase ani nie przełącza gałęzi. Repo bez remote, bez gałęzi domyślnej (zdalnej albo lokalnej), z niezacommitowanymi zmianami w śledzonych plikach wybranej gałęzi domyślnej, z gałęzią rozjechaną albo z niewypchniętymi commitami, albo z gałęzią domyślną wybraną w innym worktree jest pomijane z powodem (`SyncSkipReason`) i zdaniem dla użytkownika. Nieśledzone pliki nie blokują, a zmiany na gałęzi funkcji nie przeszkadzają w przesunięciu niewybranej gałęzi domyślnej. Błąd gita (sieć, logowanie, klucz hosta, limit czasu) jest wynikiem `failed` tego repo z komunikatem gita i nie zatrzymuje pozostałych.
  - **Wynik i katalog roboczy** (ADR-34). Każdy wynik bez błędu (`updated`, `up-to-date`, `skipped`) ma też stan katalogu roboczego po synchronizacji (`SyncWorkingTree`): wybraną gałąź oraz liczbę zmienionych śledzonych plików i osobno nowych nieśledzonych wpisów, z jednego `git status` na końcu (gdy zawiedzie, `workingTree: null`, a wynik zostaje); `updated` i `up-to-date` mają do tego gałąź zdalną (`origin/main`). UI składa z tego zdanie dla każdego repo, także aktualnego: co stało się z gałęzią domyślną, czy pliki w katalogu roboczym się zmieniły (nie, gdy wybrana jest inna gałąź) i że niezacommitowane pliki zostały nietknięte, z podziałem na zmienione i nowe.
  - **Bez pytań.** Komendy, które łączą się z serwerem (`fetch`, `remote set-head` i `merge`, bo filtr LFS pobiera obiekty), dostają poza `GIT_TERMINAL_PROMPT=0` pusty `GIT_ASKPASS`, `GCM_INTERACTIVE=never` (Git Credential Manager bez okien) i `GIT_SSH_COMMAND="ssh -o BatchMode=yes"` (`networkEnv` w `vcs/git.ts`), chyba że użytkownik sam ustawił program ssh (`GIT_SSH_COMMAND`, `GIT_SSH` albo `core.sshCommand`): wtedy zostaje jego, a przed wiszeniem chroni tylko limit 5 minut. Klon przez `gh` i `glab` tego środowiska jeszcze nie dostaje (tylko `GIT_TERMINAL_PROMPT=0`).
  - **W tle.** Jak klonowanie: `sync` od razu zwraca synchronizację z repo w stanie `waiting`, a `sync-run` zwraca ostatnią synchronizację bieżącego folderu z projektami (w pamięci daemona, do restartu). Naraz trwa jedna: drugie kliknięcie zwraca trwającą, a start w innym folderze w trakcie to `bad_request`. Repo, do którego trwa klonowanie, jest pomijane bez wpisu. Wpisy listy z tym samym katalogiem `.git` (repo i jego worktree albo dowiązanie w folderze) synchronizują się po kolei, bo dwa równoczesne fetch w jednym `.git` walczą o refy. UI odpytuje postęp co 1,5 s w trakcie i co 10 s poza nim, a wynik każdego repo, także „up to date”, pokazuje pod stanem repo na liście (zdanie w podpowiedzi) i w całości w panelu synchronizacji (w miejscu szczegółów repo), z liczbą repo aktualnych obok przesuniętych, pominiętych i nieudanych. Zdarzenie `sync.progress` (§5.2) zastąpi odpytywanie razem z WebSocketem.
- **Adres repo zdalnego** (`Repo.remote`, ADR-21) to adres głównego remote w postaci `host/ścieżka`, bez schematu, użytkownika (także z tokenem wpisanym w URL), portu i `.git`, z hostem małymi literami: `git@gitlab.example.com:sklep/api.git` i `https://gitlab.example.com/sklep/api` dają `gitlab.example.com/sklep/api`. To identyfikator repo obok nazwy katalogu: nie zmienia się po zmianie nazwy katalogu i łączy klony przez SSH i HTTPS. Ścieżka lokalna, `file://`, brak remote albo kilka remote bez `origin` dają `null`. Adres liczony jest po skrótach `url.<base>.insteadOf`, jak w gicie, a `transport::` (np. `ext::`) też daje `null`, bo to komenda, nie adres. Daemon czyta go przy każdym zapytaniu listy z `git config -z --list` (trzeci proces gita na repo) i niczego nie zapisuje; UI pokazuje go w nagłówku repo pod ścieżką.
- **Stan repo** (`RepoStatus`) jest obserwowany przy każdym zapytaniu jednym `git status --porcelain=v2 --branch` plus `git log -1`: gałąź, ostatni commit, liczba zmian w katalogu roboczym (z niej osobno nowe nieśledzone wpisy, `untracked`, ADR-34; nowy katalog to jeden wpis, jak w `git status`; UI pisze „3 changed, 1 new”), ahead/behind względem gałęzi śledzonej. Nic z tego nie jest zapisywane. Repo, którego git nie czyta (uszkodzone `.git`, brak uprawnień), zostaje na liście jako `unavailable` z komunikatem gita.
- **Zmiany katalogu roboczego** (`changes {repo}`, zakładka „Changes” w szczegółach repo, ADR-34) to pliki i diff katalogu roboczego względem HEAD, z nowymi plikami i bez ignorowanych, tym samym odczytem co zmiany zadania (`workingTreeChanges` w `vcs/worktree-changes.ts`, ADR-31): kopia indeksu w katalogu tymczasowym z nowymi plikami jako `--intent-to-add`, więc indeks użytkownika zostaje nietknięty, a do `.git/objects` trafia najwyżej pusty blob (nie nowa wersja każdego pliku), diff bez zewnętrznych programów diff i `textconv`, ucięty do 1 MB (`PATCH_MAX_BYTES`). Repo bez commitów porównuje się z pustym drzewem (`git hash-object -t tree --stdin`, więc działa dla SHA-1 i SHA-256). Tylko do odczytu: zatwierdzanie i odrzucanie zmian zostaje w edytorze. UI odpytuje zakładkę co 10 s po poprzedniej odpowiedzi, póki jest otwarta, i od razu po zmianie HEAD; lista plików jest ucięta do 500 w UI, a wyjście `--name-status`/`--numstat` ucięte w daemonie daje `truncated`; kafelek „Working tree” ze zmianami otwiera tę zakładkę.
- **Przeglądanie** czyta z commita HEAD, nie z katalogu roboczego (ADR-14): jedno `cat-file --batch-check` mówi, czy HEAD i `HEAD:<ścieżka>` istnieją, jakiego są typu i rozmiaru, potem `ls-tree` albo `cat-file blob`. Ścieżka z żądania jest ścieżką w drzewie commita, więc nie da się nią wyjść poza repo ani trafić w plik ignorowany przez gita. Podgląd pliku i README jest ucinany do 512 KB; plik z bajtem NUL w pierwszych 8000 bajtach jest binarny (ta sama heurystyka co w gicie).
- **Code search** (`searchCode`, MCP tool `search_code`, ADR-40) reads from the HEAD commit, like browsing: for each chosen repo, at most 4 at once, `git grep -n -z -I --column --no-textconv --no-recurse-submodules -C<context>` with `-F` (fixed string) or `-E` (POSIX extended regular expression, without `\d` and `\s`), optionally `-i`, the pattern after `-e` and git pathspecs after `--` (`code-search.ts` in `workspace`, `grep.ts` in `vcs`, where `commitGrep` owns these flags together with reading source files for cards). It searches the commit's objects, so uncommitted changes are invisible, a path cannot leave the tree, ignored files are never in the result, and the repo makes git run no program (no `textconv` or filters) and pull in no submodule. A repo without commits is skipped. The pattern is one line: git would split a pattern with a newline into several, and an empty line matches everywhere. A match is told from context by the column field of the output line (`-z` with `--column`: a match has a column, context does not). **Limits**: git output 2 MB per repo, `git grep` 30 s, lines cut to 500 characters, at most `limit` matches from one repo; repos start in list order, so once finished repos have given `limit` matches no further repo is searched; repos not started because of that, or 60 s after the start, go to `skipped`; line text in the whole result at most 100,000 characters (the result goes to the agent twice, like the README in `get_repo`). Each of these cuts sets `truncated`, and in `searched` also on the repo it affects (so `truncated` can be true when the skipped repos had no matches). A repo git could not search (invalid pattern, time limit, broken `.git`) goes to `failed` with git's message and does not take away the results of the others. The MCP tool builds the tag filter from the card tags (`cards`), and `workspace` gets a ready list of ids; an unknown id is `not_found`, also when tags are given. There is no index: every query reads the repos again.
- **Git, `gh` i `glab`** są uruchamiane przez `runProgram` (`modules/vcs/run.ts`): `spawn` z tablicą argumentów, bez powłoki, z limitem czasu, ograniczonym wyjściem i końcem stderr jako komunikatem błędu. **Git** dostaje `-C <repo>`, `GIT_CEILING_DIRECTORIES` na katalogu nadrzędnym korzenia repo po rozwinięciu dowiązań (z pustym albo uszkodzonym `.git` git nie szuka repo wyżej i nie pokazuje repo, w którym leży folder z projektami; jawne `--git-dir` wyłączyłoby sprawdzenie właściciela repo, `safe.directory`, więc go nie używamy), `-c core.fsmonitor=false -c log.showSignature=false` (§8), limitem czasu 15 s (`git grep`: 30 s; komendy synchronizacji: 5 minut i środowisko bez pytań, wyżej), `GIT_OPTIONAL_LOCKS=0` (odczyt stanu nie zakłada `index.lock`, gdy użytkownik akurat commituje) i `GIT_TERMINAL_PROMPT=0`, bez odziedziczonych zmiennych wybierających repo (`GIT_DIR`, `GIT_WORK_TREE`…), które przebiłyby `-C`. Wynik jest ustalany bez czekania na zamknięcie rur, bo na Windowsie `git` z `PATH` bywa launcherem, którego wnuk trzyma je po przekroczeniu czasu. Wyjście jest parsowane z formatów maszynowych (`-z`, `--porcelain=v2`), więc nie zależy od języka gita.
- **„Open in VS Code”** otwiera adres `vscode://file/<korzeń repo>` systemowym mechanizmem otwierania URL-i (to samo co `--ui`), bez uruchamiania `code` przez powłokę. Tym samym mechanizmem fasada otwiera link `http` albo `https` kliknięty w README (`workspace/open-link`, ADR-35); format README (`markdown` albo `text`) podaje `overview`.
- `workspace.yaml` jest zapisywany przez plik tymczasowy i `rename` (`atomic-write.ts`, wspólne z `daemon.json`), z ponowieniem na Windowsie, gdy plik chwilowo trzyma antywirus albo edytor. Ścieżka folderu z projektami w pliku musi być pełna (na Windowsie z literą dysku albo UNC; `\projekty` zależałaby od bieżącego dysku daemona). Klucz `repos` z wersji 0.2.0 nie jest już czytany, ale zapis go nie usuwa.
- UI odpytuje listę 10 s po poprzedniej odpowiedzi (wolny git nie piętrzy żądań) i tylko przy widocznym oknie; nowy HEAD w liście pobiera przegląd i drzewo od nowa. Lista repo nie jest tematem `/ws` (ADR-36), bo jej migawka to `git status` każdego repo; zdarzenie przyjdzie, gdy daemon zacznie obserwować repo.

### 4.6 `cards` i `graph`

Karta powstaje w dwóch krokach. Krok deterministyczny czyta pliki repo: `pom.xml` / `build.gradle(.kts)` (artefakty, zależności na klienty Feign/WebClient, konfigurację OpenAPI), `application*.yml` (URL-e, porty, nazwy topików, nazwy zmiennych środowiskowych = kandydaci na sekrety), `package.json` (paczki, skrypty), pliki OpenAPI, definicje Kafki. Ekstraktory są osobnymi plikami per system budowania, każdy zwraca tylko fakty z pozycją w pliku. Krok LLM dostaje kartę i wybrane fragmenty, zwraca opis i propozycje połączeń, oznaczone `origin: 'llm'`.

Pierwszy wycinek (ADR-25): krok deterministyczny dla plików buildu, narzędzi i spisu mechanizmów, tagi repo z filtrem w liście repo i karta w MCP. Drugi (ADR-30): aplikacje Spring Boot, endpointy i klienci HTTP z kodu Javy i Kotlina, konfiguracji Spring z profilami i adresów backendu we frontendzie. Topiki, nazwy zmiennych środowiskowych (kandydaci na sekrety) i krok LLM to następne kroki.

- **Odczyt commita** (`read-snapshot.ts`): `git ls-tree -r -z --long <commit>` daje listę plików z rozmiarami, a `git cat-file --batch` jednym procesem treść plików, które wybiera któryś ekstraktor (każdy ma swoją funkcję `reads…File`, złożone w `readsCardFile`): `pom.xml`, `build.gradle(.kts)`, `settings.gradle(.kts)`, `gradle/libs.versions.toml`, `package.json`, `pnpm-workspace.yaml`, konfiguracja mise i `.tool-versions` w korzeniu repo, `.nvmrc`, `.node-version`, `.java-version`, `.sdkmanrc`, właściwości wrapperów Maven i Gradle, konfiguracja Spring (`src/main/resources/application*` i `bootstrap*`), pliki `.env*` i konfiguracja proxy frontendu. Do tego pliki źródłowe Javy i Kotlina (ADR-30): `git grep -l -z -I -E` w commicie (bez textconv) wybiera te, które mają adnotację kontrolera, mapowania albo klienta, `WebClient`, `RestClient`, `RestTemplate` albo stałą ze ścieżką (`JVM_SOURCE_PATTERN` w `spring.ts`), a z `src/main/` na dowolnej głębokości, a bez niego tylko poza katalogami `src` (bez testów; `isJvmSource`); idą tym samym `cat-file --batch`. Potem odczyt dociąga pliki typów, które te pliki wymieniają (ADR-38): nazwy od wielkiej litery z tokenów (`referencedTypeNames`) wskazują pliki źródłowe o tej nazwie (`OrderDto.java`, `OrderDto.kt`, z tym samym `isJvmSource`), w najwyżej trzech rundach (kontroler, DTO, typ pola, typ pola zagnieżdżonego) i najwyżej 3000 plików, każda runda jednym `cat-file --batch` we wspólnym limicie bajtów. Te pliki trafiają do `RepoSnapshot.typeFiles`: czytają je tylko kontrakty, a ekstraktor Spring nie, więc fakty HTTP zależą tylko od plików z wyszukiwania; pliki typów, które nie zmieściły się w limitach, dają jeden problem karty z ich liczbą. Pliki w `node_modules` i `bower_components` nie istnieją dla karty (ani do czytania, ani dla mechanizmów). Limity: 1 MB na plik, 2000 plików buildu i konfiguracji, 3000 plików źródłowych (4 MB listy z `git grep`) i 64 MB razem; plik, którego git nie oddał w limicie, jest problemem karty, więc niepełna karta mówi, czego jej brakuje. Commit to HEAD odczytany raz przed obydwoma komendami (`rev-parse` przez `cat-file --batch-check`), więc commit zrobiony w trakcie nie miesza dwóch drzew. Katalog roboczy nie ma znaczenia (ADR-14). Pliki z BOM i `\r\n` są normalizowane, zanim zobaczą je ekstraktory.
- **Ekstraktory** to czyste funkcje na migawce commita (`RepoSnapshot`: lista plików, treść przeczytanych, pliki typów i problemy odczytu), w `modules/cards/`: `maven.ts` (z parserem `xml.ts`), `gradle.ts` (z katalogiem wersji w `gradle-catalog.ts` i skanerem komentarzy w `gradle-code-lines.ts`), `npm.ts`, `tools.ts`, `mise-tasks.ts` (ADR-34), `mechanisms.ts`, `spring.ts` i `frontend-http.ts` (ADR-30, niżej), złożone w `extract-card.ts`; ścieżki w repo (z `/`) obsługuje `repo-path.ts`. Kontrakty endpointów i DTO (`endpoint-contracts.ts`, ADR-38) czytają drzewa składni z `syntax-tree.ts` (ADR-37): `loadSyntaxParsers()` raz na proces, `withParseBudget` z łącznym czasem dla każdej karty (`cards.ts`), potem synchroniczne `read(język, tekst, odczyt)` z drzewem składni tree-sitter, zwalnianym po odczycie, więc z odczytu wychodzą tylko wartości; plik, którego parsowanie przekracza `PARSE_TIME_LIMIT_MS`, daje wynik `timeout` zamiast drzewa, a odczyt po wyczerpaniu budżetu karty `over-budget`. Gdy gramatyk nie da się załadować, karta powstaje bez kontraktów, z problemem (`unavailableParsers`). Pliki są niezaufane (§8), więc żadne wyrażenie nie cofa się kwadratowo na długiej linii, a globy workspace dopasowuje programowanie dynamiczne, nie wyrażenie regularne (`glob.ts`). Plik buildu, którego nie da się przeczytać (zły XML, JSON, TOML, YAML), jest problemem karty (`problems`), a reszta karty powstaje bez niego.
  - **Korzenie buildów.** Plik buildu bez pliku tego samego rodzaju w żadnym katalogu nadrzędnym jest korzeniem; głębszy należy do buildu tylko wtedy, gdy korzeń go wymienia (moduł Maven, także z profilu; `include` Gradle; paczka workspace z `workspaces` w `package.json` albo z `pnpm-workspace.yaml`, wzorce z `*`, `**` i `!`). Dzięki temu `pom.xml` z fixture'ów testów nie trafia na kartę, a repo z `backend/pom.xml` i `frontend/package.json` bez korzenia ma oba buildy. Każdy plik buildu na karcie ma `memberOf`: plik, który go wymienia, albo `null`.
  - **Maven** czyta pom własnym parserem XML z numerami linii (`xml.ts`; bez atrybutów, przestrzeni nazw i DTD). `groupId` i `version` bez własnej wartości dziedziczą z `<parent>`; `${…}` w wersjach podstawia właściwości pom, jego rodziców z repo (`relativePath`, domyślnie `../pom.xml`) i `project.*`, a nieznaną właściwość (albo taką, po której wartość przekroczyłaby 4096 znaków) zostawia w tekście. Udostępnia współrzędne każdego modułu; używa rodzica spoza repo (`parent`), zależności (z `scope`, domyślnie `compile`), BOM-ów z `dependencyManagement` w zakresie `import` i wtyczek z `build/plugins` (`plugin`, domyślna grupa `org.apache.maven.plugins`). Zwykłe wpisy `dependencyManagement` i zależności z profili pomija. Wersja Javy z `maven.compiler.release`, `java.version` albo `maven.compiler.source` to podpowiedź narzędzia.
  - **Gradle** nie wykonuje skryptów (to kod Groovy albo Kotlin), tylko czyta linie w typowej postaci, bez komentarzy (napisy są pomijane przy ich szukaniu, więc `exclude("META-INF/*.SF")` nie zaczyna komentarza; linie ponad 2000 znaków są pomijane): `rootProject.name` i `include` z settings (także rozpisany na wiele linii), `group` i `version` (projektu albo projektu głównego), zależności `konfiguracja("g:a:v")` (także w `platform(...)`) i z katalogu wersji (`libs.…`), wtyczki `id("…")` z kropką w nazwie i `alias(libs.plugins.…)`, wersję Javy z `JavaLanguageVersion.of(N)` albo `sourceCompatibility`. Projekt ma współrzędne `group:nazwa` tylko ze znaną grupą i nazwą. Zależność złożona w kodzie (zmienna, pętla, `project(...)`) nie trafia na kartę.
  - **npm** czyta pola `package.json` osobno (zły typ jednego nie zabiera reszty): paczka z nazwą i bez `"private": true` jest udostępniana, zależności z `dependencies`, `devDependencies`, `peerDependencies` i `optionalDependencies` (zakres to nazwa pola). Menedżer paczek z `packageManager`, a bez niego z pliku blokady w katalogu korzenia (`pnpm-lock.yaml`, `yarn.lock`, `bun.lock(b)`, `package-lock.json`, domyślnie npm); paczki workspace dziedziczą go po korzeniu. `engines.node` i wersja z `packageManager` to podpowiedzi narzędzi.
  - **Paczki z repo** nie są na liście używanych (moduł, który zależy od innego modułu tego repo, prywatna paczka workspace), a każda używana paczka jest na karcie raz, z pierwszym wystąpieniem.
  - **Narzędzia** (`ToolRequirement`): `[tools]` z konfiguracji mise w korzeniu repo (`mise.toml`, `.mise.toml`, `mise/config.toml`, `.mise/config.toml`, `.config/mise.toml`, `.config/mise/config.toml`; bez `mise.local.toml`, `mise.<środowisko>.toml`, `conf.d/` i konfiguracji w podkatalogach) i `.tool-versions` (źródło `mise`) oraz podpowiedzi (źródło `hint`) z korzenia i katalogów buildów: `.nvmrc`, `.node-version`, `.java-version`, `.sdkmanrc`, wersje z adresów dystrybucji wrapperów Maven i Gradle, a od ekstraktorów buildu wersja Javy, `engines.node` i menedżer paczek. Nie z `mise ls --json` (ADR-25).
  - **Mechanizmy** (`Mechanism`) to spis z reguł w `mechanisms.ts`: paczka po `<ekosystem>:<nazwa>` (Spring Boot, Feign, WebClient, OpenAPI, Kafka, RabbitMQ, Eureka, Config Server i klient, Spring Cloud Kubernetes, Jib, React, Angular, Vue, Svelte, Express, NestJS) albo plik po ścieżce (pliki OpenAPI i Swagger, `Chart.yaml`, `Dockerfile`, `compose.yaml`, `kustomization.yaml`, YAML w katalogu `k8s/` albo `kubernetes/`; manifesty w innych katalogach, np. `deploy/`, nie są rozpoznawane), z najwyżej trzema dowodami. Reguły są ogólne; reguły firmowe przyjdą z workspace (ADR-7).
  - **Konfiguracja Spring** (`spring-config.ts`, ADR-30): moduł to katalog nad `src/main` (repo z kilkoma aplikacjami ma kilka modułów); wszystko pod `src/test`, także projekt przykładowy w zasobach testów, to kod testów i jest pomijane (kod i konfiguracja, `isTestPath`). Pliki `application` i `bootstrap` (`.yml`, `.yaml`, `.properties`) z `src/main/resources`, profil z nazwy pliku (`application-prod.yml`) albo z dokumentu aktywowanego `spring.config.activate.on-profile` (dawniej `spring.profiles`; dokumenty YAML `---`, w `.properties` `#---`). Widok profilu to konfiguracja bez profilu nadpisana dokumentami profilu, a plik profilu (`application-prod.yml`) nadpisuje dokument `on-profile` z pliku bez profilu, jak w Spring Boot (każdy `bootstrap*` jest pod każdym `application*`); profil `default` to konfiguracja bez profilu, a profil z tą samą wartością adresu co `default` nie jest wymieniany osobno (najwyżej 32 profile na moduł). Klucze porównuje się jak w Spring Boot (bez wielkości liter, `-` i `_`, więc `baseUrl` to `base-url`). `${klucz}` i `${klucz:domyślna}` rozwija `placeholders.ts`: zagnieżdżone, z wartością domyślną, nieznany klucz zostaje tekstem, a cykl, głębokość ponad 10 i wynik ponad 4096 znaków przerywają rozwijanie. Zmienne środowiskowe nie są znane, więc `${PORT:8081}` daje `8081`.
  - **Aplikacja** (`ProvidedApp`, `kind: "app"`): `spring.application.name` modułu z portem z `server.port` (liczba 1–65535 po rozwinięciu, inaczej `null`) i dowodem z linii nazwy.
  - **Endpointy HTTP** (`ProvidedEndpoint`, `kind: "endpoint"`, `spring-endpoints.ts`): klasa z `@RestController` albo `@Controller`, ścieżka z `server.servlet.context-path` (albo `spring.webflux.base-path`), `@RequestMapping` klasy i adnotacji metody (`@GetMapping`, `@PostMapping`, `@PutMapping`, `@PatchMapping`, `@DeleteMapping`, `@RequestMapping` z `method` albo bez, czyli każda metoda: `method: null`), każda kombinacja ścieżek i metod osobno (najwyżej 20 na metodę). Mapowania z interfejsu, który kontroler implementuje (styl API first, interfejs z generatora OpenAPI), liczą się jak własne, z dowodem w pliku interfejsu. Ścieżki są w `value`, `path` albo jako pierwszy argument, w tablicy `{…}` (Kotlin `[…]`, `arrayOf(…)`), także ze stałych (`ApiPaths.ORDERS + "/{id}"`, stałe `static final` i `const val` z czytanych plików); stała, której nie ma w czytanych plikach, zostaje jako `<Klasa.NAZWA>`. Kod czyta tokenizer (`java-tokens.ts`: komentarze, napisy, bloki tekstu) i prosty parser deklaracji (`java-source.ts`, `java-expr.ts`), bez kompilacji, więc adnotacja w komentarzu albo napisie nie jest mapowaniem, a mapowanie złożone w kodzie (np. `RouterFunction`) nie trafia na kartę.
  - **Kontrakty endpointów i DTO** (`endpoint-contracts.ts` z `contract-java.ts` i `contract-kotlin.ts`, ADR-38): endpoint dostaje z drzewa składni metody, w której leży linia jego mapowania (w kontrolerze albo interfejsie API), typ parametru z `@RequestBody` (`request`) i typ zwracany bez opakowań, które nie zmieniają treści (`ResponseEntity`, `HttpEntity`, `Mono`, `Optional`, `CompletableFuture`, `CompletionStage`, `Callable`, `DeferredResult`, `WebAsyncTask`; `response`; także z `?` Kotlina; `Flux<T>` zostaje, `void`, `Unit`, `Void`, `?`, `*` i opakowanie bez argumentu to `null`, funkcja Kotlina bez jawnego typu też). Typy są w zapisie typu: tekst z drzewa bez adnotacji, ze spacją tylko przed słowem po słowie albo po `?` (`List<? extends Line>`), dłuższy niż 256 znaków przycięty z „…” (DTO są odkrywane z pełnego zapisu). Metodę wskazuje nazwa z handlera i linia mapowania wewnątrz metody (w pliku bywa kilka klas i przeciążeń), a bez linii albo bez takiej metody pierwsza metoda pliku o tej nazwie. `RepoCard.dtos` to typy z repo osiągalne z tych typów przez typy pól, w kolejności odkrycia, najwyżej 500 po 200 pól albo stałych: rekord (pola z nagłówka), `data class` (parametry konstruktora i właściwości z ciała), klasa z polami (pola instancji bez `static`; w Kotlinie właściwości z konstruktora i z ciała; typ bez pól, jak serwis albo pusty rekord, nie jest DTO), enum (stałe). Typ wskazuje prosta nazwa, a w nazwie kwalifikowanej (`Api.Summary`, `java.math.BigDecimal`) jej ostatni człon: najpierw plik o tej nazwie, potem pierwszy przeczytany plik, w którym tekst `class|record|enum|object <Nazwa>` występuje, więc dwa typy o tej samej nazwie w repo dają pierwszy, a typ spoza przeczytanych plików (biblioteka, JDK) nie jest DTO. Parsowanie całej karty ma łączny budżet 10 s (§8), sprawdzany przed każdym plikiem, więc przekroczony najwyżej o czas ostatniego pliku (parsowanie do 1 s i liniowy odczyt drzewa); po nim reszta endpointów zostaje bez typów, a karta ma problem.
  - **Klienci HTTP** (`ConsumedHttp`, `kind: "http"`) mają rodzaj (`via`), nazwę (interfejs, klasa albo klucz), nazwę aplikacji celu (`app`) albo adres (`url`) w profilach (`profiles`, z wpisem konfiguracji, z którego adres pochodzi: `urlSource`) i wywołania (`calls`: metoda i ścieżka z linią). Adres z `${…}` daje osobnego klienta dla każdego profilu, w którym ma inną wartość (najpierw `default`). `lb://nazwa` to nazwa aplikacji (load balancer Spring Cloud). Rodzaje: `feign` (`@FeignClient`: nazwa aplikacji z `name`, `value` albo `serviceId`, adres z `url` albo z `spring.cloud.openfeign.client.config.<nazwa>.url` / `feign.client.config.<nazwa>.url`, prefiks z `path` i `@RequestMapping` interfejsu, wywołania z adnotacji mapowań metod), `http-interface` (interfejs z `@HttpExchange` i `@GetExchange`…), `webclient`, `rest-client` i `rest-template` (`imperative-clients.ts`: adres bazowy z `baseUrl`, `rootUri`, `create(…)` albo pola `@Value("${…}")`, wywołania z `.uri(…)` z metodą z łańcucha (`.get()`, `.method(HttpMethod.POST)`) i z metod `RestTemplate` (`getForObject`, `exchange` z `HttpMethod`…); składnik sklejany po napisie, np. `"/orders/" + id`, to zmienna ścieżki `{}`), `config` (`config-clients.ts`: klucz konfiguracji z adresem HTTP albo `lb://` w którymś profilu, którego kod nie użył jako adresu klienta, np. `spring.cloud.gateway.routes[0].uri`; bez wywołań).
  - **Adresy backendu we frontendzie** (`frontend-http.ts`): zmienne z adresem HTTP w plikach `.env*` obok `package.json` (`via: "env"`, nazwa zmiennej), pole `proxy` w `package.json` i adresy w cudzysłowie w konfiguracji proxy serwera deweloperskiego (`vite.config.*`, `webpack.config.*`, `vue.config.*`, `next.config.*`, `proxy.conf.*`, `setupProxy.*`; `via: "proxy"`, nazwa pliku). Konfiguracji JS nie wykonuje.
  - **Sekrety w adresach**: każdy adres na karcie traci użytkownika i hasło (`http://***@host`), zapytanie i człony ścieżki wyglądające na token (`withoutCredentials` w `protocol`), a ścieżki wywołań zapytanie, zanim trafią na kartę (§8).
- **Pamięć kart** (`card-cache.ts`): karta zależy tylko od drzewa commita i wersji ekstraktorów (`EXTRACTOR_VERSION`), więc liczy się raz na commit. Leży w pamięci daemona (1000 ostatnich) i w `<katalog stanu>/cards/<commit>.json` (zapis przez `writeFileAtomic`; nieudany zapis trafia do logu). Plik z inną wersją ekstraktorów albo niezgodny ze schematem liczy się jak brak (wersja 4 od ADR-38, więc karty sprzed niej liczą się od nowa). Karta, której parsery nie dały któregoś drzewa przez czas albo brak gramatyk (`CardParsers.complete`), zależy od chwili liczenia, więc zostaje tylko w pamięci, a następny start daemona liczy ją od nowa. Start daemona usuwa pliki ponad 2000 najnowszych. Dwa równoczesne pytania o ten sam commit czytają gita raz.
- **Tagi repo** (`RepoTag`, `tags.ts`) liczone są przy każdym pytaniu z karty, identyfikatora repo, adresu repo zdalnego i reguł, każdy z powodem: `java` (plik buildu Maven albo Gradle), `typescript` (zależność `typescript`), `frontend` (React, Angular, Vue, Svelte), `backend` (Spring Boot, Express, NestJS), `bff` (słowo `bff` w identyfikatorze, adresie repo zdalnego albo nazwie udostępnianej paczki), `library` (udostępnia paczkę, a nie ma frameworka aplikacji ani plików wdrożenia), `monorepo` (plik buildu wymienia co najmniej dwa moduły albo paczki, albo co najmniej dwa korzenie buildów w różnych katalogach), `no-mise` (commit nie zapisuje żadnego taska mise, niżej, ADR-34). Tagi są ortogonalne: „BFF w Javie” to `java` + `bff`. Do tego **reguły tagów** (`repoTags` w `workspace.yaml`, tylko ręcznie): tag i wzorce identyfikatora albo adresu repo zdalnego (`*` bez `/`, `**` z `/`, bez wielkości liter), np. `core-api: ["*-core", "gitlab.example.com/core/**"]`; nazwy zespołów i grup firmy zostają w pliku użytkownika (ADR-7).
- **API i UI**: `cards/card {repo}` zwraca kartę i tagi repo, `cards/tags` tagi każdego repo z folderu (najwyżej 4 repo naraz; repo, którego git nie czyta, jest `unavailable` z komunikatem). Lista repo pokazuje tagi pod stanem repo (powody w podpowiedzi) i filtr: każdy tag z liczbą repo, a wybrane tagi zawężają listę do repo, które mają wszystkie. Tagi są pobierane od nowa, gdy zmieni się zestaw repo albo HEAD któregoś z nich, i co minutę (ręczna zmiana reguł). Tag `no-mise` (ADR-34) dostaje repo, którego commit nie zapisuje żadnego taska mise (`RepoCard.mise`: pliki konfiguracji mise w korzeniu i taski z ich `[tasks]` oraz z plików w katalogach tasków `mise-tasks/`, `.mise-tasks/`, `mise/tasks/`, `.mise/tasks/`, `.config/mise/tasks/`), z powodem „no mise config in the repo root” albo „mise.toml declares no tasks”; lista repo pokazuje go jako ostrzeżenie „no mise tasks”, a filtr po nim wybiera repo do znormalizowania. Tag mówi tylko o braku jakiegokolwiek taska; repo z taskami, ale bez `setup` albo `build`, dowiaduje się tego z pominiętego kroku komendy zbiorczej (§4.8). Konfiguracja to pliki z korzenia (`mise.toml`, `.mise.toml`, `mise/config.toml`, `.mise/config.toml`, `.config/mise.toml`, `.config/mise/config.toml`, `.config/mise/mise.toml`) i `*.toml` z katalogów `conf.d`; plik, którego karta nie przeczytała (limity), wyłącza tag, bo nie wiadomo, czy ma taski. Taski z konfiguracji globalnej użytkownika i z `task_config.includes` nie są liczone, a nazwa taska plikowego to ścieżka w katalogu tasków z `:` (bez skracania rozszerzeń, które robi mise; `_default` daje nazwę katalogu); pełną listę daje zakładka „mise tasks”, §4.7. Zakładka „Card” w szczegółach repo pokazuje tagi z powodami, problemy, mechanizmy, narzędzia, aplikacje (nazwa, port), endpointy HTTP (metoda, ścieżka, typ żądania i odpowiedzi, handler), DTO (rodzaj, nazwa, pola z typami albo stałe enuma), klientów HTTP (rodzaj, nazwa, aplikacja albo adres z profilami, wywołania), paczki udostępniane i używane oraz pliki buildu, każdy fakt z dowodem.
- **MCP**: `list_repos` podaje nazwy tagów każdego repo i przyjmuje `tags` (repo z każdym z podanych), `get_repo` nazwy tagów repo, a `get_repo_card` całą kartę z tagami i powodami (§5.3). Tagi nie zabierają reszty: `get_repo` repo, którego karty nie da się policzyć, ma puste tagi, a `list_repos` bez filtra przy złym `repoTags` daje repo bez tagów (z filtrem błąd konfiguracji). `list_repos` liczy tagi zawsze, więc pierwsze wywołanie po starcie z setkami nowych commitów czyta gita każdego repo; potem karty są w pamięci.

Graf = złączenie `consumes` z `provides` po kluczach: URL/base-path, nazwa artefaktu, nazwa topiku, nazwa zmiennej środowiskowej z hostem. Każda krawędź ma `confidence` i `evidence` (plik, linia). Zapytania MCP działają na tym grafie i zwracają identyfikatory z dowodami, nie prozę.

Pierwszy wycinek grafu (ADR-29): krawędzie z paczek, aliasy paczek i ręczne krawędzie z `workspace.yaml`, widok „Overview” i narzędzia MCP `who_calls` i `subgraph_for`. Drugi (ADR-30): krawędzie HTTP z klientów i endpointów z kart, aliasy aplikacji i `find_endpoint`. Topiki i stany serwisów w podgrafie przyjdą razem z ekstraktorami i serwisami.

- **Węzeł** (`GraphNode`) to repo z listy (dziś repo, nie serwis): identyfikator, adres repo zdalnego, nazwy tagów, liczba różnych paczek, które buduje, nazwy aplikacji Spring Boot i liczba endpointów HTTP z karty, i powód, gdy karty nie da się policzyć (`problem`; repo zostaje w grafie bez krawędzi z kart).
- **Krawędź z paczki** (`kind: "package"`): repo A używa paczki (`consumes`), którą buduje repo B (`provides`), w tej samej przestrzeni nazw (`PackageEcosystem`: Maven `grupa:artefakt` także z Gradle, npm, wtyczki Gradle). Kierunek od repo, które używa, do używanego. Dowody z obu stron: plik buildu i linia zależności w A (z wersją i zakresem) oraz plik i linia, w których B ją buduje. Pewność `exact`, a gdy tę samą paczkę buduje kilka repo z listy (dwa klony jednego repo, fork), krawędź do każdego z pewnością `medium`; repo, które buduje paczkę dwoma plikami buildu (np. w trakcie przejścia z Mavena na Gradle), liczy się raz. Zakres zależności (np. `test`) jest w dowodzie, nie zmienia krawędzi.
- **Krawędź HTTP** (`kind: "http"`, ADR-30, `http-index.ts` i `http-edges.ts`): klient HTTP z karty repo A woła repo B. Cel to pierwsze z: aplikacja o nazwie z klienta (`app`: Feign `name`, `lb://nazwa`) w karcie B; alias aplikacji z `workspace.yaml` dla tej nazwy albo hosta adresu; aplikacja albo repo o nazwie równej pierwszemu członowi hosta (`http://payments-service:8080`, `orders-api.shop.svc.cluster.local`; nazwa repo to identyfikator albo ostatni człon adresu repo zdalnego); aplikacja z portem z adresu na `localhost` (także `127.0.0.1`, `host.docker.internal`), tak jak adres z `.env` frontendu w trybie deweloperskim. Bez żadnego z nich graf szuka repo, którego endpointy pasują do ścieżek wywołań (metodą i ścieżką: zmienna `{id}`, `{}` albo `*` pasuje do jednego członu, `**` do reszty; ścieżka bez stałego członu, jak `/{id}`, nie wskazuje repo). Endpoint bez stałego członu (`/**`, `/{path}`: przekierowanie wszystkiego do aplikacji SPA) nie jest celem ani dowodem wywołania. Nazwa aplikacji, alias albo port, które wskazują tylko repo klienta, kończą szukanie bez krawędzi (aplikacja woła inną aplikację z tego samego repo). Kluczem krawędzi jest nazwa aplikacji, alias, host, `localhost:<port>` albo, dla dopasowania po ścieżce, nazwa klienta. Pewność: `exact`, gdy nazwa aplikacji wskazuje jedno repo, a każde wywołanie klienta ma w nim pasujący endpoint; `high` za samą nazwę aplikacji albo alias; `medium` za host równy nazwie repo, port na `localhost`, ścieżki pasujące do endpointów jednego repo albo nazwę aplikacji w kilku repo (klon, fork); `low` za ścieżki pasujące do endpointów kilku repo. Dowody: klient (rodzaj, nazwa, adres z profilami), wpis konfiguracji z adresem, aplikacja celu i pary wywołanie–endpoint (najwyżej 5 na klienta). Klient w kilku profilach to jedna krawędź z dowodami z każdego (najwyżej 20 dowodów), z wyższą pewnością. Repo nie łączy się samo ze sobą, a klient bez celu (np. adres Zipkina) nie daje krawędzi.
- **Wpisy użytkownika** (klucz `graph` w `workspace.yaml`, schemat `GraphConfig`, tylko ręcznie, jak `repoTags`): `packages` to aliasy paczek (nazwa paczki → repo, które ją dostarcza), działające tylko dla paczki, której nie buduje żadne repo z listy, z pewnością `high`; `apps` to aliasy aplikacji (nazwa aplikacji albo host adresu, bez wielkości liter → repo), gdy nazwa z klienta nie jest `spring.application.name` żadnej karty (adres z bramki, DNS z innej nazwy), z pewnością `high` (ADR-30); `edges` to ręczne krawędzie (`from`, `to`, `note`, rodzaj `manual`, pewność `exact`), np. wywołanie HTTP przez bramkę, którego karty nie widzą. Repo wskazuje się identyfikatorem albo adresem repo zdalnego (`host/ścieżka`, bez wielkości liter; adres przetrwa zmianę nazwy katalogu, ADR-18). Dowodem wpisu jest `workspace.yaml` (`repo: null`, pełna ścieżka) i zdanie z nazwą wpisu. Pusty podklucz (`packages:` bez wpisów) znaczy brak wpisów. Wpis wskazujący repo spoza listy albo ręczna krawędź z repo do niego samego trafia do `configProblems` grafu. Zły klucz `graph` (np. `edges` nie jest listą) albo `repoTags` nie jest błędem grafu: graf powstaje bez wpisów użytkownika (albo bez tagów z reguł), a komunikat trafia do `configProblems`, więc krawędzie z kart zostają.

```yaml
graph:
  packages:
    com.example:orders-client: orders-api            # paczka -> repo (identyfikator albo host/ścieżka)
  apps:
    orders.internal.example.com: orders-api          # nazwa aplikacji albo host -> repo
  edges:
    - from: gitlab.example.com/sklep/shop-web
      to: orders-bff
      note: HTTP /api/orders
```

- **Liczenie** (`modules/graph/`): `Cards.all()` daje karty, adresy i tagi wszystkich repo (najwyżej 4 repo naraz, karty z pamięci po commicie), a czysta funkcja `buildGraph` złącza je z wpisami `graph`; graf nie ma trwałego stanu: moduł trzyma tylko ostatni policzony graf z kluczem wejścia (commity, adresy i tagi wszystkich repo, powody braku karty i konfiguracja `graph`), bo krawędzie HTTP porównują wywołania z endpointami wszystkich repo (ADR-30), więc nowy commit, nowe repo w folderze i ręczna zmiana `workspace.yaml` działają od razu. Koszt pytania to koszt listy tagów: odczyt HEAD i remote każdego repo. Krawędzie są posortowane, a ta sama para repo, rodzaj i klucz to jedna krawędź. Nazwy paczek z repo nie sięgają do prototypu obiektu (aliasy są w `Map`).
- **Zapytania**: `who_calls(repo)` to krawędzie do repo (kto go używa), `subgraph(repo, depth)` repo w odległości do `depth` krawędzi w obie strony (1–3, `MAX_SUBGRAPH_DEPTH`) i krawędzie między nimi. Repo spoza listy to `not_found`. `findEndpoint(query, method?)` (ADR-30, `find-endpoint.ts`) to endpointy z kart wszystkich repo pasujące do zapytania: od `/` ścieżka, także konkretna (`/api/orders/42` znajdzie `/api/orders/{id}`), albo fragment ścieżki, handlera (`Klasa.metoda`) lub nazwy aplikacji bez wielkości liter; z metodą tylko endpointy tej metody i bez metody. Każdy z repo, które go wołają (`callers`: repo, rodzaj i nazwa klienta, pełna ścieżka wywołania, pewność jak krawędź, dowód), najwyżej 50 (`truncated`).
- **API i UI**: `graph/graph` zwraca cały graf (`RepoGraph`). Widok „Overview” (`GraphView`, Ctrl+4) rysuje go na całą szerokość w kolumnach: kolumna to najdłuższa ścieżka od repo, którego nikt nie używa (frontendy po lewej, biblioteki po prawej, jak warstwy sceny w §5.5; krawędzie wracające w cyklu są pomijane przy liczeniu kolumn), a kolejność w kolumnie wynika ze średniej pozycji sąsiadów (barycentrum), żeby linie rzadziej się krzyżowały. Układ liczy UI bez biblioteki grafów (`lib/graph-layout.ts`): repo to karty HUD, krawędzie jednej pary repo to jedna krzywa w SVG, ręczne przerywane. Repo bez krawędzi są pod rysunkiem („No connections”). Wybór repo podświetla jego sąsiedztwo, a panel po prawej pokazuje aplikacje repo, liczbę paczek i endpointów, kogo repo używa i kto używa jego, z rodzajem (paczka, HTTP, ręczne), kluczami, pewnością i dowodami; bez wyboru panel ma liczby, błędy wpisów `graph` i ścieżkę `workspace.yaml`. UI odpytuje graf co 30 s i na przycisk.

### 4.7 `mise`: taski repo i ich uruchamianie

Pierwszy wycinek modułów `mise` i `procs` (ADR-20): zakładka „mise tasks” w szczegółach repo pokazuje taski mise repo z folderu z projektami, uruchamia je i zatrzymuje. Logi tasków są w module `logs` (§4.2, ADR-28); serwisy (port, sonda, dzierżawy) to następny krok.

- **Log**: wyjście taska idzie do modułu `logs` jako źródło `mise-task` (§4.2), na żywo w zakładce pod wierszem taska.
- **Lista tasków** to `mise tasks ls --json` w korzeniu repo przy każdym zapytaniu (UI odpytuje, gdy zakładka jest otwarta: co 2 s, gdy coś działa, inaczej co 10 s, bo w zaufanym repo mise wykonuje przy tym `[env]`), bez ukrytych (`hide`) i bez nazw, które mise wziąłby za opcję. Brak `mise` w `PATH`, konfiguracja bez zaufania (`untrusted`) i inny błąd mise (np. składnia `mise.toml`) to stany listy, nie błędy API (tak samo przekroczony limit czasu); z komunikatu znikają ostrzeżenia mise (`mise WARN`), które nie są przyczyną. Działający task zostaje do zatrzymania także wtedy, gdy zniknął z konfiguracji albo mise przestał podawać listę (np. błąd w `mise.toml` w trakcie pracy): stan bez listy niesie `running`.
- **Uruchomienie** to `mise run <task>` w korzeniu repo przez `procs`, tylko dla taska z aktualnej listy (§1.2); działający task zwraca swój stan zamiast drugiej grupy. Brak mise przy starcie to `mise_unavailable`, task spoza listy `not_found`.
- **Zaufanie**: mise nie czyta konfiguracji z `[env]`, szablonami albo hookami, dopóki użytkownik jej nie zaufa, a sam `mise run` ufa swojej konfiguracji automatycznie. Akcja `trust` (`mise trust` w korzeniu repo, bez katalogów nadrzędnych) jest tylko w UI, z ostrzeżeniem, że konfiguracja mise może uruchamiać programy (§8).
- **Dla komendy zbiorczej** (§4.8) moduł ma dwa uruchomienia doczekane do końca grupy: `runToEnd` (task z aktualnej listy, `null`, gdy repo go nie ma; działający już task, np. ze szczegółów repo, nie startuje drugi raz, a wynikiem jest jego koniec) i `installTools` (`mise install` w korzeniu repo, własny właściciel grupy `mise-install:<repo>`, bo task może nazywać się `install`). Oba biorą `AbortSignal`: przerwanie przed startem nie uruchamia procesu, a po starcie zatrzymuje grupę tym samym stopem co szczegóły repo; gdy zatrzymania nie da się potwierdzić, wynikiem jest błąd `stop_unconfirmed` zamiast dalszego czekania.
- **Agent przez MCP** (ADR-41, §5.3): `run_mise_task`, `stop_mise_task`, `wait_for_mise_task` i `list_running_mise_tasks` to te same `start`, `stop` i `running` co w UI, plus `waitForEnd`: bieżące uruchomienie po końcu grupy potwierdzonym w systemie (`procs.ended`) albo po limicie czasu, a przerwanie przez klienta kończy tylko czekanie, nie task. Taski uruchomione przez agenta i z UI to te same grupy, więc agent widzi i zatrzymuje także task uruchomiony przyciskiem, a UI task agenta.
- **Działające taski wszystkich repo** (`mise/running`, `RunningMiseTask`): odczyt z pamięci modułu (taski uruchomione przez daemon, których grupa jeszcze nie skończyła), bez pytania mise i bez czytania folderu; z niego pulpit (§5.5) wie, w którym repo coś działa, bez `mise tasks ls` na każde repo co kilka sekund.
- Krótkie wywołania `mise` (`tasks ls`, `trust`) idą przez `mise-cli.ts`: tablica argumentów, bez powłoki, limit 15 s i 4 MB wyjścia; nie potrzebują grupy procesów.

### 4.8 `batch`: komenda zbiorcza

Komenda zbiorcza (ADR-27) to wybrane kroki na wybranych repo jednym przyciskiem w widoku „Repos”: synchronizacja, narzędzia, zależności i build, z wynikiem każdego kroku w każdym repo. Moduł nie uruchamia niczego sam, tylko składa `workspace` i `mise` ponad nimi.

- **Kroki** (`BatchStep`) idą w repo zawsze w tej kolejności, niezależnie od kolejności w żądaniu: `sync` (synchronizacja jednego repo, §4.5, ADR-21; `vcs` i tak synchronizuje jeden katalog `.git` po kolei, więc równoległa „Sync all” nie przeszkadza; repo w trakcie klonowania to błąd kroku), `tools` (`mise install` w korzeniu repo: JDK, Node i reszta z konfiguracji mise repo), `setup` (task mise `setup`, czyli zależności) i `build` (task mise `build`). Nazwy tasków to konwencja z `CONTEXT.md`; repo bez danego taska ma krok `skipped` z powodem i idzie dalej. Komendy składa daemon z nazwy kroku (§1.2); klient podaje tylko identyfikatory repo i kroki z listy.
- **Wynik kroku** (`BatchStepState`): `waiting`, `running`, `done` (synchronizacja z gałęzią i liczbą nowych commitów), `skipped` (z powodem; pominięta synchronizacja nie zatrzymuje repo, bo kolejne kroki działają na tym, co jest lokalnie), `failed` (komunikat i ostatnie linie wyjścia procesu; pozostałe kroki repo są `skipped`, a inne repo idą dalej) albo `cancelled`. Krok mise kończy się `done` przy kodzie 0, a `cancelled`, gdy grupę zatrzymał użytkownik: przerwaniem komendy, stopem taska w szczegółach repo albo wyjściem daemona.
- **Równoległość**: najwyżej 3 repo naraz (build Javy albo frontendu zajmuje kilka rdzeni i GB pamięci, a `mise install` pobiera JDK), w repo krok po kroku. Taski idą przez `procs` pod tym samym właścicielem co ze szczegółów repo, więc szczegóły repo pokazują je jako działające i mogą je zatrzymać, a drugi start tego samego taska dołącza do działającego zamiast uruchamiać drugą grupę.
- **Cache**: powtórka jest tania dzięki mise, nie Trackwallowi. Task z `sources` i `outputs` mise pomija, gdy wyjścia są nowsze od źródeł, a `depends` uruchamia zależności taska raz na `mise run`. `build` z `depends = ["setup"]` uruchomi `setup` drugi raz w tej samej komendzie, chyba że `setup` ma `sources` i `outputs`; to świadomy wybór (ADR-27). Przy krokach `setup` i `build` mise sam też instaluje brakujące narzędzia, więc krok `tools` jest po to, żeby instalacja była widoczna jako osobny wynik.
- **Przerwanie** (`cancel`): repo, które czekają, i kroki, które się nie zaczęły, kończą się jako `cancelled`, a trwający krok mise dostaje stop grupy (`AbortSignal`, §4.7). Trwającej synchronizacji nie da się przerwać, bo git nie jest w grupie procesów (§8); kończy się sama. Grupa, której zabicia nie da się potwierdzić, kończy krok błędem `stop_unconfirmed` (grupa zostaje `stopping` w szczegółach repo, skąd stop można ponowić), więc przerwanie zawsze kończy komendę. Bez przerwania komenda czeka na grupę, której końca nie da się potwierdzić (np. task ze szczegółów repo po nieudanym stopie), i pokazuje ten krok jako trwający. Przerwanie zatrzymuje też task, do którego komenda dołączyła, choć uruchomił go użytkownik ze szczegółów repo. Wyjście daemona przerywa komendę przed zatrzymaniem grup i odrzuca start nowej, także takiej, która właśnie sprawdza repo.
- **Stan** jest tylko w pamięci daemona, jak synchronizacja: `run` zwraca ostatnią komendę, naraz trwa jedna (drugi start to `bad_request`), a nieznane repo odrzuca całe żądanie (`not_found`), zanim cokolwiek ruszy. UI odpytuje co 1,5 s w trakcie i co 10 s poza nim; komenda zbiorcza może zostać kolejnym tematem `/ws` (ADR-36).
- **Wybór repo** robi klient: panel komendy zbiorczej (w miejscu szczegółów repo, jak panel synchronizacji) ma listę repo z polami wyboru, domyślnie wszystkie. Lista to repo po filtrze tagów z listy repo (ADR-25), więc „build wszystkich `java` + `bff`” to dwa kliknięcia w filtrze; zmiana filtra zaczyna wybór od nowa (wszystkie z nowej grupy).
- **Ten sam katalog, inny wpis**: dowiązanie w folderze z projektami do innego repo z listy to osobne repo (ADR-18), więc komenda grupuje repo po katalogu na dysku (`realpath`, bez wielkości liter) i repo jednej grupy idą po kolei: dwa `pnpm install` albo buildy naraz w jednym katalogu psułyby sobie pliki. Przed każdym krokiem komenda sprawdza też, że identyfikator repo wskazuje ten sam katalog co przy starcie, bo identyfikator z nazwy katalogu może przejść na nowy katalog (ADR-18); inaczej krok kończy się błędem.
- **Tryb monorepo mise** (`monorepo_root`, `mise run '//...:build'`) został sprawdzony jako silnik i odrzucony (ADR-27): wymaga pliku konfiguracji w folderze z projektami, jednego procesu dla wszystkich repo i przerywa pozostałe po pierwszym błędzie.

## 5. Protokoły

### 5.1 Odkrywanie daemona

Daemon przy starcie zapisuje `~/.trackwall/daemon.json`: `{ pid, port, token, startedAt, version }` z uprawnieniami tylko dla użytkownika. Port jest losowy z zakresu loopback, nasłuch wyłącznie na `127.0.0.1`. Drugi daemon kończy się, gdy `/api/health` istniejącego odpowiada tą samą wersją; przy innej wersji prosi o restart z UI. Klienty (Tauri, `ws`, most stdio MCP) czytają ten plik, nic nie jest konfigurowane ręcznie.

### 5.2 Daemon ↔ UI i CLI: HTTP + WebSocket

- **HTTP JSON** dla komend i zapytań: `POST /api/<moduł>/<akcja>` z ciałem walidowanym zod z `packages/protocol`. Odpowiedź `{ ok, data }` lub `{ ok: false, error: {code, message} }`. Jedna konwencja dla UI i `ws`. Ciało ma najwyżej 64 KB; puste znaczy `{}`. Akcja jest opisana w `packages/protocol` jednym obiektem `Endpoint` (ścieżka, schemat ciała, schemat `data`): daemon waliduje nim wejście (`api/routes.ts`), a UI typuje ciało i sprawdza odpowiedź, więc obie strony nie mogą ich sparować inaczej. Dziś działają akcje `workspaceApi`: `list` (`{ projectsDir, repos }`), `settings` (`{ projectsDir, configFile }`), `repo-hosts` (lista hostingów), `set-projects-dir {path}`, `overview {repo}` (README i 30 commitów), `tree {repo, path}`, `file {repo, path}`, `changes {repo}` (`WorkingTreeChanges`: pliki i diff katalogu roboczego względem HEAD, ADR-34), `open-editor {repo}`, `open-folder {repo}` (the repo folder in Explorer or Finder, `null`, ADR-51), `dropped-folder {path}` (`DroppedFolder`, ADR-51), `open-link {url}` (adres `http` albo `https` z README otwierany w przeglądarce systemu, ADR-35), `set-repo-hosts {repoHosts}` (zapisana lista), `remote-repos {query}` (`{ projectsDir, hosts }`), `clone {host, fullName}` (klonowanie w stanie `running`), `clones`; `open-editor` zwraca `data: null`. Do tego `agentsApi` (§4.4, ADR-26): `sessions` (`SessionList`: sesje od najnowszej, z grupą procesów `RunState`, ostatnią zmianą stanu, tytułem okna i tym, czy czeka na Ciebie), `start {repo}` (`Session`), `stop {session}` (wraca po potwierdzonym końcu grupy) i `dismiss {session}` (tylko zakończona sesja, inaczej `bad_request`); dla zadań (ADR-31) `create-task {repo, prompt}` i `resume-task {task}` (`Task`), `task-changes {task}` (`TaskChanges`), `open-task-editor {task}` (`null`) i `remove-task {task, keepBranch, discardChanges}` (`null`); `sessions` zwraca też zadania i katalog ich worktree. Oraz `miseApi` (§4.7): `tasks {repo}` (`MiseTasks`: lista z `RunState` albo `not_installed` / `untrusted` / `error`), `start {repo, miseTask}` i `stop {repo, miseTask}` (`RunState`; `stop` wraca po potwierdzonym końcu grupy), `trust {repo}`, `running` (`RunningMiseTask[]`: działające taski wszystkich repo, z pamięci daemona). Do tego `batchApi` (§4.8): `start {repos, steps}` (`BatchRun`: komenda zaczęta w tle), `run` (ostatnia komenda albo `null`) i `cancel`. Do tego `logsApi` (§4.2): `tail {source, sinceSeq?, limit}` (`LogTail`: `records`, `nextSeq`, `dropped`; `limit` do 1000). Do tego `cardsApi` (§4.6): `card {repo}` (`RepoCardResult`: karta albo `null` w repo bez commitów i tagi) i `tags` (tagi każdego repo z folderu albo `unavailable`). Oraz `graphApi` (§4.6, ADR-29): `graph` (`RepoGraph`: węzły, krawędzie z dowodami, błędy wpisów `graph` i ścieżka `workspace.yaml`). Komunikaty walidacji są po angielsku (domyślna lokalizacja zod, ADR-32). Błąd zgłoszony świadomie przez moduł (`DomainError`) wraca z kodem i treścią: `bad_request` 400, `not_found` 404, `repo_unavailable` 409, `projects_dir_unavailable` 409 (folder z projektami zniknął), `invalid_config` 500 (zły `workspace.yaml`), `mise_unavailable` 409 (brak mise, konfiguracja bez zaufania albo błąd mise przy starcie taska), `stop_unconfirmed` 500 (grupa żyje po zabiciu), `agent_unavailable` 409 (brak Copilot CLI w `PATH` albo PTY w tym runtime), `unsaved_changes` 409 (zakończenie zadania skasowałoby zmiany, których wołający nie potwierdził); każdy inny wyjątek to `internal` bez szczegółów.
- **WebSocket `/ws`** dla zdarzeń (ADR-36, `api/event-socket.ts`, `api/event-hub.ts`): ramki tekstowe JSON `DaemonEvent` `{ type, payload }` (`packages/protocol/src/events.ts`), w których `payload` to cała **migawka tematu**, ta sama co odpowiedź akcji HTTP: `sessions.changed` (`SessionList`, jak `agents/sessions`) i `mise.running.changed` (`RunningMiseTask[]`, jak `mise/running`). Po podłączeniu daemon wysyła najpierw migawkę każdego tematu, potem zdarzenie tylko wtedy, gdy migawka tematu się zmieniła, więc klient po zerwanym połączeniu łączy się ponownie i nie potrzebuje bufora zdarzeń, numeru zdarzenia ani `resync`; kolejność daje jedno połączenie. Zmianę daemon wykrywa, porównując JSON migawki co 200 ms (tyle co cykl sesji), dopóki ktoś słucha, i serializuje zdarzenie raz dla wszystkich klientów; komplet tematów sprawdza kompilator (`TOPICS` w `event-hub.ts`). Temat, którego odczyt się nie udał, trafia do logu daemona raz na ten sam błąd, a gdy klienci mieli już jego migawkę, daemon zamyka ich połączenia kodem 1011: po ponownym połączeniu dostają migawki bez tego tematu, więc UI wraca dla niego do odpytywania HTTP i pokazuje błąd zamiast starej migawki jako stanu na żywo. Klient nic nie wysyła (ramka ponad 1 KB kończy połączenie), a klient, który nie odbiera (ponad 4 MB w buforze), dostaje zamknięcie kodem 4429 (`EVENTS_CLOSE_SLOW`) i łączy się ponownie od migawek. Połączenie przechodzi te same sprawdzenia co terminal sesji (niżej, `api/sockets.ts`), z podprotokołem `trackwall.events` obok tokenu; w `vite dev` token dokłada proxy Vite, jak przy terminalu. UI (`lib/daemon-events.ts`) trzyma jedno połączenie na połączenie z daemonem, łączy się ponownie po 1 s, a potem coraz rzadziej, do 10 s, i podaje tematy jako `LiveFeed` do `useRemote` (opcja `live`): migawka zastępuje dane jak odpowiedź, odpytywanie HTTP czeka, dopóki temat ma migawkę z bieżącego połączenia, a pierwsze pobranie, `reload` po akcji i czas bez połączenia zostają na HTTP. Pytania i migawki numeruje jeden licznik (`LoadOrder`: pytanie przy wysłaniu, migawka przy przyjściu), a odpowiedź na pytanie wysłane przed migawką nie zastępuje nowszej migawki; migawka odczytana w daemonie tuż przed akcją, a przyjęta po niej, liczy się jako nowsza od akcji, aż następna (najwyżej 200 ms później) ją poprawi. Kolejne tematy (logi `log.append`, serwisy, synchronizacja i klonowanie, lista repo, gdy daemon zacznie obserwować repo) to kolejne warianty `DaemonEvent` i wpisy `TOPICS`; powłoka Tauri dalej odpytuje `sessions` przez HTTP (§5.4).
- **PTY** jako osobny WebSocket `/ws/pty/<sesja>` (ADR-26, `api/pty-socket.ts`, obsługa `upgrade` i sprawdzenia wspólne ze zdarzeniami w `api/sockets.ts`, biblioteka `ws`, bo Node nie ma serwera WebSocket): po podłączeniu daemon wysyła obraz ekranu sesji (ramka tekstowa z `@xterm/addon-serialize`, z trybami terminala i alternatywnym ekranem), potem wyjście PTY ramkami binarnymi, dokładnie od miejsca, w którym kończy się obraz. Klient wysyła ramki tekstowe JSON `PtyClientMessage`: `input` (klawisze i wklejony tekst, do 65 536 znaków) i `resize` (kolumny i wiersze). The client also sends `focus {focused}` after the window has been focused and visible for 1 s and when it stops being so; a focused window marks the session seen (ADR-47), and a closed connection counts as unfocused. In the session grid (ADR-48) only the selected tile reports `focused: true`; the other tiles report that they are not in front. Połączenie przechodzi te same sprawdzenia `Host` i `Origin` co reszta API; token jest drugim podprotokołem (`bearer.<token>`, `SOCKET_TOKEN_PREFIX`, porównanie w stałym czasie), a serwer potwierdza tylko `trackwall.pty`, bo przeglądarka nie ustawi nagłówka przy WebSocket, a adres trafia do logów i historii. Adres i podprotokół gniazda idą w parze (`DaemonSocket`, `ptySocket`, `EVENTS_SOCKET`, `daemonSocketAt` w `packages/protocol/src/sockets.ts`), więc daemon, proxy Vite i UI nie mogą ich połączyć inaczej. Token jest sprawdzany przed adresem (bez tokenu 401 także pod nieznanym adresem), potem adres (404) i podprotokół gniazda (400). Nieznana, zamknięta (`dismiss`) albo podana nie jako UUID sesja zamyka połączenie kodem 4404 (`PTY_CLOSE_NOT_FOUND`, okno nie łączy się ponownie), okno, które nie odbiera wyjścia (ponad 8 MB w buforze), kodem 4429 (`PTY_CLOSE_SLOW`). Żądanie, którego adresu nie da się sparsować, dostaje odmowę, a błąd w obsłudze połączenia kończy tylko to połączenie, nie daemon. W `vite dev` token dokłada proxy Vite, jak przy `/api` (§8). Stan sesji przychodzi do UI zdarzeniem `sessions.changed` z `/ws` (wyżej); bez połączenia zdarzeń UI odpytuje `sessions` co 1 s przy otwartym widoku i co 3 s poza nim (licznik na pasku widoków).
- **Uwierzytelnianie**: token z `daemon.json` w nagłówku `Authorization: Bearer`, porównanie w stałym czasie. Odrzucane są żądania, których `Host` lub `Origin` nie jest loopbackiem (DNS rebinding, CSRF ze strony w przeglądarce). Tauri podaje token do WebView przez komendę Tauri, nie przez query string.

### 5.3 Daemon ↔ agent: MCP

Daemon wystawia serwer MCP w transporcie **Streamable HTTP** pod `/mcp` z tym samym tokenem. Dla CLI, które obsługują tylko stdio, jest most stdio `trackwall-daemon mcp-stdio`, który przekazuje wiadomości JSON-RPC do `/mcp`. Docelowo funkcja „podłącz agenta” w UI dopisuje wpis do konfiguracji MCP danego CLI, nie ruszając reszty pliku; dziś UI pokazuje komendę, która robi to po stronie Copilot CLI (niżej).

Pierwszy wycinek (ADR-24) daje **agentowi nadrzędnemu** (Copilot CLI uruchomionemu przez użytkownika, np. w folderze z projektami) mapę repo, tylko do odczytu; ADR-39 dodaje zlecanie zadań innym sesjom przez propozycje, które zatwierdza użytkownik, a ADR-41 uruchamianie i zatrzymywanie tasków mise z zaufanej konfiguracji repo:

- **Serwer** (`src/mcp/endpoint.ts`) to `createMcpHandler` z `@modelcontextprotocol/server`, bez sesji MCP: każde żądanie dostaje świeży `McpServer` z tymi samymi narzędziami, bo stan trzyma fasada. Żądanie z nagłówkiem `x-trackwall-session-token` (most stdio sesji Trackwall, ADR-39) `handle()` w `api/server.ts` rozpoznaje przez `agents.callerSession`, a sesja, która woła, trafia do fabryki serwera jako `authInfo.clientId` i do każdego wywołania narzędzia; nieznany token (zamknięta sesja) to `401 unauthorized` przed SDK, żeby sesja nie wyglądała na agenta spoza Trackwall. Obsługuje rewizję 2026-07-28 i starsze klienty z `initialize` (bezstanowo; GET i DELETE sesji dają 405). `handle()` w `api/server.ts` sprawdza `Host`, `Origin` i token daemona (jedno sprawdzenie tokenu dla API i MCP; publiczne są tylko `GET /api/health` i pliki UI), zanim żądanie trafi do SDK; ciało ma najwyżej 256 KB, a rozłączony klient przerywa żądanie także w SDK. `main.ts` składa serwer MCP z fasady i podaje go do `startApi`. The server announces `instructions` with the MCP instruction (`MCP_INSTRUCTIONS` in `protocol`, ADR-46): what Trackwall is and when to reach for which tool (the repo card before reading build files, `search_code` to find code across repos, `find_endpoint` and `who_calls` before changing an API, `get_errors` (then `tail`) to diagnose a failure, `run_mise_task` and `wait_for_mise_task` to build and test, `propose_task` and `wait_for_session` to hand work over, `report_result` at the end of a task). Tool names come from `mcpTools`, and a test requires the instruction to mention every tool, so a new tool cannot land without a sentence on when to use it. Copilot CLI 1.0.103 adds `instructions` to the prompt only for servers on its own allowlist (unless started with `--allow-all-mcp-server-instructions`), so Trackwall sessions get the same instruction in their session instructions too (§4.4).
- **Narzędzia** (`src/mcp/tools.ts`): `list_repos`, `get_repo`, `get_repo_card`, `tail` (log taska mise, §4.2), `get_errors` (błędy z logów, ADR-42), `who_calls`, `subgraph_for` i `find_endpoint` (graf połączeń, §4.6), `search_code` (wyszukiwanie kodu, §4.5, ADR-40) oraz `list_sessions` i `get_session` (sesje i zadania, §4.4, ADR-36), a do zlecania pracy `propose_task`, `report_result` i `wait_for_session` (§4.4, ADR-39), a do tasków mise `run_mise_task`, `stop_mise_task`, `wait_for_mise_task` i `list_running_mise_tasks` (§4.7, ADR-41). Kontrakt narzędzia (nazwa, opis dla agenta, schemat wejścia i wyniku) to obiekt `McpTool` w `mcpTools` (`packages/protocol/src/mcp.ts`), jak `Endpoint` dla API; daemon podaje do niego tylko wykonanie na fasadzie (`defineTool`), a UI bierze z niego nazwy. Adnotacje bierze z kontraktu: `readOnlyHint` z pola `readOnly`, a narzędzie z `readOnly: false` musi podać `destructive` (`destructiveHint`). `propose_task` i `report_result` zapisują tylko tekst dla człowieka (`destructive: false`); `run_mise_task` wykonuje kod repo, a `stop_mise_task` może zabić proces, którego użytkownik potrzebuje (serwer, migracja), więc oba mają `destructive: true` i klient MCP, który pyta o zgodę na niszczące narzędzia, zapyta o nie. Każde zwraca `structuredContent` sprawdzone schematem i ten sam JSON jako tekst dla klientów, które go nie czytają. Błąd zgłoszony przez moduł (`DomainError`) wraca jako wynik z `isError` i tekstem `<kod>: <komunikat>`, inny jako `internal` bez szczegółów. Każde wywołanie trafia do logu daemona (narzędzie, sesja, która woła, czas, wynik, bez argumentów); narzędzie niszczące (`run_mise_task`, `stop_mise_task`) dopisuje przed działaniem linię ze swoimi argumentami, czyli repo i taskiem mise (ADR-41). Tabela `audit` przyjdzie z SQLite. Kolejne narzędzie to kolejny wpis `mcpTools` z wykonaniem w `runs` w `tools.ts` (jego brak to błąd kompilacji) i rejestracją, której komplet sprawdza test `tools/list`.
- **Most stdio** (`trackwall-daemon mcp-stdio [--home <dir>] [--session-token-file <plik>]`, `src/mcp/stdio-bridge.ts`) czyta linie JSON-RPC ze stdin i wysyła każdą osobno do `/mcp` z portem i tokenem z `daemon.json`, czytanym przy każdej wiadomości: restart daemona (nowy port i token) nie wymaga zmiany konfiguracji agenta, a token nie trafia do niej wcale. W sesji Trackwall most czyta też przy każdej wiadomości token sesji z pliku z `--session-token-file` i wysyła go w nagłówku `x-trackwall-session-token` (ADR-39); bez pliku (sesja zamknięta) odpowiada błędem `-32000` zamiast wysłać żądanie jako agent spoza Trackwall. Limit czasu jednego żądania to 120 s, z zapasem na `wait_for_session` (do 55 s). Wiadomości idą równolegle; odpowiedź JSON albo SSE wraca jako linie na stdout, a komunikaty mostu tylko na stderr. Wersję z `initialize` most dopisuje do kolejnych żądań jako `MCP-Protocol-Version`. Błąd transportu, który daemon zwraca z `id: null` (np. nagłówek odrzucony przez SDK), most odsyła z `id` żądania, bo klient stdio paruje odpowiedzi po `id`. Sondę rewizji 2026-07-28 (`server/discover`) most odrzuca jak serwer bez tej metody (`-32601`), bo w tej rewizji żądanie HTTP powtarza pola treści w nagłówkach, których przez stdio nie ma; klient przechodzi wtedy na `initialize` (tak robi Copilot CLI 1.0.103). Bez działającego daemona, z odrzuconym żądaniem albo z odpowiedzią bez wiadomości o tym `id` (strumień zerwany w trakcie) most odpowiada błędem `-32000` z poleceniem uruchomienia Trackwall; sam daemona nie uruchamia. Linia, która nie jest JSON-em, dostaje `-32700`, a JSON, który nie jest obiektem JSON-RPC (także paczka, której MCP nie ma od rewizji 2025-06-18), `-32600`. Po końcu stdin most czeka na odpowiedzi w drodze i kończy się sam, gdy stdout się opróżni.
- **Podłączenie Copilot CLI**: `/api/daemon/info` podaje `mcpStdioCommand`, komendę mostu tego daemona (binarka z wydania, rozpoznana po wirtualnym systemie plików Bun w ścieżce skryptu, `isCompiledBinary`; przy uruchomieniu ze źródeł runtime i skrypt, pod Bun z `--no-env-file` i `--config` wskazującym pusty `packages/daemon/bunfig.toml`; niedomyślny katalog stanu jako `--home`). Widok „Daemon” pokazuje z niej komendę `copilot mcp add trackwall -- <komenda mostu>` (cytowanie dla PowerShell na Windowsie, gdzie w apostrofach są też argumenty z `,` i `@` oraz zaczynające się od `-`, bo gołe `--` PowerShell zjada przed skryptem `copilot.ps1`; sh na macOS) i ten sam wpis do `mcp-config.json` w katalogu `.copilot` użytkownika do skopiowania. Copilot CLI uruchamia most przy starcie i trzyma go do końca sesji, więc Trackwall musi działać wcześniej.

Narzędzia (wszystkie przyjmują identyfikatory; zrobione są `list_repos`, `get_repo`, `get_repo_card`, `tail`, `get_errors`, `who_calls`, `subgraph_for`, `find_endpoint`, `search_code`, `list_sessions`, `get_session`, `propose_task`, `report_result` i `wait_for_session`, reszta to plan):

| Narzędzie | Wejście | Zwraca |

### 5.4 Tauri ↔ daemon

Tauri uruchamia daemon jako sidecar z argumentem `--parent <pid>`, czeka na `/api/health`, pokazuje ekran powitalny, a po niepowodzeniu dialog z logiem startu. Okno pokazuje się dopiero po załadowaniu UI, z już ustawionym efektem tła (ADR-11). Zamknięcie okna chowa je do traya. Każde wyjście z powłoki zatrzymuje daemon: powłoka przerywa trwający start, wysyła `POST /api/daemon/shutdown` (gdy start się nie udał, do daemona z `daemon.json`), daemon zatrzymuje serwisy i sesje tym samym łagodnym stopem co Ctrl-C, a Tauri czeka, aż przestanie odpowiadać, i po tym nie uruchamia już nowego. Daemon, który już odpowiada, dostaje łagodne zatrzymanie także wtedy, gdy wyjście przyszło w trakcie startu; zabijany jest tylko sidecar, który jeszcze nie wstał. „Quit” z traya chowa okno i ikonę, a zatrzymuje daemon w tle przed końcem pętli zdarzeń, więc pojedyncza instancja jest trzymana do końca. Cmd+Q i „Zakończ” z Docka na macOS (a według kodu tao także koniec sesji Windows, gdzie system może zakończyć proces przed końcem czekania) kończą pętlę z pominięciem `ExitRequested`, więc robi to obsługa `RunEvent::Exit`, po schowaniu okien i usunięciu ikony z traya. Powłoka co 2 s pyta daemon o sesje (`POST /api/agents/sessions`, tym samym ręcznym klientem HTTP), bo WebView schowanego okna może mieć wstrzymane timery, a zdarzeń z `/ws` nie słucha, bo wymagałyby klienta WebSocket w Rust, a na miganie okna 2 s wystarcza (ADR-36): sesja, która przechodzi z `Working` albo `Stale` w czekanie na człowieka, wywołuje `request_user_attention` (miganie na pasku zadań Windows, podskok w Docku macOS), a każda czekająca sesja ma w menu traya pozycję „Waiting: <repo>”, która pokazuje okno i wysyła do UI zdarzenie `focus-session` with `{kind: "session", id}`. Task proposals work the same way (ADR-39, from `proposals` in the same reply): the item “Proposal: <repo> · <title>” above the sessions sends `focus-session` with `{kind: "proposal", id}`, and a proposal that was neither a proposal nor a task at the previous poll (a proposal being approved is already a task, and comes back after a failed start) calls `request_user_attention`; at the first poll after the shell starts none is new. `&` in a menu item's text is doubled, because it marks a mnemonic. The icon tooltip says how many sessions and proposals are waiting. Daemon sam nie kończy się po śmierci rodzica (tryb „działa przy zamkniętym oknie”), ale sprawdza `--parent` tylko po to, żeby odróżnić start z Tauri od ręcznego. Po awarii albo zabiciu powłoki daemon działa dalej, a następne uruchomienie aplikacji podłącza się do niego przez `daemon.json`.

The shell also gives the window two things that need the system (ADR-51). The app command `pick_folder` opens the system folder picker (`tauri-plugin-dialog`, called from Rust) and returns the chosen full path, which the UI saves with `set-projects-dir`; the plugin's own JavaScript commands stay unreachable, because the window's capability is still only `core:default`. Files dropped on the window come as Tauri's webview drag-and-drop events (`onDragDropEvent`: full paths and a point in physical pixels); the UI sends a `FileDropEvent` to the element under the point, a session terminal pastes the paths and cancels it, and an uncancelled drop goes to `dropped-folder` (§4.5). Tauri's drag-and-drop handling turns off HTML5 drag and drop inside the page on Windows, so the UI does not use it.

### 5.5 Daemon ↔ scena 3D

`@trackwall/scene` nie ma własnego transportu ani nie zna API daemona (ADR-33). UI liczy z tych samych odpowiedzi co lista repo, widok „Sessions” i „Overview” migawkę pulpitu `HomeModel`: repo ze stanem (`clean`, `behind`, `changed`, `unavailable`), liczbą zmian albo commitów do pobrania i działającym taskiem mise (z `mise/running`, §4.7), sesje ze stanem (`working`, `attention`, `idle`, `error`, `done`; `idle` is `Input` the user has seen, ADR-47), połączenia z grafu, liczbę warstw i to, czy daemon działa. Warstwa repo to kolumna z układu grafu w „Overview” (najdłuższa ścieżka od repo, którego nikt nie używa), więc pulpit i graf nie różnią się co do warstw; repo bez połączeń ma warstwę `null`. `HomeScene.apply(model)` przyjmuje kolejne migawki i trzyma jedną encję Pawn na obiekt (`KeyedEntities`): nowy obiekt dostaje encję, zniknięty ją traci razem ze swoimi sesjami i połączeniami, każdy staje na swoim miejscu w nowym układzie, a model three.js buduje się od nowa tylko wtedy, gdy zmieniło się coś, co widać. Sesje i działające taski mise przychodzą do niej ze zdarzeń `/ws` (ADR-36), reszta z odpytywania; scena nie wie, skąd jest migawka.

Układ „Orbit” (`orbitLayout`, czysta funkcja): daemon w środku, sesje na wewnętrznym torze naprzeciw swojego repo, repo na zewnętrznym pierścieniu w łukach warstw, a repo bez połączeń w ostatnim łuku. Rodzaj bryły repo wynika z warstwy: wejście (terminal), brama (walec z anteną), backend (szafa), biblioteka (skrzynka). Scena decyduje, które obiekty mają etykietę (repo, które nie jest czyste, i sesje, które czekają albo mają błąd), a treść etykiety pisze UI; resztę mówią kolor i kształt. Klik wybiera obiekt i podświetla połączenia jego repo, dwuklik zgłasza przejście do sesji albo repo, a wskazanie zgłasza obiekt pod kursorem dla karty podglądu. Kolory przychodzą z tokenów UI przeliczonych na `#rrggbb`, bo three.js nie czyta `oklch`. Przy `prefers-reduced-motion` modele stoją w pozie z chwili 0.

Widok „Home” (`views/home/`, Ctrl+1, pierwszy ekran po starcie) składa migawkę w `lib/home-model.ts` (`homeModel`) z listy repo (co 10 s, jak widok „Repos”), sesji (ta sama lista co pasek widoków, ze zdarzeń `sessions.changed`), grafu (co 30 s) i działających tasków mise (ze zdarzeń `mise.running.changed`; bez połączenia zdarzeń sesje co 1 s, a `mise/running` co 3 s, §5.2). Daemon „działa”, dopóki odpowiada: błąd listy repo z kodem (np. `invalid_config`) przyszedł od niego, a gdy folder z projektami trzeba poprawić (`projects_dir_unavailable`, `invalid_config`), widok pokazuje błąd i przejście do „Settings” zamiast starej listy, tak jak „Repos”. Po lewej kolejka „Needs you” (sesje, które czekają albo mają błąd, ze stanem z widoku „Sessions”, task proposals from the session list, ADR-39, and repos that are not clean; proposals are neither in the snapshot nor on the scene, and a click opens one in “Sessions” right away, because the decision, with an edited prompt, is made there), w środku płótno, po prawej szczegóły wybranego obiektu z przyciskiem „Open repo”, „Open session” albo „Open Daemon” (bez wyboru podsumowanie środowiska), a w rogu płótna karta podglądu obiektu pod kursorem. Ton i tekst stanu obiektu pulpitu ma jedno miejsce (`homeRepoStatus`, `HOME_SESSION_STATUS`, `homeDaemonStatus`), z którego biorą kolejka, szczegóły, podgląd i etykiety sceny; repo z commitami do pobrania nie jest na pulpicie czyste, choć lista repo liczy tylko zmiany w katalogu roboczym. Wybór z kolejki i ze sceny to ten sam stan, a wybór obiektu, który zniknął z migawki, przepada: scena podświetla obiekt, a `CameraRig` kieruje na niego kamerę; bez wyboru kamera wraca do kąta ze startu i patrzy na środek z odległości dobranej do proporcji płótna (`lib/home-camera.ts`), także po zmianie rozmiaru okna, żeby cały pierścień był w kadrze. Dwuklik albo przycisk przechodzi do widoku „Sessions” z tą sesją, do „Repos” z tym repo (tylko przy tym przejściu) albo do „Daemon”. Płótno (`HomeCanvas`) jest ładowane leniwie (`React.lazy`), bo three.js i Pawn to większość wagi widoku: reszta UI bierze ze sceny tylko `@trackwall/scene/model` (wejście `src/model.ts`: klucze, typy migawki i paleta, bez three.js), czego pilnuje Biome, a build usuwa nieużywane pliki dekodera Draco, które three.js zgłasza mimo braku glTF (`drop-unreferenced-draco.ts`). Kolory sceny czyta `lib/scene-palette.ts`: każdy token maluje na jednym pikselu płótna 2D na tle `--background` i odczytuje sRGB, więc półprzezroczyste tokeny wychodzą takie, jak widać je w aplikacji. Gdy WebGL 2 nie działa (sprawdzane na osobnym płótnie przed silnikiem, bo nieudany konstruktor `Engine` zostawia świat koota, a koota ma ich najwyżej 16) albo kontekst przepadnie (`webglcontextlost`), w miejscu płótna jest komunikat z przyciskiem „Try again”, a kolejka „Needs you” i szczegóły działają dalej. Schowane okno (`visibilitychange`) zatrzymuje pętlę silnika, bo Pawn sam jej nie wstrzymuje; render tylko przy zmianie to zgłoszenie do Pawn.

## 6. Model danych

Typy żyją w `packages/protocol`. Poniżej rdzeń; pola pomocnicze pominięte.

```ts
type RepoId = string;      // slug z nazwy katalogu w folderze z projektami, np. "orders-bff"
type ServiceId = string;   // zwykle = RepoId; repo może mieć kilka serwisów
type TaskId = string;      // ulid

// Dziś w protocol: { id, path, remote, status: RepoStatus } (§4.5; remote jako host/ścieżka, ADR-21); reszta pól dochodzi z kartami.
interface Repo {
  id: RepoId; path: string; remote: string; vcs: 'github' | 'gitlab' | 'git';
  defaultBranch: string; head: string;
  analysis?: { commit: string; at: string; cardId: string };
  lastSetup?: RunResult; lastTest?: RunResult;
}

// Dziś w protocol (cards.ts, http.ts, ADR-25, ADR-30): RepoCard bez `repo` (karta zależy tylko od commita) i bez
// `description`; provides to kind 'package' (ekosystem 'maven' | 'npm' | 'gradle-plugin', nazwa, wersja), 'app'
// (spring.application.name, port, moduł) i 'endpoint' (metoda, ścieżka, aplikacja, handler, typ żądania i odpowiedzi, ADR-38), consumes to 'package'
// (z zakresem) i 'http' (rodzaj klienta, nazwa, aplikacja albo adres z profilami, wywołania); zamiast `stack`
// i `runtime` są pliki buildu, narzędzia, mechanizmy i problemy.
interface RepoCard {
  commit: string;
  buildFiles: BuildFile[];   // { path, tool: 'maven'|'gradle'|'npm'|'pnpm'|'yarn'|'bun', name, memberOf }
  provides: Provided[];   // { kind: 'http'|'topic'|'package', key, evidence }
  consumes: Consumed[];   // { kind: 'http'|'topic'|'package'|'env-url', key, evidence }
  dtos: Dto[];            // { name, kind: 'record'|'data-class'|'class'|'enum', fields: { name, type }[], values, evidence } (ADR-38)
  tools: ToolRequirement[];   // { tool, version, source: 'mise'|'hint', evidence }
  mise: MiseSetup;            // { configFiles, tasks: { name, evidence }[] }: konfiguracja i taski mise z commita (ADR-34)
  mechanisms: Mechanism[];    // { id: MechanismId, evidence: (Evidence & { detail })[] }
  problems: CardProblem[];    // { path, message }: plik, którego ekstraktor nie przeczytał
  runtime: { ports: number[]; databases: string[]; secretNames: string[] };   // plan: z application*.yml
  description?: { text: string; origin: 'llm'; model: string; at: string };
}

interface RepoTag { name: string; reason: string }   // z karty i z reguł `repoTags` w workspace.yaml

// Dziś w protocol (graph.ts, ADR-29, ADR-30): GraphEdge między repo (RepoId), kind 'package' | 'http' | 'manual',
// dowody EdgeEvidence z repo (albo null dla workspace.yaml) i zdaniem `detail`.
interface Edge { from: ServiceId; to: ServiceId; kind: Consumed['kind']; key: string;
                 confidence: 'exact' | 'high' | 'medium' | 'low'; evidence: Evidence[] }

interface Service {
  id: ServiceId; repo: RepoId; port?: number;
  state: 'stopped'|'starting'|'healthy'|'unhealthy'|'stopping'|'crashed';
  groupId?: string; exitCode?: number; lastStderr?: string;
  lease: Lease;
}

interface Lease { service: ServiceId; holder: { kind: 'main' } | { kind: 'task'; taskId: TaskId };
                  worktree: string; since: string }

// Dziś w kodzie: `RuntimeGroup` w runtime.json (owner jako klucz tekstowy) i `RunState` w protocol (§4.1).
interface ProcessGroup { id: string; leaderPid: number; command: string[]; cwd: string;
                         startedAt: string; owner: { kind: 'service'|'task'|'run'; id: string } }

// Dziś w protocol: LogRecord bez source i pól ECS, LogSource = { kind: 'mise-task'; repo; miseTask } (§4.2, ADR-28).
interface LogRecord { seq: number; ts: string; source: LogSource; stream: 'stdout'|'stderr'|'pty';
                      level: 'trace'|'debug'|'info'|'warn'|'error'; msg: string;
                      traceId?: string; spanId?: string; fields?: Record<string, unknown>; raw: string }

// Dziś w protocol (agents.ts, ADR-31, ADR-39): Task z prompt, branch, baseBranch, base (commit bazowy), worktree,
// createdAt, title i proposedBy (z propozycji zadania) i summary ({ text, reportedAt } z report_result); sesja wskazuje
// zadanie (Session.task); bez adapter, budżetu, dzierżaw, changedPaths i nagrania, a stan zadania to stan jego sesji.
interface Task {
  id: TaskId; title: string; repo: RepoId; branch: string; worktree: string;
  adapter: 'copilot' | 'claude' | 'codex'; prompt: string;
  state: 'Working'|'Input'|'Approval'|'Plan'|'Done'|'Error'|'Stale';
  stateSource: 'hook'|'osc'|'screen'|'keyboard'|'timeout'|'exit'; stateConfidence: 'exact'|'high'|'medium'|'low';
  stateSince: string;   // TaskState, TaskStateChange: packages/protocol/src/task-state.ts
  budget: { maxMinutes?: number; maxCommits?: number };
  leases: ServiceId[]; changedPaths: string[]; recording: string;
  summary?: string;   // blok podsumowania z protokołu zakończenia
}

interface AuditEntry { id: number; at: string; client: string; tool: string;
                       args: unknown; durationMs: number; ok: boolean; resultDigest: string }
```

Trwałość: SQLite (`~/.trackwall/trackwall.db`) dla repos, cards (dziś pliki `cards/<commit>.json`, ADR-25), edges (cache; dziś daemon trzyma w pamięci tylko ostatni graf z kluczem wejścia, ADR-29, ADR-30), services, leases, tasks, audit; JSONL dla logów; nagrania sesji jako pliki; `runtime.json` tylko dla żywych grup procesów. Konfiguracja workspace to `workspace.yaml` (folder z projektami, hostingi repo, reguły tagów repo, aliasy paczek i ręczne krawędzie grafu, nadpisania portów, wskazanie repo sekretów), który użytkownik może trzymać w prywatnym repo; do czasu wyboru katalogu workspace leży w katalogu stanu daemona (ADR-12). Stan nigdy nie miesza się z konfiguracją.

## 7. Przepływy

**Start aplikacji.** Tauri → sidecar → `daemon.json` → `/api/health` → UI pobiera dane widoków akcjami HTTP i otwiera `/ws`, z którego dostaje migawki tematów zdarzeń (ADR-36). Daemon przy starcie: sprząta sieroty wg `runtime.json`, odtwarza listę zadań i proponuje wznowienie sesji agentów (komenda wznowienia z adaptera).

**`ws sync`.** Dla każdego repo równolegle (limit współbieżności): fetch, fast-forward gałęzi domyślnej, jeśli `head` ≠ `analysis.commit` to zależności (`mise run setup`) i ekstraktory kart; po wszystkim przeliczenie grafu i zdarzenie `graph.updated` (gdy graf dostanie pamięć; dziś liczy się przy każdym pytaniu, ADR-29). Repo, w którym fast-forward ruszyłby lokalne zmiany (niezacommitowane zmiany w wybranej gałęzi domyślnej, gałąź rozjechana albo z niewypchniętymi commitami), jest pomijane z ostrzeżeniem; zmiany na innej gałęzi nie przeszkadzają (ADR-21). Zrobione (ADR-21, §4.5): fetch i fast-forward z przycisku w UI, z powodem pominięcia per repo. Zależności z krokami `mise install`, `setup` i `build` na wybranych repo daje komenda zbiorcza (ADR-27, §4.8), na razie zawsze, a nie tylko przy nowym `head`; ekstraktory, graf i komenda CLI dojdą razem z tymi modułami.

**Uruchomienie serwisu.** UI → `services.start(id)` → `leases.check` → `secrets.resolve(repo)` (git show manifestu `Secret` z gałęzi `origin/<repo>`, klucze z `data` dekodowane z base64, z `stringData` brane wprost, do env) → `mise.run('dev')` przez `procs.spawn` w grupie → `logs` rejestruje źródło i maski → sonda `mise run health` cyklicznie → `service.state`. Awaria: `crashed` z kodem i ostatnią linią stderr na wierszu serwisu, bez restartu w pętli (co najwyżej trzy próby, potem rezygnacja).

**Zadanie agenta.** Dziś (ADR-31, §4.4): UI → `create-task {repo, prompt}` → `vcs.addWorktree` od gałęzi domyślnej → `tasks.json` → sesja Copilot CLI w worktree z `--interactive=<polecenie>` → zakładka „Changes” odpytuje `task-changes` → po zakończeniu sesji wznowienie (`--resume`) albo `remove-task` (worktree, opcjonalnie gałąź). While the task runs, its panel also asks `task-shared-files` for the shared-files warning (ADR-44). Z sesji głównej (ADR-39): sesja → `propose_task` → propozycja w widoku „Sessions” → użytkownik czyta polecenie, poprawia i „Start task” (`approve-proposal`) → to samo co `create-task`, z identyfikatorem propozycji → sesja zadania pracuje i woła `report_result` → sesja główna dostaje wynik z `wait_for_session` i czyta zmiany przez `get_session`. Docelowo: UI tworzy zadanie (repo, prompt, adapter, budżet) → `vcs.worktree.add` → zapis promptu do pliku → adapter buduje komendę i konfigurację MCP (adres `/mcp`, token sesji) → `procs.spawnPty` → detektory stanu → zdarzenie `sessions.changed` z migawką sesji (ADR-36) → tray i „skok do czekającego”. Gdy agent zmienia serwis, prosi o dzierżawę (`Approval` w UI lub automatycznie wg ustawienia). Zakończenie: blok podsumowania → `summary`, propozycja PR, oddanie dzierżaw, nagranie zamknięte.

**Błąd cross-repo.** Użytkownik widzi błąd w FE → klika rekord z `trace_id` → `trace(trace_id)` zwraca rekordy z BFF i serwisów w kolejności `seq` → widok osi czasu po serwisach → „utwórz zadanie z tym kontekstem” wkleja do promptu identyfikatory serwisów i zakres `seq`, a agent sam dociąga szczegóły przez MCP.

## 8. Bezpieczeństwo

- Loopback only, token, sprawdzenie `Host`/`Origin`, porównanie w stałym czasie.
- Token sesji (ADR-39) obok tokenu daemona: daemon wie, która sesja woła MCP, więc `report_result` zapisuje tylko do jej własnego zadania, a wywołanie trafia do logu z sesją, a `run_mise_task` i `stop_mise_task` działają tylko w repo sesji (ADR-41); później wpisze sesję do audytu. Token leży w katalogu sesji w katalogu stanu (plik z prawami tylko dla użytkownika na macOS i Linuksie), a nie w argumentach mostu, bo argumenty procesu widzą inni użytkownicy systemu; daemon trzyma tylko jego skrót. Proces działający jako ten sam użytkownik może przeczytać token innej sesji (jak `daemon.json`), więc token mówi, kto woła, ale nie chroni przed procesem użytkownika; nie daje też żadnego uprawnienia, którego nie ma token daemona.
- Katalog roboczy procesu zawsze wewnątrz repo lub worktree; ścieżki z wejścia są normalizowane i sprawdzane na wyjście poza korzeń. Przeglądanie repo czyta tylko obiekty z commita HEAD, a ścieżkę w repo waliduje schemat `RepoPath` (bez `.`, `..`, pustych segmentów i znaków sterujących; `\` jest zwykłym znakiem nazwy).
- Daemon uruchamia `git` w każdym podkatalogu folderu z projektami, który ma `.git` (ADR-18), więc na listę trafia też repo, którego użytkownik świadomie nie wybrał (np. rozpakowane archiwum). Konfiguracja repo (`.git/config`) obowiązuje jak w terminalu, z wyjątkiem kluczy, którymi repo kazałoby uruchomić program: daemon wyłącza `core.fsmonitor` (`git status`) i `log.showSignature` (`git log` wołałby `gpg.program`). Komendy przeglądania i stanu repo (`status`, `log`, `ls-tree`, `cat-file`) nie uruchamiają hooków ani `textconv` (synchronizacja uruchamia, niżej), ale `git status` może uruchomić filtr `clean` (np. git-lfs) zdefiniowany w `.git/config` dla ścieżek z `.gitattributes`: to luka, którą zostawiamy, bo wyłączenie filtrów psułoby stan repo z LFS; zamknie ją dopiero lista dozwolonych filtrów albo pytanie użytkownika o zaufanie przy pierwszym repo. Nowa komenda gita w daemonie musi to sprawdzić od nowa.
- Klon z hostingu (ADR-19) uruchamia `glab` albo `gh` z pełną nazwą repo z żądania UI. Nazwę waliduje schemat `RemoteRepoName` (segmenty nie zaczynają się od `-` ani `.`), więc nie zostanie wzięta za opcję programu ani nie wyjdzie katalogiem poza folder z projektami; hosting musi być w `workspace.yaml`. Token hostingu zostaje w `glab` i `gh`. Odpowiedź API to dane z zewnątrz: parsowana schematem, a błąd nie zawiera jej treści. Sklonowane repo podlega tym samym zasadom co każde repo w folderze (luka z filtrem `clean` wyżej). Luka: `glab`/`gh` i git klonu nie są w grupie procesów, więc klon przerwany limitem czasu albo końcem daemona może dalej działać w tle, aż git sam skończy (§4.5).
- Task mise to program z konfiguracji repo: uruchomienie go z UI to zgoda użytkownika na wykonanie kodu repo, tak jak `mise run` w terminalu. Daemon uruchamia tylko task z aktualnej listy `mise tasks ls`, w korzeniu repo, bez powłoki po stronie daemona; samą listę mise odmawia podać dla konfiguracji bez zaufania. `mise trust` (akcja `trust`) jest tylko w UI i dotyczy tylko konfiguracji w korzeniu repo; MCP nie ma narzędzia, które by zaufało. Na macOS daemon raz uruchamia interaktywną powłokę logowania użytkownika (`$SHELL -ilc`), żeby poznać `PATH`, więc wykonuje jego pliki startowe powłoki, jak każdy nowy terminal.
- Komenda zbiorcza (ADR-27, §4.8) uruchamia jednym kliknięciem `mise install` i taski `setup` i `build` w każdym wybranym repo, domyślnie we wszystkich z folderu z projektami, także w takim, którego użytkownik świadomie nie wybrał (ADR-18). Wybór repo i kroków w UI jest zgodą jak uruchomienie taska ze szczegółów repo. Taski idą tylko z listy `mise tasks ls`, której mise nie poda bez zaufania. Luka: `mise install` nie pyta o zaufanie, gdy konfiguracja repo ma same `[tools]` (sprawdzone na mise 2026.10.18: `mise trust --show` mówi `untrusted`, a instalacja idzie), więc pobiera i uruchamia instalator narzędzia wskazanego przez repo (np. wtyczkę asdf z adresem z `mise.toml`), tak jak `mise install` w terminalu. Zamknie ją wymaganie `mise trust` przed krokiem `tools` albo lista dozwolonych backendów narzędzi w ustawieniach.
- Sprzątanie sierot ufa `runtime.json` w katalogu stanu; proces użytkownika, który zapisze tam cudzy PID, i tak może zabić ten proces sam. Grupa, której lider nie żyje, jest zabijana bez sprawdzenia czasu startu: wyjątkiem byłby nowy proces z tym samym PID-em, który sam założył sesję, a potem zakończył się, zostawiając w niej potomków.
- Pod Node na Windowsie (tryb zgodności, ADR-20) grupa to drzewo z `taskkill /T`: pusta grupa znaczy tylko „lider nie żyje”, potomek osierocony przez wcześniejszą śmierć rodzica wypada z drzewa i przeżywa stop, a po twardym zabiciu daemona nic nie jest sprzątane (żywy PID z `runtime.json` trafia tylko do logu). Wydanie jest binarką Bun z Job Object, więc luka dotyczy uruchomienia ze źródeł pod Node.
- Krótkie zapytania do `mise` (`tasks ls`, `trust`) idą poza `procs`, jak `git`: po przekroczeniu limitu daemon kończy sam `mise`, a program uruchomiony przez mise z `[env]` zaufanej konfiguracji może przeżyć.
- Synchronizacja (ADR-21) uruchamia `git fetch` i `git merge --ff-only` w każdym repo z folderu z projektami, także w takim, którego użytkownik świadomie nie wybrał (ADR-18). Luka: fetch uruchamia programy wskazane w lokalnym `.git/config` repo (`core.sshCommand`, `remote.<nazwa>.uploadpack`, `credential.helper`), a `merge` hooki repo (`post-merge`, `reference-transaction`) i filtry `smudge` (np. git-lfs), tak jak `git pull` w terminalu. To ta sama klasa luki co filtr `clean` wyżej, ale szersza, bo dotyczy też kluczy, których daemon nie wyłącza; zostawiamy ją, bo wyłączenie helperów poświadczeń, ssh i LFS psułoby synchronizację zwykłych repo. Zamknie ją dopiero odczyt tych kluczy tylko z konfiguracji użytkownika i systemu albo pytanie o zaufanie przy pierwszym repo. Nazwa remote z `.git/config` idzie do gita po `--`, więc nie zostanie wzięta za opcję. Adres remote na liście nie zawiera użytkownika ani tokenu z URL, a `transport::` (z komendą) nie trafia na listę wcale. Luka: git synchronizacji nie jest w grupie procesów, więc przerwany limitem czasu albo końcem daemona może dalej działać w tle (jak klon, §4.5).
- Karta repo (ADR-25) czyta pliki z repo, którego użytkownik mógł nie wybrać (ADR-18), więc ich treść jest niezaufana: git czyta obiekty (`ls-tree`, `cat-file --batch`) bez filtrów, textconv i hooków, a ścieżki z drzewa idą do `cat-file` przez stdin, nie jako argumenty. Ekstraktory niczego nie wykonują (skrypt Gradle jest czytany jak tekst), parser XML nie zna DTD ani encji zewnętrznych, a limity (1 MB na plik, 2000 plików buildu i konfiguracji, 3000 plików źródłowych, 3000 plików typów dociąganych do kontraktów endpointów, 64 MB razem, 64 MB listy plików, 4096 znaków wartości po podstawieniu właściwości Maven) ograniczają pamięć na repo. Czas też: wyrażenia ekstraktorów nie mają sąsiadujących `\s*` ani klas, które na długiej linii dają kwadratowe cofanie (adres wrappera dopasowywany tylko w nazwie pliku, `${` bez zagnieżdżeń), linie Gradle ponad 2000 znaków i ścieżki ponad 1024 znaki w spisie mechanizmów są pomijane, linie kluczy (dowody zależności npm i narzędzi mise) liczy jedno przejście przez plik, globy workspace z repo dopasowuje programowanie dynamiczne (wzorzec × ścieżka), a korzenie buildów sprawdzają tylko przodków pliku; `cards-limits.test.ts` trzyma każdy z tych przypadków poniżej 1–2 s. Klucz z repo nie sięga do prototypu obiektu (`version.ref = "constructor"`). Świadomie zostaje: wzorzec `k8s/…/*.yaml` w spisie mechanizmów jest kwadratowy w długości ścieżki, ale ścieżka ma najwyżej 1024 znaki (ułamek milisekundy na plik), a skaner Gradle nie traktuje `\` jako ucieczki w potrójnym cudzysłowie (dobrze dla Kotlina; w Groovy pokazuje najwyżej kilka linii więcej, nigdy nie ukrywa linii). Fakty z karty to tekst z repo: UI pokazuje je jako tekst, a agent dostaje je przez MCP jako dane, które mogą zawierać próbę wstrzyknięcia poleceń (tak jak README z `get_repo`). Plik karty w katalogu stanu ma nazwę tylko z hashu commita sprawdzonego wzorcem i jest parsowany schematem przy odczycie.
- Kod Javy i Kotlina, konfiguracja Spring i pliki frontendu (ADR-30) są tak samo niezaufane jak pliki buildu: niczego się nie kompiluje ani nie wykonuje (konfiguracja Vite czy webpack to tekst), `git grep` dostaje stałe wyrażenie z daemona i ścieżki z drzewa nie trafiają do argumentów, a pliki źródłowe mają te same limity odczytu (3000 plików, 4 MB listy). Tokenizer i parser deklaracji przechodzą plik raz, zagnieżdżone nawiasy liczy stos, a sklejanie stałych ma limit głębokości (8) i długości (2048 znaków); `${…}` w konfiguracji rozwija się z pamięcią, limitem głębokości (10) i długości (4096), więc cykl ani klucze, które się podwajają, nie zajmują pamięci; YAML ma limit głębokości (64), a linie konfiguracji proxy ponad 2000 znaków są pomijane. Pary nawiasów liczy się raz na plik, niedomknięty nawias nie ciągnie wyrażenia do końca pliku, a z listy argumentów wywołania dłuższej niż 256 tokenów brane są tylko argumenty mieszczące się w limicie w całości (adres i metoda są na początku). YAML jest czytany bez sprawdzania powtórzonych kluczy (biblioteka porównuje każdy z każdym), plik ma najwyżej 20 000 wpisów we wszystkich dokumentach, moduł najwyżej 32 profile (więcej to problem karty), a w każdym profilu rozwija się tylko klucze z adresem albo `${…}`. Błąd albo limit czasu `git grep` jest problemem karty, nie zabiera jej (karta zostaje bez faktów z kodu). Liczba faktów też jest ograniczona (20 endpointów na metodę, 200 wywołań na klienta, 2000 rozkładanych wywołań `.uri(…)` i `RestTemplate` na plik, 500 adresów z konfiguracji na moduł, a ponad ten ostatni limit problem karty). Pliki `.env*` są czytane z całego commita (wybór pliku zna tylko jego ścieżkę), ale na kartę trafiają tylko zmienne z adresem HTTP z plików obok `package.json`, bez użytkownika, hasła i zapytania; reszta wartości zostaje w pamięci daemona na czas liczenia karty. Adresy na karcie tracą użytkownika i hasło (do ostatniego `@` przed ścieżką, a gdy przed pierwszym `/` nie ma hosta z portem, do ostatniego `@` przed zapytaniem, bo hasło może mieć `/`; część przed ścieżką, która nadal nie jest hostem z portem, znika cała), zapytanie, fragment i człony ścieżki wyglądające na token (20+ znaków z literami i cyframi, np. klucz webhooka), a ścieżki wywołań zapytanie, bo adres z `.env` albo `application.yml` bywa z hasłem albo kluczem API, a karta trafia do UI i do agenta. Dopasowanie wywołań do endpointów w grafie porównuje wywołanie tylko z endpointami o tej samej liczbie członów, które mają jego najrzadszy stały człon (albo zmienną) na tej samej pozycji (i z `**`), więc tysiące endpointów w kilkudziesięciu repo liczą się w ułamku sekundy; `cards-limits.test.ts` trzyma te przypadki poniżej 1–2 s.
- Parser tree-sitter (ADR-37) dostaje kod z repo bez zmian: działa w pamięci WASM bez dostępu do plików i sieci, ale synchronicznie w wątku daemona, a gramatyka Kotlina na złośliwym wejściu rośnie w czasie szybciej niż liniowo. Dlatego każde parsowanie ma limit czasu (`PARSE_TIME_LIMIT_MS`, 1 s), po którym jest przerywane, a plik nie ma drzewa, a cała karta łączny budżet 10 s (ADR-38), po którym nie parsuje już nic. Luka: pierwsze liczenie karty takiego repo może zatrzymać API daemona na około 11 s (budżet i czas ostatniego pliku: parsowanie do 1 s i odczyt drzewa; raz na commit, a po restarcie daemona jeszcze raz, bo taka karta nie trafia na dysk); parsowanie w wątku roboczym by to zamknęło.
- Graf połączeń (ADR-29) niczego nie czyta z repo poza kartą: krawędzie z kart niosą te same niezaufane napisy (nazwy paczek, ścieżki; nazwa paczki nie sięga do prototypu obiektu), a wpisy `graph` pochodzą z `workspace.yaml` użytkownika. Żadne narzędzie MCP ich nie zmienia; `who_calls` i `subgraph_for` tylko czytają graf, a `subgraph_for` ma ograniczoną głębokość (3), żeby wynik nie rósł do całego grafu, a `find_endpoint` liczbę wyników (50) i długość zapytania (300 znaków).
- Klon repo sekretów poza workspace, w katalogu niewidocznym dla worktree; w profilu zadania repo sekretów jest wykluczone z narzędzi plikowych agenta (konfiguracja adaptera).
- Zmienne środowiskowe nigdy nie trafiają do logów ani do audytu; maskowanie wartości przed buforem (§4.2). Luka: daemon maskuje tylko wartości zmiennych o nazwach sekretów ze środowiska, z którym sam uruchamia proces. Sekret, który proces dostaje inaczej (z `[env]` konfiguracji mise, z pliku `.env`, z menedżera haseł) albo który ma nazwę spoza listy, trafia do logu w UI, w pliku JSONL w katalogu stanu i do agenta przez narzędzie MCP `tail` jawnym tekstem, tak jak do terminala. Zamknie to moduł `secrets`, który zna wartości, które sam wstrzykuje; odczyt `[env]` z mise (`mise env --json`) to możliwe uzupełnienie. Pliki logów leżą w katalogu stanu z uprawnieniami użytkownika, jak reszta stanu. Znane przypadki brzegowe maskowania: sekret przecięty sekwencją ANSI w wyjściu procesu, linia klucza wieloliniowego krótsza niż 8 znaków (np. ostatnia linia base64 klucza PEM) i linia bez końca dłuższa niż 64 KB złożona w całości z zachodzących na siebie wystąpień sekretów (wtedy podział idzie na końcu).
- Terminal sesji (ADR-26) przyjmuje z UI dowolne klawisze: to jedyny wyjątek od zasady identyfikatorów zamiast komend (§1.2), tak jak terminal w VS Code. Sesję uruchamia daemon z komendy, którą składa sam (program z `PATH` użytkownika i katalog wtyczki), w korzeniu repo z folderu z projektami. WebSockety terminala i zdarzeń mają te same zabezpieczenia co HTTP, z tokenem w podprotokole (`api/sockets.ts`). Copilot CLI dostaje środowisko użytkownika (`userEnv`), tak jak w jego terminalu; ekran sesji nie trafia do logów ani do MCP, tylko do okna użytkownika, więc maskowane (`logs.lastLinesOnly`, §4.2) są tylko ostatnie linie stanu sesji. Hook wtyczki to binarka daemona uruchamiana przez Copilot CLI z katalogu wtyczki (nie repo), która tylko dopisuje rekord do pliku sesji, bez tokenu daemona. Proxy `vite dev` dokłada token także do połączenia terminala bez nagłówka `Origin`, więc w trybie deweloperskim każdy lokalny proces dostaje przez Vite terminal sesji i zdarzenia `/ws`, tak jak dziś `/api`; wydanie tego proxy nie ma. Luka: Copilot CLI uruchomiony z PTY może sam uruchamiać programy poza grupą procesów, jeśli założą własną sesję POSIX (`setsid`) albo wyjdą z joba z `BREAKAWAY_OK`; takie procesy przeżyją stop sesji.
- Stan zadania z hooków i OSC pochodzi od procesu sesji, więc sesja może go sfałszować (dopisać rekord do `hooks.jsonl`, wypisać OSC 9;4). Stan jest tylko informacją dla człowieka i nie daje sesji żadnego uprawnienia; tak ma zostać. Rekord hooka zapisuje tylko pola z listy (bez promptu, argumentów i wyników narzędzi), a payload hooka jest parsowany schematem jak każde wejście z zewnątrz. Wyjątki, o których trzeba pamiętać przy fixture'ach: przycięta treść powiadomienia (może zawierać komendę albo pełną ścieżkę, o które agent prosi) i tytuł okna w `states.jsonl` (opis bieżącej pracy), a nagranie `.cast` ma cały ekran sesji (z klawiatury tylko rodzaj klawisza sesji, bez treści). Stan z klawiszy sesji przychodzi z okna terminala przez `/ws/pty/<sesja>`, ale proces sesji działa jako ten sam użytkownik, może przeczytać token z `daemon.json` i wysłać klawisz tym samym WebSocketem, więc i ten stan może sfałszować, jak hooki i OSC.
- Zadanie (ADR-31) przekazuje polecenie użytkownika z UI do Copilot CLI jednym argumentem `--interactive=<polecenie>`, bez powłoki: polecenie jest treścią, nie komendą, a forma z `=` nie pozwala mu stać się opcją. Gałąź i katalog worktree składa daemon z polecenia tylko ze znaków `[a-z0-9-]`. `git worktree add` wypełnia katalog roboczy jak `git checkout` w terminalu: uruchamia filtry (`smudge`, LFS) i hook `post-checkout` repo; to ta sama zgoda na kod repo co sesja agenta w nim. `tasks.json` leży w katalogu stanu i można go zmienić ręcznie, a zakończenie zadania kasuje worktree z `--force` i gałąź z `branch -D`, więc katalog worktree nie jest w pliku (liczy go daemon w `worktrees/`), a odczyt przyjmuje tylko gałąź `trackwall/[a-z0-9-]` i pełny hash commita bazowego, który trafia do `git diff`. Zmiany zadania liczy `git diff` bez zewnętrznych programów diff i `textconv` z konfiguracji repo; diff katalogu roboczego uruchamia filtr `clean`, jak `git status` (luka z filtrem `clean` wyżej). To samo dotyczy zakładki „Changes” repo z folderu z projektami (ADR-34), także repo, którego użytkownik świadomie nie wybrał.
- Sesje w MCP (ADR-36): każda sesja z serwerem MCP Trackwall widzi przez `list_sessions` i `get_session` wszystkie sesje i zadania, z poleceniami zadań i tytułami okien; to polecenia użytkownika w jego własnym daemonie, a narzędzia tylko czytają. Ekran sesji i ostatnie linie zakończonej grupy (`run.lastLines`) do MCP nie trafiają: ostatnie linie są maskowane tylko wartościami sekretów ze środowiska procesu (§4.2), a agent wypisuje w terminalu także to, co przeczytał z plików (`.env`) albo dostał w poleceniu, więc sekret wypisany w terminalu jednej sesji nie przejdzie do innej. Luka: tytuł okna (`windowTitle`, z OSC 0 / 2) idzie do MCP bez maskowania; Copilot CLI wpisuje tam opis bieżącej pracy, ale proces sesji może tam wypisać dowolny tekst. Token sesji (wyżej) pozwoli później zawęzić to, co sesja widzi; dziś każda widzi wszystko, także propozycje zadań.
- Propozycje zadań i podsumowania (ADR-39) to tekst od agenta, który mógł przeczytać niezaufane treści z repo (README, kod, wyjście tasków), więc niosą tę samą klasę prompt injection co wyniki narzędzi: polecenie z propozycji trafi do innej sesji jako pierwsza wiadomość, a podsumowanie do sesji, która czeka. Bramką jest człowiek: propozycja nic nie uruchamia, UI pokazuje całe polecenie do przeczytania i poprawy przed „Start task”, a zadanie z niej ma te same granice co zadanie z formularza (worktree w katalogu stanu, komenda składana przez daemon, polecenie jako treść `--interactive=`). Zatwierdzanie automatyczne, jeśli kiedyś powstanie, będzie tylko ustawieniem w UI, nigdy narzędziem MCP. UI pokazuje polecenie, tytuł i podsumowanie jako tekst, a narzędzia MCP odrzucają w nich znaki, których człowiek nie zobaczy, a model przeczyta (`visibleText`: znaki formatujące z ukrytymi znacznikami U+E0000–E007F i zmianą kierunku, prywatne, separatory linii; nieprzypisanych nie, bo ich lista zależy od tablic Unicode silnika); kosztem tego emoji złożone przez U+200D z propozycji nie przejdą. Limity (20 czekających propozycji, 80 znaków tytułu, 8000 polecenia, 4000 podsumowania, 55 s czekania w jednym wywołaniu) ograniczają, ile pamięci i czasu daemona zajmie sesja w pętli. Luki: sesja może proponować bez końca po każdej decyzji, a lista nie mówi, ile propozycji ta sesja już zgłosiła. Zatwierdzenie w UI jest bramką dla agenta, który korzysta z narzędzi MCP, a nie granicą bezpieczeństwa: proces sesji działa jako ten sam użytkownik, może przeczytać token z `daemon.json` i sam wywołać `approve-proposal` albo `create-task` przez HTTP API, tak jak może uruchomić dowolny proces bez Trackwall. Zamknie to dopiero osobny token UI, którego procesy sesji nie mogą przeczytać.
- README w UI (ADR-35) jest treścią z repo: HTML przechodzi sanityzację ze schematem GitHuba, diagram Mermaid powstaje w trybie `strict`, obrazy się nie ładują, a link otwiera się poza oknem tylko jako `http` albo `https` w postaci kanonicznej. `workspace/open-link` każe systemowi otworzyć taki adres; kto ma token daemona, może to zrobić bez kliknięcia, tak jak `open-editor`. Luka: daemon nie wysyła nagłówka CSP przy plikach UI, więc w trybie przeglądarki (`--ui`) obrazek z internetu w etykiecie diagramu Mermaid (tryb `strict` przepuszcza `<img>`) się załaduje; w oknie Tauri blokuje go CSP. Okno Tauri nie ma też strażnika nawigacji (`on_navigation`), więc ochrona przed linkiem z README to tylko przechwycenie kliku w UI; menu kontekstowe WebView („otwórz w nowym oknie”) zostaje do sprawdzenia ręcznie.
- Taski mise przez MCP (ADR-41): `run_mise_task` wykonuje kod z konfiguracji mise repo, jak przycisk w UI i jak `mise run` w terminalu agenta. Granice: task tylko z aktualnej listy `mise tasks ls` (mise nie poda jej dla konfiguracji bez zaufania, a zaufać da się tylko w UI), komenda składana przez daemon z nazwy (§1.2), w korzeniu repo przez `procs`, sesja Trackwall tylko w repo, w którym działa, linia w logu daemona z repo, taskiem i sesją przed startem, a `destructiveHint` (także na `stop_mise_task`), żeby klient MCP pytał o zgodę jak przy komendzie powłoki (Copilot CLI pyta o każde narzędzie MCP, dopóki użytkownik nie pozwoli na wszystkie). Wyjście taska wraca do agenta przez `tail` z maskowaniem i luką z sekretami z `[env]` (niżej), a `lastLines` w `run` jest maskowane tak samo. Luki: mise ufa ścieżce konfiguracji, nie treści, więc agent, który może zmienić zaufany `mise.toml` albo plik taska w korzeniu repo (sesja w korzeniu repo, agent nadrzędny), może przez `run_mise_task` wykonać dowolną komendę; to ta sama zgoda, którą klient MCP i tak daje na zapis pliku i na komendę powłoki, ale zgoda na samo narzędzie MCP nie pokazuje treści taska. Zamknie to tryb `paranoid` mise (zaufanie do skrótu treści) albo uruchamianie tylko tasków z commita (karta repo zna je z `RepoCard.mise`). Sesja zadania działa w worktree, a `run_mise_task` w korzeniu repo z folderu z projektami, więc uruchamia kod z gałęzi, na której jest repo, nie z gałęzi zadania. Wywołania trafiają tylko do logu daemona, bo tabeli `audit` nie ma. Ograniczenie sesji do jej repo działa tylko dla wywołań z jej mostu (z tokenem sesji): proces sesji może sam przeczytać token daemona z `daemon.json` i zawołać `/mcp` bez tokenu sesji, jak agent spoza Trackwall, więc to bramka dla agenta, a nie granica bezpieczeństwa (jak zatwierdzanie propozycji, ADR-39).
- Folder picker, Show in Explorer/Finder and drag and drop (ADR-51): `dropped-folder` reads any full path the UI sends (a `stat` and the folder's entries) and answers what it is, which tells a token holder no more than `set-projects-dir` already does; it saves nothing. `open-folder` takes only a repo id, so the system opens a path from the list, never one from the request. A path dropped on a session goes into its terminal as pasted text, the same as the user typing it. The window still gets no plugin commands: the picker is the app's own `pick_folder` command.
- Autostart i „podłącz agenta” tylko z UI; agent nie ma narzędzia do zmiany konfiguracji daemona.
- Serwer MCP (ADR-24) przyjmuje token daemona, a sesje Trackwall dokładają token sesji (ADR-39): agent nadrzędny jest programem użytkownika, a narzędzia czytają, zapisują propozycję i podsumowanie albo uruchamiają i zatrzymują taski mise (ADR-41). Most stdio bierze token z `daemon.json`, więc nie trafia on do konfiguracji Copilot CLI; proces użytkownika i tak może odczytać ten plik, tak jak UI. Propozycja zadania staje się zadaniem dopiero po kliknięciu użytkownika w UI, a procesy uruchamia tylko `run_mise_task` (niżej). Treść z repo w wynikach narzędzi (README, tematy commitów, opisy tasków mise, wyjście tasków w `tail`, linie kodu z `search_code`) jest danymi z zewnątrz także dla agenta: repo może w ten sposób podsunąć agentowi polecenia (prompt injection); Trackwall jej nie filtruje. `search_code` (ADR-40) returns any committed text from every repo in the projects folder, including secrets someone committed (`.env`, keys, passwords in `application.yml`), and to every session with the Trackwall MCP server, not only the one working in that repo; Trackwall does not mask them (the masks from §4.2 cover only values from process environments). The pattern and pathspecs from the agent reach git only as arguments after `-e` and `--`, without a shell; a pathological regular expression keeps git busy for at most 30 s per repo, and the whole search starts no new repo after 60 s, but a running `git grep` is not stopped when the MCP client gives up. `get_repo` pyta mise o listę tasków tak samo jak zakładka w UI, więc w zaufanej konfiguracji mise wykonuje przy tym `[env]` (§4.7); konfiguracji bez zaufania nie czyta, a zaufać da się tylko w UI.
- Binarka daemona nie czyta `.env` ani `bunfig.toml` z bieżącego katalogu (`--no-compile-autoload-dotenv`, `--no-compile-autoload-bunfig` w `scripts/build.ts`), bo most MCP startuje w katalogu agenta, czyli w repo użytkownika; ze źródeł pod Bun to samo dają `--no-env-file` i `--config` z pustym `bunfig.toml` paczki daemona w `mcpStdioCommand`.
- Jeśli kiedyś pojawią się narzędzia bazodanowe, rola bez superużytkownika i transakcja tylko do odczytu.
- Podatności zgłasza się prywatnie według `SECURITY.md` (GitHub Security Advisories).

## 10. Testy i CI

- `procs` i `logs`: testy integracyjne uruchamiające prawdziwe procesy potomne (skrypt, który odpala wnuka i ignoruje łagodny stop), na obu systemach w macierzy CI (każdy PR, ADR-22).
- `cards`: ekstraktory, tagi i mechanizmy testowane na migawkach commita w pamięci (małe `pom.xml`, skrypty Gradle, `package.json`, `mise.toml`) bez gita i sieci; moduł z odczytem commita i pamięcią kart na prawdziwym repo gita w katalogu tymczasowym.
- `agents`: sesje testowane z prawdziwym PTY, grupą procesów, podkomendą `copilot-hook` daemona i interaktywną atrapą Copilot CLI (`test/fixtures/fake-copilot-session.ts`), zadania tak samo na prawdziwym gicie (klon z `origin/HEAD`, `tasks.test.ts`), także przez WebSocket terminala (`pty-socket.test.ts`); detektory stanu testowane na nagraniach `.cast` odtwarzanych przez `replayCopilotRecording`; nagrania z prawdziwych sesji Copilot CLI trafiają do repo jako fixture'y dopiero po anonimizacji. Do tego czasu fixture jest syntetyczny (`test/fixtures/copilot/`, oznaczony w tytule nagrania), a pełną ścieżkę (PTY, wtyczka sesji, procesy hooków, nagranie) sprawdza test z atrapą Copilot CLI.
- `api`/`mcp`: kontrakt z `packages/protocol`, testy przez prawdziwy klient MCP SDK (`@modelcontextprotocol/client`): przez Streamable HTTP w obu rewizjach, przez most w tym samym procesie i przez komendę mostu z `/api/daemon/info` z procesem daemona pod Bun i pod Node; test dymny binarki (`scripts/smoke.ts`) robi `initialize` przez `mcp-stdio`.
- CI (ADR-22): każdy PR i push na `main` przechodzi równolegle lint, `cargo fmt`, typecheck i testy na `ubuntu-latest`, audyt zależności, job `test` (testy) oraz job `desktop` (build daemona jako binarki i Tauri → clippy → `cargo test` → smoke test sidecara → portable → artefakty) na `windows-latest` i `macos-latest`. Zbiorczy job `CI ok` jest zielony tylko wtedy, gdy wszystkie pozostałe są zielone; to on ma być jedynym wymaganym checkiem w ochronie `main`, którą ustawia właściciel repo. Podatność bez poprawionej wersji trafia do `auditConfig` w `pnpm-workspace.yaml` (`pnpm audit --ignore`) z uzasadnieniem, żeby nie blokowała każdego PR. CI idzie także przy zmianach tylko w dokumentacji, bo wymagany check musi raportować przy każdym PR. Nowy push na gałąź PR przerywa jej poprzedni przebieg, a każdy commit `main` ma własny przebieg, którego nic nie przerywa. Ręczne uruchomienie zostaje dla gałęzi bez PR. Wydanie z tagu (`release.yml`): GitHub Release powstaje dopiero po przejściu obu buildów, opis w `docs/release.md`.

## 12. Decyzje (ADR w skrócie)

**ADR-1 Runtime daemona: Bun, z zachowaniem zgodności z Node.** Bun daje `bun build --compile` do jednej binarki i wbudowane SQLite. Kod pisany tak, by działał też pod Node 22 (`node:` API, bez API specyficznych dla Bun poza warstwą `platform/`). Jeśli spike z etapu 1 pokaże, że ConPTY lub Job Objects nie działają pod Bun, przechodzimy na Node 22 + SEA bez zmian w modułach. Uzupełnienie (2026-10-23): zgodności z Node pilnuje narzędzie, bo bez tego się rozjechała (właściwość w parametrze konstruktora w `api/guard.ts` blokowała start pod Node). Daemon i `protocol` mają `erasableSyntaxOnly` i wymagane rozszerzenia w importach, API Bun poza `platform/` odrzuca Biome, a testy procesu daemona idą pod Bun i pod Node z flagami ze skryptu `start:node` (Node 22.12+ uruchamia kod źródłowy bez kompilacji). Wynik spike'ów z etapu 1 (Bun 1.4.2, Windows x64, macOS arm64, Linux, także w binarce z `--compile` przeniesionej poza repo): Job Objects przez `bun:ffi` działają na Windowsie, grupa procesów (`setsid` + `kill(-pgid)`) na macOS; PTY dają `bun-pty` i `Bun.spawn({ terminal })` (na Windowsie ConPTY), a `node-pty` pod Bun nie działa i nie ładuje `.node` w `--compile`. ADR-1 jest więc potwierdzony. Kod spike'ów (`spikes/job-objects`, `spikes/conpty`) usunięto z repo i z CI 2026-10-24, bo odpowiedź jest tutaj, a ich rozwiązania żyją w `platform/` daemona i jego testach na Windowsie i macOS; kod jest w historii gita (ostatnio w `9e1c1bd`). Świadoma luka: spike'i uruchamiały Job Object i PTY także w skompilowanej binarce. Testy daemona robią to ze źródeł, a smoke test binarki (`scripts/smoke.ts`) sprawdza tylko start, `/api/health`, `/api/daemon/info`, MCP i zatrzymanie, więc zmianę wersji Bun, która psuje FFI albo PTY tylko w `--compile`, łapie dopiero ręczny krok przed tagiem w `docs/release.md`. Zamknie ją smoke test, który w binarce uruchamia sesję z atrapą Copilot CLI. Addendum (2026-10-24, PR #46): Bun 1.4.2 on Windows crashed (segfault) or hung `bun test` about 1–2 s after a test file had run four ConPTY sessions, at a random point that did not depend on how the session was stopped (closing the terminal or killing the leader), on garbage collection or on `--isolate`; macOS and Linux were fine. Bun 1.4.4 passes the same tests, so `mise.toml` and both workflows moved to 1.4.4. What would reverse it: the crash coming back on a later Bun, which would mean running the PTY test files in separate `bun test` processes.

**ADR-2 Transport UI: HTTP + WebSocket, nie tylko IPC Tauri.** Dzięki temu ten sam UI działa w przeglądarce (etap 1) i w Tauri, a `ws` CLI i testy używają tego samego API. Tauri IPC zostaje dla spraw natywnych: tray, autostart, token.

**ADR-3 MCP w daemonie, transport Streamable HTTP, stdio jako most.** Jeden proces trzyma stan, więc narzędzia MCP nie potrzebują osobnego kanału. Most stdio dla CLI, które HTTP nie obsługują. Pierwszy wycinek (serwer z SDK, bezstanowy, tylko do odczytu, Copilot CLI przez most): ADR-24.

**ADR-4 Trwałość: SQLite + JSONL, bez zewnętrznej bazy.** Jedna osoba, jedna maszyna; SQLite wystarcza, a JSONL jest czytelny ręcznie i tani w zapisie.

**ADR-5 Dzierżawy zamiast proxy.** Jedna instancja serwisu na porcie i przejęcie przez zadanie rozwiązuje 90% przypadków bez proxy; interfejs `leases` zostawia miejsce na routing po nagłówku.

**ADR-6 Fakty z ekstraktorów, LLM tylko w polu `description` i w propozycjach z `origin: 'llm'`.** Powtarzalność analizy i możliwość testów bez modelu.

**ADR-7 Nic firmowego w repo.** Wszystkie reguły specyficzne dla firmy (wzorce URL, nazwy topików, adapter GitLab z adresem instancji) są konfiguracją workspace, a ekstraktory przyjmują je jako parametry.

**ADR-8 Tylko Copilot CLI.** (2026-10-23) Jeden adapter agenta. Abstrakcja adaptera zostaje jako granica w kodzie, ale nie jest rozwijana pod inne CLI.

**ADR-9 Bez auto-merge i plannera, na stałe.** (2026-10-23) Zadanie kończy się podsumowaniem i propozycją PR; łączenie i rozbijanie celów robi człowiek. W modelu danych nie ma miejsca na zależności między zadaniami ani kolejkę.

**ADR-10 Repo sekretów trzyma manifesty k8s `Secret`.** (2026-10-23) Gałąź `origin/<repo>` zawiera pliki YAML `kind: Secret`; `secrets.resolve` czyta `data` (base64) i `stringData` (jawny tekst) i mapuje klucze na zmienne środowiskowe 1:1. Nazwy kluczy są porównywane z `runtime.secretNames` ze szczegółów repo, stąd `check_secrets`. Docelowe szyfrowanie sops + age nie zmienia formatu, tylko dodaje krok odszyfrowania przed parsowaniem.

**ADR-11 Półprzezroczyste okno z efektem systemowym, nieprzezroczyste tło jako fallback.** (2026-10-23) Okno Tauri jest przezroczyste (`transparent`, motyw `Dark`), a powłoka w `setup` próbuje efektów po kolei przez `window-vibrancy`: na Windows Mica (Windows 11), potem Acrylic (Windows 10 1809+), na macOS vibrancy `UnderWindowBackground`. Po załadowaniu strony powłoka ustawia na `<html>` atrybut `data-window-effect` z nazwą przyjętego efektu i pokazuje okno (startuje z `visible: false`) dopiero po wykonaniu tego skryptu, więc przy starcie nie miga nieprzezroczyste tło; gdyby strona nie zgłosiła końca ładowania, okno pokazuje się po 10 s. Odświeżenie strony (F5) maluje ją nieprzezroczyście do końca ładowania, co zostawiamy jako rzadki przypadek. Atrybut zdejmuje tło strony i robi powierzchnie półprzezroczystymi; bez niego (brak efektu, przeglądarka) UI zostaje nieprzezroczyste, a `prefers-reduced-transparency` przywraca nieprzezroczystość także przy działającym efekcie. `set_effects` z Tauri odpada, bo bierze tylko pierwszy efekt z listy i nie mówi, czy się udał. `macOSPrivateApi` nie jest potrzebne: od Tauri 2.12.1 (dolna granica w `Cargo.toml`) przezroczystość na macOS działa bez tej flagi. Odwróciłoby to zauważalne przycinanie Acrylic przy przeciąganiu okna na Windows 10 (wtedy Windows 10 dostaje nieprzezroczyste tło) albo słaba czytelność na jasnych tapetach (wtedy mniejsza przezroczystość powierzchni).

**ADR-12 Nazwa: Trackwall.** (2026-10-23) Robocza nazwa „Pitwall” była zajęta przez istniejące narzędzia deweloperskie (quanticstudios/pitwall, aenzenith/pitwall-vscode), więc projekt nazywa się Trackwall: paczki `@trackwall/*`, binarki `trackwall` i `trackwall-daemon`, katalog danych `~/.trackwall`, zmienne `TRACKWALL_*`, identyfikator aplikacji `dev.trackwall.desktop`. Nazwa zostaje przy motywie ściany przy torze i w chwili decyzji była wolna na npm (także jako scope), crates.io i PyPI. Stan z wersji 0.1.0 w `~/.pitwall` nie jest przenoszony, bo poza tokenem i logami nic tam nie ma. Odwróciłaby ją kolizja nazwy z narzędziem lub znakiem towarowym znaleziona przed publikacją.

**ADR-13 `workspace.yaml` w katalogu stanu daemona, do czasu wyboru workspace.** (2026-10-23) Lista repo (od ADR-18: folder z projektami) jest w `<katalog stanu>/workspace.yaml` (`~/.trackwall/workspace.yaml`). Dzięki temu pierwsza wersja nie potrzebuje ekranu wyboru workspace, a plik ma już docelowy format i można go przenieść. Odwróci to wybór katalogu workspace w UI (np. prywatne repo z konfiguracją): wtedy daemon dostaje ścieżkę do pliku, a w katalogu stanu zostaje tylko wskazanie na niego. Ręczna lista `repos` w tym pliku zastąpiona przez ADR-18; położenie pliku obowiązuje dalej.

**ADR-14 Przeglądanie repo z commita HEAD, nie z katalogu roboczego.** (2026-10-23) Drzewo plików, README i podgląd czytają obiekty gita (`ls-tree`, `cat-file`). Ścieżka z UI nie dotyka systemu plików, więc nie ma ryzyka wyjścia poza repo, dowiązań symbolicznych, plików zablokowanych przez procesy ani przypadkowego pokazania sekretów z ignorowanych plików (`.env`). Kosztem jest to, że niezacommitowanych zmian w przeglądarce nie widać; pokazuje je liczba zmian w stanie repo, a docelowo diff (Monaco). Odwróci to potrzeba edycji plików w UI albo podglądu katalogu roboczego; wtedy osobna trasa z walidacją ścieżki względem korzenia.

**ADR-15 CI przy PR tylko na Linuksie, Windows i macOS na `main`, ręcznie i przy wydaniu.** (2026-10-23) W prywatnym repo minuta runnera Windows liczy się w limicie GitHub Actions podwójnie, a macOS dziesięciokrotnie, a pełna macierz przy każdym PR i pushu wyczerpała limit. Błąd specyficzny dla systemu w PR bez ręcznego przebiegu wychodzi najpóźniej na `main`, a wydanie (`release.yml`) uruchamia testy na obu systemach przed publikacją. Odwróci to upublicznienie repo (standardowe runnery są wtedy bez limitu) albo własny runner: wtedy macierz Windows + macOS wraca do każdego PR. Zastąpiona przez ADR-22.

**ADR-16 Wygląd UI: jeden ciemny motyw HUD z jednym akcentem, tokeny tylko w `index.css`.** (2026-10-23) UI ma jeden motyw, ciemny, w duchu HUD-a: czarne tło (to samo co `ACRYLIC_TINT`, więc ADR-11 działa bez zmian w powłoce), chłodne szklane powierzchnie z cienkimi liniami i siatką pod treścią, cyjan jako jedyny akcent dla tego, co aktywne, a zielony, bursztynowy i czerwony wyłącznie dla stanu (`success`, `warning`, `destructive`). Wszystkie tokeny są w `packages/ui/src/index.css`: kolory w `:root`, w `@theme` kroje, rozmiar `text-2xs`, rozstrzelenie liter `tracking-hud`, wymiary `--spacing-activity-bar` (`w-activity-bar`) i `--spacing-sidebar`, poświaty `shadow-glow-*`, oraz narzędzia `surface`, `hud-label` (etykiety sekcji i pól, mono wersalikami; nie dla zdań), `hud-grid` i `hud-active-edge`. Komponenty używają tylko tokenów, a test `packages/ui/test/design-tokens.test.ts` odrzuca surowe kolory i dowolne wartości wyglądu w `.tsx`. Pozostałe odstępy to skala Tailwinda. Wspólne klocki: `Surface` (powierzchnia z nagłówkiem i przypisem), `StatusLabel` (kropka stanu z tekstem; ton z `repoStatusTone`), `Loading` i komponenty shadcn/ui w `components/ui`. Fonty są systemowe (Segoe UI Variable i Cascadia Mono na Windowsie, SF na macOS), bo aplikacja działa offline i nie chcemy dokładać plików fontów. Kierunek pochodzi z inspiracji dla grafu i sceny 3D (etap 5), żeby reszta UI do nich pasowała; główny widok ze sceną lub grafem ma mieć układ „scena na całą szerokość, szczegóły wybranego węzła w panelu po prawej”. Odwróciłaby to słaba czytelność na prawdziwym Windowsie z Mica/Acrylic albo potrzeba jasnego motywu; wtedy drugi zestaw kolorów pod klasą i przełącznik.

Doprecyzowanie (2026-10-23): widoki aplikacji przełącza pasek widoków przy lewej krawędzi okna (`ActivityBar`, jak activity bar w VS Code) zamiast zakładek w nagłówku, bo pionowy pasek mieści kolejne widoki (sync, graf, sesje Copilot CLI) bez ściskania nagłówka i zostawia całą wysokość okna treści. Widoki pracy są u góry paska, Daemon i Ustawienia przy dolnej krawędzi; każdy ma ikonę, podpowiedź z nazwą i skrótem oraz skrót Ctrl (⌘ na macOS) + klawisz (cyfry po fizycznym klawiszu, także z klawiatury numerycznej, przecinek po znaku, bo w AZERTY i Dvorak leży gdzie indziej, a na jego klawiszu bywa litera z własnym skrótem; w cyrylicy przecinek wymaga Shift, więc tam ustawienia otwiera tylko ikona): Repo 1, Daemon 9, Ustawienia przecinek, następne widoki pracy kolejne cyfry. Widok pojawia się na pasku dopiero razem z działającą treścią, bez pustych miejsc na zapas. Zakładki (`TabBar`) zostają tylko wewnątrz widoku, np. w widoku Repo. Clarification (2026-10-24, ADR-48): the view shortcuts listen in the capture phase on `window` and stop the event, because xterm.js turned Ctrl + digit into a control character for the session and stopped it, so with the focus in a session terminal the views did not switch.


**ADR-17 Stan Copilot CLI z hooków wtyczki sesji, OSC 9;4 jako zapas, bez parsera ekranu na start.** (2026-10-23) Copilot CLI ma według dokumentacji hooki dla końca tury (`agentStop`), powiadomień (`notification`, w tym prośby o zgodę), błędów i końca sesji, a wtyczka podana przez `--plugin-dir` ładuje je tylko dla jednej sesji, bez zmian w `~/.copilot` i bez plików w repo. Na Copilot CLI 1.0.103 (Linux) sprawdzone: `copilot plugin list` pokazuje taką wtyczkę, a jej hook `sessionEnd` z `exec` + `args` odpalił się już na ekranie zaufania folderu, przed logowaniem; reszty zdarzeń bez zalogowanego konta nie dało się wywołać. Hook to program z `exec` + `args`, bez powłoki, więc ta sama definicja działa na Windowsie i macOS. Pasek postępu OSC 9;4 Copilot CLI wysyła domyślnie, więc daje `Working` także wtedy, gdy hooki nie działają (tylko przy `WT_SESSION`, doprecyzowanie z 2026-10-24 niżej). Parser ekranu (VT w daemonie) odkładamy, bo wymaga zależności i wzorców, których bez nagrań nie da się sprawdzić. Rozważony tryb `copilot --acp` (Agent Client Protocol: JSON-RPC na stdio z dokładnym stanem i prośbami o zgodę) odpada na teraz, bo zastępuje TUI Copilot CLI własnym widokiem rozmowy w UI; wraca, jeśli hooki okażą się zawodne albo UI i tak dostanie własny widok sesji. Inne źródła odrzucone: `copilot -p --output-format json` daje zdarzenia JSONL, ale tylko bez TUI i z `--allow-all-tools`, więc nie ma w nim stanu `Approval` ani rozmowy z człowiekiem; katalog `~/.copilot/session-state/<sesja>/` i logi w `~/.copilot/logs` mają nieudokumentowany, wewnętrzny format, który może zmienić się z każdą wersją. Odwróciłoby to: hooki z `--plugin-dir` niedziałające na Windowsie (wtedy wtyczka w `.github/hooks` worktree wykluczona przez `.git/info/exclude`), hooki działające tylko częściowo, np. bez `notification` (po pierwszym hooku OSC może już tylko zakończyć `Working`, więc wtedy reguła łączenia per zdarzenie albo wzorce ekranu), albo rodzaje `notification` niedające odróżnić zgody od pytania (wtedy wzorce ekranu dla `Approval`). PTY w prototypie daje `Bun.spawn({ terminal })` (ADR-1); gdyby nie działał w ConPTY, wraca `bun-pty` ze spike'a (kod w historii gita, ADR-1). Wynik z macOS (2026-10-24, Copilot CLI 1.0.103 z zalogowanym kontem, `copilot-record.ts` z `-p`): hooki z `--plugin-dir` przychodzą wszystkie (`sessionStart`, `userPromptSubmitted`, `postToolUse`, `agentStop`, `sessionEnd` z `reason: complete`), a prośba o zgodę to `notification` z polem `notification_type: permission_prompt`, tytułem „Permission needed” i ścieżką albo komendą w treści, więc `Approval` przychodzi z rodzaju, nie z treści. Copilot CLI pyta tylko o to, czego nie ma na swojej liście bezpiecznych działań (np. zapis poza katalogiem sesji); `ls` i `date` uruchamia bez pytania. Doprecyzowanie (2026-10-24): sesje z TUI w widoku „Sessions” na macOS dały ten sam `notification_type: permission_prompt` przy prośbie o zgodę na zapis i usunięcie pliku, więc `Approval` z tego rodzaju ma pewność `high` (UI: „asking for approval”); `elicitation_dialog` zostaje `medium`, bo żadne nagranie go jeszcze nie pokazało. Zostaje: Windows, `elicitation_dialog` i rodzaj powiadomienia przy gotowym planie. Doprecyzowanie (2026-10-24, pięć sesji z TUI na macOS, `copilot-record.ts` w PTY 120×30): po odpowiedzi na prośbę o zgodę Copilot CLI nie wysyła żadnego hooka. Po zgodzie pierwszy jest `postToolUse` po końcu komendy (przy testach wiele sekund), po „No, and tell Copilot…” z tekstem `postToolUse` następnego narzędzia, a po Esc, który przerywa całą turę („Operation cancelled by user”), nic aż do `sessionEnd`; stan wisiał więc w `Approval` i sesja „prosiła o zgodę” w trakcie pracy albo po przerwaniu. Stąd detektor klawiszy (§4.4): Enter w `Approval` albo `Plan` → `Working`, Esc i Ctrl+C → `Input`. OSC 9;4 Copilot CLI wysyła tylko przy `WT_SESSION` (bez niego, także z `TERM=xterm-256color` i `COLORTERM=truecolor` jak w daemonie, ani razu): stan 3 od początku tury, potem co 5 s, także przez całą prośbę o zgodę, i stan 0 ok. 20 ms przed `agentStop`; zapas z OSC działa więc tylko w Windows Terminal i nie odróżnia `Approval` od `Working`. Ustawienie `WT_SESSION` w środowisku sesji, żeby dostać pasek także poza Windows Terminal, odłożone: Copilot CLI mógłby zmienić też inne zachowania pod Windows Terminal. Tytuł okna (OSC 0) nie zmienia się przy prośbie o zgodę, odmowie ani końcu tury. Kolejne sesje (2026-10-24): Ctrl+C działa jak Esc, jednym naciśnięciem, przy prośbie o zgodę i w trakcie pracy, bez hooka i bez pytania o drugie Ctrl+C; po przerwaniu ekran pokazuje „Operation aborted by user” przy narzędziu i „Operation cancelled by user” na końcu, oba ciągłym tekstem, więc drugi z nich jest wzorcem ekranu (§4.4). Ta sama odmowa na Windowsie (wątek testów) dała „Operation cancelled by user” bez żadnego hooka, a stan trzymał `Approval` ponad minutę. Sesje z poprawką (klawisze i odtwarzanie) dały na żywo i z nagrania te same zmiany. Zostaje dalej: Windows z poprawką, `elicitation_dialog`, rodzaj powiadomienia przy gotowym planie oraz wybór opcji cyfrą (czy Copilot CLI go przyjmuje). Doprecyzowanie (2026-10-24, Windows po PR #38): w oknie „Allow path access” cyfra opcji „No” działa od razu, bez Entera, i kończy turę komunikatem „Operation cancelled by user” bez hooka, więc cyfra 1–9 w `Approval` albo `Plan` jest odpowiedzią (`choice`), jak Enter.

**ADR-18 Lista repo to repo gita w folderze z projektami, nie ręczna lista.** (2026-10-23) `workspace.yaml` wskazuje jeden folder (`projectsDir`), a lista repo to jego bezpośrednie podkatalogi z `.git`, odczytywane przy każdym zapytaniu. Tak użytkownik i tak trzyma repo (jeden folder z klonami), więc konfiguracja to jedna ścieżka zamiast listy, a repo sklonowane z terminala albo usunięte z dysku nie rozjeżdża się z Trackwallem. Ten sam model obsłuży dodawanie repo przez wybór z listy dostępnych w GitHub albo GitLab: klon trafia do folderu i od razu jest na liście, bez osobnego zapisu (zrobione: ADR-19). Ręczne dodawanie ścieżką i usuwanie z listy znikają; identyfikator repo zależy teraz od nazwy katalogu, więc zmiana nazwy katalogu zmienia identyfikator, a nowy katalog o kolidującej nazwie, który sortuje się wcześniej, może przejąć identyfikator istniejącego repo (dziś nic go nie zapisuje; tabela `tasks` z §6 będzie musiała zapisywać też ścieżkę; karty są kluczowane hashem commita, więc ich to nie dotyczy, ADR-25). Skan tylko na jeden poziom, bo zagnieżdżone repo (submoduły, przykłady w repo) dawałyby fałszywe wpisy, a skan całego drzewa jest drogi przy `node_modules`. Odwróciłyby to: potrzeba repo spoza folderu (wtedy dodatkowa lista `extraRepos` obok `projectsDir`), układ folderu z grupami jak w GitLab (`<grupa>/<repo>`, wtedy głębokość skanu w konfiguracji) albo kilka folderów naraz (`projectsDir` jako lista).

**ADR-19 Repo do folderu z projektami z wyszukiwarki GitLab i GitHub przez `glab` i `gh`.** (2026-10-23) Repo dodaje się, wyszukując je w hostingu z `workspace.yaml` (`repoHosts`) i klikając „Clone”; klon trafia do folderu z projektami, więc lista repo łapie go sama (ADR-18). Daemon pyta hosting i klonuje przez zalogowane w systemie `glab` (GitLab) i `gh` (GitHub), a nie przez własnego klienta HTTP: logowanie (także SSO i instancje firmowe), token w pęku kluczy systemu, proxy i wybór protokołu klonu (SSH albo HTTPS) są już ustawione w tych programach, a Trackwall nie dotyka tokenu, więc nie musi go chronić ani maskować. Kosztem są dwa programy do zainstalowania i zalogowania oraz zależność od ich wyjścia, ograniczona do `api` (JSON z REST API, stabilny) i `repo clone`. GitLab jest główny: instancja firmowa ma tysiące projektów, więc szuka GitLab (jedna strona wyników), a GitHub, gdzie lista repo użytkownika jest mała i nie ma wyszukiwania, daemon filtruje sam. Klon biegnie w tle, a jego stan żyje tylko w pamięci daemona, bo po zakończeniu prawdą jest katalog w folderze. Odwróciłyby to: brak `glab` na maszynie użytkownika bez możliwości instalacji (wtedy klient HTTP w `vcs` z tokenem jako sekretem, §4 `secrets`), potrzeba klonu z innego hostingu (Bitbucket, Gitea: kolejny program albo klient HTTP) albo grupy GitLab jako podkatalogi folderu (wtedy razem ze zmianą głębokości skanu z ADR-18).

**ADR-20 Grupa procesów: Job Object pod Bun na Windowsie, sesja POSIX na macOS, bez Effect i bez natywnego addonu.** (2026-10-23) Moduł `procs` uruchamia każdy task mise jako grupę: na Windowsie Job Object z `KILL_ON_JOB_CLOSE` przez `bun:ffi` (spike z etapu 1, ADR-1), na macOS i Linuksie `setsid` i sygnały do `-pgid`; stan `exited` i sukces stopu dopiero po potwierdzeniu w systemie, że grupa jest pusta. Kod systemowy siedzi w `platform/` za interfejsem `GroupPlatform`, więc moduł nie zależy od Bun. Pod Node na Windowsie nie ma FFI: grupą jest drzewo z `taskkill /T /F`, bez sprzątania sierot; Node to tryb zgodności (ADR-1), a wydanie jest binarką Bun. Łagodny stop na Windowsie to zamknięcie stdin, bo Ctrl+C wymaga wspólnej konsoli. Sieroty na macOS sprząta następny start daemona według `runtime.json` z czasem startu lidera z `ps`. Effect (anulowanie, zasoby, limity czasu jako biblioteka) rozważony i odłożony: przebieg stopu to kilka kroków z limitami czasu, które czyta się wprost, a Effect zmieniłby styl całego daemona, więc to osobna decyzja. Interfejs `ProcessGroups` (obietnice) da się później owinąć bez zmian w `platform/`. Odwróciłyby to: lider uciekający z joba przed przypisaniem (wtedy start wstrzymany przez `CreateProcessW` z `CREATE_SUSPENDED` w FFI), serwery na Windowsie, które wymagają Ctrl+C do czystego zamknięcia (wtedy osobna konsola i `GenerateConsoleCtrlEvent`), albo wydanie pod Node (wtedy Job Object przez natywny addon).

**ADR-21 Synchronizacja to fetch i fast-forward gałęzi domyślnej, nic więcej; adres remote jako identyfikator repo.** (2026-10-23) „Sync all” pobiera zmiany każdego repo z folderu z projektami i przesuwa lokalną gałąź domyślną do zdalnej tylko wtedy, gdy to czysty fast-forward i nie ruszy niezacommitowanych zmian; każdy inny przypadek zostawia repo nietknięte z powodem. Użytkownik zwykle pracuje na gałęziach funkcji, więc niewybrana gałąź domyślna przesuwa się bez dotykania katalogu roboczego (`git fetch . <zdalna>:<lokalna>`, który sam odmawia dla gałęzi w użyciu, także w trakcie rebase i bisect), a wybrana przez `merge --ff-only`; scalanie, rebase i `git pull` z konfiguracją użytkownika (`pull.rebase`) odpadają, bo w tle nikt nie rozwiąże konfliktu. Gałąź domyślna pochodzi z `refs/remotes/<remote>/HEAD`, bo nazwa (`main`, `master`, `develop`) różni się między repo. Rozważone narzędzia do wielu repo (`meta`, `mu-repo`, `gita`, `myrepos`) odpadają: wymagają własnego pliku z listą repo, której źródłem jest już folder z projektami (ADR-18), i uruchamiają dowolne komendy przez powłokę, a daemon składa komendy sam (§1.2). Fetch dostaje środowisko bez pytań o hasło i klucz hosta, bo daemon nie ma terminala; program ssh ustawiony przez użytkownika ma pierwszeństwo przed trybem wsadowym. Synchronizacja biegnie w tle, 4 repo naraz (firmowy GitLab i VPN potrafią ograniczać równoczesne połączenia SSH), a stan żyje tylko w pamięci, jak klonowania (ADR-19). Adres głównego remote (`host/ścieżka`, bez protokołu i użytkownika) trafia do każdego repo na liście jako identyfikator niezależny od nazwy katalogu (ADR-18), pod który podepną się karty, graf i MCP; liczony jest przy każdym zapytaniu, bo nic jeszcze nie jest zapisywane. Odwróciłyby to: potrzeba aktualizacji także gałęzi funkcji (wtedy fast-forward każdej gałęzi do jej gałęzi śledzonej, z tymi samymi regułami), repo z kilkoma remote bez `origin` u użytkownika (wtedy wybór remote w `workspace.yaml`) albo zbyt wolna lista przy setkach repo na Windowsie (wtedy adres zapisywany w tabeli `repos` i odświeżany przy synchronizacji).

**ADR-22 Pełne CI na każdym PR: Windows i macOS równolegle z Linuksem, jeden wymagany check `CI ok`.** (2026-10-23) Repo jest publiczne, więc standardowe runnery GitHub Actions nie mają limitu minut i warunek odwrócenia ADR-15 się spełnił. Każdy PR uruchamia testy i build na `windows-latest` i `macos-latest`, bez ręcznego `workflow_dispatch`; to na Windowsie wychodzi najwięcej błędów, których Linux nie widzi. Testy i build są osobnymi jobami bez czekania na Linuksa, więc przebieg trwa tyle, co najdłuższy job (build na Windowsie), a nie sumę. Ochrona `main` (ustawienie repo, robi ją człowiek) wymaga jednego checka `CI ok`, który zbiera wyniki pozostałych jobów: zmiana macierzy albo nazwy joba nie wymaga zmiany ustawień repo, a pominięty lub przerwany job daje czerwony wynik (pominięty wymagany check GitHub liczy jako zaliczony). Z tego samego powodu CI nie ma `paths-ignore`: PR tylko z dokumentacją też musi dostać werdykt, a `docs/release-notes` sprawdza test. Każdy commit `main` ma własną grupę współbieżności, bo wspólna grupa kasuje czekający przebieg, gdy przyjdzie następny, i wtedy nie wiadomo, który commit zepsuł `main`. Audyt zależności jest częścią `CI ok`: nowa podatność wysokiej wagi blokuje każdy PR, dopóki ktoś nie podbije zależności albo, gdy poprawionej wersji nie ma, nie wpisze jej z uzasadnieniem do `auditConfig` w `pnpm-workspace.yaml`; wolimy to niż ciche wydanie z podatnością. Odwróciłby to powrót do repo prywatnego, audyt blokujący PR-y częściej, niż łapie podatność wprowadzoną przez PR (wtedy audyt poza `CI ok` i osobno przed wydaniem), albo kolejka runnerów macOS tak długa, że czekanie na nią spowalnia PR bardziej, niż kosztuje błąd znaleziony dopiero na `main`.

**ADR-23 Ikona „Węzeł” z jednego SVG; tray na macOS jako szablon, poza macOS kolorowa ikona aplikacji.** (2026-10-23) Ikona aplikacji to cyjanowy pierścień (Trackwall) połączony z czterema węzłami (repo i agenci), z których jeden świeci jako aktywny, na ciemnym kaflu w motywie UI (ADR-16). Wybrana z pięciu propozycji, bo wprost pokazuje graf połączeń i Trackwall jako jego centrum, a sylwetka zostaje czytelna w 16 px. Źródłem są `apps/desktop/assets/icon.svg` i `tray-icon.svg`, a `apps/desktop/scripts/icons.ts` generuje z nich pliki z `bundle.icon`, favicon UI i szablon traya; wygenerowane pliki są w repo, żeby build nie zależał od renderowania SVG. Kafel w SVG ma margines siatki ikon macOS, a `.ico`, `32x32.png` i favicon powstają z kadru bez tego marginesu, bo ikony Windowsa wypełniają prawie całe pole. Tray na macOS dostaje jednobarwny szablon (`icon_as_template`), który system przebarwia do jasnego i ciemnego paska menu; na Windowsie i Linuksie zostaje kolorowa ikona aplikacji, bo zasobnik bywa jasny albo ciemny, a czarny lub biały znak zniknąłby na jednym z nich. Odwróciłaby to nieczytelna kolorowa ikona w zasobniku Windows (wtedy osobne znaki traya dla jasnego i ciemnego motywu, przełączane po motywie systemu) albo stan zadań pokazywany na ikonie traya (wtedy warianty ikony ze znacznikiem stanu z tego samego SVG).

**ADR-24 MCP dla agenta nadrzędnego: serwer z SDK w daemonie, bezstanowy, tylko do odczytu, Copilot CLI przez most stdio.** (2026-10-23) Daemon wystawia `/mcp` przez `createMcpHandler` z `@modelcontextprotocol/server` 2.x (zależności: tylko `zod` i `@modelcontextprotocol/core`), z narzędziami `list_repos` i `get_repo` mapowanymi na fasadę. SDK zamiast własnego JSON-RPC, bo protokół zmienia się co kilka miesięcy (rewizja 2026-07-28 dodała sondę `server/discover`, nagłówki z polami treści i nową kopertę), a SDK obsługuje i ją, i klienty z `initialize`; wersja 1.x (`@modelcontextprotocol/sdk`) odpadła, bo wciąga Express, Hono i klienta OAuth do binarki daemona, a adapter `@modelcontextprotocol/node` z tego samego powodu (Hono), więc `IncomingMessage` zamienia się na `Request` w kilkunastu liniach w `endpoint.ts`. Serwer jest bezstanowy, bo narzędzia tylko czytają fasadę; sesje i powiadomienia przyjdą, gdy będzie co ogłaszać (np. `graph.updated`). Copilot CLI podłącza się przez most stdio (`copilot mcp add trackwall -- <trackwall-daemon> mcp-stdio`), a nie wpisem HTTP z nagłówkiem, bo token i port daemona zmieniają się przy każdym starcie, a most czyta je z `daemon.json` przy każdej wiadomości i nie zostawia tokenu w `~/.copilot/mcp-config.json`. Most mówi tylko protokołem z `initialize`; sondę 2026-07-28 odrzuca, bo przez stdio nie ma nagłówków, które ta rewizja wymaga w HTTP. Konfigurację Copilot CLI zapisuje jego własna komenda `copilot mcp add` uruchomiona przez użytkownika, a UI tylko ją pokazuje: daemon nie dotyka plików w `~/.copilot`, a format zostaje sprawą Copilot CLI. Token daemona wystarcza, dopóki narzędzia tylko czytają (§8). Sprawdzone z Copilot CLI 1.0.103 na Linuksie bez logowania: Copilot uruchamia most przy starcie, sonda `server/discover` dostaje `-32601`, `initialize` (rewizja 2025-11-25) i `tools/list` przechodzą; wywołania narzędzia bez zalogowanego konta nie da się wywołać. Odwróciłyby to: pierwsze narzędzie, które zmienia stan albo uruchamia procesy (wtedy token zadania i audyt w SQLite przed nim), potrzeba powiadomień serwera (wtedy sesje Streamable HTTP i strumień GET, a w moście kanał od daemona), Copilot CLI wymagający rewizji 2026-07-28 bez przejścia na `initialize` (wtedy most przepisuje pola treści do nagłówków HTTP) albo SDK 2.x zmieniający API co wydanie (wtedy własny serwer JSON-RPC dla rewizji z `initialize`). Zmieniona przez ADR-39 (2026-10-24): serwer nie jest już tylko do odczytu, bo `propose_task` zapisuje propozycję zadania, a `report_result` podsumowanie zadania, choć żadne narzędzie dalej niczego nie uruchamia; sesje Trackwall dokładają do tokenu daemona token sesji, a wywołanie trafia do logu z sesją, która woła. Tabela `audit` w SQLite wciąż nie powstała: ADR-39 uzasadnia, dlaczego nie jest warunkiem tych dwóch narzędzi. Zmieniona przez ADR-41 (2026-10-24): narzędzia `run_mise_task` i `stop_mise_task` uruchamiają i zatrzymują taski mise.

**ADR-25 Karta repo deterministycznie z plików commita HEAD, z pamięcią po hashu commita; tagi repo z karty i z reguł workspace.** (2026-10-23) Moduł `cards` czyta pliki buildu i konfiguracji narzędzi z obiektów gita commita HEAD (`ls-tree` i `cat-file --batch`, bez checkoutu i bez filtrów), wyciąga z nich paczki udostępniane i używane (Maven, Gradle, npm), wymagane narzędzia i spis mechanizmów, każdy fakt z plikiem i linią, a kartę zapamiętuje po hashu commita w pamięci i w `cards/<commit>.json`. Z karty, identyfikatora i adresu repo zdalnego liczy tagi repo z powodami, a reguły `repoTags` w `workspace.yaml` dodają tagi z nazw (np. zespołu), których nie widać w plikach. Uzasadnienie: commit zamiast katalogu roboczego, bo karta ma opisywać to, co jest w repo, a nie niezapisane zmiany na gałęzi funkcji, i bo tylko wtedy hash commita jest kluczem pamięci: setki repo przelicza się raz, a restart daemona nie czyta ich od nowa. Bez wykonywania buildu (Maven, Gradle, `mise ls --json`): to uruchamiałoby kod z repo (skrypty Gradle, wtyczki, konfigurację mise wymagającą zaufania, ADR-20), wymagało zainstalowanych narzędzi i sieci, trwało sekundy na repo i czytało katalog roboczy oraz konfigurację globalną zamiast commita. Ceną jest to, że Gradle czytany jest z typowych postaci linii, a zależność złożona w kodzie nie trafia na kartę; pewne krawędzie grafu (wspólne paczki) i tak dają typowe zapisy. Własny parser XML (ok. 140 linii, z numerami linii, bez DTD i encji zewnętrznych, więc bez XXE) zamiast zależności, bo dowód wymaga linii, a pom nie potrzebuje przestrzeni nazw ani atrybutów; TOML przez `smol-toml` (bez zależności, czysty JS, działa w `bun build --compile`), bo katalog wersji Gradle i mise to pełny TOML, a YAML przez istniejącą zależność `yaml`. Tagi są ortogonalne i krótkie (`java`, `bff`, `frontend`, `monorepo`…), zamiast złożonych jak `#java-bff`, bo filtr łączy je sam (wybrane tagi to AND), a jeden tag na kombinację mnożyłby reguły. Tagi bez LLM i bez stanu: liczone przy każdym pytaniu z karty z pamięci, więc zmiana reguł działa od razu. Karta daje paczki udostępniane i używane w jednej przestrzeni nazw, ale złączenie ich w krawędzie (kto używa czego) jest osobnym krokiem: moduł `graph` i narzędzia MCP nad nim, kolejne zadanie. Odwróciłoby to: potrzeba faktów, których nie da się wyczytać z plików bez wykonania buildu w wielu repo użytkownika (wtedy opcjonalny krok z buildem w worktree, oznaczony innym źródłem), albo karta liczona tak wolno, że trzeba ją trzymać w SQLite razem z grafem (§6).

**ADR-26 Sesje Copilot CLI w PTY daemona, terminal w UI przez WebSocket z obrazem ekranu, hooki przez plik sesji.** (2026-10-23) Widok „Sessions” uruchamia Copilot CLI w repo z folderu z projektami w PTY należącym do daemona (`Bun.spawn({ terminal })`, ConPTY na Windowsie), jako grupę procesów modułu `procs`, kilka sesji naraz; sesja działa przy zamkniętym oknie i kończy się razem z daemonem. Okno terminala to xterm.js podłączony WebSocketem `/ws/pty/<sesja>`. Daemon trzyma ekran każdej sesji w emulatorze bez okna (`@xterm/headless`) i przy podłączeniu wysyła jego obraz (`@xterm/addon-serialize`), bo TUI Copilot CLI pracuje na alternatywnym ekranie, a odtwarzanie całego wyjścia od startu rośnie z czasem sesji; obie paczki to czysty JavaScript, który działa w `bun build --compile` i pod Node. Token idzie w podprotokole WebSocketu (przeglądarka nie ustawi nagłówka), nie w adresie. Hook wtyczki sesji (ADR-17) to sam daemon z podkomendą `copilot-hook`, który dopisuje rekord do `hooks.jsonl` sesji, a daemon czyta plik co 200 ms: żądanie HTTP do daemona wymagałoby podania hookowi tokenu w `hooks.json`, a plik w katalogu stanu nie wymaga niczego. „Czeka na Ciebie” to `Input`, `Approval` i `Plan` działającej sesji, liczone w daemonie (`needsAttention`); UI pokazuje liczbę takich sesji na pasku widoków i przełącza na następną, a powłoka Tauri sama odpytuje daemon (WebView schowanego okna może mieć wstrzymane timery) i, gdy sesja przechodzi z pracy w czekanie, miga oknem na pasku zadań (podskok w Docku) i dodaje sesję do menu traya. (Note 2026-10-24: `Input` waits only until the user has seen it; superseded in this part by ADR-47.) Powiadomienia systemowe (toast) odpadły na start: na Windowsie wymagają zarejestrowanego AppUserModelID, którego aplikacja portable nie ma. Rozważone i odrzucone: `node-pty` (nie działa pod Bun, ADR-1), PTY po stronie Rust (`portable-pty`, plan C z §9; dokłada most między powłoką a daemonem, a sesje mają działać bez okna) i tryb `--acp` (ADR-17). Każda sesja dostaje serwer MCP Trackwall (ADR-24) przez `--additional-mcp-config` z plikiem w katalogu sesji, na tym samym moście stdio co agent nadrzędny. Pod Node sesji nie ma (`agent_unavailable`), bo Node nie ma PTY bez natywnego addonu, a Node to tryb zgodności (ADR-1). Daemon sesji nie nagrywa (robi to `copilot-record.ts`), a sesje nie przeżywają restartu daemona. Odwróciłyby to: `Bun.spawn({ terminal })` niedziałające w ConPTY na prawdziwym Windowsie (wtedy `bun-pty` ze spike'a za tym samym `TerminalPlatform`; kod w historii gita, ADR-1), obraz ekranu z `@xterm/headless` rozjeżdżający się z ekranem TUI (wtedy odtworzenie wyjścia od ostatniego przełączenia ekranu), potrzeba wznowienia sesji po restarcie daemona (wtedy `copilot --resume` z identyfikatorem sesji z hooka `sessionStart`) albo wydanie pod Node (wtedy PTY z natywnego addonu).

**ADR-27 Komenda zbiorcza jako moduł daemona nad `workspace` i `mise`, jeden `mise run` na repo, bez trybu monorepo mise.** (2026-10-23) Komenda zbiorcza (§4.8) to stała lista kroków (synchronizacja, `mise install`, task `setup`, task `build`) na wybranych repo, najwyżej 3 repo naraz, w repo po kolei, z wynikiem każdego kroku w każdym repo i przerwaniem. Każdy krok mise to osobny `mise run <task>` albo `mise install` w korzeniu repo, w grupie procesów `procs` pod tym samym właścicielem co ze szczegółów repo, więc stan, stop i sprzątanie po awarii są te same co dla taska uruchomionego ręcznie, a cache i zależności między taskami zostają w mise (`sources`, `outputs`, `depends`). Sprawdzony i odrzucony silnik: tryb monorepo mise (mise 2026.10.18, `monorepo_root = true` w `mise.toml` folderu z projektami, `mise run '//...:build'`). Taski wszystkich repo idą wtedy jednym procesem z wyjściem poprzedzonym `[//repo:task]`, więc wynik per repo trzeba by wyczytywać z tekstu, a zatrzymać da się tylko całość; pierwszy błąd przerywa pozostałe repo (bez `-c`); folder z projektami potrzebuje pliku konfiguracji z `monorepo_root` i jawną listą `[monorepo].config_roots` (automatyczne wykrywanie jest przestarzałe), który Trackwall musiałby pisać i utrzymywać, a mise ufać; repo bez `mise.toml` i synchronizacja gita są poza nim, a tryb jest eksperymentalny. Sprawdzone na folderze z trzema repo: `mise run '//...:build'` z buildem jednego repo kończącym się kodem 3 przerwał trwający build drugiego, a mise ostrzega, że `experimental_monorepo_root` i automatyczne wykrywanie są przestarzałe. Osobne kroki `setup` i `build` zamiast samego `build` z `depends` są świadome: wynik zależności jest widoczny osobno, kosztem drugiego przebiegu `setup` bez `sources` i `outputs`, gdy `build` od niego zależy. Odwróciłby to tryb monorepo ze stabilnym, maszynowym wynikiem per task (np. JSON) i bez wymogu pliku w folderze z projektami albo potrzeba grafu zależności między repo (build biblioteki przed jej konsumentami), którego dziś nie ma: wtedy kolejność da graf z kart, a silnikiem może zostać mise.

**ADR-28 Logi tasków mise: bufor w pamięci i JSONL w module `logs`, lekka lista w UI zamiast xterm.js, odpytywanie od kursora do czasu WebSocketu.** (2026-10-23) Wyjście każdej grupy procesów z wyjściem przez potoki idzie z `procs` do modułu `logs`, który robi z niego rekordy z globalnym `seq`, maskuje sekrety i usuwa ANSI przed zapisem do bufora (2000 rekordów na źródło) i pliku JSONL rotowanego po 10 MB (§4.2). W jednym miejscu powstają też ostatnie linie stanu `exited`, więc i one są zamaskowane; dlatego `procs` zależy od `logs` (tabela §4). UI pokazuje log jako listę linii z kolorem z poziomu rekordu, a nie terminal xterm.js: rekord jest już tekstem bez ANSI (ten sam dla UI, pliku i narzędzia MCP `tail`, więc da się go maskować, filtrować i szukać), lista ma zwykłe zaznaczanie i zawijanie, a xterm.js dodałby kilkaset KB do UI i własny bufor ekranu bez korzyści dla wyjścia bez interakcji. Kolory ANSI, które narzędzia wypisują same, przepadają; poziom z treści linii (`ERROR`, `WARN`) wyróżnia to, co ważne. Na żywo znaczy odpytywanie `logs/tail` od kursora co sekundę, póki log jest otwarty: odczyt z pamięci jest tani, a WebSocket `/ws` jeszcze nie istnieje. Numer `seq` startuje od chwili startu daemona (ms × 1000), żeby kursor z poprzedniego działania dało się rozpoznać bez osobnego identyfikatora działania w każdym kursorze. Narzędzie MCP `tail` to cienkie mapowanie na `logs.tail` z `repo` i `miseTask` zamiast `source`, żeby agent podawał to, co zna z `get_repo`. Grupy z liderem w PTY (sesje zadań, ADR-26) logu nie mają, bo ekran TUI to nie linie; ich ostatnie linie stanu przechodzą przez to samo maskowanie (`logs.lastLinesOnly`). Odwróciłoby to: potrzeba interaktywnego wyjścia (to PTY, ADR-17) albo kolorów ANSI w logu (wtedy `raw` z sekwencjami obok `msg`), a odpytywanie zastąpi WebSocket `log.append` bez zmiany rekordu.

Dopisek (2026-10-24, ADR-36): WebSocket `/ws` już istnieje, ale logi nie są jego tematem: ich migawka to cały bufor źródła, więc przyjdą jako `log.append` z rekordami od kursora, a do tego czasu UI odpytuje `logs/tail` jak wyżej.

**ADR-29 Graf połączeń między repo liczony przy każdym pytaniu z kart i wpisów `graph` w `workspace.yaml`, rysowany w UI bez biblioteki grafów.** (2026-10-23) Moduł `graph` złącza paczki używane i budowane z kart wszystkich repo (ADR-25) w krawędzie od repo, które używa, do repo używanego, z dowodami z obu stron, i dokłada aliasy paczek oraz ręczne krawędzie z klucza `graph` w `workspace.yaml`; narzędzia MCP `who_calls` i `subgraph_for` oraz widok „Overview” czytają ten sam graf. Uzasadnienie: wspólna paczka to najpewniejsze połączenie, jakie da się wyczytać z plików bez wiedzy o infrastrukturze firmy (discovery, Config Server, Feign czy WebClient), więc graf zaczyna od niej, a połączenia, których pliki nie pokazują, dopisuje użytkownik w pliku, który i tak trzyma lokalnie (ADR-7) i który agent może przeczytać, ale nie zmienić (§8). Węzłem jest repo, bo serwisów (kilka na repo) jeszcze nie ma. Bez stanu i bez SQLite: karty są w pamięci po commicie, a złączenie kilkudziesięciu kart trwa milisekundy, więc graf liczony przy każdym pytaniu nie rozjeżdża się z kartami, nowym repo ani ręczną zmianą `workspace.yaml` i nie potrzebuje zdarzenia `graph.updated`. Alias działa tylko dla paczki, której nie buduje żadne repo z listy, bo fakt z plików buildu ma pierwszeństwo przed wpisem, który mógł się zestarzeć; repo w wpisach wskazuje identyfikator albo adres repo zdalnego, bo identyfikator zmienia się z nazwą katalogu (ADR-18). Zły klucz `graph` albo `repoTags` nie zabiera krawędzi z kart, tylko trafia do `configProblems`, tak jak zły `repoTags` nie zabiera listy repo w `list_repos`. Układ w UI to kolumny z najdłuższej ścieżki (te same warstwy co w scenie 3D, §5.5) i barycentrum w kilkudziesięciu liniach (`lib/graph-layout.ts`), zamiast biblioteki (React Flow, Cytoscape, ELK), bo dla kilkudziesięciu repo daje czytelny rysunek od frontendów do bibliotek, bez zależności w bundlu WebView i z wyglądem z tokenów HUD (ADR-16); trójwymiarowa scena to osobna paczka (Pawn). Odwróciłoby to: graf z setkami repo i tysiącami krawędzi (wtedy przybliżanie, filtr po tagach i może biblioteka z układem warstwowym), krawędzie, których liczenie przestaje być tanie (HTTP z `application*.yml` i kodu, wtedy pamięć grafu po zestawie commitów i zdarzenie `graph.updated`), albo serwisy jako węzły (wtedy węzeł `ServiceId` i repo jako grupa). Doprecyzowanie (ADR-30): krawędzie HTTP z kodu przestały być tanie w liczeniu przy każdym pytaniu, więc moduł trzyma ostatni graf z kluczem wejścia (zestaw commitów i konfiguracja); zdarzenie `graph.updated` wciąż nie jest potrzebne, bo klucz zmienia się razem z commitami.

**ADR-30 Krawędzie HTTP z kodu Spring i konfiguracji z profilami, czytane deterministycznie z commita, z pewnością zależną od tego, co łączy klienta z celem.** (2026-10-23) Karta repo dostaje aplikacje (`spring.application.name`, port), endpointy z kontrolerów (`@RestController`, `@*Mapping`, także z interfejsów API first) i klientów HTTP (Feign, `@HttpExchange`, `WebClient`, `RestClient`, `RestTemplate`, adresy z `application*.yml` i `.properties` w każdym profilu z rozwinięciem `${…}`, adresy z `.env` i proxy frontendu), każdy fakt z plikiem i linią; graf łączy klienta z repo po nazwie aplikacji, aliasie z `workspace.yaml`, hoście, porcie na `localhost` albo po ścieżkach wywołań pasujących do endpointów, a narzędzie MCP `find_endpoint` podaje endpoint z repo, które go wołają. Uzasadnienie: użytkownik nie wie, czego używa jego firma (discovery, Kubernetes, Feign czy WebClient), więc ekstraktor rozpoznaje wszystkie typowe zapisy i każdy daje fakt z dowodem, a o tym, czy połączenie jest pewne, mówi `confidence` krawędzi, nie zgadywanie: nazwa aplikacji, pod którą każde wywołanie ma endpoint, to `exact`, sama ścieżka pasująca do kilku repo to `low`. Profile są osobnymi klientami, bo adres lokalny (`localhost:8081`) i produkcyjny (`orders-api.svc`) wskazują to samo repo różnymi drogami, a agent pytający „kto woła” potrzebuje obu. Bez kompilacji i bez parsera Javy z zależności: tokenizer i parser deklaracji (ok. 470 linii) wystarczają do adnotacji, stałych i łańcuchów wywołań, działają tak samo na Javie i Kotlinie, nie wykonują kodu z repo (ADR-25) i mają liniowy koszt na złośliwym pliku; ceną jest to, że ścieżka złożona w kodzie (`RouterFunction`, adres z metody) nie trafia na kartę albo zostaje jako `<Klasa.NAZWA>`. Pliki źródłowe wybiera `git grep` w commicie, bo czytanie całego kodu setek repo kosztowałoby gigabajty, a fakty są tylko w plikach z adnotacjami i klientami. Bez LLM: krok LLM (§4.6) może później opisać to, czego reguły nie widzą, z innym `origin`. Graf trzyma ostatni wynik z kluczem wejścia, bo dopasowanie wywołań do endpointów wszystkich repo przestało być darmowe przy odpytywaniu co 30 s (warunek z ADR-29). Słowo „aplikacja” zamiast „serwis”, bo serwis to proces uruchomiony przez Trackwall (§4.3). Odwróciłoby to: firma z innym frameworkiem HTTP (Micronaut, Quarkus, JAX-RS; wtedy kolejny ekstraktor obok `spring.ts`), wiele fałszywych krawędzi po ścieżkach (wtedy dopasowanie po ścieżce tylko na żądanie albo próg), adresy w Config Server albo w manifestach Kubernetes zamiast w repo aplikacji (wtedy ekstraktor repo konfiguracji i alias z `ConfigMap`), albo potrzeba ścieżek liczonych w kodzie (wtedy krok LLM albo analiza z kompilatorem w worktree).

**ADR-31 Zadanie agenta w osobnym worktree w katalogu stanu, polecenie przez `copilot --interactive`, zmiany przez odpytywanie gita.** (2026-10-23) Widok „Sessions” tworzy zadanie: nową gałąź `trackwall/<skrót polecenia>-<6 znaków UUID>` od gałęzi domyślnej repo, jej worktree w `worktrees/<repo>/` katalogu stanu i sesję Copilot CLI (ADR-26) w tym worktree z poleceniem jako pierwszą wiadomością (`--interactive=<polecenie>`) i UUID zadania jako identyfikatorem rozmowy (`--session-id`), więc wznowienie to `--resume=<UUID>`. Zadania są w `tasks.json` i przeżywają restart daemona; worktree i gałąź znikają tylko na prośbę użytkownika, a zmiany, które by przy tym przepadły, tylko po potwierdzeniu odmowy `unsaved_changes` (§4.4). Zmiany zadania to katalog roboczy względem commita bazowego, liczony gitem z indeksem tymczasowym, a UI odpytuje je co 2 s. Sprawdzone na Copilot CLI 1.0.103: `--session-id` w pomocy to „set the UUID for a new session”, a próba z nim utworzyła `~/.copilot/session-state/<ten UUID>`, więc `--resume=<UUID zadania>` trafia w rozmowę zadania; `--interactive=<polecenie>` z `=` jest przyjmowane także dla polecenia od `-`. Uzasadnienie: worktree daje każdemu zadaniu własny katalog roboczy i gałąź, więc kilka zadań w jednym repo i praca użytkownika w repo głównym nie wchodzą sobie w drogę, bez kopii repo; katalog stanu zamiast `<repo>/.worktrees` z poprzedniego planu (§4.4), bo worktree w repo to nieśledzony katalog w `git status` użytkownika (bez wpisu w `.git/info/exclude`) i kolejny katalog repo, który narzędzia (IDE, `mise`, wyszukiwanie) przeglądają, a lista repo i tak nie widzi katalogów spoza folderu z projektami. Gałąź od gałęzi domyślnej, a nie od wybranej, bo zadanie jest nową pracą, a gałąź funkcji użytkownika mogłaby mieć jego niedokończone zmiany; lokalna gałąź domyślna, bo to ją przesuwa synchronizacja. Polecenie jako argument zamiast pliku, bo Copilot CLI w trybie interaktywnym nie czyta promptu z pliku, a `-p` (tryb nieinteraktywny) wyłącza TUI, zgody i rozmowę (ADR-17). Odpytywanie zamiast watchera plików, bo diff i tak liczy git, a rekursywny watcher na worktree z `node_modules` albo `target` jest drogi i różny na każdym systemie; indeks tymczasowy z `--intent-to-add`, żeby nowe pliki agenta były w diffie bez dotykania indeksu, którego agent używa do commitów, i bez zapisywania obiektów do `.git` przy każdym pytaniu. Koszt jednego pytania to kopia indeksu i kilka poleceń gita (`add -N`, `diff`, `rev-list`, `status`), na repo Trackwall (350 plików, Linux) około 30 ms; odpytuje tylko otwarta zakładka „Changes”, a następne pytanie idzie po odpowiedzi. Zadanie nie dostało budżetu czasu, ostrzeżenia o konflikcie ścieżek między zadaniami ani tokenu zadania dla MCP: to kolejne kroki. Odwróciłoby to: Copilot CLI z własnym zarządzaniem worktree, które daje to samo bez daemona (pomoc 1.0.103 wspomina katalog `--worktree`, ale bez opcji), `--interactive` przestające wysyłać polecenie (wtedy wpisanie polecenia do PTY po pierwszym hooku `sessionStart`), odpytywanie zbyt drogie na dużych repo na Windowsie (wtedy watcher tylko jako sygnał do przeliczenia) albo potrzeba worktree obok repo, np. dla narzędzi, które szukają konfiguracji w katalogach nadrzędnych. Doprecyzowanie (2026-10-24, #36): pierwsza wersja dodawała nowe pliki przez `git add --intent-to-add`, który przy każdym pytaniu zapisuje (albo odświeża) w `.git/objects` pusty blob; kilka okien „Changes” naraz pisało więc ten sam plik obiektu, a na Windowsie drugi zapis kończył się „Permission denied” i chwilowym `repo_unavailable`. Wpisy przez `ls-files --others` i `update-index --index-info` dają ten sam diff bez żadnego zapisu (koszt pytania: `ls-files` i `update-index` zamiast `add -N`), więc nie trzeba ani kolejki liczeń w jednym repo, ani ponawiania po błędzie, a zapis pustego bloba przez samego agenta (`git add` pustego pliku) nie ma już z kim się ścigać po stronie daemona. Doprecyzowanie (2026-10-24, ADR-39): zamiast tokenu zadania każda sesja, także w korzeniu repo, dostaje token sesji; zadanie może powstać z propozycji zadania, z jej identyfikatorem i tytułem (skrót gałęzi z tytułu), i ma podsumowanie od swojej sesji (`Task.summary`).

Angielski, bo repo jest publiczne, a narzędzie trafia do zespołów, w których nie każdy czyta po polsku; opisy MCP czyta też agent, który i tak pracuje po angielsku. Dokumentacja projektu zostaje po polsku, bo piszą i czytają ją dziś ci sami ludzie i agenci co dotąd, a tłumaczenie jej teraz to dużo pracy bez użytkownika, który by na nią czekał. `README.md` mówi tylko, czym jest Trackwall, że to wczesna wersja i gdzie są wydania z instrukcją instalacji; opis funkcji jest w `docs/features.md`, a uruchomienie ze źródeł w `docs/development.md`. `CONTEXT.md` podaje przy każdym pojęciu widocznym w UI, komunikatach daemona i MCP słowo angielskie, którego tam używamy. `SECURITY.md`, formularze zgłoszeń w `.github/ISSUE_TEMPLATE/` i notatki o zmianach w `docs/release-notes/` (treść wydania na GitHubie) czytają użytkownicy, więc od tego ADR też są po angielsku; wcześniejsze notatki zostają po polsku. Liczba mnoga to angielskie `one` / `other` (`pluralNoun` i `countLabel` w `protocol`, wspólne dla daemona i UI) zamiast polskich trzech form. Odwróciłyby to: współtwórcy spoza Polski (wtedy także dokumentacja i komentarze po angielsku, w osobnym PR) albo potrzeba kilku języków UI (wtedy teksty w katalogu tłumaczeń zamiast w kodzie). The project-language part (documentation, ADRs, `AGENTS.md`, comments, commits, PR descriptions, test names, scripts) is superseded by ADR-43.

**ADR-33 Pulpit 3D na Pawn z npm, zasilany migawką `HomeModel` zamiast strumienia zdarzeń, w układzie „Orbit” z modeli złożonych z prostych brył.** (2026-10-24) Pierwszym ekranem Trackwall ma zostać pulpit 3D (widok w UI doszedł po paczce sceny, zob. doprecyzowanie niżej), który od razu mówi, czy środowisko działa, które sesje Copilot czekają na człowieka i w jakim stanie są repo. Scena jest osobną paczką `@trackwall/scene` na `@pawnjs/core` w dokładnej wersji z npm (silnik three.js + koota); Trackwall nie korzysta z niczego spoza opublikowanych paczek Pawn, a czego w nich brakuje, zgłasza projektowi Pawn i do czasu decyzji obchodzi u siebie (render na żądanie i utrata kontekstu WebGL po stronie UI, łuki i przewody jako własne modele three.js). Scena dostaje migawkę, a nie zdarzenia (zmiana względem pierwotnego §5.5), bo UI nie ma jeszcze `/ws`, a migawka jest tą samą wartością przy odpytywaniu i przy zdarzeniach; porównanie z poprzednią migawką robi `KeyedEntities` i podpis wyglądu obiektu, więc koszt to jedno `JSON.stringify` na obiekt przy skali 10–15 repo i około 10 sesji. Układ „Orbit” wygrał z warstwami w rzędach i siatką, bo przy tej skali mieści wszystko w jednym kadrze, a sesje stoją obok swojego repo. Modele są z prostych brył (bez glTF), dopóki wygląd się ustala; ten sam kształt może później przyjść przez `Model` z Pawn bez zmiany reszty sceny. Kolory pochodzą z tokenów UI (ADR-16), podawane jako `ScenePalette` w `#rrggbb`, a treść etykiet pisze UI, więc scena nie ma własnych tekstów ani kolorów. Decyzję odwróciłoby: skala znacznie większa niż kilkadziesiąt repo (wtedy układ z warstwami w rzędach i grupowanie), koszt porównywania migawek widoczny w profilu (wtedy zdarzenia z `/ws` wprost na encje) albo rezygnacja z Pawn przez projekt.

**ADR-34 Wynik synchronizacji mówi, co zostało w katalogu roboczym; zmiany katalogu roboczego w zakładce „Changes”; tag `no-mise` z karty.** (2026-10-24) Każdy wynik synchronizacji bez błędu ma stan katalogu roboczego po niej (wybrana gałąź, zmienione i osobno nowe pliki), a UI pokazuje zdanie o wyniku dla każdego repo, także aktualnego; zakładka „Changes” w szczegółach repo pokazuje pliki i diff katalogu roboczego względem HEAD; repo bez tasków mise w commicie dostaje tag `no-mise`. Uzasadnienie: użytkownik po „Sync all” widział na liście „4 changes” i nie dostał żadnego komunikatu, bo repo było aktualne (lista ukrywała „up to date”), a liczby zmian nie dało się otworzyć; z samego wyniku nie wynikało też, że przesunięta gałąź domyślna nie zmienia plików, gdy wybrana jest inna. Stan katalogu roboczego przychodzi z daemona jako część wyniku, a nie z listy repo w UI, bo opisuje chwilę synchronizacji, trafia też do `list_repos` w MCP (`lastSync`) i kosztuje jeden `git status` na repo; gdy ten `git status` zawiedzie, wynik ma `workingTree: null`, a nie błąd, bo gałąź już się przesunęła. Zakładka używa odczytu zmian zadania (ADR-31) zamiast `git status` z listą plików, bo daje od razu diff i nowe pliki bez zapisu do indeksu użytkownika; jest tylko do odczytu, bo zatwierdzanie i odrzucanie zmian w tle łatwo zgubić, a edytor robi to lepiej. `no-mise` jest tagiem z karty commita, a nie wynikiem `mise tasks ls`, bo lista repo nie może uruchamiać mise w każdym repo (zaufanie, czas, konfiguracja globalna, ADR-20, ADR-25), a tag daje filtr „repo do znormalizowania” bez nowego pola w liście; jest negatywny, bo to brak trzeba znaleźć. Odwróciłyby to: potrzeba commitowania albo odrzucania zmian z Trackwall (wtedy akcje z potwierdzeniem w `vcs`), taski w repo trzymane głównie w `task_config.includes` (wtedy czytanie dołączonych plików albo `mise tasks ls` w tle po zaufaniu) albo `git status` na końcu synchronizacji widoczny w czasie przy setkach repo (wtedy stan katalogu roboczego z listy repo w UI).

Doprecyzowanie (2026-10-24, widok Home): pulpit jest pierwszym widokiem paska (Ctrl+1), a Repos, Sessions i Overview przesunęły się na 2, 3 i 4, bo to ekran, od którego zaczyna się dzień. Migawka nie ma już pola „repo ma mise”: jedynym tanim źródłem byłoby `mise tasks ls` na każde repo, a to uruchamia mise (i `[env]` w zaufanym repo) co kilka sekund, więc kafel repo bez mise nie różni się od innych. Działający task przychodzi z nowego `mise/running`, odczytu z pamięci daemona. Tokeny przelicza na `#rrggbb` płótno 2D przeglądarki zamiast własnej konwersji `oklch`, bo przeglądarka i tak je rysuje i zna przestrzeń barw ekranu.

Dopisek (2026-10-24, ADR-36): UI ma już `/ws`, a sesje i działające taski mise przychodzą do pulpitu ze zdarzeń; scena dalej dostaje migawkę `HomeModel`, bo zdarzenia też niosą migawki tematów.

**ADR-35 README w karcie repo renderuje gotowy Streamdown z wtyczką Mermaid; linki otwiera daemon w przeglądarce systemu, obrazy zastępuje opis.** (2026-10-24) Zakładka README pokazywała surowy Markdown. Zamiast składać własny renderer, UI używa gotowego komponentu Streamdown (`streamdown`, Apache-2.0) z `@streamdown/mermaid` (Apache-2.0; Mermaid MIT; reszta zależności MIT, ISC, BSD i Apache-2.0, bez copyleftu): GFM (tabele, listy zadań), bloki kodu i diagramy Mermaid w trybie `strict` z ciemnym motywem, z kopiowaniem, pełnym ekranem i przybliżaniem. Komponent jest ładowany leniwie (`ReadmeMarkdown.tsx`), bo z Mermaidem to około 4 MB JS, a reszta UI go nie potrzebuje; błąd ładowania albo renderowania pokazuje surowy tekst (`ReadmeFallback.tsx`). O formacie decyduje daemon (`readme.format` w `overview`): `.txt`, `.rst` i `.adoc` są tekstem, reszta Markdownem, jak na GitHubie. README to treść z repo, więc niezaufana. Surowy HTML przechodzi `rehype-raw` i `rehype-sanitize` ze schematem GitHuba (`defaultSchema`, z prefiksem `user-content-` dla `id` i `name`), podanymi wprost zamiast domyślnych wtyczek Streamdown, bo te zdejmują prefiks i dokładają `rehype-harden`, który bez adresu bazowego zamienia linki i obrazy względne w „[blocked]”. Nic z README nie nawiguje oknem: kontener przechwytuje każdy klik (także środkowym przyciskiem i Enter) w `<a>`, również w SVG diagramu, gdzie Mermaid w trybie `strict` zostawia linki z `click … href`; adres `http` albo `https` (`ExternalLink` w `protocol`, w postaci kanonicznej z `normalize`) otwiera daemon akcją `workspace/open-link` tym samym `openUrl` co VS Code, a inne linki (względne, kotwice, `mailto:`) są tekstem. Okno Tauri nie ma przeglądarki, a kliknięty link podmieniłby w nim aplikację. Obrazy z Markdownu i HTML nie są ładowane, tylko opisane (`alt`): okno Tauri wpuszcza obrazy tylko z `self` i `data:` (CSP), a obrazek z internetu to też piksel śledzący. Pobieranie diagramów, tabel i kodu do pliku jest wyłączone, bo nie wiadomo, czy WebView2 i WKWebView je obsłużą. Decyzję odwróciłyby: potrzeba obrazów z repo (wtedy akcja daemona z obrazem z HEAD jako `data:`), linków wewnątrz repo (wtedy przejście do zakładki „Files”) albo koszt rozmiaru paczki UI.

**ADR-36 Sesje w MCP tylko do odczytu i zdarzenia `/ws` jako migawki tematów, wykrywane porównaniem w daemonie.** (2026-10-24) Widok „Sessions” ma być rejestrem wszystkich sesji, a agent (agent nadrzędny albo inna sesja) ma o nich wiedzieć, więc serwer MCP dostaje dwa narzędzia tylko do odczytu: `list_sessions` (sesje i zadania, te same `Session` i `Task` co w UI, opcjonalnie dla jednego repo) i `get_session` (sesja, jej zadanie i zmiany zadania bez diffu: diff do 1 MB nie mieści się sensownie w kontekście agenta, agent może przeczytać worktree sam, a git nie musi go wtedy liczyć). Ekranu sesji narzędzia nie zwracają, także ostatnich linii zakończonej grupy (`AgentSession`): ostatnie linie są maskowane tylko wartościami sekretów ze środowiska procesu (§4.2), a agent wypisuje w terminalu także to, co przeczytał z plików (`.env`) albo dostał w poleceniu, więc ekran mógłby przenieść do innej sesji sekret wypisany w terminalu (§8). Narzędzia nie uruchamiają, nie odpowiadają i nie zatrzymują sesji: sesja nadrzędna, która zleca zadanie (`propose_task` z zatwierdzeniem w UI), zgłasza wynik (`report_result`) i czeka na sesję (`wait_for_session`), to następny krok, który potrzebuje tokenu zadania, żeby daemon wiedział, kto woła; dziś most stdio sesji nie mówi daemonowi, z której sesji jest, więc `list_sessions` nie zaznacza „to ja”. Zdarzenia `/ws` (§5.2) niosą całą migawkę tematu (`sessions.changed`, `mise.running.changed`), a nie różnicę ani zdarzenie domenowe w rodzaju `task.state`: klient po każdym podłączeniu dostaje migawki, więc bufor zdarzeń, `seq` i `resync` z pierwotnego §5.2 nie są potrzebne (zdarzenie nie ma numeru, bo kolejność daje jedno połączenie, a nikt go nie czytał), a UI dostaje tę samą wartość co z akcji HTTP i ten sam kod widoków działa z obu źródeł (odpytywanie zostaje jako zapas na czas bez połączenia i dla tematu, którego daemon nie umie odczytać). Zmianę wykrywa daemon, porównując JSON migawki co 200 ms, dopóki ktoś słucha, zamiast powiadomień z modułów: stan sesji zmienia się w wielu miejscach (hooki, OSC, klawisze, próg `Stale`, koniec grupy w `procs`), migawki to odczyt z pamięci, a jedno porównanie nie zgubi zmiany, o której moduł zapomniałby powiadomić. Świadomy koszt: dwa `JSON.stringify` i odczyt sesji pięć razy na sekundę przez cały czas, gdy okno UI jest otwarte, także schowane w trayu (wcześniej UI przy schowanym oknie nie pytało); przy kilkunastu sesjach to ułamki milisekundy. Pierwsze tematy to te, które UI odpytywało najczęściej i które czyta pulpit Home (§5.5); powłoka Tauri dalej odpytuje HTTP (§5.4). WebSockety mają jedną obsługę `upgrade` (`api/sockets.ts`) z tymi samymi sprawdzeniami dla zdarzeń i terminali, a adres z podprotokołem gniazda jedno miejsce w `protocol` (`DaemonSocket`). Źródło zdarzeń (`EventHub`) jest dziś w `api/`, bo słucha go tylko `/ws`; `wait_for_session` w MCP dostanie ten sam obiekt z `main.ts`, tak jak `createMcpEndpoint` dostaje fasadę, a hub przejdzie wtedy do `infra/`. **ADR-40 Code search through `git grep` in the HEAD commit, without an index and without ripgrep.** (2026-10-24) The `search_code` MCP tool searches for a fixed string or a regular expression in many repos of the projects folder at once, with `git grep` over the objects of each repo's HEAD commit (§4.5, §5.3). Git is required anyway, and `git grep` over a commit gives the same guarantees as browsing (ADR-14): paths only from the commit tree, no ignored files, no programs run from the repo (`--no-textconv`), and machine-readable output (`-z`) that does not depend on git's language. ripgrep is faster on a working tree, but it is a second native binary to ship and sign for every platform, and it would search the working tree, including files the repo does not track (`node_modules` without `.gitignore`, secrets in `.env`). There is no index (e.g. trigrams, as in Zoekt): the pool holds dozens of repos, not thousands, and an index would need refreshing after every sync. What would reverse it: searches over hundreds of large repos taking longer than a few seconds (then an index), a need to search uncommitted changes (then `git grep --untracked` in the working tree), or a need for PCRE (`-P` depends on git being built with PCRE2). Without an index every query costs a full read of each commit, so the search is bounded: per-repo output and time limits, an overall budget after which no new repo starts, and a stop once the limit of matches is reached (§4.5).

**ADR-41 The agent runs and stops mise tasks over MCP from the list of a trusted config, without a separate approval in the UI.** (2026-10-24) The tools `run_mise_task`, `stop_mise_task`, `wait_for_mise_task` (waits up to 55 s for the group to end) and `list_running_mise_tasks` (§4.7, §5.3) map to `mise.start`, `mise.stop`, `mise.waitForEnd` and `mise.running`, like the buttons in the "mise tasks" tab. An agent needs the loop "change, run the tests or the build, read the result" without asking a human to click, and with `tail` (ADR-28) and the exit code from `wait_for_mise_task` it has all of it. The consent to run repo code is the mise trust given in the UI: without it mise does not list the tasks, and the daemon runs only a task from that list, with the command built from its name (§1.2), so the agent cannot run anything the user could not run with the button; MCP has no tool for `mise trust`. A separate "agents may run tasks" switch was rejected, because an agent with shell access can type `mise run` anyway, and the MCP client asks for approval of the tool (`destructiveHint` on `run_mise_task`, and on `stop_mise_task`, which can kill a dev server or a migration the user started) as it does for a shell command. The names carry `mise_` instead of the planned `run_task` (§5.3 before this decision), because in English text a bare *task* is an agent task (`propose_task`, `CONTEXT.md`); for the same reason the allowlist of names (`setup`, `test`, `build`, `lint`, `health`) was dropped: repos name their tasks their own way (`test:unit`, `build:ui`), and the services that were to take over `dev` do not exist yet. A Trackwall session (by its session token, ADR-39) runs and stops only tasks of the repo it works in, as planned in §8; an agent outside Trackwall is the user's program and reaches every repo. Like the proposal approval in ADR-39, this is a guard for an agent using its own bridge, not a security boundary: a session process can call `/mcp` with the daemon token alone. The `audit` table that ADR-24 and ADR-39 put before `run_task` is not a precondition: before acting, a destructive tool writes its arguments (repo and mise task, never free text) to the daemon log with the tool and session, and the run shows in the UI (state, log, Home) like a run from the button. The run is always in the repo root in the projects folder, also for a task session in a worktree, because mise trust is per path and a worktree in the state directory is not trusted. The gap of trusting a path rather than its content is in §8. What would reverse it: abuse by an agent that changes a trusted config (then only tasks from the commit, or mise `paranoid` mode), a need to run tasks in a task worktree (then trusting the worktree when it is created), services with leases (then `dev` through a lease instead of `run_mise_task`) or an audit the user requires (then the `audit` table before these tools).

**ADR-42 Errors from logs for the agent as blocks of in-memory records, detected by line heuristics.** (2026-10-24) The MCP tool `get_errors` returns errors from the buffers of all log sources (filters `repo` and `miseTask`, a `sinceSeq` cursor across the workspace): a block from an `error` (or `warn`) record, an exception header or a Spring/Gradle report, together with the lines that belong to it (stack trace, `Caused by:`, indented compiler context), the same errors of a source merged with a count, the stack trace trimmed and the cause in `exception` (§4.2). The `errors` tool planned in §5.3 is named `get_errors`, like the other tools that read one thing, and takes `repo`/`miseTask` instead of `service`, since there are no services yet. Rationale: an agent asking what broke needs the stack trace and the cause, not 2000 `tail` lines from one task; the planned single records with `level>=error` would cut a Java stack trace into a header without its cause (frames and `Caused by:` have level `info`), and a flood of the same error from every request would eat the context. Blocks computed on each request from the buffer (at most 2000 records per source) cost less than an index and keep no state of their own, and line heuristics work without changes to the user's repos until there is an ECS parser. Compiler levels (javac, tsc, kotlinc, `npm error`) and the mise task prefix went into `logLevel`, because the UI uses the same rule. Would reverse it: the ECS parser (then `error.stack_trace` from the record replaces block building for structured logs), service logs longer than the buffer in which the agent looks for older errors (then an error index or reading the JSONL), or formats the heuristics miss that recur in work repos (then block rules from the workspace config).

**ADR-44 Shared files of two tasks as a warning in the task panel, computed on request from the worktrees' lists of changes.** (2026-10-24) Two tasks in one repo work in separate worktrees, each from its own base commit (the default branch when it was created), so they do not get in each other's way while working, but the one merged second will likely get a conflict in the files both changed. The daemon answers `task-shared-files` with the intersection of the file lists from git (the same read as the “Changes” tab, without the diff), and the UI shows a warning above the selected task's tabs. At the level of files, not lines: two diffs in one file usually need attention anyway, and comparing line ranges against two different bases would give false certainty. A list of changes cut off at its limit (`truncated`) can miss a shared file, which is acceptable for a warning. On request, not in the background or on the session list, because the list refreshes every second, and a git read of every task on every list change would cost more than the warning is worth; a marker on the list and a warning for the main session in MCP (`get_session`) are possible next steps. Only a warning: Trackwall does not stop a task or merge anything by itself (ADR-9). This would be reversed by many false warnings on files that always change together (then line ranges or a trial merge with `git merge-tree`), or by a need for the warning without opening the task (then computing in the background with a cache and a `/ws` event).

**ADR-46 The agent learns how to work with Trackwall from the MCP server and from session instructions, without changes to the user's repo.** (2026-10-24) One MCP instruction (`MCP_INSTRUCTIONS` in `protocol`) says what Trackwall is and when to reach for which tool; the MCP server announces it in `instructions` (§5.3), and every Trackwall session gets it in its **session instructions** together with the session's role (§4.4): the file `trackwall.instructions.md` in the session directory, whose directory the daemon appends to `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` in the session environment. Checked in the Copilot CLI 1.0.103 binary without signing in: MCP server `instructions` reach the prompt only for servers on an allowlist (`mcpRegistryServerInstructionAllowlist`; the `--allow-all-mcp-server-instructions` workaround would also turn on the instructions of every other server the user has), so the MCP server alone is not enough; `copilot instruction list` shows a file from a `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` directory as a repository instruction, and the variable separates directories with commas. The role is built only from the repo and task ids, so agent text never becomes another session's instruction (§1.2). A test requires the MCP instruction to mention every tool in `mcpTools`, so a new tool comes with its instruction. No `llms.txt` in the Trackwall repo: agents that develop Trackwall have `AGENTS.md`, and agents that use it get the instruction from Trackwall. To check by hand with a signed-in Copilot CLI: whether the file with `applyTo: "**"` is in the prompt from the first turn (not only after a file is opened) and whether the agent follows its role. What would reverse it: a Copilot CLI that takes `instructions` from every local MCP server or lets the user allow a single server (then the server is enough and the file keeps only the role); a change or removal of `COPILOT_CUSTOM_INSTRUCTIONS_DIRS` (then an instruction file in the session plugin, if Copilot CLI starts reading one there, or a preamble in the task prompt).

**ADR-47 "Waiting for you" ends when the user has seen the end of the turn; approval and plan wait for an answer.** (2026-10-24) A session in `Input` (the turn ended, the agent asked a question, or the user interrupted it) stops waiting for you once a session terminal window has been in front of the user (focused and visible) or the user typed into the session; `Approval` and `Plan` keep waiting until the answer, which the hooks and the session keys already report. Before this, `Input` waited until the next prompt, so a session the user had already looked at kept the warning, the counter and the tray entry for as long as it stayed idle, and "waiting for you" stopped meaning anything. The rule follows tools that solved the same problem: Agent Deck has `waiting` (yellow, not acknowledged) and `idle` (grey, acknowledged on attach), and a tmux status indicator for Claude Code clears a finished session when its pane is viewed but keeps the permission prompt until work resumes. The window counts as in front only after 1 s, because a click on "Waiting: <repo>" in the tray first brings the window to the front with the previous session's terminal and only then switches to the chosen session. Focus comes from the window over the existing PTY WebSocket instead of a separate HTTP action: the daemon sees when the window disconnects, so a closed window cannot leave the session "watched", and the window that shows the session is the one that knows whether the user can see it. Only a change to another state makes a seen session unseen again, so a hook that confirms `Input` after a session key does not bring the warning back. The state stays `Input` (the detectors do not change); "idle" is how the UI and the dashboard show seen `Input`. Reversed if Copilot CLI reports turns in a way that tells a question apart from an ended turn (then a question could wait like `Approval`), or if the user wants an explicit "mark as read" instead of focus.

**ADR-48 Sessions switch from the keyboard with Alt + digit and Alt+J, and show several terminals in a grid of pages.** (2026-10-24) The Sessions view gets a layout switch: `1` is the selected entry with its full panel as before, `2` and `4` show a page of that many entries as a grid of terminals, and `auto` shows the whole list, up to nine per page (`lib/session-grid.ts`). The page is always the one with the selected entry, so a shortcut to any position also turns the page and the selected tile never leaves the screen. Columns and rows come from the size of the area (`gridShape`: the shape with the largest tile of ratio 1.6 that fits a cell), so two tiles sit side by side on a wide window and stack on a tall one, and six fill three columns and two rows on a 34-inch ultrawide. Alt + digit (⌥ on macOS) selects the entry at that position in the list, and Alt+J opens the next session that is waiting for you from any view, after the selected one like the "Next waiting" button (`lib/session-shortcut.ts`; `App` owns Alt+J, the view the positions). The selected tile has the accent ring and the keyboard (a tile of a task without a session takes the focus itself, so keys stop going to the terminal selected before); a waiting tile keeps its warning frame also when selected. The last page keeps the tile size of a full page, and tiles appear only once the grid area is measured, so that no terminal reports a size to its session from a shape that is about to change. Rationale: switching between sessions that need you was a mouse click each time, and a large screen fits several Copilot CLI sessions at once. Ctrl/⌘ + digit already switches views (ADR-16), and Ctrl+J, proposed first, is a line feed in a terminal, which a TUI can read as Enter; Alt + digit and Alt+J have no meaning in Copilot CLI 1.0.103 that we know of, and on macOS Option + key on a US layout only types a character such as `¡`, so the keys are matched by position (`code`). What Alt and Option exist for stays a key: AltGr (Ctrl + Alt on Windows), the keypad (Alt + keypad digits type a character by its code on Windows) and, on macOS, an Option + key that types an ASCII character (⌥5 is `[` on a German layout, ⌥2 `@` on a Swedish one), which on such layouts leaves those positions without a shortcut. Pages instead of choosing the tiles by hand, because the list order is already the order the user knows and the shortcut numbers match it without a second list to maintain. The shortcuts listen in the capture phase on `window` and stop the event: xterm.js turns Ctrl + digit into a control character and stops its propagation, so the view shortcuts did not work while a terminal had the focus, and a session shortcut must not also reach the terminal. In Sessions the session shortcuts are always taken, also when there is nothing to switch to; outside Sessions Alt+J is taken only when a session is waiting, so ⌥J still types in a text field. The capture listener is one function for view and session shortcuts (`lib/window-shortcuts.ts`). Only the selected tile counts as in front of the user for ADR-47, so a session that waits in another tile keeps its warning frame until the user selects it. A terminal in a grid tile reports its size to the PTY like any other window (§5.2), so a session shown in a small tile is resized; switching back to layout 1 resizes it again. Known gap: a tile smaller than the PTY minimum (10 columns, 4 rows; nine tiles in a window about 400 px tall) sends a size the daemon rejects, so the PTY keeps its last size and the terminal shows a fragment of the screen. The layout lives in `App` and is lost when the app closes. Not done yet, from the same proposal: opening a main session with all its tasks as a grid, and pinning a session to a panel on the right that stays visible in other views. What would reverse it: Copilot CLI giving Alt + digit or Alt+J a meaning (then another modifier, or shortcuts that work only outside the terminal), more than nine sessions being the usual case (then chosen tiles instead of pages), or terminals that need a minimum size the grid cannot give (then a minimum tile width).

**ADR-51 The projects folder is chosen in the system picker, a repo opens in Explorer or Finder, and dropped files go to the session or the repo list.** (2026-10-24) Settings gets "Choose…" next to the path field in the Tauri window: the app command `pick_folder` (Rust, `tauri-plugin-dialog`) opens the system folder picker and the chosen folder is saved at once. The repo header gets "Show in Explorer" (Finder on macOS): the daemon opens the folder of the listed repo, like "Open in VS Code" (`open-folder`), so it also works in the browser. A file or folder dropped on a session terminal is pasted into it as its path (quoted when it has a space or a quote, with a space after it), and a folder dropped anywhere else goes to `dropped-folder`: a listed repo opens in Repos, and a folder with repos, or the folder that holds a dropped repo, is offered as the projects folder. Reasoning: Trackwall lists the repos of one folder (ADR-18), so a single repo from elsewhere cannot join the list without changing that rule; offering its folder keeps the rule and still makes the drop useful. The picker is an app command rather than the plugin's JavaScript API, so the window's capability stays `core:default` and the page gets no general dialog or file access; Show in Explorer/Finder goes through the daemon rather than `tauri-plugin-opener` because the daemon already opens things in the system from its own configuration (`open-editor`, `open-link`) and the page opened from the daemon gets it too. `clipboard-manager` is not needed: the terminal already copies with `navigator.clipboard`. What would reverse it: a list of repos from several folders (dropping a repo would then add it), or a need for the plugin dialog in the page (file pickers in several views).
