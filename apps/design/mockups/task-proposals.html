Approving tasks proposed by a main session

A main session proposes tasks (propose_task, ADR-39), and you decide what starts. Below: what got in the way in this flow, three variants and the recommendation. The mockups use sample repos; UI texts are in English, as in the app.

What was not intuitive

1One proposal at a time

A main session usually proposes several tasks in one go, and each had to be clicked in the list, read and started on its own. You could not see them together, so it was hard to judge the plan as a whole.

2Home and the tray only point elsewhere

In “Needs you” and in the tray panel a proposal is a row that takes you to Sessions. A decision always meant switching views, even to reject quickly.

3A dead tile in the grid

In the terminal grid a proposal showed only “Open it alone to read its prompt, then start or reject it.” You had to leave the grid, decide and come back.

4Counters disagree

The view bar counted sessions and proposals, but “Next waiting” and Alt+J jumped only between sessions. The badge said 3, the button 1, and Alt+J never showed a proposal.

5“Reject” without a reason

Rejecting was one click next to “Start task”, with no undo and no reason. The main session got only proposal_rejected, so it did not know whether to propose differently or give up.

6After a decision, no next step

After a rejection the panel jumped to the first entry of the list, whatever it was. The warning about shared files (ADR-44) showed only on running tasks, not at the decision. Five proposals also meant five notifications.

A. A proposal inbox in Sessions

chosen, with two parts of B

Selecting any proposal opens one panel with all waiting proposals, grouped by the session that made them. Each is folded to its title and the first line of its prompt, and unfolds for editing. You tick which to start and start them together. Rejecting asks for a short reason, which goes back to the main session. The mockup is clickable.

Each task gets a new branch from the default branch of its repo, in a separate worktree. Alt+J and “Next waiting” also go through proposals.
For
  • The main session's plan is visible as a whole, the decision in one place.
  • Fewest new places in the UI: mostly ProposalPanel and the list entry change.
  • You still read the prompt before the start, as ADR-39 requires.
  • The reason for a rejection returns to the main session through wait_for_session.
Against
  • Home and the tray still only point elsewhere (unless parts of B are added).
  • Starting several at once means several worktrees and sessions at the same time; noticeable on a slow Windows machine.
  • A protocol change: a reason in reject-proposal and in the wait result.

B. Decide where you are

quick actions

No new panel: a proposal can be approved or rejected wherever it already shows. In “Needs you” the row unfolds with a preview of the prompt, the grid tile has a preview and buttons, and the tray panel has “Reject” and “Review” but not “Start”, because the prompt cannot be read properly there.

Against

  • The preview shortens the prompt, which tempts a “Start” without reading it all.
  • The same actions in three components; they must live in one place so they do not drift apart.

C. Proposals next to the main session

conversation context

Proposals stop being separate entries in the list. The main session gets a “3 to approve” badge, and its panel has a drawer of proposals next to the terminal. You decide while seeing the conversation they came from, and can tell the session right away what to change.

  • A natural place for “Start all”.
Against
  • A proposal from an agent outside Trackwall has no session, so it needs a separate place anyway.
  • Tight next to the terminal on a smaller screen; fine on a 34" ultrawide.
  • The biggest change: list, tree, grid and shortcuts.

Recommendation: A, plus two parts of B

  1. Proposal inbox (A): all waiting proposals in one panel, grouped by the session that made them, with ticking and “Start N selected”. In the list one row “3 proposals” under the main session instead of three.
  2. Reject with a reason: “Reject…” opens a field for a short, optional reason, and the main session gets it in the result of wait_for_session, so it can propose differently.
  3. After a decision, the next proposal, not the first entry of the list; the shared files warning already at the decision.
  4. From B: a proposal tile in the grid with a preview and “Start” / “Reject…” buttons, and “Next waiting” and Alt+J going through proposals too, so the counters agree.
  5. No “Start” in the tray or Home: they keep pointing to the inbox, because a prompt from an agent has to be read before it runs. Notifications about several proposals from one session merge into one (“3 task proposals from orders-api”).

Decided and built as ADR-55. Variant C was left for later: it gives the best context, but changes the list and the grid.
