mise tasks of packages

A monorepo often keeps a mise.toml in a package folder, such as packages/client/mise.toml, next to the one in the repo root. mise run from the repo root does not read it, and its own notation for package tasks (//packages/client:test) needs mise's experimental mode. Trackwall finds the mise config files of packages below the repo root, lists their tasks under their folder, and runs each in its folder (mise -C packages/client run test), which needs no experimental mode.

2. Recommended: one box per package, under the repo root's

The repo root's tasks stay first, as today. Each package folder with its own mise config gets its own box, named by its path, with only the tasks that config defines (the root's tasks mise also shows there are not repeated). Run starts the task in the package folder, so it gets the package's [env] and tools. Folders are searched up to four levels deep, skipping node_modules, build output and hidden folders.

3. A package's config mise does not trust yet

mise trusts each config file on its own, so a package's config added after the repo was trusted is refused. Its box says so and offers the same trust as the repo root's; the repo's other tasks stay usable. Trusting the repo root also trusts the package configs found at that moment.

4. What an agent sees

The agent's list of mise tasks names a package's task by its folder in mise's own notation, and runs it by that name; Trackwall turns it into a run in the folder, also in a task's worktree. A task's worktree runs package tasks only while their configs are the ones the user trusted, as for the root config today.
