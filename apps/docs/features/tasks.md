# Agent tasks

Give an agent a task on its own branch and worktree, and review its changes before anything lands.

![An agent task in pricing on its own branch, with a failed verification of its tests](/screenshots/tasks.png)

## What you get

- A task for an agent in two fields, a repo and a prompt, on a fresh branch and a separate working copy, so several agents can work in one repo at once, your own working copy stays untouched, and the task survives a restart of Trackwall.
- The task's changes live: files, diff and commits against the default branch, with a warning when two tasks in one repo change the same files, and every turn of the agent as a round with its own diff and "Undo round", so you can take back one step without asking the agent to undo its own work.
- Comments on the lines of that diff, sent to the agent as one review, so it fixes what you pointed at without you retyping file names and lines into its terminal.
- A worktree ready to run: the task's builds and tests run there, where you can watch and stop them, with your local config files (`.env`, a local profile) copied in and a port of its own, so the agent can also start the service it changed next to yours, and one "Verify" button that runs the task's tests there and shows whether they pass.
- A merge request in two clicks: push the task's branch, then open GitLab's or GitHub's form with the title and the agent's summary filled in, and follow the merge request and its pipeline on the Sessions list, with a notification when the pipeline fails.

## How it works

Press "+" in "Sessions", pick a repo, keep the "Own worktree" pill on and write the prompt. Trackwall creates a branch named after the task's title or prompt (`trackwall/<slug>`) from the repo's default branch, in a separate git worktree, and starts Copilot CLI there with your prompt as the first message. The task shows on the list like a session, with the same states. "Start task" on an item of your [plan](/features/plan) opens the same form with the item's repo and prompt filled in. To start the same work in several repos at once, press "Add a repo" in the form: see [Changes across several repos](/features/changes).

The "Changes" tab follows the worktree live: the files and diff against the default branch, the task's commits and what the agent has not committed yet. "VS Code" opens the worktree in your editor. A task started or proposed with a model shows the model next to the task port, and its session runs on that model every time it starts. When the agent finishes, it leaves a summary above the task's tabs. When there is something you can try by hand, such as a page or an endpoint, the summary also has a few steps for checking it, each with what to do and what you should see; open the summary ("How to check", or "Show all" for a long one) to read them. They are only a hint: nothing waits for you to follow them, and you carry on with the task either way. Everything above the tabs is folded into one line of notices, such as "Summary" or "Verification failed"; click one, or "Details", to see the sections. A task that another session proposed also shows, above the summary, the messages that session sent its agent (see [Main session and task proposals](/features/main-session)).

The "Rounds" tab lists the task's rounds, newest first. A round is one turn of the agent that changed something: when the agent finishes a turn and waits for you, Trackwall commits whatever it left uncommitted on the task's branch as `WIP round 3`, with your own git name and email, so each round has a commit and a diff of its own. Click a round to see what that turn changed. If the agent made a commit of its own in that turn, the round shows it, and nothing extra is committed.

When the last round went wrong, press "Undo round 3" and confirm. The worktree and the task's branch go back to where they were before that round, and the agent is told, first thing when it next waits for you, that its last round was undone, so it does not build on changes that are gone. You can undo again to go back one more round. Trackwall only undoes when nothing else would be lost with the round, and otherwise the button is greyed out with the reason next to it: the agent is still working, you (or the agent) changed files since the round ended, the round started on changes you made by hand, or the round is already pushed. Commit or remove your own changes, or ask the agent instead.

To ask for changes, hover a line of the diff in "Changes" and press the comment icon in front of it. Write what the agent should change and press "Add comment" (or Ctrl+Enter, ⌘+Enter on a Mac). Add as many comments as you like, on added, unchanged or removed lines; they gather in a list above the diff, where you can remove one before sending. "Send N comments to the agent" sends them all as one review. If the agent is waiting for you, it gets the review at once; if it is in the middle of something, or asks for your approval, it gets it as soon as it waits for you again; and if the task has no session, it gets it when you press "Resume". The line under the list says which of these happened. The agent reads every comment with its file, line and the code on that line, makes the changes, commits and reports again. Copilot CLI can review the changes for you first, and you pick which of its findings become comments: see [Automatic review](/features/auto-review).

![Two review comments waiting to be sent, and a third being written under its line](/screenshots/task-review.png)

When another task in the same repo changes some of the same files, a warning above the tabs names that task and lists the shared files, with "Open that task". Trackwall only warns; both tasks carry on.

The agent builds and tests its changes by running the repo's mise tasks in the task's worktree. While one runs, it shows above the task's tabs with "Log" and "Stop". Their logs go away when you end the task. Trackwall runs them only with the mise configuration you have agreed to: the one the worktree started with. If the agent changes a mise file (`mise.toml`, `.tool-versions`, a file task), a warning above the tabs lists the changed files, each of which you can open to read, and no mise task runs in the worktree until you have read them and press "Trust this config". If the agent changes them again while the warning is open, it says so and shows the new version only when you ask, so you always trust what you read. When the agent was already turned away because of the change, Trackwall tells it once you trust the config, also after Trackwall restarted in between, and it runs its mise task again without you having to ask.

To check the task's changes yourself, press "Verify" in the task's header. Trackwall runs the repo's mise task `test` in the worktree and, when it ends, shows a "Verification" section below the summary: passed or failed, why it failed (such as the mise task's exit code), how many tests ran, failed and were skipped, and the first failed tests with their messages and the first errors from the run's log. "Log" opens the whole output, and "Cancel" stops a run in progress. The agent gets the same verdict: Trackwall asks it to verify its task before it reports that it is done, so a finished task usually shows its verdict already. A verification passes when the mise task exits with code 0 and no test in the reports the run wrote failed; a report Trackwall cannot read counts as a failure, since it may hide one.

When the task is done, the "Merge request" section below the verification takes it to your repo host. It shows once the task has a commit: the branch's commits, how many are not pushed yet, and files the agent has not committed (they are not part of a push). "Push" pushes the task's branch to the repo's remote. "Open merge request" shows a title (the task's title, or the first line of its prompt) and a description (the agent's summary, its steps for checking the change under "How to check:" and the verdict of the last verification; for a part of a [change](/features/changes), first the list of the change's merge requests) for you to edit; "Open in GitLab" (or GitHub) opens the repo host's new merge request page in your browser with the branches and those two fields filled in, and you create the merge request there, with the reviewers, labels and template your project uses. From then on the section shows the merge request's number and title, whether it is open, merged or closed, and its pipeline (passed, failed, running), each a link to the repo host. When the agent commits again after a review, press "Push" again; the merge request picks up the new commits. Before every push, Trackwall squashes the `WIP round` commits that are not on the remote yet: each one joins the agent's own commit after it, which keeps its message, and the ones at the end become one commit named after the task, so the merge request shows the agent's commits and no round commits.

You do not need to keep a task open to follow it. Each task's row in the Sessions list says "In review" once its agent has reported its summary and nothing new has gone to it since (your review, "Fix", or a message from the session that proposed the task takes the mark away until it reports again), then the verdict of its last verification ("Verified", "Verify failed", or "Verify outdated" once the files changed after it) and its merge request's number (`!12` on GitLab, `#12` on GitHub) in the colour of its pipeline: green when it passed, yellow while it runs, red when it failed. Hover over the number to read the merge request's title, its state and the jobs that failed. In the grid, the same number sits in the tile's header. When a pipeline fails, Trackwall shows a notification, "Pipeline failed in orders-api", with the merge request and the failed jobs; a click opens the task. The section in the task names the failed jobs too, each a link to its page on the repo host. The log button next to a job shows the end of its log right there, where a job says why it failed. "Fix" hands the end of the failed jobs' logs to the task's agent and asks it to fix the cause on the same branch, like a review: it gets them at once if it waits for you, after its turn if it is working, or when you resume the task. Then press "Push" again, and the merge request runs a new pipeline. If another session proposed the task, such as the supervisor, it hears about the failure as well and can ask the task's agent to fix it.

A new worktree has only the files git tracks, so local config that is ignored by git is missing there. List those files in a `.worktreeinclude` file in the repo, with the same patterns as `.gitignore` (for example `.env` and `src/main/resources/application-local.yml`), and Trackwall copies them from the repo into every new task's worktree. Only files git ignores are copied, so the list never overwrites a file of the repo, and the agent does not commit them by accident. The task panel lists the files it copied and anything it left out. [Where agents work](/guide/where-agents-work) shows how a worktree builds on the repo and your projects folder, and which of your files it gets.

Every task also gets a port of its own, shown in the task's header. Every mise task that runs in the worktree gets it in `SERVER_PORT` and `PORT`, so the agent can start the repo's [service](/features/services) from the worktree without taking the port of the one you run from the repo.

"Resume" starts Copilot CLI again with the task's conversation. You can also ask the [supervisor](/features/supervisor) to resume a task, for example after Trackwall restarts. "End task" (also the X of a task without a session in the Sessions list and grid) removes the worktree and keeps the branch, or removes both; if that would lose changes, Trackwall asks first. A task cannot be ended while a mise task runs in its worktree: stop it first.

## Use it

1. Open "Sessions" and press "+".
2. Pick a repo, write the prompt and start the task. The pills under the prompt hold the task's options: turn on "No approvals" when the agent may work without stopping for you, and press "Model: default" to type a Copilot CLI model id for this task (with your own model provider the field suggests its models). In a Java repo, "Java navigation" gives the agent a language server once you have set it up ([Java navigation](/features/java-navigation)). Turn on "Chat (preview)" to see the task as a conversation instead of a terminal. Hover over a pill to see what it does. The form remembers the worktree, model, Java navigation and chat choice for each repo, but "No approvals" is always off at first.
3. Watch the agent in the "Terminal" tab, or, with "Chat (preview)" on, in the "Chat" tab, where you also answer its approval requests and write to it. Its work is in "Changes" and each of its turns in "Rounds"; press "Undo round" when a turn went wrong.
4. Press "Verify" to see whether its tests pass.
5. Comment on the lines you want changed and press "Send N comments to the agent"; repeat until you are happy.
6. Review the changes in VS Code, then press "Push" and "Open merge request", and create the merge request in your browser.
7. Once it is merged, end the task.

## Good to know

- When you end a task, Trackwall keeps a short record of it on your computer: what it was asked, what its agent last reported, its commits, the files it changed and its last verification. Agents find these records with the `search_task_history` tool, so a later task can see how a similar change was done before, even after the branch is gone. Trackwall keeps the newest 2000.
- Worktrees live in `.trackwall/worktrees` in your projects folder, so they sit on the same disk as your repos and fall under the same antivirus exclusion. The Repos list does not show that folder. To put them somewhere else, set "Task worktrees folder" in Settings; it cannot be the projects folder itself or a folder inside one of your repos. Existing tasks keep their worktrees where they are, and tasks created with an older version have them in `~/.trackwall/worktrees/<repo>/`.
- Tasks you never ended keep their worktree, with its dependencies and build output, which can fill a disk, especially a container's volume. The "+" page in Sessions lists "Old task worktrees": tasks without a running session idle for at least the days you choose (7 by default), with when each was last active, how much disk its worktree takes and what removing it would delete. "Remove worktrees" ends the chosen tasks one by one as "End task" with the branch kept, so every commit stays on its branch. Tasks that would lose work (uncommitted changes, commits outside the branch) are not chosen at first; when you choose one, Trackwall asks once more and names what goes before it removes anything, and if the task's files or commits changed after you confirmed, that task is not removed. A task whose worktree Trackwall cannot read cannot be chosen there; end it from its own panel.
- Comments you have not sent yet stay while you switch between "Terminal" (or "Chat") and "Changes", but not when you open another task. While a comment form is open, "Changes" stops refreshing, so the line does not move under it. A review holds up to 15 comments of up to 2000 characters, and up to 60 comments can wait for the agent to read them; beyond that Trackwall asks you to wait. Sent comments the agent has not read yet wait for it also when Trackwall restarts or updates.
- Trackwall asks the agent to read the review by typing one line into its terminal, but only while the agent waits for your message. If you have typed something there that you have not sent yet, the review waits until you send it; if you stopped the agent with Esc, it waits until the agent's next turn ends, or until you press **Deliver now** in the "Unread by the agent" strip under the task's header.
- `.worktreeinclude` can stay untracked; Claude Code reads the same file. At most 100 files and 10 MB are copied, and only regular files, not links; the task panel names every file left out and why.
- Files are copied when the task is created. After you add a line to `.worktreeinclude`, **Copy included files** in the task's panel, or in its menu in the grid, copies what is missing into the running task's worktree. A file the worktree already has stays as it is, since the agent may have changed it there; a later change in the repo does not reach the worktree. A copied `mise.local.toml` counts as trusted, like at the start, and a running session shows that its environment from mise changed, with a restart to apply it.
- The copied files often hold secrets. The task's agent can read them, as it could read them in the repo, and they are removed with the worktree when the task ends.
- A task keeps the model it started on for every resume. To change it, press the robot button ("Restart the session on another model", or "Resume the task on another model" for a stopped one) in the task's header: a running task restarts on the new model with the same conversation, and a stopped one resumes on it. The task keeps the new model from then on, which also gets a task out of a model your provider stopped serving.
- Task ports are 41000 to 41999. A task keeps its port until it ends; Trackwall does not check that no other program uses it, and a service that finds its port taken says so.
- A task created with an older version of Trackwall asks you to trust its mise configuration once before its first mise task.
- A mise file or folder that is a symbolic link Trackwall cannot check (to something outside the worktree, a broken link, or a linked folder) stops mise tasks there, and the warning says why.
- Trusting a mise configuration covers the commands it defines, not the code they run: tests and build scripts the agent changed run as written. Review the changes as you would before merging.
- **Conversation view (preview).** A task started with "Chat (preview)", on the form or on a proposal, shows as a conversation instead of Copilot CLI's terminal, the same as the supervisor's ([supervisor](/features/supervisor)): its answers, the commands and file changes it makes, and its approval requests with buttons, with a message box below and a line above it that says whose turn it is; a message you write while the agent works shows at once as waiting and goes when its turn ends. In the task's own panel this is the "Chat" tab, in place of "Terminal". It stays that way for every resume, also after Trackwall restarts, and goes on with the same conversation. Reviews and messages for the task go in as soon as it finishes its turn. "Show diff" beside a file change opens it in a panel beside the conversation, with the other files that turn changed; ✕ closes it, and the "Changes" tab still has the task's whole diff. The button in front of a line there offers "Comment", which adds a review comment you send from the top of the panel just as in "Changes", and "Open in VS Code" at that line, both on the lines a change added when it is the latest change of that file, and "Ask about this" on any line, which puts the line as a quote in front of your message. Java navigation needs the terminal for now, so its pill is off while chat is on.
- A task started with "No approvals" runs commands, edits files and calls tools without asking you, every time it starts or resumes, also after Trackwall restarts; its header says "No approvals". That includes commands such as `git push` or installing packages. Your `toolPermissions` deny rules still refuse what they name, so add one such as `shell(git push)` for anything such a task must never run; Copilot CLI still asks before paths it sees outside the worktree and before URLs. Only tasks have it: a session in your own working copy and the supervisor always ask. To go back to asking, end the task and start a new one.
- On Linux such a task also runs its commands in Copilot CLI's sandbox, and in a container once you give it the sandbox (the [dev container guide](/guide/dev-container#copilot-cli-s-sandbox) says how; on macOS and Windows you turn it on): a command, or a build script it runs, can write only in the task's worktree and cannot see your other repos or your credential folders such as `~/.ssh`. The form says so under the options, and the task's header says "Sandbox". See [Approvals](/features/approvals) for what it covers and how to change it.
- Copilot CLI asks to trust a folder before it works there. The session then waits for you like an approval, with the question in the tray and on Home, and "Yes" answers it. To stop it asking for every repo and task, add your projects folder (the new task form shows its full path) to `trustedFolders` in `~/.copilot/config.json`: that covers every repo and their task worktrees.
- Trackwall tells a task's agent to stay in its worktree, commit on its branch and not push unless your prompt asks for it. This is an instruction to the agent, not a lock: the branch is yours to push.
- Round commits stay on your computer until you press "Push", and they need a git name and email (`git config user.name` and `user.email`); without them, or while a merge or rebase waits in the worktree, or when the worktree is not on the task's branch, the "Rounds" tab says why the last turn was not saved as a round. They run none of the repo's git hooks. A round that was pushed, or squashed before a push, cannot be undone, since that would need a force push. A change you make by hand while the agent is working goes into that turn's round, because Trackwall cannot tell it from the agent's, so make hand edits while the agent waits for you. The agent is told about the round commits and asked to leave them as they are; if its history has a merge commit, the round commits before the merge stay as they are. A round takes every file that is not ignored, so keep build output and secrets in `.gitignore`; files Trackwall copied into the worktree for the task stay out. "Push" is refused while the agent is in the middle of a turn, and a push that fails leaves the branch as it was.
- "Push" uses your own git sign-in, as a push in a terminal would. It never forces: if the remote's branch has commits the task does not (a colleague pushed, or the agent amended a pushed commit), the push is refused with git's message, and the section says how many commits the remote has. It runs none of the repo's git hooks, because the agent could change them in the worktree; your repo host's pipeline runs the checks instead. It pushes only over HTTPS or SSH to a repo host it knows (GitHub, or one from Settings), and only to the address the remote fetches from: if the repo's git config sends pushes somewhere else, Trackwall refuses and says where. A repo that stores files in Git LFS cannot be pushed from here yet.
- Trackwall creates nothing on your repo host: the merge request is created by you, in the repo host's form. It finds the merge request by the task's branch, so one you or anyone else opened for that branch shows too.
- The merge request and pipeline come from `glab` (GitLab) or `gh` (GitHub), signed in as for [cloning a repo](/features/repos); without them, "Push" and the form still work and the section says why it cannot show the merge request. GitHub works at `github.com` without settings; a GitLab or GitHub Enterprise remote needs its repo host in Settings. The section refreshes every 30 seconds while the task is open. In the background Trackwall checks each task's merge request every minute while its pipeline runs and every few minutes otherwise, so a failure shows about a minute after the job ends.
- A job's log is read from the repo host only when you press its log button or "Fix", and Trackwall shows its last 150 lines at most; the job's page has the whole log. Secrets Trackwall knows from your environment are masked as in other logs (GitLab and GitHub mask their own CI secrets). "Fix" sends the logs of the first three failed jobs and names the others. On GitHub only GitHub Actions jobs have a log here; other checks and commit statuses are links. A log over 8 MB is too long to read its end: open the job's page. A job that is allowed to fail is not listed, and jobs of a child pipeline show only on the pipeline's page.
- A pipeline that had already failed when Trackwall started does not show a notification; the row still shows it in red.
- The description is at most 4000 characters, and less when it has many accented letters or emoji, because the browser carries it in the page's address; a longer summary is cut with "…", and you can add the rest in the form.
- "Verify" needs a mise task named `test` in the repo; without one, Trackwall says so and runs nothing. A Maven, Gradle or npm repo without its own `test` can get one from the [convention tasks](/features/mise-tasks#convention-tasks). If the agent is already running `test`, "Verify" waits for that run instead of starting another. The test counts come from the JUnit reports the run wrote (Maven, Gradle, jest-junit, Vitest); a run that wrote none, for example because Gradle found the tests up to date, passes on its exit code alone, and the section says so.
- The sections above the task's terminal (included files, warnings, messages, summary, verification, merge request, mise tasks) fold into one line of notices, so the terminal keeps almost the whole panel. Warnings come first, in yellow. Click a notice, or "Details", to unfold the sections; unfolded they take at most a third of the panel and scroll when they need more. The summary shows its first two lines across the panel's width; "Show all" opens the rest.
- The verdict is about the files as they were when the run started. When they change afterwards, by the agent or by you, Trackwall marks the verdict as outdated within about 15 seconds: the section says "passed · outdated" (or "failed · outdated"), the notice and the grid tile's chip say "Outdated", the task's row says "Verify outdated", and the merge request's description says the verification ran on an earlier version of the changes. Press "Verify" again for a verdict on the files as they are now. Only what the files hold counts: a commit, or a file written again with the same content, keeps the verdict. Files the repo ignores, such as `target/` or `build/`, do not count either, so a repo whose tests write files it does not ignore, or rewrite a tracked file such as a snapshot or a lockfile, sees its verdict outdated right after the run; add such files to `.gitignore`.
- Trackwall keeps the last verification of each task, also when it restarts or updates; one that was still running then shows as cancelled, so press "Verify" again.
- After running the tests in its worktree, the agent reads which tests failed and why from the reports your build tools write there, instead of scrolling the build log.
- An agent can also propose a task for you to start: see [Main session and task proposals](/features/main-session).
- The "Shell" tab opens your own shell in the task's worktree: see [Shell](/features/shell). Ctrl+PageDown and Ctrl+PageUp (⌘⇧] and ⌘⇧[ on macOS) step through the task's tabs, so "Terminal" and "Shell" are one key apart.
- The "Impact" tab shows which repos the endpoints and library classes the task's commits change reach, and hands each of them a task; the repos that call a changed endpoint or import a changed class get a task proposed when the agent finishes a turn: see [Impact of a task](/features/impact).
- When Trackwall runs in a [dev container](/guide/dev-container), "VS Code" opens the worktree in VS Code inside the container (with the Dev Containers extension), and the merge request form opens in a new tab of your browser.
